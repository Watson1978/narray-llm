# GPT-2 124M の計測結果

Ruby (Numo / Cumo) と Python (NumPy / CuPy / PyTorch) で GPT-2 124M の推論を走らせ、tokens/sec を比べたもの。目的は「Ruby の NArray 実装が Python エコシステムにどこまで近いか」を測ることで、速い実装を作ることではない。したがって Python 側は速く書けるところをあえて Ruby と同じ形にしてある (`python/gpt2.py` の docstring に該当箇所を明記)。

**共通の条件と手順は [method.md](../method.md)、機械の性質は [machine.md](../machine.md)、cumo の版ごとの所見は [cumo-history.md](../cumo-history.md)、未対応の問題は [cumo-issues.md](../cumo-issues.md) にある。**

### バッチ生成

**バッチ生成もできる** (`--batch 8`)。**長さ 128 で batch 16 が batch 1 の 6.7 倍** (742.9 → 4973.8 tokens/sec 合計)。1 本あたりは 743 → 311 に落ちるので、待ち時間と引き換えに台数を稼ぐ形。

**Cumo の CuPy に対する差はバッチで縮む** (3.50 → 2.23 倍、両条件とも 10/10)。投入が支配する帯から外れるぶん、投入回数の少なさが効かなくなる。**PyTorch にはどちらの batch でも勝つ** (10 ラウンド中 1 回も負けない)。

**1 ステップの GEMM 49 本がどのカーネルに行くかは、バッチについて単調でない。** batch 2/4 は 12 本、**batch 8 は 1 本**、batch 16 は 24 本が cutlass の sgemm に行き、残りは `gemmSN` (batch 1 はすべて `gemvx`)。**長さには依らない。** **cutlass に行った GEMM は `splitKreduce` を 1 本連れてくる** ので、バッチごとの投入数の差はそれで閉じる。cumo は `CUBLAS_GEMM_DEFAULT` を固定で渡すので、選んでいるのは cuBLAS の既定のヒューリスティクス。**そして長さ 512 では batch 8 が batch 4 を下回るが、原因は未分離** (下の「サンプリング」の節)。

### サンプリング

**`sort` と `cumsum` を実ワークロードで踏むために足したもの。** 全モデルが貪欲法だけで、どちらも一度も通っていなかった。Bit 配列も fancy index も使わず、**比較は算術で作る** (`(threshold - x).clip(0, 1).ceil`)。

**乱数はデバイスではなくホストの `Random` から引く。** Numo と Cumo は同じ seed でも系列が一致しないので、デバイスで引くと **トークン列の完全一致という関門が壊れる**。1 トークンに 1 スカラーなので、デバイスに置いても得るものが無い。

**`[50257]` の `sort` 1 回は 8 本。** CUB の radix 6 本 + キー生成 1 本 + **`cumo_na_copy` 1 本** (`sort` は壊せないレシーバを必ずコピーするので、**外から連続化しても減らない**)。

**`cumsum` はホストループに落ちない。** Switch の MoE で踏んだ **8192 未満でホストに落ちる帯** の反対側で、**同じ演算の両側が実ワークロードで埋まった。**

**top_k の 3.7% は分離しない。** ペア比が 1 をまたぐ (最小 0.9939) うえ、対照そのものが 0.9860〜1.0332 の幅を出している。**top_p と「両方」は 10/10 で分離する。**

**top-k と top-p は同じ並びを要求するので、1 度だけソートして両方に渡している** (共有前は 290 本)。**本数が 9 本減ることは確定していて、wall では見えない** — ペア比 0.9851 が 1 をまたぎ、予算 (20 us/token = 1.2%) も幅の中である。

**README のサンプリングの表は 2026-09-21 に測り直したもの。** 前の版は計測スクリプトに偏りがあり、**サンプラが EOT で途中停止した回を `best-of-N` が系統的に選んでいた** (下の「サンプリング」の節)。

### 学習

**このリポジトリで初めて推論以外を書いたもの。** 参照は llm.c の `train_gpt2.c`、関門は `test_gpt2.c` のものをそのまま借りた — **16 本の勾配テンソルが 2e-2 以内**、**AdamW 10 ステップの損失列が 1e-2 以内**。**トークン列の完全一致はここでは使えない** (累算順序が C と揃わない) ので、許容誤差の根拠も自前で作らず llm.c の値を使っている。

**推論とは踏む経路が違う。** 外側の軸に沿った縮約 (bias の勾配は `[B*T, C]` を軸 0 で畳む)、同じバッファへの累算、両向きの転置行列積、`[50257]` の softmax の逆伝播、そしてパラメータ 3 本ぶんのメモリ (重み・勾配・m/v で約 2.0 GB、活性 280 MiB と合わせて 2.46 GiB)。

**同じコードなのに、Cumo のほうが llm.c と 10〜18 倍よく一致する。** Numo は 2e-2 に対して 1.6 倍の余裕しかない。畳む順序の違いだと思われるが、**測っていない。**

**CuPy は別のバッチで測ってある** (2026-09-20)。そちらでは Cumo 0.07725 に対し CuPy 0.08406 で、**同じアルゴリズムなら Cumo が CuPy を 8.8% 上回る** (10/10)。**README の区間別の表と並べて読まないこと** — 別のセッションの数字である。**PyTorch は autograd と `torch.optim.AdamW` なので、そもそも同じアルゴリズムではない。**

**いちばん開いているのは AdamW で、backward ではない。** パラメータが 148 本、1 本の更新が要素演算 19 本で、**本数の 58%、wall の 49%** を占める。ただし **AdamW は自分の式の予算どおりに動いている** — 融合していないので走査は 44P = 21.9 GB、600 GB/s で 36.5 ms に対し実測 37.7 ms (1.03 倍)。**平坦化 (148 → 1) では 1.03 倍しか動かず、融合 AdamW なら 1.71 倍で PyTorch の既定と並ぶ** (44.8 対 46.0 ms)。前者はこちら、後者は cumo 側の仕事で、**桁が違う。**

**踏んだものは 2 つとも「片方のバックエンドでだけ出る」。** Cumo の `x[i]` はビューを返すので、`old = x[i]` を取ってから `x[i] = old + h` と書くと `old` も動き、中心差分がちょうど半分になる (Numo は Float を返すので出ない)。逆に `Ops.contiguous` の既定が `XF` なので fp64 のテストが黙って fp32 に落ち、丸め 1e-7 が `2h` で 5 桁増幅されて 3.6e-2 に化けた。**両バックエンドで回していなければ片方を見落としていた。**

**fp16 / bf16 で学習が通るかは未確認。** 詳細は下の「学習」の節と [PLAN-training.md](../plans/PLAN-training.md)。

### カーネル数と fp16

README のカーネル数の表は、decode で GPU に投入するカーネルの本数 (nsys、`--length 128` と `--length 64` の差 ÷ 64)。**GPT-2 と Llama 2 では 1 投入あたりの費用が Cumo も PyTorch も 2.0〜2.2 us で同じなので、差は本数から来る。Mamba ではそれが成り立たない** ([mamba-130m.md](mamba-130m.md))。

**fp16 と bf16 でも測ってある。**`DTYPE=fp16` / `DTYPE=bf16` で切り替わり、GPT-2 の decode は fp32 の 1.17〜2.37 倍になる。numpy にも cupy にも bfloat16 が無いので、3 実装を並べられるのは fp16 まで。

## GPU: Cumo 対 CuPy

tokens/sec、**プロセスごとに best-of-3 の中央値、10 ラウンド**。**Cumo / CuPy / PyTorch / 対照 (Cumo をもう一度) の 4 系列 × 4 条件** を 1 ラウンド内でインターリーブし、系列の順序をラウンドごとに回転させて、計 160 プロセスを直列に走らせた。**クロックは `-lgc 3090` / `-lmc 14001` で固定してある** (負荷中のメモリクロックは 70% が 14001 MHz、電力は中央値 97.2 W)。**Cumo の列はバイアスを GEMM の C に置き、scores の積を 1 本の縮約に畳んだあとの値である** (下記の節)。cumo は master `49153d31` (#475)。**バッチの頭に捨てるラウンドを 1 本置いてある** (計測の作法 22)。

**CuPy 側でループ版を測るには `IDIOMATIC=1` を外す。**`python/gpt2.py` は **ヘッドごとのループが既定** で、バッチ版は `IDIOMATIC=1` で選ぶ。付け忘れると CuPy だけが 3 倍遅く出る (228.54 対 77.24)。上の表の CuPy 列はすべて `IDIOMATIC=1` で測ってある。`python/llama2.py` にこの分岐は無い。

**バッチ版の 4 行は 3 実装とも同一セッションで測り直してある。** 1 プロセス 1 条件、プロセス内で 64 トークン生成を 3 回してクロックを上げてから best-of-3、3 実装 × 4 条件を 1 ラウンド内でインターリーブして 5 ラウンド (捨て走行 1 ラウンドを別に取ってある)。表の値はプロセスの best。

**動いたのは Cumo 列だけである。** CuPy は前の記録を +1.1 / +0.6 / −0.7 / +1.0%、PyTorch は −0.6 / −0.6 / −0.1 / −0.4% で再現した。Cumo が +8.6 / +4.0 / +8.9 / −0.0% 上がったのは cumo の版ではなく **実装側の書き換え** による。`Ops.layernorm` が逆数 (`1.0 / sqrt(...)`) を作らなくなり、`Ops.gelu` が `sqrt(2/pi)` を 3 次の係数に畳んだので、1 トークンあたりのカーネルが 677 本から 640 本に減っている。書き換えの前後を同一セッションで 4 条件 × 10 ペア測った差は +3.8 / +7.0 / +3.0 / +1.0% で、「無し、256」以外はペア比の範囲が 1 を超える (10/10)。表の差がこれより大きいのは、表が 5 プロセスの best だからである。

**PyTorch の「原因不明のずれ」は解消した。** 以前ここには、記録より +41.0 / +28.9 / +11.5 / +3.8% 速く出て原因が特定できない、と書いてあった。**今回の測り直しは現在の表の値を 0.6% 以内で再現した** ので、外れていたのは差し替え前の古い値のほうである。**ずれの原因そのものは分かっていない** が、現在の 3 列はいずれも 2 セッションで再現している。

**PyTorch はメモリクロックに強く依存し、Cumo はあまり依存しない。** ずれの向きを説明できるかを確かめるため、メモリクロックを 14001 MHz と 9001 MHz に固定して両方を測った (SM は 3090 に固定、条件ごとに 3〜4 往復インターリーブ、走行ごとに負荷中のクロックを採って全サンプルが同じ段であることを確認した中央値)。

| 条件 | 14001 MHz | 9001 MHz | 差 |
|---|---|---|---|
| PyTorch 有り、64 | 786.23 | **600.29** | **−23.6%** |
| PyTorch 有り、256 | 708.35 | **556.86** | **−21.4%** |
| Cumo 有り、64 | 449.61 | 412.97 | −8.1% |
| Cumo 有り、256 | 431.93 | 407.66 | −5.6% |

**PyTorch の依存は Cumo の 3 倍である。** 1 トークンあたり 196 本のカーネルで GPU 側が律速の PyTorch は段の影響を直接受け、640 本で投入が律速の Cumo は 3 分の 1 しか受けない。**これで「同じセッションで PyTorch の列だけがずれ、Cumo と CuPy は再現した」という記録の形は説明が付く。**

**そして PyTorch の感度は、丸ごと gemv の帯域で説明が付く。** 1 トークンで読む重み 494.1 MB を上の読み出し帯域で割ると、14001 MHz で 0.824 ms、9001 MHz で 1.196 ms、差は **0.372 ms** になる。実測の差は 1.272 → 1.666 ms の **0.394 ms** で、**予測と 6% 以内で一致する**。**PyTorch は帯域の床にほぼ座っていて、段を変えると床がそのまま動き、それが全部 wall に出ている** ということである。同じ計算を Cumo に当てると、実測の差 2.224 → 2.422 ms の 0.198 ms は **予測 0.372 ms の 53% しかない**。残り半分は投入待ちに吸われる。**「3 倍敏感」の正体はこれで、感度の比 23.6 / 8.1 = 2.9 は「帯域の床に座っている割合」の比である。**

**ただし古い記録の水準までは届かない。** 493.84 / 497.50 tok/s は、9001 MHz の 600.29 / 556.86 よりさらに 17.7 / 10.7% 低い。**クロックはこのずれの 3 分の 2 までしか説明しない。** しかも古い記録は 64 と 256 がほぼ同値 (493.84 対 497.50) で、**どの段でも保たれる「64 のほうが速い」という順序が壊れている** (14001 で 786 対 708、9001 で 600 対 557)。段を落としても順序は保たれるので、残りは別の要因である。

**この測定自体にも限界がある。**`nvidia-smi -lmc 14001` はコマンドとしては成功するが、**カードが従わないことがある** (負荷中のサンプル 41 本中 38 本が 9001 のままだった回がある)。上の 14001 の行は、走行ごとにサンプリングして実際に 14001 だったものだけを採ってある。9001 への固定は確実に効く。

**ループ版の 4 行だけは cumo 0.5.10 の値ではない。** 構造を書き換える前の測定 (cumo #268 より前) をそのまま残してある。この 4 行は「ヘッドをまとめる書き換えが何を買ったか」を見るためのもので、cumo の版に紐付けて読む行ではない。

**Cumo の 4 行はプロセス間のばらつきが大きい。** 上の測り直しでの幅は次のとおり (プロセスごとに best-of-3、5 プロセス)。**プロセス数が少ないほど best は上振れしにくい** ので、この列を過去の 8〜10 プロセスの表と直接は比べないこと。

| 条件 | プロセス数 | 最小 | 中央 | 最大 (表の値) | 幅 |
|---|---|---|---|---|---|
| 有り、64 | 5 | 426.23 | 446.44 | **467.62** | 9.7% |
| 有り、256 | 5 | 424.97 | 435.27 | **442.70** | 4.2% |
| 無し、64 | 5 | 285.52 | 290.12 | **299.30** | 4.8% |

**幅そのものが測り直すたびに動く。** 同じ機械・同じ手順で 5 度測った幅は、条件の順に 9.1 / 3.2 / 6.0 / 0.4% (`07f0af91`)、3.6 / 3.5 / 10.5 / 1.2% (0.5.10)、11.2 / 6.0 / 7.1 / 1.6% (0.5.10 再測)、7.1 / 3.5 / 9.6 / 0.9% (0.6.0)、10.5 / 6.2 / 4.4 / 2.0% (0.6.0 再測、5 プロセス)、9.7 / 4.2 / 4.8 / 1.8% (0.7.0、5 プロセス) で、条件ごとの大小の順位すら入れ替わっている。安定して言えるのは、**1 回が約 2 秒かかる「無し、256」だけが 0.4〜1.7% に収まり、1 秒に満たない残り 3 条件は 3.0〜11.2% ぶれる** というところまでである。幅は前回の値を流用せず、比較のたびに測り直すこと。

**回数は動かないが、時間は 1 本の profile では決められない。** 上の 4 本で層内 gemv 48 本は 0.758 / 0.883 / 0.880 / 0.882 ms となり、3 本は 0.4% 以内に揃うのに 1 本だけ 14% 速い。速いほうは 64 プロセスの A/B ベンチ直後に走らせた 1 本目で、GPU がブーストしたまま入ったものである。GPU 時間の合計も 1.699 / 1.864 / 1.893 / 1.902 ms と動く (`cudaLaunchKernel` は 1.362 / 1.351 / 1.355 / 1.362 ms と安定している)。**上の表の時間は、外れた 1 本を除く 3 本が支持する側の値である。**

**差分に使う 2 本は、どちらも「温まった長さ」にすること。** 以前ここでは `--length 40` と `--length 8` の差を使っていたが、**8 トークンの走行は GPU が冷えていて 1 カーネルあたりが系統的に遅い** (gemv の中央値が 27.36 対 21.87 us、埋め込み転置が 455 対 384 us)。冷えて遅い側を引くので、**差分法は時間を過小に出す**。回数には影響しない。72 と 40 に変えると、同じ 677 本という回数はそのままで、時間だけが正しい側に寄る。

**行ごとに推定量を変える必要がある。** 原則は「平均 × 本数」(総時間 ÷ 走行回数と同じ)。ただし `store_sfloat` などモデル読み込み時の managed メモリのページフォルトを踏む行は、最大値が中央値の 1 万倍以上に跳ね、平均が壊れる。**最大値 / 中央値が 100 を超える 4 行だけ「中央値 × 本数」に置き換えた** (`store_sfloat_dim1` / `dim2`、`add_dim1`、縮約 1 行)。逆に、層内 gemv の 48 本は 4 種類の形が混ざっているので、**この行だけは中央値を使ってはいけない** (中央値は 4 形のうち 1 つの値でしかない)。平均・総時間差・別の長さの 3 通りで 0.878〜0.886 に収まることを確認してある。

**この直接計数は、以前ここに載せていた逆算 (830〜1050 演算) を置き換えるものである。** 逆算は「decode がほぼ起動律速」という前提に立っていたが、その前提が誤りだった。

### decode は起動律速ではなく帯域律速

以前ここには「247 MFLOP をピークの 0.8% でしか回していないので、時間のほぼ全部が起動と待ちである」と書いていた。**FLOP 利用率の数字は正しいが、結論が誤りだった。**

decode はバッチ 1 なので行列積ではなく gemv になる。gemv は 1 バイト読むごとに 2 FLOP しかしないため、**演算ではなく帯域で決まる**。FLOP 利用率が低いのは GPU が遊んでいるからではなく、この形の演算では低くなるのが当たり前だからである。

| | 値 |
|---|---|
| 1 トークンで読む重み | **494.1 MB** (12 層 × 28.3 MB + 埋め込み転置 154.4 MB) |
| このマシンの実測帯域 | 470〜509 GB/s (メモリクロック 11001 MHz の状態。**14001 MHz なら 599.5**。[machine.md](../machine.md)) |
| 帯域から決まる下限 | **1.00 ms/token** (11001 MHz) / **0.82 ms** (14001 MHz) |
| gemv の実測 | 1.270 ms/token (11001 MHz の天井に対して **79%**) |
| GPU が busy な時間 | 1.864 ms/token |
| 実測の 1 トークン | 2.139 ms |

**GPU は 1 トークンの時間の 87% を実際に働いている。** 起動の隙間は 0.27 ms しかない (書き換え前は 2.332 ms のうち 0.47 ms だった)。バッチ 1 の decode は毎トークン全部の重みを 1 回ずつ読むので、この 494.1 MB は実装をどう変えても減らせない。

**別のビルド・別の構造で測った内訳とも整合する。** cumo 側のセッションが cumo `#284` 時点・ヘッドごとのループ版を nsys で測った値は、gemv 49 本 = 1.43 ms、cumo 自前 738 本 = 0.57 ms、合計 787 本 / 約 2.0 ms、1 トークン 2.5 ms に対して GPU busy 80% だった。**ビルドも構造も違うのに gemv が 1.27〜1.43 ms に収まる** のは、読む重みの量が構造に依らないという帯域律速の予測そのものである。gemv 以外も 0.57 対 0.620 ms で揃っている。

ただし **この 3 つの時間は上記の冷えたバイアスを持つ**。cumo 側に確認したところ、`--length 40` と `--length 8` の差で取ったものだった。**下振れしている前提で読むこと** (回数の 787 / 738 / 49 はバイアスを受けない)。整合の根拠として強いのは時間の一致ではなく、**構造を変えても gemv の本数と読む重みの量が変わらない** という側である。

CuPy 側は profile していないが、構造が同じなので本数も同程度と見ると 3.61 us × 640 で **約 2.31 ms** となり GPU 時間を超え、投入が律速に回る計算になる (こちらは推定)。**「実装間の差が起動で決まる」のであって「絶対時間が起動律速」ではない。**

### CPU 側の内訳 (nsys の `cuda_api_sum`)

同じトレースから CPU 側も同じ差分法で出せる。

| CUDA API | 回数/token | CPU 時間 (ms/token) |
|---|---|---|
| `cudaLaunchKernel` | 640 | **1.25** (1.257 と 1.246 の 2 本) |
| `cudaDeviceSynchronize` | **1** | **0.40** (0.410 と 0.381) |
| `cuKernelGetName` / `cuStreamGetGreenCtx` / その他 | 738 | 0.05 |
| `cudaFree` | **0** (#297 前は 172) | **0** (#297 前は 0.022) |
| CUDA API 合計 | | 1.70 |
| Ruby 側 (wall − API) | | 0.44 |
| **wall** | | **2.139** |

**3 行目の 738 回を「cumo が払っているコスト」として読んではいけない。**`cuKernelGetName` (640 回) も `cuStreamGetGreenCtx` (98 回) も **cumo は呼んでいない** (`grep -rn cuKernelGetName ext/` も `grep -rn GreenCtx ext/` も空)。前者は `libcudart.so.13` にシンボルがあるので `cudaLaunchKernel` の内側から呼ばれていると見るのが自然だが、後者は libcudart に無く、出どころを特定できていない。そして **どちらもプロファイラを付けない実行で同じ回数出るのかは確かめていない** (確かめるにはプロファイラが要る、という循環がある)。この行は合計 0.05 ms、API 合計の 3% なので、どう転んでも上の結論は動かない。

wall は上の表の tokens/sec (467.62、プロセスの best) の逆数で、API の各行は profile を 2 本取った値である。**残差である「Ruby 側」の行は食い違いをまとめて被る** ので、中央プロセス (446.44 tok/s = 2.240 ms) を使えば 0.44 ではなく 0.54 ms になる。0.1 ms 単位で読む行ではない。

**`cudaFree` が 172 回/token から 0 回/token になったのが #297 である** (`cumo_na_aref_md_ensure` が確保していない添字の次元まで解放していた。docs/cumo-history.md)。回数は離散的な事実として確定しているが、**CPU 時間の合計はこれで下がっていない。** 削れたのは 0.022 ms なのに、`cudaLaunchKernel` の行は走行ごとに 1.357〜1.431 ms と 0.07 ms 動いており、節約はそこに埋もれる。

**同期は 1 トークンにちょうど 1 回** (72 トークンの走行が 88 回、40 トークンが 56 回、差がちょうど 32)。貪欲法で次のトークンを選ぶには argmax をホストに読み戻すしかないので、これは構造的に消せない。0.40 ms はその間 CPU が GPU のキューの吐き切りを待っている時間で、**待ちであって無駄ではない** (GPU はその間働いている)。

読み戻しに **D2H の memcpy は出ない**。`cudaMemcpyAsync` は両方の走行で 1 回きりで差が 0 である。cumo の確保は `cudaMallocManaged` なので、ホストが値を読む経路は「同期 + ページフォルト」になり、明示的な転送 API を通らない。`cudaMallocManaged` 自体も両方 168 回で **差が 0**、つまり decode 中はメモリプールがドライバに新規確保を要求していない。

そして **CPU が busy な時間 (投入 1.25 + Ruby 0.44 + その他 0.05 = 1.74 ms) は GPU が busy な時間 (1.864 ms) を下回る**。書き換え前は 2.02 対 1.866 ms で CPU 側が上回っていたので、**37 本を削ったことで釣り合いが GPU 寄りに移った** ことになる。それでも GPU が 0.27 ms 遊んでいるのは、投入が追いつかずキューが痩せる瞬間があるためである。0.6.0 でキャッシュ有りが 1.9% 遅くなるのは、GPU 時間が縮んだのに CPU 側が伸びてこの釣り合いが CPU 寄りに動いたから、という形になる (ただしホスト側の内訳はこのトレースでは割れない)。

### 伸びしろ: 2 つのてこは別のものを削る

gemv の 1.270 ms は帯域の下限に対して効率 79% で、どちらのてこでも動かない。残りを削る手は 2 つあり、**削る対象が違う**。

| | 削るもの | 到達点 |
|---|---|---|
| CUDA Graph (投入をまとめる) | CPU の投入 1.25 ms | wall が GPU 時間まで落ちる → **1.864 ms = 536 tok/s** |
| 要素演算 591 本の融合 | GPU 時間 0.597 ms | **実測で 308 本 / 585 tok/s** (下記) |
| 両方 | | **約 1.4 ms = 約 710 tok/s** |

現状 467.62 tok/s からの余地は合わせて **1.52 倍**。**融合のほうは実測できた** (下記。中央 585 tok/s、GPU busy 95%)。**PyTorch eager の 691.87 tok/s は、この「両方やった到達点」(約 710 tok/s) にほぼ並ぶ。** 融合カーネルを持つ実装が、こちらが 2 つのてこを両方使って初めて届く位置に eager のまま立っている、ということになる。**CUDA Graph だけ (536 tok/s、+15%) では届かない。** 以前ここには「PyTorch は 7 割の位置で CUDA Graph だけでも届く範囲」と書いていたが、それは記録側の 493.84 tok/s に基づくもので、再測定とは合わない。

以前ここには「930 tok/s まで行ける」「1.2〜2.2 倍の余地」と書いていたが、これは帯域の下限を見ていない見積もりだった。また「投入は GPU 時間の裏に隠れているので投入を速くしても効かない」とも書いたが、これも誤り。隠れているのは平均の話で、実際には GPU が 0.27 ms 遊んでいる。

**2 つのてこの優先順位は、37 本を削ったことで動いた。** CPU busy が 2.02 から 1.74 ms になって GPU busy (1.864 ms) を下回ったので、**投入側はもう律速ではない**。CUDA Graph 単独の取り分は +24% から **+15%** に下がる。融合は投入と GPU 時間の両方を削るので、**片方だけ選ぶなら融合が先** になる。ただし融合にも床がある。削れるのは要素演算の 0.60 ms までで、**gemv の 1.27 ms は帯域律速なのでどちらのてこでも残る**。

### 融合を実測した: 640 → 308 本で 1.3 倍

上の「融合」の行は見積もりだったが、cumo master に融合カーネルが入ったので実際に測れた。`x.layer_norm(gamma, beta, eps:)` (#423)、`x.softmax` (#426)、`Cumo::NMath.gelu_tanh(x)` (#427) の 3 本で、下の表は master `c28b9217` で測ったものである。

**この 3 本は 0.8.0 に入った。** 測った時点ではどのリリースにも無かったが、**いまは `gem install cumo -v 0.8.0` から再現できる** (released 0.8.0 での測り直しは下記)。

**リポジトリのコードは変えていない。**`Ops.layernorm` / `softmax_rows` / `gelu` をこの 3 本に差し替えるモンキーパッチとして測った。両方の側を **同じ master ビルド** で走らせているので、差は融合の有無だけである。plain 側の中央値 444.78 は released 0.7.0 で測った 441.77 とほぼ同じで、**master 自体はベースラインを動かしていない**。

**トークン列は 4 条件 (64 / 256 × キャッシュ有無) すべて完全一致した。** ただし **`gelu` ではなく `gelu_tanh` を使うこと**。`Cumo::NMath.gelu` は erf を使う正確版 (PyTorch の既定) で、GPT-2 が学習された tanh 近似とは別物である。両者は最大 4.1e-4 しか違わないので、数値を眺めただけでは取り違えに気づけない。

| 固定 14001 (5 往復) | 624.6 / 628.0 / 629.6 / 631.8 / 632.7 | 395.1 / 428.7 / 437.3 / 438.9 / 441.9 | **1.440** | 1.432〜1.581 |

**固定なしの 1.341 倍は、バーストの 1.32 倍と一致する。** そして **クロックを固定すると差は縮まらず、1.44 倍に開く。** 2 つのペア比の範囲は交わらない。融合なしは既に 14001 MHz で回っていて伸びしろが無く (+1.4%)、**融合版だけが低い段から引き上げられる** (+8.5%) ためである。バーストで測った +8.6 / +9.6% 対 +0.2 / +2.1% と同じ形で、2 つのハーネスが同じことを言っている。**融合の利得は、クロックの段を揃えるほど大きく見える。**

固定側は 1 往復目を落としてある (融合 506.6、固定を入れた直後の 1 回だけ低く、2 本目以降は 625〜633 に揃う)。固定なしの負荷中のクロックは、融合版がメモリ 11001 MHz・SM 2685 MHz・99.2 W、融合なしが 14001 MHz・2700 MHz・98.7 W だった。**融合版のほうが低い段に居ながら勝っている** ことになる。

**ただし融合版だけが低い段に落ちる状態が実在する。** インターリーブする前に測った 2 回では、融合版が **378.7 / 400.6 tok/s** で融合なし (429.7 / 433.5) より遅く、そのとき負荷中のメモリクロックは **9001 MHz**、SM 1290 MHz、消費電力 39.1 W だった。**インターリーブした 3 往復では一度も再現しなかった** ので、上の表のほうを採る。**この低い段に落ちる条件は特定できていない。**

`nvidia-smi -lmc 14001` で固定すると融合版だけが +8.6 / +9.6% 伸びる (融合なしは +0.2 / +2.1%) のも、この「融合版のほうがクロックの段に敏感」という性質と整合する。**固定には root が要るので、固定込みの数字は既定の利用者が得るものではない。**

**利用率はクロックの段を説明しない。** 融合版は `utilization.gpu` 94% / `utilization.memory` 75% で 11001 MHz、融合なしは 85% / 46% で 14001 MHz だった。**利用率が高いほうが低いクロックに居る** ので、どちらの指標も段の選択と単純には連動していない。

**decode は起動律速ではなくなった。** 中央プロセスの 1 トークンが 1.707 ms、profile の GPU 時間が 1.616 ms である。ただし **この 1.616 ms は上限側の値である** (下記)。真の GPU busy は 1.45〜1.62 ms、割合にして **85〜95%** と読むのが妥当で、**投入側のてこはほぼ使い切っている** という結論は変わらない。この上に CUDA Graph を足しても残りは 1 割に届かない。**残った gemv は帯域律速で、融合でも Graph でも動かない。**

**この 1.616 ms は nsys の値で、上限側である** (プロファイラは wall より過大に出る。[machine.md](../machine.md) の「nsys のカーネル時間は wall より過大に出る」)。

**PyTorch eager との差は 7% になった** (fused の best 646.84 対 691.87)。カーネル数はまだ 308 対 196 で 1.6 倍ある。

**この節の値を上の比較表に混ぜないこと。** 比較表は released 0.7.0 の gem を固定なしで測った数字で、この節は融合を差し替えたモンキーパッチをクロック固定で測ったものである。**リリースに入るという条件は 0.8.0 で満たされた。** 当初ここには「実装に取り込むには Numo 側のフォールバックが要る」と書いていたが、**フォールバックは今まで書いてあったコードそのもので足りた** (下記)。

**Cumo が全体に 1.2〜2.0 倍速い。** GEMM はどちらも cuBLAS を叩くので、差が出るのは 1 演算あたりの固定費とカーネルの質になる。

| | a+b (256 要素) 1 回あたり |
|---|---|
| Cumo | **2.2〜2.8 us** |
| CuPy | 3.61〜3.74 us |
| PyTorch (CUDA) | 2.58 us (記録は 4.71 us。上記のとおり再測定と合わない) |
| Numo | 0.66〜0.74 us |
| PyTorch (CPU) | 0.42〜0.44 us |

**Cumo の値は走行ごとに 25% ほどぶれる。** 温めた状態で 5 回続けて測って 2.24 / 2.83 / 2.42 / 2.69 / 2.39 us だった。単一の値として扱わず、下の逆算でも幅を持たせている。

**測り方**: 両側とも素朴な `a + b` を 1000 回、出力は毎回確保して都度破棄、ウォームアップ 100 回のあと best-of-5。CuPy の `cupy.add(a, b, out=c)` は 2.90 us と 2 割ほど安いが、Ruby 側に対応物が無いので使っていない。`cupy.fuse` や CUDA graph も同じ理由で使っていない (einsum を避けたのと同じ理屈)。結果を保持するか破棄するかで CuPy の値は 3.54 対 3.61 us と誤差範囲だった。

例外はキャッシュ無し・256 トークンのバッチ版で、ここだけ CuPy が速い (145.87 対 142.71、1.02 倍)。cumo 0.6.0 で縮約が速くなるまでは 133.39 対 146.98 の 1.10 倍だった (下記)。この経路は毎ステップ全系列を再計算するので演算量が支配的になり、固定費の差が効かなくなる。**投入が律速に回る経路では Cumo、演算量が支配する経路では横並びかわずかに CuPy** という形になっている。内訳は下記。

### 埋め込みを one-hot GEMM から gather に変えた: キャッシュ無しで 1.22〜1.31 倍

`Ops.embed` は `one_hot(ids) . wte` で埋め込みを引いていた。one-hot 行列にしたのは「NArray の添字による gather は同期する」という理由だったが、**同期するのは NArray を添字にしたときだけで、Ruby の Array を添字にすると同期しない。**`embed` に届く時点で `ids` は既に Ruby の Array なので、gather はもともと使えた。

| 添字の形 | 同期 |
|---|---|
| `wte[Cumo::Int32.cast(ids), true]` | **する** (`cumo_na_parse_narray_index` の警告が出る) |
| **`wte[ruby_array, true]`** | **しない** |
| `wte[integer, true]` | しない |

**行はビット完全一致する** (one-hot GEMM との max|d| が Numo / Cumo とも 0.0)。生成トークン列も変わらず、174 テストが両バックエンドで通る。`CUMO_SHOW_WARNING=ON` で残る同期は、読み込みの `from_binary` とトークンごとの `extract_cpu` (argmax の読み戻し) だけである。

### `mulsum` への置き換えは入れなかった (カーネルは減るが wall が付いてこない)

`Ops.decode_attention` の `(a * b).sum(axis:)` を `a.mulsum(b, axis:)` にする案を測って、**採用しなかった**。cumo の `mulsum` は積と縮約を 1 本に畳む zip 縮約 (`gen/tmpl/accum_binary_kernel.cu` の `cumo_reduce_zip_split`) なので、`[t, C]` の一時配列が書かれも読み戻されもしなくなる。

**カーネルは確かに減る。** キャッシュ有り 64 トークンで **17476 → 16720 本 (−756、1 トークン −11.8 本)**。12 層 × 1 本で、減るのは **values 側だけ** である。

**scores 側は 1 本も減らない。**`keys * q` を `keys.mulsum(q, axis: 2)` にするには q を `[1, H, hs]` に変形する必要があり、**`reshape` はコピーする** ので `mul + sum` の 2 本が `コピー + mulsum` の 2 本になるだけになる。`[t, C]` の一時配列を `[1, C]` のコピーと交換する取引で、**得か損かは q の連続性で変わる**。

| | q の出どころ | 連続か |
|---|---|---|
| GPT-2 | `qkv[true, 0...channels]` の列スライス | **非連続** (`reshape!` は拒否する) |
| Llama 2 | `Ops.rope` の戻り値 | 連続 |

#### 前提が変わったので測り直した (2026-09-18)

**当時「scores 側は減らない」と書いた根拠が無くなった。** 理由は 2 つある。

- **Cumo は `[1, N]` の列スライスを `reshape!` させる** (Numo は拒否する)。当時は「q が非連続だから `reshape` のコピーが要る」と判断していたが、**Cumo では `reshape!` で済む**
- Llama 2 の q は `Ops.rope` の戻り値で、もともと連続である

そこで **両側を `mulsum` にすると、両モデルとも 1 トークン 24 本減る** (当時は values 側だけの 11.8 本)。

| | カーネル/token |
|---|---|
| GPT-2 | 222 → **198** |
| Llama 2 | 354 → **330** |

**それでも GPT-2 は遅くなる。** 長さ 1000、段を記録して 20 ラウンド、資格外なし。

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| GPT-2 | **0.943〜0.993 0/20** | いいえ | **0.970** |
| Llama 2 | 0.982〜1.093 17/20 | はい | 1.021 |

**当時の 0.939 / 0.963 と符号が一致した。** 削るカーネルが 2 倍になっても向きは変わらない。**Llama 2 は 1 をまたぐので、こちらも主張できない。**

**ストライドのせいではない。** GPT-2 の q は結合 qkv の列スライスなので、`mulsum` がストライド付きの被縮約オペランドを読むのが不利ではないかと考えて、**q を連続化して測り直した**。カーネルは 198 → 210 本 (コピーが 12 本増える)、**ペア比は 0.941〜0.972 (0/10)、中央値 0.965 で、むしろわずかに悪い。** 仮説は外れた。

#### 原因はブロードキャストの向きだった

**`mulsum` が遅いのは values 側だけで、しかも「縮約しない最内軸をブロードキャストする」形のときである。**`[1000, 12, 64]` を axis=0 で縮約して単体で測った (1 ケース 1 プロセス、ウォームアップ 20 回、50 回平均を 7 セット取って min)。

| | 1 回あたり |
|---|---|
| `(v3 * w3).sum(axis: 0)` (`w3` は `[t, 12, 1]`) | 10.45 / 10.42 us |
| `v3.mulsum(w3, axis: 0)` | **13.49 / 13.51 us** |
| `(v3 * wf).sum(axis: 0)` (`wf` は同形、対照) | 9.17 / 9.18 us |
| `v3.mulsum(wf, axis: 0)` | **7.14 / 5.03 us** |

**同形の行が対照である。** そこでは `mulsum` が 1.3〜1.8 倍速く、cumo 側が独立に測った 0.534 / 0.544 とも整合する。**違いはブロードキャストの向きだけである。**

`decode_attention` の 2 か所は向きが逆になっている。

| | ブロードキャスト | 縮約 | `mulsum` |
|---|---|---|---|
| scores | q が `[1, 12, 64]` = 最外軸 | axis 2 | **1.9 倍速い** (8.07 対 15.01 us) |
| values | w が `[t, 12, 1]` = 最内軸 | axis 0 | **1.29 倍遅い** |

全体で切り分けると、そのまま足し算になる (T=1000、3 往復とも ±0.03 us)。

| | 1 回あたり | 基準との差 |
|---|---|---|
| 両方 `mul` + `sum` | 25.26 us | — |
| scores だけ `mulsum` | **22.71 us** | −2.5 us |
| values だけ `mulsum` | 27.98 us | **+2.7 us** |
| 両方 `mulsum` | 25.69 us | +0.4 us |

**機構は cumo 側が特定した** (2026-09-18、こちらでは追試していない)。`reduce_kernel.h:82` の `axes_are_flat` は「i 番目のオフセットが `i * step` になるか」を見るが、**最内軸のストライドが 0 だと `acc` が 0 になり、外側の次元の検査が必ず落ちる。** 述語としては正しく、stride 0 の軸が途中にあればアドレスは単一ストライドでは書けない。問題は `cumo_reduce_zip` が **両オペランドの平坦性を AND している** ことで、片方が非平坦なだけでカーネル全体が実体化の経路に落ちる。**`(a*b).sum` が勝てるのは、カーネル 1 本と中間配列を払って平坦なアドレス計算を買っているから** である。**直れば values 側も scores 側と同じ向きになる見込みなので、そのときは再度試す価値がある。**

**「モデルで符号が違う」という当初の枠組みは的外れだった。** GPT-2 と Llama 2 の `decode_attention` は同じ形・同じコードで、**両側を同時に置き換えた差し引きが、モデルごとの比重で違って見えていた** だけである。

#### scores 側だけにして入れた

単体の切り分けがモデル全体でもそのまま出た。長さ 1000、段を記録して 20 ラウンド、資格外なし。

| | カーネル/token | GPT-2 のペア比 | Llama 2 のペア比 |
|---|---|---|---|
| 両側 `mulsum` | 198 / 330 | **0.943〜0.993 0/20** (0.970) | 1.021 (17/20) |
| 両側 + q を連続化 | 210 | 0.941〜0.972 0/10 (0.965) | — |
| **scores 側だけ** | **210 / 342** | **0.989〜1.028 18/20** (1.009) | **0.974〜1.092 18/20** (1.046) |

**同じ 210 本でも中身が違えば結果が違う。**「両側 `mulsum` + q のコピー 12 本」は 0.965、「scores 側だけ」は 1.009 で、**本数ではなく、どの演算がどの形で走るか** が決めている。

**どちらも 1 をまたぐので速くなったとは書けないが、どちらのモデルも遅くならず、カーネルは 12 本減る。** その 2 つで入れた (`17374ca`)。

**このセッションで 3 例目の「カーネル数が結論を決めない」例である。** 残差を C に置く案は −23 本で中央値 0.993 かつ二峰性、両側 `mulsum` は −24 本で 0/20 の減速、そして同じ 210 本の 2 つの版が 0.965 と 1.009 に分かれた。**投入が律速だという読みは、削った本数に比例して効くという意味ではない。**

**両側を置き換える形は、このときは入れなかった。** GPT-2 が確実に遅くなるためで、**scores 側だけを入れた** (下記)。**その後 cumo #475 が values 側の原因を直し、両側とも入れた** (さらに下記)。

**この節はこのセッションで 2 つ目の「カーネルを減らしても速くならない」例である** (もう 1 つは Llama 2 の残差を C に置く案、docs/results/llama2-110m.md)。**投入が律速だという読みは、削った本数に比例して効くという意味ではない。**

#### 測った (クロック固定、10 ラウンドインターリーブ、両モデル)

キャッシュ無しは `Ops.attention` を通って `decode_attention` を呼ばないので、**そちらが陰性対照** である。8 条件すべて 1 をまたいだ。

| 条件 | 両方 mulsum | values 側だけ |
|---|---|---|
| GPT-2、有り、256 | **0.939** (0.877〜0.971) またがない **0/10** | 0.963 (0.938〜1.018) またぐ 2/10 |
| GPT-2、有り、64 | 0.969 (3/10) | 1.008 (6/10) |
| Llama 2、有り、200 | **1.068** (1.046〜1.117) またがない 10/10 | **1.044** (1.002〜1.136) またがない **10/10** |
| Llama 2、有り、64 | 1.052 (7/10) | 1.011 (7/10) |

**モデルで符号が反転する。** Llama 2 は 2 通りとも 10/10 で速くなり、GPT-2 は 2 通りとも遅い側に出る。**変更を半分 (values 側だけ) にすると効果も両方向とも半分になる** ので、大きさは scores 側の取引で説明が付く。**ただし values 側だけにしても GPT-2 が負に残る理由は特定できていない** (計測の作法 18 番: 2 つの測定の差から機構を提案しない)。

**採用しなかった理由。** GPT-2 の `有り、256` は values 側だけにすればペア比が 1 をまたぐので「遅くなった」とは主張できないが、**2 通りとも符号が負** である。前面に出しているモデルで理由の分からない負を抱えるより、**Llama 2 の +4.4% を見送るほうを選んだ。**

**これは計測の作法 9 番の実例でもある。**「その演算を消して wall が動くまで、行の時間を信じないこと」。**1 トークン 12 本のカーネルが確かに消えたのに、GPT-2 の wall は動かなかった。**

### キャッシュ無しの減衰は平均文脈長に比例する

再計算の 1 ステップは、**固定費 + 文脈長に比例する GEMM** でできている。`T` トークン生成したときの 1 トークンあたりの時間は、平均文脈長 `(T+1)/2` を使って `a + b (T+1)/2` になる。表の 2 点 (64 と 256) から係数を出すと次のとおり。

| | 固定費 `a` | 1 文脈位置あたり `b` | 同じセッションの decode 実測 |
|---|---|---|---|
| Cumo | 2.100 ms | 38.2 us | 2.139 ms |
| CuPy | 4.091 ms | 21.5 us | 4.333 ms |

**固定費が decode の 1 トークンとほぼ一致する。** 再計算のステップも起動するカーネルの数は decode と同程度で (824 本対 640 本)、増えるのは全系列を作り直す GEMM だけだからである。

2 点で合わせた式なので、別の長さで検算した (キャッシュ無し、1 プロセス 1 条件、3 プロセスの best)。

| T | Cumo 実測 | Cumo 予測 | 差 | CuPy 実測 | CuPy 予測 | 差 |
|---|---|---|---|---|---|---|
| 32 | 3.134 ms | 2.730 | +14.8% | 4.758 ms | 4.446 | +7.0% |
| 64 | 3.341 | 3.341 | (合わせた点) | 4.790 | 4.790 | (合わせた点) |
| 128 | 4.587 | 4.563 | **+0.5%** | 5.060 | 5.478 | −7.6% |
| 192 | 5.866 | 5.784 | **+1.4%** | 5.927 | 6.167 | −3.9% |
| 256 | 7.007 | 7.006 | (合わせた点) | 6.855 | 6.855 | (合わせた点) |

**Cumo は 128 と 192 で 1.4% 以内に収まる。** T=32 だけ 15% 外れるのは、走行が 0.1 秒と短く固定費の割合が高い領域だからで、線形近似が効くのは 64 以上と読むのが妥当である。**CuPy はこの式に乗り切らない** (128 で −7.6%)。

**減衰の大きさはこの式の第 2 項がすべてである。** T=64 なら平均文脈は 32.5 位置なので Cumo は 2.10 + 1.24 = 3.34 ms (キャッシュ有りの **1.56 倍**)、T=256 なら 128.5 位置で 2.10 + 4.91 = 7.01 ms (**3.10 倍**)。長さに比例して開くだけで、64 が特別なわけではない。

**Cumo のほうが減衰が大きいのは、再計算が遅いからではない。** 33〜64 手目の 32 ステップを nsys で比べると、GPU の仕事はほぼ同じである。

| | Cumo | CuPy |
|---|---|---|
| cuBLAS gemm | 2,336 本 **57.3 ms** | 2,336 本 **59.4 ms** |
| GPU カーネル合計 | 26,384 本 88.7 ms | 23,529 本 94.2 ms |
| 1 ステップあたり | 824 本 / 2.773 ms | 735 本 / 2.945 ms |
| この 32 ステップの wall (実測差) | 113.6 ms | 154.3 ms |
| GPU が busy な割合 | **78%** | **61%** |

**同じ仕事を同じ速さでやっている。** 違うのは基準点のほうで、Cumo の decode は 2.10 ms と速いので追加された 1.24 ms が相対的に大きく出る。CuPy は decode の 4.09 ms を起動に使っているので、**増えた GEMM がその裏に隠れる**。

**したがって「キャッシュ無しの減衰が小さい」ことは速さの証拠ではない。** decode が遅い実装ほど減衰は小さく出る。絶対値では T=64 で 299.30 対 208.78 tok/s と Cumo が勝っている。

### ヘッドをまとめた効果

| | 64 トークン | 256 トークン |
|---|---|---|
| Cumo | 3.42 倍 | 3.55 倍 |
| CuPy | 3.02 倍 | 2.98 倍 |

**両者ともほぼ 3 倍で、構造の効き方に大きな差は無い。** API の豊富さが結果を変えるのではなく、起動回数を減らすという同じ工夫が同じだけ効いている。

## バッチ生成 (2026-09-20)

|---|---|---|---|
| 1 | 696.0 | 696.0 | 5.2% |

**batch 8 が batch 4 を下回る。** 5 ラウンドとも 1448〜1515 で、幅 4.6% の外である (batch 4 は 1971〜2048)。**長さ 128 では起きない。**

**原因は分かっていない。** 下の「追いかけて外した」を参照。

### 1 ステップあたりのカーネル数

nsys の差分法。**同じ表が長さ 128/64 の差からも 512/256 の差からも出た** ので、**この振り分けはバッチだけで決まり、長さには依らない**。

| batch | `gemvx` | `gemmSN` | cutlass sgemm | `splitKreduce` | その他 | 合計 |
|---|---|---|---|---|---|---|
| 1 | **49** | 0 | 0 | 0 | 188 | 237 |
| 2 | 0 | 37 | 12 | 12 | **202** | 263 |
| 4 | 0 | 37 | 12 | 12 | **202** | 263 |
| **8** | 0 | **48** | **1** | **0** | **202** | 251 |
| 16 | 0 | **25** | **24** | 24 | **202** | 275 |

**1 ステップの GEMM は 49 本である** (12 層 x 4 + 出口 1)。**その 49 本がどのカーネルに行くかが、バッチで変わる。**

- batch 1 はすべて `gemvx::kernel`
- **batch 2 と 4 は 12 本が cutlass の `sgemm_128x32_8x5_nn_align1` に行き、残り 37 本が `gemmSN_NN_kernel`**
- **batch 8 は 48 本が `gemmSN` に戻る。** 8 行あるのに cutlass に行くのは 1 本だけ
- batch 16 は 24 本が cutlass に行く

**cuBLAS の選択は行数について単調ではない。** cumo は `CUBLAS_GEMM_DEFAULT` を固定で渡すので、選んでいるのは cuBLAS の既定のヒューリスティクスである。

**cutlass に行った GEMM は `splitKreduce_kernel` を 1 本連れてくる。** batch 2/4 は 12 と 12、batch 16 は 24 と 24 で一致する (batch 8 の 1 本だけは連れてこない)。**投入律速の帯では、行数を増やすと 1 回の GEMM あたりの投入が倍になる点がある** ということになる。

**合計の差はこれで閉じる。**

```
その他は batch 2 以上でどれも 202 本 (batch 1 だけ 188 なのは埋め込みと列切り出しの経路が違うため)
251 (batch 8) + 12 = 263 (batch 2/4)
251 (batch 8) + 24 = 275 (batch 16)
```

**当初この表は `gemvx` と `gemmSN` を「gemv 系」にまとめ、`splitKreduce` を「その他」に入れていた。** 数字は同じだが、**まとめたせいで「cutlass に行くと投入が倍になる」が見えなくなっていた。** 別セッションが 1 形状 5 点の単体測定で `cutlass + splitKreduce` の 2 本を見つけ、こちらの表に当て直して分かった。

**単体でも同じ振り分けが出る。** 別セッションが `[M, 768] x [768, 3072]` を M = 1 / 2 / 4 / 8 / 16 で叩いたところ、**M=1 が `gemvx`、M=2〜8 が `gemmSN`、M=16 が cutlass + splitKreduce** で、**cumo (`gemmStridedBatched` 経由、batch=1) と CuPy (素の gemm) が全点で同じカーネルに落ちた**。**「batch=1 でも StridedBatched を通すから違うカーネルが選ばれる」は、この形状では起きていない。**

**ただし 1 形状 5 点では 49 本の混ざり方は説明できない。** decode には形の違う GEMM が何種類も入っていて、**混ざり方は形ごとの振り分けの重ね合わせ** である。

**ただしこれが長さ 512 の落ち込みの原因だとは言っていない。** 振り分けは長さに依らないのに、落ち込みは長さ 512 でしか出ない。**同じ振り分けで長さ 128 では単調に伸びる。**

### 3 実装をバッチで並べる

Python の 2 実装も同じ形にバッチ化してから測った (`python/gpt2.py` と `python/gpt2_torch.py`)。長さ 256 (fixture が固定している長さ)、7 系列をラウンド内でインターリーブして順序を回転、**11 ラウンドの先頭 1 本を位置で捨てて 10 ラウンド**。**対照は `cumo8` をもう一度。** **3 実装とも fixture のトークン列を通ってから計測に入る。**

| batch | Cumo | CuPy | PyTorch | Cumo / CuPy | PyTorch / Cumo | 対照 |
|---|---|---|---|---|---|---|
| **1** | 724.6 | 226.4 | 701.2 | **3.196 (3.100〜3.248)** 10/10 | 0.968 (0.955〜**1.003**) **またぐ** 1/10 | — |
| **8** | 3504.5 | 1703.7 | 3591.6 | **2.059 (2.021〜2.099)** 10/10 | 1.028 (**0.9998**〜1.050) **またぐ** 9/10 | 1.005 **またぐ** |

**Cumo の CuPy に対する差は、バッチを増やすと縮む** (3.20 倍 → 2.06 倍)。投入が支配する帯から外れるぶん、投入回数の少なさが効かなくなる。**これは両条件とも 10/10 でまたがない。**

**PyTorch との差は、どちらの batch でも決まらない。** 多数派の向きは batch 1 で Cumo 側 (9/10)、batch 8 で PyTorch 側 (9/10) と入れ替わるが、**どちらもペア比が 1 をまたぐ** (batch 1 の最大が 1.0030、batch 8 の最小が 0.9998)。**「向きが入れ替わる」とも言えない。** それぞれの条件で決まっていないので、比べるものが無い。

**なお PyTorch は SDPA を使っていて、[docs/method.md](../method.md) の対応表の外にある。** 同じアルゴリズムの比較ではなく、**到達可能な上限の参照点** として読む。

#### 「batch 8 で PyTorch が 1.5% 上回る」は取り下げた

**5 ラウンドで 1.015 (1.011〜1.031) と出て、幅の外だと書いた。** 作法 7 は **差を主張するなら 10 ラウンド** と言っているのに、6 ラウンドの先頭を捨てた 5 ラウンドで確定扱いにしていた。**10 ラウンド取ったら 1 をまたいだ。**

**そして同時に、比較そのものに欠陥があった。** Python の 2 実装の `generate_batch` が、1 ステップに **B 回** 読み戻していた。

```python
[int(v) for v in rows.argmax(axis=1)]   # デバイス配列を 1 要素ずつ int() する
rows.argmax(axis=1).get().tolist()      # 1 回でまとめて転送する
```

**「バッチ全体で 1 回」とコメントに書いておきながら、B 回やっていた。** Ruby 側は `(flat - offsets).to_a` で 1 回である。**費用を測った** (B=8、キューを空にしないようにして 1 ステップあたり)。

| | 1 要素ずつ | まとめて |
|---|---|---|
| CuPy | 250.6 us | 206.5 us |
| PyTorch | 206.0 us | 170.0 us |

**1 ステップ 36〜44 us で、長さ 256 なら PyTorch の総時間の約 1.6% に当たる。** **主張していた差 1.5% と同じ大きさだった。** 上の表は修正後に測り直したものである。

**CuPy の arm を 1 度取り違えた。**`python/gpt2.py` の既定は **ヘッドごとのループ** で、Ruby の現行 HEAD は **全ヘッドをまとめる** 形である (docs/method.md の対応表)。既定のまま測って **Cumo / CuPy = 9.47 倍** と出たが、**それは別のアルゴリズムと比べた数字だった**。`IDIOMATIC=1` で揃えたら 3.06 倍になった。**バッチ経路のほうは batch > 1 で必ずまとめる形を通るので、batch 1 だけが古い綴りという食い違いが表の中にできていた。**

### 追いかけて外した

**nsys の行を信じて、単体で測ったら再現しなかった。**

長さ 512 の profile で、`cumo_iter_sfloat_mul_kernel_dim2` が **1 ステップあたり 0.193 → 3.518 → 3.992 ms** (batch 4 → 8 → 16) と、batch 4 から 8 で **18 倍** に跳ねていた。attention の `[t, B, nh, hs] * [t, B, nh, 1]` がそれに当たる。

**その積だけを 1 プロセス 1 ケースで、対照を並べて測った** (作法 11)。

| B | 放送あり | 対照 (両辺とも全長) | 要素数 |
|---|---|---|---|
| 2 | 7.4 us | 7.1 us | 0.79 M |
| 4 | 13.5 us | 12.5 us | 1.57 M |
| 6 | 21.9 us | 47.4 us | 2.36 M |
| **8** | **44.6 us** | 88.8 us | 3.15 M |
| 12 | 74.2 us | 141.6 us | 4.72 M |
| 16 | 130.4 us | 189.5 us | 6.29 M |

**batch 4 から 8 で 3.3 倍** (要素数は 2 倍) であって、**18 倍ではない**。しかも **対照のほうが遅い** ので、放送に固有の崖でもない。**nsys の行の時間から読んだ帰属は取り下げる。**

**残るのは「長さ 512 で batch 8 が batch 4 を下回る」という観測だけである。** 5 ラウンドで再現し、幅の外にある。**原因は未分離。**

**`[50257]` の `sort` 1 回は 8 本である。** CUB の `DeviceRadixSort` 系 6 本、`float_key_kernel` 1 本 (float は並べ替え用のキーを別に作る)、**`cumo_na_copy` 1 本** (`sort` は inplace でないレシーバを必ずコピーする)。

**当初この表は「7 本」と書いていた。**`cumo_na_copy` を「要素演算ほか」に入れていたためで、**合計は同じだが「sort 1 回の値段」を 1 本少なく見せていた**。別セッションが単体で内訳を取って気づいた。**`splitKreduce` のときと同じ形で、今日 2 度目である** (計測の作法 20)。

**両方ありでも sort は 1 回である。** top-k と top-p は同じ並びを要求するので、**`Sampler` が 1 度だけソートして両方に渡す**。共有する前は 2 回で、**合計が 290 本だった**。

**`reverse` はカーネルを出さない。** cumo の `reverse` はビューで、`cumsum` も後続の要素演算もそのまま受ける。**当初 `Ops.contiguous` を通していたが、要らなかった** (1 本減)。

**`cumsum` 1 回は 2 本** (`DeviceScanInitKernel` + `DeviceScanKernel`)。top_k は抽出の 1 回だけ、top_p は降順の累積と抽出で 2 回。**ホストループには落ちていない** — Switch で踏んだ 8192 未満の帯とは別の経路である。**同じ演算の両側が、実ワークロードで埋まったことになる。**

**貪欲法の `max_index` 2 本は消える。** 抽出は縮約 1 つで済むので、argmax の行と入れ替わる。

#### 前の表は壊れた器械で測っていた

**以前ここにあった表 (貪欲法 653.6 / top_k 624.3 / top_p 608.4 / 両方 592.8) は取り下げる。**`script/gpt2_generate.rb` が **表示用の生成で数えたトークン数を、計測用の生成の時間で割っていた**。サンプラは計測ごとに乱数が進むので毎回違う列を出し、**EOT に当たった回は途中で止まる**。

4 回目  1.357 s  実際 655 トークン  正しい 482.6 tok/s  スクリプトの式  663.2 tok/s
```

**`best-of-N` は `times.min` を採るので、いちばん短く止まった回を系統的に選ぶ。** ノイズではなく偏りで、**N を増やすほど悪化する。**`872bce0` で、計測用の生成は EOT を無視し、長さが足りなければ例外にした。

**気づけたのは「サンプリングが貪欲法より 3 倍速い」というありえない値が出たからである。** EOT 停止だと当たりを付けたら外れ (`stop_at_eot: true` でも 900 生成された)、`stop_at_eot` 自体も無関係 (1.616 対 1.624)。**スクリプトがサンプラを使い回している** ことに気づいて再現した。

### AdamW は自分の式の予算どおりに動いている

**当初ここには「帯域の底から 5〜7 倍離れている」と書いていたが、取り下げた。** **底を計算する式が、測ったコードのものではなかった。**

**ただし PyTorch は同じアルゴリズムではない。**[docs/method.md](../method.md) の対応表のとおり、**numpy 版は Ruby の構造の写し** (手書きの backward、手書きの AdamW) で、**torch 版は autograd と `torch.optim.AdamW`** である。**「同じアルゴリズムを別の配列ライブラリで」と「エコシステムがこの問題に何を出すか」は別の問いで、両方を並べている。**

### 区間で割ると、いちばん開いているのは AdamW (2026-09-21)

**PyTorch の backward だけを取り出せるようになったので、3 区間を並べた。** それまで `--stop-after backward` が optimizer まで走っていたので、torch の列は 1 ステップの合計しか出せなかった (`4ee9416` で分離)。

40 ステップ (先頭 1 本を除く 39 本の平均)、1 プロセス 1 条件、**Cumo 3 区間 + PyTorch 3 区間 + 対照の 7 条件をインターリーブ** し、順序を回転して 11 ラウンド、先頭を位置で捨てて 10 ラウンド。クロックは固定 (アイドル SM 2805 MHz、計測後 2790 MHz)。**Cumo の既測値は流用せず、同じバッチで測り直してある** (計測の作法 10)。

| backward | **0.02944** (38.4%) | 0.01805 (39.3%) | **1.64 (1.539〜1.706)** 10/10 |

**いちばん開いているのは AdamW (1.87 倍) で、backward (1.64 倍) ではない。**

**forward の幅は 17.2% ある。** 1 条件が 0.38 秒しかないためで、**比は 10/10 で 1 を超えるので向きは言えるが、1.21 という値を読んではいけない** (計測の作法 7)。

**そして当初ここには「backward が 2.07 倍でいちばん開いている」と書きかけた。** 3 ステップ 1 本の値で、ラウンドを回していなかった。**区間ごとに違う向きにずれていて、順位まで入れ替わっていた。**

**「これは計測ではない」と明示して渡してあったが、明示は正しさの代わりにならない。** 受け取った側は「backward がいちばん開いている」を先に覚える (計測の作法 21)。

### PyTorch の foreach AdamW は 20.0 ms (逆算では 17.6 ms だった)

**上の表の update の差から直接読める。** それまでは `fused` との差と帯域下限から逆算していた。

| | 値 | 出どころ |
|---|---|---|
| 逆算 (2026-09-20) | 17.6 ms | `foreach - fused = 11.8 ms` に融合の帯域下限 5.8 ms を足した |
| **実測 (2026-09-21)** | **20.0 ms** | 区間の差 |

**逆算は 12% 低く出ていた。** cumo の素の式 (37.7 ms) との比は **2.2 倍ではなく 1.87 倍** である。**帯域下限を「相手の実装がそこに居る」として使うと、相手を速く見積もる向きに外れる。**

**結論は動かない。** 融合 AdamW で 76.69 → 44.8 ms、全体で **1.71 倍**、PyTorch の既定 (45.98 ms) と並ぶところまでは同じである。

### PyTorch の 1.67 倍のうち、オプティマイザは 26%

**`torch.optim.AdamW` は実装を選べるので、そこだけ振った** (同じ 10 ラウンドの手順、対照つき)。

| 実装 | s/step | 幅 |
|---|---|---|
| `foreach=True` (既定) | 0.04612 | 1.3% |
| `foreach=False` | 0.04180 | 1.0% |
| **`fused=True`** | **0.03429** | 1.0% |
| 対照 (`fused` をもう一度) | 0.03426 | 0.5% (またぐ) |

**既定と融合版の差は 0.01183 s = 1 ステップの 26%。** つまり **オプティマイザだけで 1.67 倍の全部は説明できない。** 融合版にしても 0.0343 s で、**こちらの forward + backward だけ (0.0392 s) より速い。**

**この 26% は PyTorch の数字で、こちらには移らない。**`foreach=True` は **既に複数テンソルをまとめて回す実装** で、こちらの素の式とは出発点が違う。逆算するとこうなる。

```
PyTorch  foreach - fused = 11.8 ms   融合版を帯域下限 5.8 ms と置くと foreach の AdamW ≒ 17.6 ms
cumo     素の式の AdamW   38.4 ms    PyTorch の foreach の 2.2 倍

**この逆算の 17.6 ms は、2026-09-21 に区間を直接測って 20.0 ms に置き換わった** (上記)。**比は 2.2 倍ではなく 1.87 倍。** 差し引き 32.6 ms と step の 42% は動かない。

| | いま | 融合 AdamW 後 | cumo との比 |
|---|---|---|---|
| **cumo** | 77.2 ms | **44.7 ms** | — |
| PyTorch (既定 `foreach`) | 46.1 ms | — | 1.67 → **0.97** |
| PyTorch (`fused`) | 34.3 ms | — | 2.25 → **1.30** |

**融合 AdamW だけで PyTorch の既定と並ぶ** (全体で **1.73 倍**)。**残る 1.30 倍が forward / backward の側である。** **2026-09-21 の測り直しでは 76.69 → 44.8 ms で 1.71 倍、PyTorch の既定が 45.98 ms である** (上記)。

**ただしこれは上限である。** 5.8 ms は帯域の下限なので、起動と端数のぶん実際には届かない。

**こちらは「融合 AdamW を入れれば全体で 1.72 倍」と見積もっていて、上の 1.73 倍と一致する。** **PyTorch の既定が 0.0462 でほぼ同じ値なのは偶然で、予測が当たった証拠にはならない** — あれは **別の実装の時間** であって、こちらの融合版を measure したものではない。

**そして当初ここには「オプティマイザの寄与は 26% しかない」と書いていた。** PyTorch の step に対する割合を、こちらの見込みの上限として持ってきていた。**落ち着いて見える数字ほど、出どころを確かめる理由が消える。**

## AdamW を 1 カーネルに融合した (cumo 0.10.0、2026-09-22)

**予算だけ立てて置いてあったものが、cumo 0.10.0 の `Cumo::CUDA::ElementwiseKernel` (#519) で取れた。** 「44P = 21.9 GB を 7P = 3.25 GB に落とせば 6.6 倍」という見積もりは上の節にある。**C を書かずに Ruby 4 行で書ける。**

```ruby
Cumo::CUDA::ElementwiseKernel.new(
  'T g, float32 lr, float32 b1, float32 b2, float32 eps, float32 wd, float32 bc1, float32 bc2',
  'T m, T v, T p',
  'm = b1 * m + (1 - b1) * g;
   v = b2 * v + (1 - b2) * g * g;
   T c = (m / bc1) / (sqrt(v / bc2) + eps);
   p = p - lr * (c + wd * p);', 'adamw')
```

**出力は `const` ではないので、`m` / `v` / `p` をその場で読んで書ける。** 入力は `const` なので、書く配列は出力側に置く。

5 条件をインターリーブ、順序を回転、**15 ラウンドの先頭を位置で捨てて 14**。1 条件は 30 ステップで、**先頭のステップは cuBLAS ハンドルとプールを払うので捨てる**。クロック固定 (アイドル SM 2790 MHz)。

| 条件 | steps/sec | ms/step | 幅 |
|---|---|---|---|
| 書き下し | 13.0 | 76.9 | 1.9% |
| **融合** | **20.5** | **48.8** | 3.5% |
| `CUMO_ALLOW_TF32=1` + 融合 | 24.8 | 40.3 | 1.9% |
| backward まで (最適化なし) | 25.2 | 39.7 | 2.7% |
| 対照 (融合) | 20.5 | | 4.2% |

| | ペア比 | 1 をまたぐ | 両側 p |
|---|---|---|---|
| **融合 / 書き下し** | **1.5738 (1.5359〜1.6031)** 14/14 | またがない | 1.2e-04 |
| **TF32 + 融合 / 融合** | **1.2120 (1.1860〜1.2293)** 0/14 | またがない | 1.2e-04 |
| TF32 + 融合 / 書き下し | **1.9002** 0/14 | またがない | 1.2e-04 |
| 対照 / 融合 | 0.9970 (0.9755〜1.0414) 8/14 | **またぐ** | 0.791 |

**10 ステップの loss は 10 個とも llm.c の参照と一致する** (許容 1e-2)。

### backward のアームを引くと、オプティマイザ自身が出る

| | オプティマイザだけ |
|---|---|
| 書き下し | 76.9 - 39.7 = **37.2 ms** |
| **融合** | 48.8 - 39.7 = **9.1 ms** |
| | **4.1 倍** |

**37.2 ms は、前に測った書き下しの 38.4 ms と 3% で合う。** 予算のほうは **6.6 倍と見積もっていたので届いていない。** 残る 2 つは分けていない。

- **148 本のテンソルを 1 本ずつ起動している。** 縮めるには **パラメータを 1 本の連続バッファに置いて各層がそのビューを持つ** 形にして、オプティマイザを 1 回だけ呼ぶ。前に「平坦化で 1.17 倍」と見積もった箇所と同じ話である
- **転置勾配の `Ops.contiguous` がオプティマイザの区間の中にある。** 別セッションによると **`ElementwiseKernel` は非連続な入力を自分で `dup` する** ので、**いまはこちらが呼んでも呼ばなくてもコピーは 1 回**。cumo 側が strided のまま読めるように直せば、こちらの呼び出しを外すぶんが浮く。**未着手**

### `CUMO_ALLOW_TF32` は学習では関門を割る

**decode では動かない。これは測る前に予算で名指ししてあった** (計測の作法 18)。1 トークンに重み 498 MB を読むので **600 GB/s でも 0.83 ms が下限**、実測 1.40 ms で **帯域側に張り付いている**。演算スループットを上げても出ないはず、と書いてから測った。

| 対照 / なし | 1.0003 (0.9974〜1.0040) 5/12 | **またぐ** | 0.774 |

### 転置勾配のコピーは外さないほうが速い (cumo master、2026-09-23)

**cumo #535 で `ElementwiseKernel` が転置ビューを複製せずにストライドで読めるようになった** ので、`each_parameter` の `Ops.contiguous` を外したアームを並べた。計測に使った cumo は master (`ba27577a`、#535〜#537 入り) を `rake install:local` で入れたもので、**`Cumo::VERSION` は 0.10.0 のままだがリリース版とは中身が違う。**

**ところが遅くなる。** 4 条件をインターリーブ、13 ラウンドの先頭を捨てて 12、クロック固定。

## fp16 で測るとどうなるか

**速度の結論は cumo #474 の前後で反転した。** いまの結論はすぐ下の小節にあり、**それ以降の小節はすべて #474 前の測定である**。数値計算の話 (layernorm が壊れる、トークン id が飛ぶ、KL や top-k の一致) は #474 と無関係なのでそのまま有効である。


**`Cumo::HFloat` は 0.7.0 (#365〜#371) で入った。** 当初は master `93528379` で測ったが、**released 0.7.0 で測り直してあるので、この節は `gem install` から再現できる**。例外は 2 か所ある。CuPy と PyTorch を並べた表は master のときのセッションのままで、その表の Cumo 列も master の値である。nsys の時間も master の値で、released 0.7.0 で一致を確かめたのはカーネル数のほうである (どちらも該当箇所に明記した)。

いずれにしても、**ここに出る fp32 の数字を上の比較表の Cumo 列と突き合わせてはいけない** (別セッションの数字を並べるなという上記の理由がそのまま当てはまる)。比較して意味があるのは、この節の中の fp32 と fp16 だけである。

**この節は `Ops.layernorm` と `Ops.gelu` を書き換える前の測定である。** 節の中の比 (fp16 対 fp32) はそのまま読めるが、fp32 の絶対値は現在の実装より 4〜7% 低い。

リポジトリのコードは fp32 のままで、`XM::SFloat` を差し替えるモンキーパッチとして測った。重みは fp32 のファイルから読み、`Ops.contiguous` の `zeros + store` が dtype の載せ替えを兼ねる。重みは 621.9 MiB から 311.0 MiB になる。

### #474 の後: 4 条件すべてで fp16 が速い (2026-09-18)

cumo #474 (master `e4c6f4b3`) でメモリプールの `CompactIndex` が直り、**向きがひっくり返った**。以前は 4 条件すべてで fp16 が fp32 より遅かったが、いまは 4 条件すべてで速い。

**どちらの cumo で測ったかは、バージョン文字列では判別できない。**#474 は 0.8.0 のリリース後に入ったので、released gem も master も `0.8.0` と名乗る。シンボルで見る。

```
nm -C $(gem contents cumo | grep 'cumo\.so$') | grep -o 'CompactIndex(CUstream_st\*[^)]*)'

  CompactIndex(CUstream_st*, bool)   # #474 前
  CompactIndex(CUstream_st*)         # #474 後
```

### 素朴に fp16 にすると layernorm で壊れる

GPT-2 の外れ値特徴のせいで、**残差ストリームは fp16 の範囲に収まるのに、その二乗が収まらない**。

| | 124M (C=768) | 355M (C=1024) | 774M (C=1280) |
|---|---|---|---|
| 母分散の最大 | 12,965.1 (`h.11.ln_1`) | 15,023.4 (`h.17.ln_2`) | **4,996.7** (`h.22.ln_1`) |
| 二乗の最大 | 9,305,713 | 14,712,223 | 6,185,265 |
| \|x\| の最大 | 3,055.4 | 3,840.1 (`h.16.ln_2`) | 2,489.0 |
| fp16 上限 65,504 に対して | 分散は 5.05 倍の余裕 | 4.36 倍の余裕 | **13.11 倍の余裕** |
| 二乗を配列として作った場合 | **142 倍オーバー** | **225 倍オーバー** | **94 倍オーバー** |

`(x - mean) * (x - mean)` を fp16 の配列として作った時点で Inf になり、variance が Inf、rstd が 0 になって出力が全部 0 になる。生成は "the first of the first of the ..." のように退化し、KL(fp32 || fp16) は 2.33 nats (perplexity 比 10.3) になる。

**避け方は二乗を配列にしないこと。** cumo の縮約は fp32 で畳んでから最後に 1 度だけ丸めるので、`x.var(axis: 1)` は fp16 の二乗を作らない。ただし `var` は **上限を免れるのではなく収まっているだけ** で、余裕は 124M で 5.05 倍、355M で 4.36 倍しかない (774M は 13.11 倍)。そして **見るべきは最大の活性ではなく最大の分散である**。外れ値 1 本は幅 C の行に均されるので、分散はその二乗よりはるかに小さくなる。実際 3 モデルとも「二乗の最大 ÷ C」が分散の最大にほぼ一致する (12,117 対 12,965、14,367 対 15,023、4,832 対 4,997。残差が行の他の要素)。層を見ても代用にはならない。355M では 2 つの最大が別の層に出るが (活性が `h.16.ln_2`、分散が `h.17.ln_2`)、124M と 774M では同じ層だった。**3 モデル中 1 つでしか起きないので、層の位置は当てにしないこと。**

**モデルが大きいほど危ないわけではない。** 余裕は 5.05 → 4.36 → **13.11 倍** と単調に動かない。774M で広がるのは、行の幅 C が 1280 と広いうえに最大の活性そのものが小さい (2,489。355M の 3,840 より小さい) ためである。**外れ値はモデルサイズとともに大きくなる、という一般論からこの余裕を外挿してはいけない。** 当初ここでは 355M や 774M が危ない側に回りうると見ていたが、測ったら逆だった。

なお `var` は不偏 (n-1) なので、llm.c の layernorm が使う母分散にするには `(n-1)/n` を掛ける。これは numo 由来の定義で fp16 固有ではない。

355M と 774M の行は PyTorch と HuggingFace の重みで測った。同じ手順で 124M を測ると Ruby 側と 12,965.1 / 9,305,716 まで一致するので、**チェックポイント形式も loader もフレームワークも違う 2 経路が同じ値を出している**。

### 数値: 分布は一致するが、貪欲法のトークン列は一致しない

1 手目のロジット (V = 50257、fp32 のロジットは -64.1 〜 -38.9) を fp32 と比べたもの。

| layernorm の実装 | 最大絶対差 | RMS | top-1 | top-5 | top-50 | KL(fp32 \|\| fp16) |
|---|---|---|---|---|---|---|
| 素朴 (fp16 のまま) | 51.71 | 40.75 | 不一致 | 1/5 | 6/50 | 2.33 nats |
| 統計だけ fp32 | 0.0948 | 0.0661 | 一致 | 5/5 | 50/50 | **0.00005 nats** |
| `var` を使う | 0.2551 | 0.2037 | 一致 | 5/5 | 50/50 | 0.00008 nats |

**perplexity 比は 1.0000 で、sampling には影響しない。** それでも **貪欲法のトークン列は 2 番目で分岐する** (動く 2 実装は同じ列を出し、どちらも自然な英語のまま)。fp32 の 1 位と 2 位の差は 1 手目で 0.5023 あるが、どこかの手でそれがロジットの誤差を下回るためである。**このリポジトリの受け入れテストはトークン列の完全一致なので、fp16 はその前提を壊す。** 上の「fp32 の天井」はこの意味である。

### decode は帯域律速から起動律速に変わる

nsys、`--length 72` と `--length 40` の差 ÷ 32。**この表の時間だけは master `93528379` の測定である。** released 0.7.0 で 2 巡数え直したところ **カーネル数は 677 / 727 / 677 で一致した** が、時間のほうは fp16 の 2 巡とも外れ値の尾を引いて安定しなかったので (`var` の埋め込み gemv が中央値 196 us に対して平均 667 us、最大 2.7 ms)、置き換えていない。

| fp16 (統計 fp32) | **727** | 1.598 ms | 1.465 ms | 0.163 ms |
| fp16 (`var`) | 677 | **1.341 ms** | 1.351 ms | 0.158 ms |

**重みが半分になったぶんは GPU 時間にそのまま出る。** 埋め込み転置の gemv `[1,768] x [768,50257]` は 0.386 → 0.199 ms と **ちょうど半分**、層内 48 本は 0.881 → 0.53 ms で、GPU 時間の合計は 27% 減る。

**それでも wall は 2〜6% しか動かない。** 投入は dtype で変わらないので (1.368 対 1.351 ms)、GPU が速くなるとそちらが律速に回る。GPU busy は 76% から 59% に落ちる。上の「伸びしろ」の表で言えば、**CUDA Graph の到達点が 545 から 746 tok/s に上がる** ということで、**fp16 と CUDA Graph は組み合わせて初めて効く**。

キャッシュ無しが 1.65 倍になるのは、毎ステップ全系列を作り直すので演算量が支配し、tensor core が実際に使われるためである (`[T,50257] x [50257,768]` の one-hot 埋め込み GEMM を含む)。

#### 残差は GEMM に畳める (バイアスと違って)

**バイアスが畳めないのは C を毎回詰め直すからだった。残差の C は潰してよい。**`x = x + attn.dot(W) + b` の `x` は、その行より後どこからも参照されない。

```ruby
# 3 本: gemv、バイアス加算、残差加算
attproj = Ops.linear(attn, weights[:attprojw_t], weights[:attprojb])
x + attproj

# 2 本: gemm(beta: 1)、バイアス加算
attn.gemm(weights[:attprojw_t], x.inplace, beta: 1) + weights[:attprojb]
```

**丸めは変わらない。**`a.gemm(w, c.inplace, beta: 1)` は `a.dot(w) + c` と **ビット完全一致** する (単体で確認、`max|d| = 0.0`)。非連続な A も受ける。生成トークン列も 257 個完全一致した。

**増えたカーネルは無い** (バイアスの拡張案が store 48 本に化けたのと対照的)。速度は長さ 1000 で 10 ラウンド、プロセス内 best-of-5、クロック固定。

#### バイアスを GEMM に畳む

1 トークンの 269 本のうち **`add_dim2` が 72 本** を占める。内訳はモンキーパッチで数えて確定した。

| | カーネル/token | `add_dim2` | `store_dim2` |
|---|---|---|---|
| 現行 | 269 | 72 | 36 |
| バイアスを外す (数学的には誤り) | **221** | **24** | 36 |
| 重みを拡張して畳む | 269 | **24** | **84** |

**72 本はバイアス加算 48 本 (`Ops.linear` が 1 層 4 回) と残差加算 24 本 (1 層 2 回) である。**

**重みの拡張は本数を減らさない。**`[x, 1] @ [[W], [b]]` は数学的には正しく (生成トークン列が現行と一致する)、バイアスの加算 48 本は消える。しかし **入力を拡張バッファに書き写す store が 48 本増えて相殺する**。cumo の `dot` は出力を自分で確保するので、拡張した入力を作る所でカーネルを 1 本払うことになる。

速度も測った (長さ 1000、1 回 1.5〜1.9 秒、10 ラウンドをインターリーブ、プロセス内 best-of-5、クロック固定)。

| | ペア比 (対 現行) | 1 をまたぐ |
|---|---|---|
| バイアスを外す | **1.025〜1.122** 10/10 | いいえ |
| 重みを拡張して畳む | 0.998〜1.255 8/10 | **はい** |

**1 ラウンド目だけ冷えていて、両方とも外れ値になっている** (現行 520.7 に対し 2 ラウンド目以降は 636〜649)。**それを除くと、バイアスを外した側が 1.025〜1.059 の 9/9、拡張した側が 0.998〜1.022 で 1 をまたぐ。**

**したがって上限は 2.5〜5.9% である。** 投入だけから見積もると 48 本 x 2.08 us = 0.10 ms で、1 トークン 1.56 ms の 6.4% にあたるので、実測はそれをやや下回る。**そしてこの 2.5〜5.9% は Ruby 側からは取れない。**

**`beta` では取れない。** 当初ここには「cuBLAS の `beta` を使える形が要る」と書いていたが、**`Cumo::SFloat#gemm` は既に `c` と `beta` を取る** (`a.gemm(w, c, beta: 1)`)。cumo 側が nsys で数えた結果は次のとおりで (200 回、`[1,768] x [768,768]`)、**どの形でも 1 回 2 本から下がらない**。

| 呼び方 | カーネル/回 |
|---|---|
| `gemm(w)` のみ | 1 |
| `dot(w) + bias` | 2 |
| `gemm(w, c, beta: 1)` | **2** |
| `gemm(w, c.inplace, beta: 1)` | 1 (ただし `c` が結果で潰れる) |
| 同上 + 毎回 `c.store(bias)` | **2** |

**cuBLAS の `beta` は C が入力かつ出力なので、バイアスを毎回 C に詰め直す 1 本が必ず残る。** 上の「重みを拡張して畳む」が store 48 本に化けたのと同じ構造である。

**ただし詰め直しはまとめられる。** 当初ここには「要るのは `cublasLtMatmul` の bias エピローグである」と書いていたが、**それは 1 回ずつ詰め直す前提での結論だった**。C が潰れるのは事実でも、**潰れるのは呼び出しごとではなくトークンごとにまとめて直せる**。

**モデル中のバイアスを 1 本の連続バッファに並べ、1 トークンに 1 回だけ master から詰め直す。** GPT-2 124M の decode では `qkvb` / `attprojb` / `fcb` / `fcprojb` の 48 本ぶんで 82,944 要素 (324 KiB) になる。

```ruby

ln1.gemm(w[:qkvw_t], bias_c(layer, :qkvb).inplace, beta: 1)    # 1 層 4 か所
```

| | カーネル/token | `add_dim2` | `store_dim2` |
|---|---|---|---|
| 現行 | 269 | 72 | 36 |
| バイアスを C に置く | **222** | **24** | 37 |
| (バイアスを外した天井) | 221 | 24 | 36 |

**48 本消えて 1 本増える。**`C` にビューを渡しても余分なカーネルは出ない (単体で 200 回呼んで 200 本)。**生成トークン列は 257 個ビット完全一致する。**

**CuPy だけ decode で fp16 が遅い。** 5 ラウンドすべてで fp32 が勝ち、ペア比の最大が 0.900 と 1 を超えない。演算量が支配するキャッシュ無しでは 1.15 倍になるので、fp16 の GEMM が遅いわけではない。Cumo の decode は投入が律速だと nsys で確かめてあり (上記)、CuPy も 1 演算あたりの固定費からそう見積もられている。**そこで dtype を落として遅くなるということは、CuPy の要素演算・縮約が fp16 で fp32 より高くつく** と読めるが、**どのカーネルかは追っていない** ので、ここは測定結果の記述にとどめる。

**PyTorch の伸びが最も大きい** (1.5〜2.7 倍)。fp16 では attention が mem-efficient から **flash** に替わるので (profile で確認。後述)、dtype だけでなく attention の実装ごと変わっている。上の「fp32 の天井」が fp32 の天井でしかない、というのはこの意味である。

同じ dtype どうしで Cumo と CuPy を比べると、fp32 で 1.83 / 1.81 / 0.98 倍、fp16 で 2.18 / 2.12 / 1.38 倍。**fp16 にすると Cumo の優位が広がる。**

### 差はカーネルの数で、1 本あたりの費用ではない

nsys で 1 トークンあたりのカーネルを数えた (`--length 72` と `--length 40` の差 ÷ 32、KV キャッシュ有り)。

| | カーネル/token | 投入回数/token | 投入時間 (ms/token) | 1 投入あたり |
|---|---|---|---|---|
| Cumo fp32 | 677 | 677 | 1.368 | 2.02 us |
| Cumo fp16 | 677 | 677 | 1.351 | 2.00 us |
| PyTorch fp32 | **196** | 196 | 0.408 | 2.08 us |
| PyTorch fp16 | **148** | 148 | 0.309 | 2.09 us |

**1 投入あたりの費用は 4 通りとも 2.0〜2.1 us で同じである。** 投入時間の比 3.4 倍は、そのままカーネル数の比 (677 対 196) である。**差は 1 演算の速さではなく、演算の回数から来ている。**

内訳で効いているのは融合である。PyTorch は attention が 1 トークンあたり 12 本 (層ごとに 1 本) の融合カーネルで、layernorm も `vectorized_layer_norm_kernel` が 25 本 (層ごとに 2 本 + 最終 1 本) と 1 対 1 に対応する。Cumo 側は同じ仕事を要素演算と縮約に分解するので、628 本が cumo 自前のカーネルになる。

**PyTorch の attention は fp16 で flash に替わる。** fp32 では `fmha_cutlassF_f32_aligned_64x64_rf_sm80` (mem-efficient) が、fp16 では `pytorch_flash::flash_fwd_kernel` が走っている。fp16 でカーネル数が 196 から 148 に減るのはこの入れ替わりを含む。

**ただし `sdpa_backend` の報告は fp16 で実際と食い違う。**`can_use_*` を優先順に問い合わせる実装は fp16 で `cudnn` と答えるが、profile に出るのは flash である。**fp32 の `efficient` は profile と一致している** ので、食い違うのは fp16 だけである。バックエンドを言うときは profile を見ること。

**この profile の時間は信用しないこと。** GPU 時間の合計が PyTorch fp32 で 1.596 ms/token となり、同じ日の wall (1.478 ms) を超えている。デスクトップが GPU を 2 割ほど使っている状態で取ったためと見ているが、確かめていない。**回数と投入時間 (CPU 側) だけを使う。**

### 3 実装の数値をまとめて

それぞれ自分の fp32 を基準にした 1 手目のロジット。V = 50257、fp32 のロジットは -64.1 〜 -38.9、1 位と 2 位の差は 0.5023。

| 実装 | layernorm の扱い | 最大絶対差 | RMS | KL | トークン列 (64 / 256、キャッシュ有無) |
|---|---|---|---|---|---|
| Cumo | 素朴 | 51.71 | 40.75 | 2.33316 | 0 番目で分岐 |
| Cumo | 統計を fp32 にキャスト | 0.0948 | 0.0661 | 0.00005 | 2 番目で分岐 |
| Cumo | `var` (n-1 を補正) | 0.2551 | 0.2037 | 0.00008 | 2 番目で分岐 |
| CuPy | 素朴 | 51.71 | 40.75 | 2.33316 | 0 番目で分岐 |
| CuPy | 統計を fp32 にキャスト | 0.0949 | 0.0662 | 0.00005 | 2 番目で分岐 |
| CuPy | `var(dtype=float32)` | **0.0766** | **0.0471** | 0.00004 | **完全一致** |
| PyTorch | `F.layer_norm` のまま | 0.0751 | 0.0441 | 0.00006 | 2 番目で分岐 |

**素朴な fp16 は Cumo と CuPy で誤差まで同じ** になる (51.71 / 40.75 / KL 2.33316)。壊れているのはライブラリではなく式なので、そうなるのが当たり前である。

**CuPy の `var` 版だけトークン列が完全に一致する。** これは偶然ではなく、その実装が最も正確だからである (RMS 0.0471 で、キャッシュ版の 0.0662 より小さい)。逆に Cumo の `var` 版は RMS 0.2037 と 4 倍悪い。**差は縮約 API の形にある。**

| | 累算の dtype | 結果の dtype | accumulator の指定 | 分散の定義 |
|---|---|---|---|---|
| Cumo | 常に fp32 (選べない) | 入力の dtype に丸める | 無い (`unknown keyword: :dtype`) | n-1 (不偏) |
| CuPy / NumPy | 既定は入力の dtype | 指定した dtype | `var(dtype=float32)` | n (母分散) |
| PyTorch | `F.layer_norm` が内部で fp32 | — | — | — |

**逃げ道の形が逆である。** cumo は素朴に書いても累算は守られるが、答えが 65504 を超えると丸めで壊れ、それを避ける手段が API に無い。numpy / cupy は素朴に書くと `var()` がそのまま溢れるが (`np.float16` の `var()` は `inf` を返す)、`dtype=` を書けば累算も結果も fp32 になる。PyTorch は融合された layernorm が内部で上げるので、利用者が罠を踏む機会が無い。

**このワークロードでは cumo 側の丸めが実際に効いている。** 分散を fp32 のまま受け取れないぶんが RMS で 4 倍、そしてトークン列が一致するかどうかの差になって出た。cumo の縮約に `dtype:` があれば埋まる差である。

**3 実装の fp32 どうしは 1.5e-4 以内で一致する** (Ruby 対 CuPy が最大 0.00009、Ruby 対 PyTorch が 0.00015)。fp16 の差はこの実装間差より 3 桁大きい。

**Ruby 側は `DTYPE=fp16` で切り替わるようになった** (`GPU=1 DTYPE=fp16 ruby script/gpt2_generate.rb`)。下の表はモンキーパッチで測っていた当時の差し替え箇所で、**いま同じことをしているのは `XF` 定数である。**`one_hot` を fp32 で作ってから cast すること、因果マスクを `-1.0e4` にすること、`exp` の clip を 11.0 にすることは `Ops` が dtype で分岐して行う。**Python の 2 実装も `DTYPE=fp16` で切り替わるようになった** (`GPU=1 DTYPE=fp16 python/.venv/bin/python python/bench_gpt2.py --impl torch`)。`python/gpt2.py` は `DT` 定数を持ち、layernorm の統計を fp32 で畳み、因果マスクと one-hot を dtype に合わせる。`python/gpt2_torch.py` は重みと KV キャッシュの dtype だけで、`F.layer_norm` が統計を自分で fp32 に上げるので layernorm は触らない。**numpy にも cupy にも bfloat16 が無いので、Python 側は fp16 までである** (torch は `DTYPE=bf16` も受ける)。

| | 差し替えるもの |
|---|---|
| Ruby (`lib/narray_llm`) | `Ops.contiguous` / `layernorm` / `causal_mask` / `one_hot` / `KVCache`。重みは fp32 のまま読み、`contiguous` の `zeros + store` が載せ替えを兼ねる |
| Python (`python/gpt2.py`) | `load_checkpoint` / `layernorm` / `causal_mask` / `one_hot` / `KVCache`。`IDIOMATIC=1` (バッチ版) で測る |
| PyTorch (`python/gpt2_torch.py`) | `load_checkpoint` と `KVCache` だけ。`F.layer_norm` が内部で統計を fp32 に上げるので layernorm は触らない |

3 実装に共通して、**`one_hot` は fp32 で作ってから cast する** (トークン id が 2048 を超えると fp16 で飛ぶ) こと、**因果マスクの `-1.0e9` を `-1.0e4` に置き換える** (fp16 では `-Infinity` になる) ことが要る。1 手目のロジットを fp32 で書き出して突き合わせれば、上の表の数値は再現できる。

モデルごとの分散は cumo にも Ruby にも依存しないので、PyTorch で直接測れる。`gpt2` / `gpt2-medium` / `gpt2-large` を引数に取る。

```python
import sys, torch
from transformers import GPT2LMHeadModel
EOT, LENGTH = 50256, 256
for name in sys.argv[1:]:                      # gpt2 / gpt2-medium
    model = GPT2LMHeadModel.from_pretrained(name, dtype=torch.float32).cuda().eval()
    with torch.inference_mode():
        out = model.generate(torch.tensor([[EOT]]).cuda(), max_new_tokens=LENGTH,
                             do_sample=False, pad_token_id=EOT)
        seen = {}
        def hook(n):
            def fn(_m, inp, _o):
                x = inp[0].detach().float()
                sq = (x - x.mean(-1, keepdim=True)) ** 2
                seen[n] = (x.var(-1, unbiased=False).max().item(), sq.max().item())
            return fn
        hs = [m.register_forward_hook(hook(n)) for n, m in model.named_modules()
              if isinstance(m, torch.nn.LayerNorm)]
        model(out)
        [h.remove() for h in hs]
    v = max(seen.items(), key=lambda kv: kv[1][0])
    s = max(seen.items(), key=lambda kv: kv[1][1])
    print(name, "var", f"{v[1][0]:,.1f}", v[0], "| sq", f"{s[1][1]:,.1f}", s[0])
```

`unbiased=False` が要る。LayerNorm が使うのは母分散で、`unbiased=True` だと C/(C-1) だけずれる。

## 読み取れること

1. **同じ土俵 (構造を揃えた比較) では Cumo が CuPy より 1.47〜2.99 倍速い。** 差の出どころは 1 演算あたりの固定費 (2.06 us 対 3.7 us) で、投入が GPU 時間の裏に隠れるか超えるかの分かれ目になる。演算量が支配する「無し、256」は 0.997 (判別できず) から 1.120 (融合後)、1.474 (gather 後) と動いた
2. **構造の工夫 (ヘッドのまとめ) は両エコシステムで同じだけ効く。** どちらも約 3 倍。「Python は API が豊富だから速い」という形にはなっていない
3. **天井 (PyTorch eager) との差は、融合カーネルを取り込んでほぼ消えた。** 1 投入あたりの費用は Cumo も PyTorch も 2.0〜2.1 us で同じで、差は 1 トークンあたりの起動数から来ていた。融合前は Cumo 640 本対 PyTorch 196 本 (fp32) で 1.56〜1.66 倍離されていたが、**cumo の `layer_norm` / `softmax` / `gelu_tanh` を取り込んで 308 本になり、キャッシュ有りでは対照と区別が付かないところまで来た** (64 で 1.091、256 で 1.028、どちらもペア比が 1 をまたぐ)。**キャッシュ無しも埋め込みを gather にして 1.12〜1.14 倍まで詰まった** (gather の前は 1.36〜1.50 倍)。この経路は演算量が支配するので、起動を削っても効かず、効いたのは毎ステップ 154 MB を読んでいた one-hot GEMM を消したほうである。以前ここには「1 演算あたりの固定費は PyTorch が 4.71 us と 4 実装中で最も高いのに生成では勝つ」と書いていたが、**その 4.71 us は再測定と合わず (2.58 us)、固定費で負けているという前提自体が成り立たない。**
4. **CPU の差は BLAS の有無であって言語差ではない。** numo-linalg を入れずに GEMM を回すと、単一スレッドの OpenBLAS にも 6.3 倍離される
5. 5 実装すべてが同一のトークン列を生成した。fp32 の丸めが argmax を割ることは、この長さ (256 トークン) では起きていない。SDPA は演算順序が違うので僅差の割れを想定していたが、実際には起きなかった
