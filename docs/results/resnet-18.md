# ResNet-18 (2 次元の畳み込み)

[PLAN-conv2d.md](../plans/PLAN-conv2d.md) の記録。**条件・手順・外した経緯をここに置く。** 則は [AGENTS.md](../../AGENTS.md)、実例は [measurement-cases.md](../measurement-cases.md)。

## 要約

README の「数字」に書いていた要約をここに移した (2026-09-23)。**表は [README](../../README.md#数字) にある。**

**このリポジトリで初めて生成しないモデル。** 関門もトークン列ではなく **16 枚の画像に対するクラス番号の完全一致** で、参照は transformers。**2 綴り x BatchNorm を畳む / 畳まないの 4 通りとも、16 枚が 1 つも違わない。**

**畳み込みは 3 通りで書いた。** Whisper の Conv1d と同じ 2 綴り (カーネル位置ごとに行列積を並べる `shift`、窓を展開して 1 本にする `unfold`) に、**cumo 自身が持っている cuDNN 版の `conv`** を足した。

**1 次元では `unfold` が 1.65% しか勝たなかったのに、2 次元では 47% 勝つ。** 測る前に「`unfold` が負けるとしたら窓行列が入力の 9 倍になるから」と名指ししてあったが、**外れた。9 倍は正しく、小さいほうだった** — `shift` は `gemm(beta: 1)` で累積するので **タップごとに出力を読んで書く** (`3 x 3` で 9 往復、`7 x 7` で 49 往復)。**累積 6.79 GB 対 窓行列 1.88 GB で、3.6 倍大きいほうを数えていなかった。** 差 4.75 GB は 600 GB/s で 7.9 ms、実測の差が 8.3 ms で閉じる。**起動回数では 5% しか説明できない。**

**そしてそれは、ほぼ stem の話だった。** 綴りを層ごとに選べるようにして、**全部 `unfold` から 1 か所だけ `shift` に替えたアーム** を 5 つ測った (7 条件をインターリーブ、14 ラウンド)。**5 か所すべてで `unfold` が勝ち、符号はどこでも反転しない。** **stem だけで penalty の 82%** で (`7 x 7` はタップが 49 個あるので 49 往復する)、**部分ごとの増分の合計 8.13 ms が、全部 `shift` の実測 8.17 ms と 0.6% で閉じる。** `3 x 3` だけのモデルなら差は 2〜3% に縮む。**効いていたのはカーネルの大きさそのものだった。**

**綴りを変えると Cumo と CuPy の勝ち負けが入れ替わる。** `shift` では Cumo が 45% 速く、`unfold` では CuPy が 7.6% 速い。**他のモデルでは Cumo が一貫して勝っていたので、逆転は初めて。** **`unfold` の差は部品に分けて閉じた** — 窓行列の組み立てが 54%、畳み込みの外 (BatchNorm や ReLU) が 34%、パディングが 10%、GEMM は 0。**組み立ては 3x3 の層で一様に 1.18〜1.26 倍遅く、読み書きの両側がストライドのビューになるコピーだけが遅い** (下の各節)。`shift` で Cumo が勝つ理由は測っていない。

**3 つ目の綴りは cuDNN で、ここだけ相手が torch になる。** **CuPy 14.2 は cuDNN の畳み込みを公開していない** ので、CuPy 側にこの腕は無い。**README の 2 つの表は別のバッチなので、またいで比を取らないこと** (計測の作法 10)。

**cumo は cuDNN のワークスペース上限を既定 8 MiB に固定していた。** 2019 年の移植初日から動いていない chainer 由来の値で、**それを超えるアルゴリズムは探索の候補にすら入らない**。環境変数 1 本で **1.59 倍** (12/12、12.94 → 8.09 ms/pass)。**同じビルド・同じコード・同じ入力で、数値 1 つだけを振った A/B である。** カーネル名を数えると **アルゴリズムが完全に入れ替わっていた** — implicit GEMM が 19 本から 3 本に減り、**Winograd と FFT** が入る。**合計は 99 本から 183 本に増えるのに速い。**

**ただしその 1 本のつまみは、精度も一緒に動かしていた。** 選ばれたカーネルのうち 7 本が **テンソルコアの TF32** で、logits の差が 1.6e-05 から 3.8e-03 へ **2 桁動く** (クラス番号は 16/16 のまま)。`NVIDIA_TF32_OVERRIDE=0` でドライバ側から TF32 だけを切ると内訳が割れた — **1.5045 倍 (精度そのまま) x 1.0709 倍 (TF32) = 1.5941 倍**。**利得 4.85 ms のうち 4.33 ms、89% は精度を落とさずに取れる。**

**1 GiB は要らなかった。** 頭打ちは **TF32 ありで 64 MiB、なしで 256 MiB** で、それ以上はプールが増えるだけである (別セッションのスイープ)。**最初に測った 1.62 倍は、64 MiB で足りるものを 1 GiB で払って取っていた。**

**この 2 つは cumo 本体に入った。** HEAD (23b2ec35) では **既定が 128 MiB** になり、**単精度の畳み込みはテンソルコアに載らなくなった** (#501、#502)。**環境変数を 1 つも立てずに 1.51 倍** (15/15) で、TF32 の 1.07 倍は `CUMO_CUDNN_ALLOW_TF32=1` で選べる。**リリース済みの 0.9.0 はまだ 8 MiB である。**

**そして幅が広かったのは、探索が 2 通りの答えを返していたからだった。** 同じ条件でも **プロセスごとに Winograd が 13 本の組と 17 本の組のどちらかに行き**、**速度の帯が重ならない** (1868〜1888 対 1917〜1927 枚/sec、20 本)。**どちらを引いたかは logits に出る** ので、`perf_result.algo` を外に出さなくても判別できる。**幅をノイズとして丸めると、2 群の混合であることが見えなくなる。**

**PyTorch の既定も cuDNN の TF32 を使う。** 精度を揃えずに並べると帰属できないので切って測った — torch 自身で **1.22 倍が TF32** である。**精度を揃えた残りの差は、まだ同一バッチで測っていない。未分離。**

**cuDNN はチャネル先を要求するので、綴りがモデル全体の並びを決める。** `shift` と `unfold` はチャネル最後で行列積に合わせ、`cudnn` はチャネル先。**`cudnn` のアームは入口の転置を 1 度も払わない** ぶん、`store` が **215 本から 1 本** に落ちる。

## 何を測りに来たか

**2 次元の畳み込みを `shift` と `unfold` のどちらで書くか。** Whisper の `Conv1d` で同じ 2 綴りを測ったとき、**1 次元 (kernel 3) では `unfold` が 1.65% 勝った** (10/10、CuPy と PyTorch でも同じ向き)。

**2 次元では比が変わるはずだった。**`3 x 3` では `shift` の行列積が 3 本から 9 本に増える一方、**`unfold` の窓行列は入力の 3 倍から 9 倍になる**。**測る前に負ける形を名指ししてあった** (計測の作法 18) — 「`unfold` が負けるとしたら、窓行列が大きい `conv1` (7.4 MB) の側」。

**予想は外れた。** 符号は反転せず、**`unfold` の勝ち幅が 1.65% から 47% に広がった。**

## 1 パスあたりのカーネル数 (2026-09-21)

nsys の差分法 (`--repeat 12` と `--repeat 4` の差 ÷ 8)。1 パスは 16 枚。**回数はクロックにも外乱にも依らない** (計測の作法 8)。

| | `shift` | `unfold` |
|---|---|---|
| **GEMM** | **196** | **20** |
| `store_sfloat_kernel_dim4` (窓行列) | 76 | **193** |
| `store_sfloat_kernel_dim3` (タップのコピー) | **139** | 22 |
| `fill` | 38 | 18 |
| **合計** | **526** | **330** |

**`shift` の GEMM 196 本は、書いたコードから数えた値と 1 本も違わない** — `3 x 3` が 16 本 x 9 + `7 x 7` が 1 本 x 49 + `1 x 1` が 3 本 x 1 = 196。**`unfold` の 20 本は畳み込み 1 本につき GEMM 1 本である。**

## 効いているのは起動回数ではない。累積のトラフィックである

**増える 196 本を起動費 2.1 us で掛けても 0.4 ms** で、実測の差 8.3 ms/pass の **5%** にしかならない。**本数が減ることと速くなることは別** なので (measurement-cases 11)、予算を別に立てる。

**`shift` は `gemm(beta: 1)` で累積するので、タップごとに出力を読んで書く。**`3 x 3` なら 9 往復、`7 x 7` なら 49 往復である。**`unfold` は出力を 1 度書くだけで、代わりに窓行列を 1 度書いて 1 度読む。**

| | 1 パス (16 枚) |
|---|---|
| `shift` の累積の往復 | **6.79 GB** |
| `unfold` の出力書き込み | 0.16 GB |
| `unfold` の窓行列 (往復) | 1.88 GB |
| **差** | **4.75 GB → 600 GB/s で 7.9 ms** |
| **実測の差** | **8.3 ms** |

**予算が 95% を説明する。** 1 次元で 1.65% しか離れなかったのは、**タップが 3 本しかなく、Whisper の出力が小さかった** ためで、**2 次元で開いたのは窓行列が 9 倍になったからではなく、累積が 9 往復になったからである。**

**負ける形の名指しは外れたが、外れ方が答えになった。** 予算を立てていれば測る前に分かった — **窓行列の 9 倍 (1.88 GB) より、累積の 9 往復 (6.79 GB) のほうが 3.6 倍大きい。**

## cumo の cuDNN 版 `conv` を第三のアームにした (2026-09-21)

別セッションの指摘で気づいた。**`ext/cumo/narray/gen/tmpl/conv.c` が `cudnnConvolutionForward` をアルゴリズム探索つきで呼ぶ。**`conv_transpose.c` と `conv_grad_w.c` もある。

**cuDNN はチャネル先を要求する** ので、綴りがモデル全体の並びを決める形にした (`Conv2d::LAYOUTS`)。`shift` と `unfold` はチャネル最後、`cudnn` はチャネル先で、**`cudnn` のアームは入口の転置を 1 度も払わない** (torch と同じ並びで入力が届くため)。BatchNorm の scale と shift、max pooling、global average pooling も両方の並びを受ける。**Numo に `conv` は無いので、その綴りは `Error` で断る。**

**4 通りとも 16 枚のクラス番号が参照と完全一致する** (2 綴り x 畳む / 畳まない、および `cudnn` の畳む / 畳まない)。

## 3 実装を並べる (2026-09-21、測り直し)

**最初に測ったときは Python 側だけ、計測区間の中で毎回 CPU から GPU へ転送していた。** Ruby は読み込み時にデバイスへ載せた配列を使い回すので、**測っていた範囲が違った** (cupy 0.659 ms、torch 0.339 ms、1 pass の 4.0% と 5.8%)。`prepare` を計測区間の外に出して測り直した。**Python を不利にする向きだったので、直して差は広がった。**

5 条件をインターリーブ、順序を回転、**11 ラウンドの先頭を位置で捨てて 10 ラウンド** (条件数の倍数)。1 条件が約 2 秒。クロック固定 (アイドル SM 2805 MHz)、`load average` を確認してから開始。

| 条件 | 枚/sec | 幅 |
|---|---|---|
| Cumo `shift` | 625.0 | 0.9% |
| Cumo `unfold` | 922.1 | 0.6% |
| CuPy `shift` | 430.2 | 0.7% |
| **CuPy `unfold`** | **993.8** | 0.5% |
| 対照 (Cumo `unfold`) | 923.0 | 0.6% |

| | ペア比 | 1 をまたぐ |
|---|---|---|
| 対照 / Cumo `unfold` | 1.0004 (0.9961〜1.0053) | **またぐ** |
| Cumo `unfold` / `shift` | **1.4777 (1.4674〜1.4832)** 10/10 | またがない |
| **CuPy `unfold` / `shift`** | **2.3085 (2.3020〜2.3147)** 10/10 | またがない |

**綴りの効きは実装で違う。** Cumo では 1.48 倍、**CuPy では 2.31 倍** である。**どちらの実装でも `unfold` が勝つが、勝ち幅が 1.6 倍違う。**

### 綴りを変えると Cumo と CuPy の勝ち負けが入れ替わる

| | ペア比 | |
|---|---|---|
| **Cumo / CuPy (`shift`)** | **1.4523 (1.4500〜1.4558)** 10/10 | **Cumo が 45% 速い** |

**当初ここには「GEMM が 20 本で両者同数なので、差は窓行列の組み立ての側にある」と書いていた。取り下げた。** **本数が同じでも実行時間が同じとは限らない。** 行き先は **未分離** である。`shift` で Cumo が勝つ理由も同じく測っていない (計測の作法 18)。

### 7.3% の行き先は分かった (cumo 0.10.0、2026-09-23)

**取り下げた帰属と結論は同じになったが、今度は部品を直接測った。**

**まず「GPU が空いている」側ではない。** nsys の差分法で本数は 3 組とも完全に一致し (Cumo 330、CuPy 316)、**GEMM は同じカーネルが同じ本数** である。計測区間の 12 パスで GPU が埋まっている割合を出すと、**Cumo が 99.1〜99.2%、CuPy が 98.2〜98.3%** で、**空いているのは CuPy のほうだった。** 差はカーネルの実行時間にある。

**畳み込みを部品に分けて、それぞれ 2 秒以上回した** (scratchpad の `parts.rb` / `parts.py`、1 パスぶんの 20 本を順に)。5 条件をインターリーブ、**11 ラウンドの先頭を位置で捨てて 10**、クロック固定。

| 部品 (ms/pass) | Cumo | CuPy | 差 | Cumo / CuPy | 両側 p | 対照の範囲 |
|---|---|---|---|---|---|---|

**GEMM は区別できない。** パディングの差は Cumo が `XF.zeros` で **パディング後の配列全体を 0 で埋めてから** 内側を書くことに出ていて、nsys では 1 パスに `fill` が 18 本 (0.247 ms) ある。CuPy は 4 本 (0.008 ms)。**これはこちらのコードの書き方である。**

### 窓の組み立ては 3x3 の層で一様に遅い。stem ではない

**測る前は「チャネル 3 の stem で細い書き込みが 49 本並ぶところ」を疑っていた。外れた。** 層ごとに組み立てだけを測った (10 ラウンド)。

| 層 | Cumo | CuPy | Cumo / CuPy |
|---|---|---|---|
| stem 7x7、3ch、112x112 | 4.043 ms | 3.737 ms | 1.046 (2/10) |
| **3x3、64ch、56x56** (4 層) | **0.505〜0.511** | **0.404〜0.412** | **1.23〜1.26** (0/10) |
| **3x3、128ch、28x28** (3 層) | **0.248〜0.252** | **0.199〜0.204** | **1.23〜1.24** (0/10) |
| 3x3、256ch、14x14 (3 層) | 0.126〜0.129 | 0.102〜0.104 | 1.24〜1.25 (0/10) |
| 3x3、512ch、7x7 (3 層) | 0.058 | 0.049 | 1.18〜1.20 (0/10) |
| 1x1 と小さい 3x3 (3 層) | 0.003〜0.032 | 0.006〜0.048 | **0.51〜0.86** (10/10、起動が支配) |

**3x3 の 16 層すべてで Cumo が 1.18〜1.26 倍遅い。** 書くのは 1 タップあたり連続した `in` 個 (256〜2048 バイト) で、**読みは空間方向にストライドのあるビュー** である。Cumo は `cumo_iter_sfloat_store_sfloat_kernel_dim4`、CuPy は `cupy_copy__float32_float32` を使う。**stem は 1 タップ 12 バイトしか書かないので、両方とも遅く、差が出ない。**

**当初ここには「CuPy は帯域の天井 600 GB/s の 95%、Cumo は 75%」と書いていた。取り下げた。** 読む側の `src` は 13.8 MB で **L2 に載る** ので、バイト数を時間で割った値はキャッシュ込みであり、**DRAM の天井に対する割合としては読めない** (別セッションの指摘)。**言えるのは比までである。** 分母を確かめずに割合を書いた (計測の作法 24)。

**別セッションが同じ形を 4 通りに分けた** (cumo 0.10.0)。**両側がストライドの形だけが遅い。**

| 形 (1 タップ) | 時間 |
|---|---|
| **ストライドの `src` → ストライドの `win` の列スライス** (この組み立て) | **0.0494 ms** |
| ストライドの `src` → 連続の書き先 | 0.0368 ms |
| 連続の `src` → `win` の列スライス | 0.0260 ms |
| 連続 → 連続 (同じバイト数) | 0.0187 ms |

**cumo の `CUMO_NA_INDEXER_DECOMPOSE` は既に 32 bit で割っている** (配列が 32 bit に収まるとき)。#504 で直した 64 bit 除算の形ではなく、**CuPy の copy も CIndexer で同じ分解をする** ので、除算の有無では説明しきれない。**原因は測っていない** (計測の作法 18)。**再現は `win[:, :, :, a:a+64] = src[:, i:i+56, j:j+56, :]` の形** (`src` が `[16, 58, 58, 64]`、`win` が `[16, 56, 56, 576]`) で、cumo 側に渡した。

### パディングは縁だけ埋めるようにした (2026-09-23)

**`Ops.pad_with` を、全面を埋めてから内側を書く形から、縁の 4 本だけ `fill` する形にした。** `Conv2d#pad` もこれを呼ぶ。**新旧は両バックエンド・両レイアウトでビット一致** し、テストと 4 綴りのクラス番号も変わらない。

**最初の書き方は本数を増やした。** 縁に `= value` で代入すると **スカラーを一時配列にしてから store するので 1 回 2 本** になり、1 パスが 330 本から **456 本** に増えた。**ビューに `fill` を掛けると 1 本で済み、384 本 (= 330 − 18 + 72)** に収まる。

| nsys (1 パス) | 旧 | 新 |
|---|---|---|
| 全面の `fill` | 18 本 / 0.314 ms | 0 |
| 縁の `fill` | 0 | 72 本 / 0.089 ms |

旧版を scratchpad のパッチで戻したアームと並べた (5 条件インターリーブ、10 ラウンド、クロック固定)。

| | 新 / 旧 | 1 をまたぐ | 両側 p |
|---|---|---|---|
| **`unfold`** | **1.0072 (1.0055〜1.0117)** 0/10 | またがない | 0.002 |
| **`shift`** | **1.0068** 10/10 | またがない | 0.002 |

### 上限を上げるとアルゴリズムが入れ替わる。そして TF32 に載る

**このアームが要因を実際に動かしたかどうかは、カーネル名で確かめられる。** 差分法で数えた (1 pass = 16 枚)。

| | 既定 8 MiB | 1 GiB |
|---|---|---|
| `implicit_convolve_sgemm` | **19** | 3 |
| `winograd_nonfused` (data / filter / output) | 0 | **6 / 6 / 6** |
| `fft2d_r2c_32x32` / `fft2d_c2r_32x32` | 0 | **20 / 16** |
| `nchwToNhwcKernel` / `nhwcToNchwKernel` | 0 | 13 / 6 |
| **`cutlass_tensorop_s1688fprop_optimized_tf32`** | **0** | **7** |
| 合計 | **99** | **183** |

**アルゴリズムは完全に入れ替わっている。** 8 MiB では 20 本の畳み込みがほぼ implicit GEMM に行き、1 GiB では **Winograd と FFT** が入る。**カーネル数は 1.85 倍に増えるのに 1.62 倍速い。**

**そして 7 本がテンソルコアの TF32 カーネルに行く。**`ext/cumo/narray/gen/def/sfloat.rb:37` が `cudnn_math_type: "CUDNN_DEFAULT_MATH"` を設定していて、**cumo の fp32 経路はテンソルコアを禁じていない。** **8 MiB では探索がそこまで届かないので、結果として fp32 で走っていただけ** である。

**数値に出る。**

| | logits の `max\|d\|` | クラス番号 |
|---|---|---|
| 既定 8 MiB | 1.621e-05 | 16/16 |
| **1 GiB** | **3.752e-03** | 16/16 |

**関門は通るが、桁が 2 つ動く。** TF32 の仮数 10 ビットと整合する。

**したがって 1.62 倍は「同じ計算をより良いアルゴリズムで」ではない。** **より良いアルゴリズムと、一部の層での精度の低下が混ざっている。** **どちらがどれだけかは分けられていない** — 分けるには `CUDNN_FMA_MATH` に落とす必要があり、外からは振れない。

**そして「torch fp32 / Cumo 1 GiB = 1.1410」は取り下げる。** torch 側は `allow_tf32 = False` にしてあるのに、**cumo 側は TF32 を許している。** 精度を揃えた比較になっていない。**方針を揃えるなら torch の既定 (TF32 有効) と比べる側で、そちらは 1.3969 である。**

**上限と精度が 1 つのつまみに束ねられている** のが、この驚きの出どころである。**畳み込みを測るときは、上限だけでなく「どのカーネルが選ばれたか」まで見ること。**

### 速さの 89% は、精度を落とさずに取れる

## 幅が広かったのは、探索が 2 通りの答えを返していたから

**「1 GiB のアームだけ幅が 3.5%」を観測として置いてあった** (上記)。HEAD で TF32 を切ったアームに同じ形が出たので追った。**入口は logits が 2 値を行き来することだった。**

nsys でカーネル名を数えると、**2 値が 2 通りのアルゴリズム選択に対応している** (1 forward、`--spelling cudnn`)。

| logits の `max\|d\|` | `winograd_nonfused` (data / filter / output) | `fft2d_r2c` / `fft2d_c2r` |
|---|---|---|
| 2.956e-05 | 13 / 13 / 13 | 114 / 106 |
| **3.266e-05** | **17 / 17 / 17** | 94 / 90 |

**4 本ぶん多く Winograd に行き、そのぶん FFT が減る。**`implicit_convolve_sgemm` 38 本と `precomputed_convolve_sgemm` 1 本はどちらの組でも同じだった。

**同じプロセスの中で logits と速度を両方取った。** forward 1 回で logits を出し、そのまま 230 パス x best-of-3 を回す。

| 引いた組 | 枚/sec | 本数 |
|---|---|---|
| 13 / 13 / 13 (2.956e-05) | **1867.9〜1888.2** | 15 |
| **17 / 17 / 17 (3.266e-05)** | **1916.9〜1927.2** | 5 |

**帯が重ならない。** しかも **256 MiB の 6 本のうち 1 本だけが 13 側を引いて、その 1 本が 1876.4** だった。**同じ条件・同じブロックの中で、引いた組が速度を決めている。**

**上限は速度を直接は決めず、どちらの組を引きやすいかを変えているように見える。** 128 MiB では 26 本中 23 本が 13 側、256 MiB では 10 本中 9 本が 17 側だった。**これは観測で、なぜそうなるかは測っていない** (計測の作法 18)。

**「256 MiB / HEAD 既定 = 1.0243 がまたぐ」の中身もこれである。** 両方のアームが 2 群の混合で、混合比だけが違う。**幅を「ノイズ」として丸めると見えなくなる** ので、**2 群の混合として読むこと。**

**判別は外から無料でできる。** cumo は `perf_result.algo` を出さないが、**選ばれた組が logits に出る**。

## Python 移植

`python/resnet.py` (numpy / cupy、Ruby の構造の写し。**同じ 2 綴り、同じチャネル最後**) と `python/resnet_torch.py` (**エコシステムの天井**。`F.conv2d` を直に呼び cuDNN に任せる)。`python/bench_resnet.py` が 1 プロセス 1 条件で回す。

**CuPy 14.2 は cuDNN の畳み込みを公開していない** ので、**CuPy 側に `cudnn` の綴りは無い。** この側で cuDNN を代表するのは torch である。

**3 実装とも、計測に入る前に 16 枚のクラス番号を fixture と照合する。**
