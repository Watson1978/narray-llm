# Whisper tiny の計測結果

[`openai/whisper-tiny`](https://huggingface.co/openai/whisper-tiny) を Numo::NArray / Cumo だけで実装したもの。進め方は [PLAN-whisper.md](../plans/PLAN-whisper.md)。

**このモデルを選んだ理由は畳み込みである。** このリポジトリは 5 つのモデルを通して一度も畳み込みを書いていなかった。**汎用の配列演算だけで書くのに 2 つの道があり、どちらが速いかを測ること** が第四段階の中心である。

**答えは「窓を展開して 1 回の行列積にするほうが速い」だった。** ただし差は 1.65% で、消えるカーネルは 217 本中 10 本である。**同じ向きが CuPy でも出た** (1.41%、10/10)。**cumo に固有の話ではない。**

## 要約

README の「数字」に書いていた要約をここに移した (2026-09-23)。**表は [README](../../README.md#数字) にある。**

**このリポジトリが初めて畳み込みを書いたモデル。** 音声 30 秒を 80 メル x 3000 フレームにして、encoder 4 層 + decoder 4 層で書き起こす。**C の単一ファイル参照が無いので、Switch と同じく参照は transformers。**

| | 本/回 | 中央値 |
|---|---|---|
| **メル** (3000 フレーム) | **24** | 0.26 ms |
| **encode** (1500 位置) | **217** | 6.6 ms |
| **decode** (1 トークン) | **341** | 1.35 ms |

**同じモデルの中に 2 つの帯がある。** encoder は 1500 位置を 217 回の起動で処理する (行列積が支配)。decoder は 1 位置に 341 回使う (起動が支配)。

**畳み込みは 2 つの書き方で書いた。** カーネル位置ごとに行列積を 3 本作って足すか、窓を展開して 1 本にするか。**掛け算の総数は同じで、違うのは起動の回数。** **窓を展開するほうが 1.65% 速い** (10/10、対照はまたぐ)。**同じ向きが CuPy でも出たので** (1.41%、10/10)、**cumo に固有の話ではない** (PyTorch はペア比が 1 をまたぎ、この幅では決まらない)。

**3 実装を並べると、同じモデルの中で勝ち負けが入れ替わる。** decode (341 本/位置、投入が支配) は Cumo が PyTorch より 5.8% 速く CuPy の 3.27 倍、encode (217 本/1500 位置、行列積が支配) は PyTorch が Cumo より 15.1% 速い。**ただし encode でも Cumo は CuPy に 27.3% 勝っている。** メルはほぼ互角。

**encode の 15.3% は本数の話ではない。** 3 実装のカーネルを数えたら、**GEMM は 1 encode あたり 78 本で 3 実装とも一致した** (合計は Cumo 217 / CuPy 408 / PyTorch 177)。**Cumo と PyTorch は cutlass のタイルと grid まで同じ** なので、PyTorch は融合していない。**GPU 時間も 3 組取ったが、GEMM の時間はペア比が 1 をまたいで区別できなかった** (Cumo 自身が 3 組で 21% 動く)。**15.3% の帰属は未分離。**

**メルは FFT を使っていない。** Numo にも Cumo にも変換が無いので、**DFT を余弦と正弦の実数表との行列積 2 本** で書いた。参照との差 1.6e-03 は打ち消し合う帯に集中していて、**fp32 の DFT の精度が支配していることは fp64 で踏み直して確かめた**。

**メルの前段だけは `XF` によらず fp32 で回す。** DFT の位相表が添字の積 `n_fft * bins` = 79800 を通るので、**fp16 では Infinity になって `cos` が NaN になり、bf16 では 79872 に丸まって余弦の符号が反転する**。出口で一度だけ変換する形にしてあり、**`XF` が fp32 のときは変換を挟まない**。

## 畳み込みの 2 つの書き方

| | やること | 本/encode |
|---|---|---|
| **`shift`** | カーネル位置ごとに `[frames, in] x [in, out]` を作って足し込む。**行列積 3 回 + 加算 2 回** | **217** |
| **`unfold`** | `[frames, in * 3]` の窓行列を作ってから **1 回の行列積**。**コピー 3 回 + 行列積 1 回** | **207** |

**掛け算の総数は同じである。**`[3000, 240] x [240, 384]` を 1 本やるのと `[3000, 80] x [80, 384]` を 3 本やるのは、同じ積の数になる。**違うのは起動の回数と、間に置く配列である。**

| | 値 |
|---|---|
| `unfold` / `shift` | **1.0165 (1.0138〜1.0202)** |
| またぐ | **いいえ 10/10** |
| 対照 (`unfold` をもう一度) | 0.9987 (0.9958〜1.0024) **またぐ** |

**幅が 0.5〜0.8% しかない。** 1 回の encode は 6.6 ms で、**計測の作法 7 が言う「1 秒未満は 3〜11% ぶれる」帯にいる**。そこで **区間の中で 300 回繰り返して 1.9 秒にした**。幅はその通りに縮んだ。

**本数の割合 4.6% に対して効きが 1.65% で、換算率は 0.36 である。** Mamba の 7 点では 0.4〜0.9 だった。**低いのは、encoder が投入律速ではないからだと思われるが、測っていない。**

## `unfold` が速いのはバックエンドの性質ではない

**「窓を展開するほうが速い」が cumo に固有の話かどうかを分ける** ため、同じ 2 つの書き方を CuPy と PyTorch の移植でも測った。encode の条件で、`shift` / `unfold` / 対照 (`unfold` をもう一度) を 1 ラウンド内でインターリーブし、11 ラウンドの先頭 1 本を位置で捨てて 10 ラウンドで読む。

| 実装 | `unfold` / `shift` | またぐ | 対照 |
|---|---|---|---|
| **Cumo** | **1.0165 (1.0138〜1.0202)** | いいえ **10/10** | 0.9987 (0.9958〜1.0024) **またぐ** |
| **CuPy** | **1.0141 (1.0053〜1.0247)** | いいえ **10/10** | 0.9991 (0.9888〜1.0125) **またぐ** |
| **PyTorch** | 1.0078 (0.9946〜1.0332) | **またぐ** 8/10 | 1.0007 (0.9825〜1.0224) **またぐ** |

**3 実装中 2 実装で、同じ向きに同じくらい出た。** Cumo が 1.65%、CuPy が 1.41%。**cumo に固有の性質ではない** と言える。

**PyTorch では決められない。** 向きは 8/10 で揃っているが、**ペア比が 1 をまたぐ**。同じラウンドの対照が 0.9825〜1.0224 と 4% 開いていて、**効き幅 0.8% より対照の幅のほうが大きい**。区間の長さは 3 実装でほぼ同じ (1.7〜1.9 秒) なのに **幅だけが実装ごとに違う** ので、PyTorch でこの差を決めたければ幅を詰めるところからになる。**「差が無い」ではなく「この幅では決まらない」である。**

## 本数と時間

tokens/sec などはプロセスごとに best-of-3、10 プロセスの中央値。クロックは `-lgc 3090` / `-lmc 14001` で固定 (アイドル SM 2805 MHz)。GPU は RTX 5070 Ti Laptop。cumo は master ビルド。**畳み込みは `shift`。**

| | 本/回 | 中央値 | 幅 |
|---|---|---|---|
| **メル** (3000 フレーム) | **24** | 11,534,199 frames/sec (0.26 ms) | 6.2% |
| **encode** (1500 位置) | **217** | 227,603 positions/sec (6.6 ms) | 0.7% |
| **decode** (1 トークン) | **341** | 740.75 tokens/sec (1.35 ms) | 3.8% |

**encoder と decoder で像がまったく違う。**

- **encoder は 1500 位置を 217 回の起動で処理する。** 1 起動あたり 1500 行の仕事があり、**行列積が支配する帯** にいる
- **decoder は 1 位置に 341 回の起動を使う。** 1 起動あたり 1 行しかなく、**起動が支配する帯** にいる

**同じモデルの中に両方の帯がある。** Switch で encode 2048 と decode 72 が別の像を見せたのと同じ形だが、**こちらは前段と後段で分かれている** ぶん分かりやすい。

**30 秒の音声を 200 トークン書き起こすなら、メル 0.26 ms + encode 6.6 ms + decode 270 ms である。** 時間のほぼ全部が decode に行く。

## 3 実装を並べる

Cumo / CuPy / PyTorch と対照 (Cumo をもう一度) の 4 系列を 1 ラウンド内でインターリーブし、系列の順序をラウンドごとに回転。11 ラウンド回して **先頭 1 ラウンドは位置で捨て**、残る 10 ラウンドで読む。クロックは `-lgc 3090` / `-lmc 14001` で固定 (アイドル SM 2805 MHz、計測後のメモリ 14001 MHz)。**Python の 2 つは transformers ではなくこちらの移植である** (`python/whisper.py` と `python/whisper_torch.py`)。transformers を使うと「レシピの比較」になるので、他の表と同じくアルゴリズムを固定した。**3 実装とも fixture のトークン列を通ってから計測に入る。** 畳み込みは 3 つとも `shift` で揃えた。

**1 回が短い条件は区間の中で繰り返した** (メル 2000 回、encode 300 回、decode は 200 トークンを 3 回)。

| 条件 | Cumo | CuPy | PyTorch | Cumo / CuPy | PyTorch / Cumo | 対照 |
|---|---|---|---|---|---|---|
| **メル** (3000 フレーム) | 11,366,046 frames/sec | 11,172,115 | **12,001,963** | 1.017 (0.960〜1.058) **またぐ** | 1.060 (1.007〜1.106) 10/10 | 0.982 (0.963〜1.033) **またぐ** |
| **encode** (1500 位置) | 227,379 positions/sec | 178,470 | **262,393** | **1.276 (1.265〜1.281)** 10/10 | **1.153 (1.150〜1.163)** 10/10 | 1.001 (0.998〜1.004) **またぐ** |
| **decode** (1 トークン) | **739.98 tokens/sec** | 231.73 | 703.34 | **3.187 (3.123〜3.247)** 10/10 | **0.949 (0.927〜0.969)** 0/10 | 1.000 (0.984〜1.026) **またぐ** |

**3 条件で 3 通りの像が出た。**

- **decode では Cumo が勝つ。** PyTorch より **5.4% 速く**、CuPy の **3.19 倍**。1 位置あたり 341 本の起動で、**投入が支配する帯** にいる
- **encode では PyTorch が勝つ。** Cumo より **15.3% 速い**。ただし **Cumo も CuPy に 27.6% 勝っている** ので、「Python 側が速い」ではなく **PyTorch だけが速い**。**PyTorch 側も畳み込みを `F.conv1d` ではなく行列積で書いてある** ので、cuDNN は関係しない。3 実装とも同じ形の GEMM を cuBLAS に渡していることになる。**差がどこから来るかは分けていない。**
- **メルはほぼ互角。** Cumo / CuPy は 1 をまたぐ。PyTorch / Cumo は 1.060 で 10/10 だが、**同じ条件の対照が 0.963〜1.033 と 7% 開いている**。区間が 1 回 0.52 秒しかなく、作法 7 の「1 秒未満は 3〜11% ぶれる」帯である。**向きは 10/10 揃ったが、この幅を見てから読むこと**

**同じモデルの中で勝ち負けが入れ替わる。** encode で 15% 負けて decode で 5% 勝つ。**どちらか一方だけを測って「Cumo は速い / 遅い」と言えない** ことが、この表のいちばんの中身である。

**Switch の decode も Cumo が PyTorch を上回っていた** (1.029 倍、CuPy の 2.99 倍)。**別セッションの数字なので幅を突き合わせてはいけない** (計測の作法 10)。**読めるのは向きが揃ったことだけである。**

## 3 実装のカーネル数 (encode 1 回あたり)

nsys の差分法 (`--inner 20` と `--inner 10` の差 ÷ 30 encode)。**回数は温まり具合に影響されない** (計測の作法 8)。

| 実装 | GEMM | GEMM 以外 | 合計 |
|---|---|---|---|
| **Cumo** | **78** | 139 | **217** |
| **CuPy** | **78** | 330 | 408 |
| **PyTorch** | **78** | **99** | **177** |

**GEMM は 3 実装とも 78 本で一致する。** **PyTorch は融合していない。** Cumo と PyTorch は **cutlass のタイルと grid まで同一** で、CuPy だけ 30 本のうち 3 本が `nt` の向きになる。

**Cumo の 217 本は、上の「本数と時間」で別に測ってあった値と一致する。** 差分法の分母が正しいことの内部検査になる (3 実装とも整数で出たことも同じ)。

**差が見えるのは GEMM 以外のほうである** (Cumo 139 対 PyTorch 99、1 encode あたり 40 本)。

**同じ profile から GPU 時間も差分で出し、3 組取った。** **GEMM の時間は区別できない** (Cumo/PyTorch のペア比 0.997〜1.220 で 1 をまたぐ。Cumo 自身の GEMM 時間が 3 組で 21% 動く)。**GEMM 以外は 3 組とも重ならない** (1.348〜2.027)。**1 組目だけを見ると「GEMM が 21% 遅い」と読めたが、3 組目では同じ値になった。** 内訳は [../cumo-issues.md](../cumo-issues.md)。

**それでも 15.3% をここに帰属させない。** nsys の duration は wall の仕事とは限らず、**その演算を消して wall が動くまで行の時間は信じない** (計測の作法 9)。**時間の帰属は未分離である。**

## メモリ使用量

**3 回ずつ取った。** GPU 側は 3 回とも 1 MiB も動かず、ホスト側も 1〜2 MiB に収まったので、幅は書かない。**ここは 10 ラウンド要らない。**

### 外から見た使用量 (`nvidia-smi --query-compute-apps`、実行中の最大)

| 実装 | GPU MiB | ホスト RSS MiB |
|---|---|---|
| **Cumo** | **222** | 914 |
| CuPy | 536 | 853 |
| PyTorch | 510 | **1152** |

**この 3 つを並べて読んではいけない。** **cumo は `cudaMallocManaged` で確保する** (`ext/cumo/cuda/memory_pool.cpp:73`)。managed メモリはページがホストにも居られるので、**`nvidia-smi` はデバイスに常駐しているぶんしか数えない**。実際、同じ走行で cumo のプールは 418.8 MiB あるのに、外からは 222 MiB に見えた。**外から見た数字は「カードが実際に失う量」であって、「確保した量」ではない。**

### 中から見た使用量 (アロケータ、200 トークン生成したあと)

| 実装 | 重み | 生成後に使用中 | プール確保済み |
|---|---|---|---|
| **Cumo** | **218.9** | **225.5** | 418.8 (`free_all_blocks` 後 282.8) |
| CuPy | 222.7 | 223.7 | 316.0 |
| PyTorch | 223.2 | 256.1 (peak 286.9) | reserved 308.0 |

**テンソルの実量は 3 実装でほぼ同じである** (重み 218.9〜223.2 MiB)。同じアルゴリズムで同じ重みを持つので当然だが、**外から見た 222 対 536 対 510 とは像がまったく違う。**

**パラメータは 37,760,640 個 = 144.0 MiB なのに、重みが 220 MiB ある。** 差の 76 MiB は **埋め込みの転置** で、**3 実装とも埋め込みを 2 部持っている** (`[51865, 384]` が 76.0 MiB、分類器は結んであるが転置した写しを別に作る)。**このモデルは埋め込みがパラメータの 53% を占める** ので、ここが効く。

### 反復では増えない (リークの検査)

**上の表は「走行中のピーク」で、反復に対して増えないことの検査にはなっていない。** 別に測った。

**生成を 120 回繰り返しても、生きているテンソルは 1 バイトも増えない** (200 トークン x 120 回 = 24,000 トークン)。

| generate | used (GC 後) | total |
|---|---|---|
| 1 回目 | 225.5 MB | 423.3 MB |
| **10 回目** | 225.5 MB | **474.8 MB** |
| 20 / 40 / 60 / 80 / 100 / 120 回目 | 225.5 MB | 474.8 MB |

**プールの確保量だけ最初の 10 回で 423.3 → 474.8 MB に伸び、そこで止まる。** 120 回まで 1 バイトも動かない。**伸びているのはプールが新しい大きさのブロックを取る間だけで、リークではない。**

**Python の 2 つも同じ長さで確かめた。**`--repeat 1` と `--repeat 120` で、外から見た GPU が **CuPy 536 / PyTorch 510 MiB のまま** 動かない (ホスト RSS も 853〜857 / 1151〜1162 MiB で誤差)。**3 実装とも反復で増えない。**

### cumo の `used_bytes` は GC の前に読むと 76 MiB 多い

**`Cumo::CUDA::MemoryPool.used_bytes` は、参照が切れていても GC がまだ回収していないブロックを数える。** 読み込み直後は **294.9 MiB** と出て、`GC.start` のあとで **218.9 MiB** になった。**76 MiB は転置の元になった中間で、余分な写しではなかった。**

**最初これを「cumo だけ埋め込みをもう 1 部持っている」と読みかけた** (294.9 − 222.7 = 72.2 が埋め込みの 76 MiB に近い)。**算術は合っていたが、原因は違った。**`GC.start` を挟むだけで消える。**cumo のプールを測るなら、読む前に GC を回すこと。**

## メルは FFT を使っていない

**Numo にも Cumo にも複素数型はあるが、変換が無い。** DFT を **余弦と正弦の実数表との行列積 2 本** で書いた。1 フレームあたり 400 x 201 回の積で、FFT なら全体で 3500 回ほどのところだが、**30 秒ぶんで 0.48 GFLOP、24 本のカーネル、0.26 ms** にしかならない。

**参照との差は 1.6e-03 で、打ち消し合う帯に集中している** (参照が 0.5 以上の 20944 要素では 1.5e-05)。**fp32 の DFT の精度が支配していることは、同じ手順を fp64 で踏んで確かめた** — 1.593e-03 が 4.75e-05 になる。**残る 4.75e-05 は DFT と FFT の畳む順序の違いと最後の丸めで、分けていない。**

## メルの前段は fp32 で回す (2026-09-20 に直した)

**`DTYPE=fp16` / `DTYPE=bf16` を通すと、メルの位相表が壊れていた。** 別セッションのレビューで指摘され、こちらで再現した。

| | `rows * cols` の最大 | 余弦表の非有限 | 参照との max\|d\| |
|---|---|---|---|
| fp32 | 79800.0 | 0 / 80400 | 1.2e-04 |
| **fp16** | **Infinity** | **1415 / 80400** | **1.06** |
| **bf16** | 79872.0 | 0 / 80400 | **2.0** |

**DFT の位相表は添字の積 `n_fft * bins` = 79800 を通る。** fp16 の上限 65504 を超えるので `Infinity` になり、`cos` が NaN を返す。**bf16 は指数部が足りるので溢れないが、仮数部が 8 ビットしかないので添字が丸まる。** 79800 が 79872 になり、**余弦の符号が反転する** (値域 ±1 の関数で max|d| が 2.0)。`log10` の下限 `1e-10` も fp16 では 0 に落ちる。

**位相表だけ直しても足りない** ので、**前段全体を fp32 で計算して、最後に一度だけ `XF` へ変換する** (`Mel::PRECISION`)。`XF` が fp32 のときは変換を挟まないので、**fp32 の経路は 1 演算も変わらない** (CPU で max|d| 1.593e-03 のまま、カーネル 24 本のまま)。

| | 参照との max\|d\| (直したあと) |
|---|---|
| fp32 | 1.606e-03 |
| fp16 | 1.570e-03 |
| bf16 | **3.907e-03** |

**bf16 の 3.9e-03 は出口の変換そのものである。** bf16 の eps が 3.9e-03 で、log-mel の値域が ±1 なので **これ以上は縮まない**。テストの閾値 2.5e-03 を超えるので、**bf16 のメルは「走るが参照の閾値には入らない」**。

**fp16 と bf16 で生成も通るようになった。** 8 トークンで fp32 と同じ列 (2411 の繰り返し) が出る。**ただしこの入力の参照出力は同じ id が並ぶだけなので、関門としては弱い** (下記「正しさ」)。**fp16 / bf16 の速度は測っていない。**

## 正しさ

**トークン列が transformers と完全一致する。** 2 つの畳み込みの書き方の両方、両バックエンド。

**ただしこの入力の参照出力は同じ id が 32 個並ぶだけである。** 合成波形なので当然だが、**それだけを関門にすると、ほとんどどう間違えても通る**。そこで **固定した列に対する teacher forcing のロジットを位置ごとに突き合わせている** — 10 位置、51865 語彙で max|d| が 7.2e-05、argmax は 10 位置すべて一致。

**`--spelling shift` / `--spelling unfold` で畳み込みの書き方を選ぶ** (Ruby 側も Python 側も同じ綴り)。**`bench_whisper.py` は計測の前にトークン列を fixture と照合し、ずれていたら数字を出さずに失敗する。**

**インターリーブは外側のシェルで回す。** 1 プロセス 1 条件で、系列の順序をラウンドごとに回転させ、先頭 1 ラウンドを位置で捨てる (計測の作法 11 と 22)。

カーネル数は nsys の差分法で数える。**`--inner` を 2 つ取って差を (repeat x inner の差) で割る。**

```
GPU=1 nsys profile --trace=cuda --cpuctxsw=none --sample=none -f true -o enc20 \
  ruby script/whisper_generate.rb --encode-only --inner 20
GPU=1 nsys profile --trace=cuda --cpuctxsw=none --sample=none -f true -o enc10 \
  ruby script/whisper_generate.rb --encode-only --inner 10
nsys stats --force-export=true --report cuda_gpu_kern_sum --format csv enc20.nsys-rep
nsys stats --force-export=true --report cuda_gpu_trace    --format csv enc20.nsys-rep
```

`cuda_gpu_kern_sum` の列は 0 始まりで 1=Total Time、2=Instances、8=Name。**grid と block を見るなら `cuda_gpu_trace`** (3〜5 が GrdX/Y/Z、6〜8 が BlkX/Y/Z、20 が Name)。**時間を比べるなら 3 組取る** (計測の作法 9)。

## 測っていないこと

- **encode で PyTorch が 15% 出る理由。** GEMM の本数は 3 実装とも同じと分かった (上記) ので **そこではない** が、時間の帰属は分けていない
- **CuPy と PyTorch の同期の回数** (カーネル数は上記で数えた)
- **`gemmStridedBatched` を batch=1 で通す費用。** cumo は 2 次元 1 本の行列積もこの道を通る。素の `cublasSgemm` との差は測っていない ([../cumo-issues.md](../cumo-issues.md) に候補を 4 つ並べてある。**4 つとも未計測**)
- **`unfold` の換算率が 0.36 と低い理由。** encoder が投入律速でないためだと思われるが、測っていない
- **PyTorch で `unfold` が効くかどうか。** 向きは 8/10 で揃ったがペア比が 1 をまたぐ。対照の幅 4% が効き幅 0.8% より大きく、**この幅では決まらない**
- **実際の音声。** 波形は式で作ったもので、**「動くこと」は示せているが「書き起こせること」は示していない**
- **トークナイザ。** 生成はトークン id のままで、文字列にしていない
- **fp16 / bf16 の速度。** 走ることは確かめたが (上記)、計測はしていない
- **メルの DFT を FFT にしたらどうなるか**
