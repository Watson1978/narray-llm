# Llama 2 110M (stories110M) の計測結果

Ruby (Cumo) と Python (CuPy / PyTorch) で llama2.c の stories110M を走らせ、tokens/sec を比べたもの。目的は GPT-2 と同じで、**Ruby の NArray 実装が Python エコシステムにどこまで近いか** を測ることであり、速い実装を作ることではない。CuPy 側は速く書けるところをあえて Ruby と同じ形にしてある (`python/llama2.py` の docstring に該当箇所を明記)。

**共通の条件と手順は [method.md](../method.md)、機械の性質は [machine.md](../machine.md) にある。** GPT-2 の結果は [gpt2-124m.md](gpt2-124m.md)。

## 要約

README の「数字」に書いていた要約をここに移した (2026-09-23)。**表は [README](../../README.md#数字) にある。**

**KV キャッシュのある decode では、両モデルとも PyTorch eager を上回っている。** ペア比は GPT-2 が 0.977 と 0.913、Llama 2 が 0.773 と 0.775 で、**4 条件とも 1 をまたがず、10 ラウンド中 1 回も PyTorch が勝っていない**。

**キャッシュ無しはまだ 5〜12% 負けている。** 毎ステップ全系列を再計算する経路で、演算量が支配するためカーネルの投入を削っても頭打ちになる。**Llama 2 のキャッシュ無し 64 だけは追いついた** (0.976、10/10)。

**README の表の Llama 2 キャッシュ有りの 2 行は幅が 20% ある。** 生の系列が **585 前後と 725 前後の 2 群** に分かれ、中央値は高いほうの群にいる。**低い群は、プロセスの計測ループ全体がメモリクロック 9001 に張り付いた回だった** — GPU を 20 分温めてから 50 ms 間隔で見ると、該当する 2 本は窓の中の 56 サンプルがすべて 9001 だった。**単独では出ず、なぜ張り付くかは測っていない。** **さらに温めたあとは 700 前後から 725 前後へ 3.5% 上がる水準の変化があり、クロックも電力も温度も同じで、こちらは未分離** ([cumo-issues.md](../cumo-issues.md))。他の 16 条件の幅は 0.3〜5.5% で、対照の範囲も 0.97〜1.05 に収まっている。

## 前提: 3 実装とも llama2.c と完全一致する

**Ruby / CuPy / PyTorch のどれも、`run.c` を温度 0 で走らせた出力とバイト単位で一致する。** stories260K (200 トークン、`test_all.py` の公開文字列) と stories110M (64 トークン、vendor の `run.c` の出力) の両方で、キャッシュ有無・CPU/GPU の 4 通りとも確認した。ベンチのドライバは **計測の前に必ずトークン列を fixture と照合し、ずれていたら数字を出さずに失敗する** (`python/bench_llama2.py`)。

数値が合っているだけでは足りない。**ずれた実行は「遅い実行」ではなく別の計算** なので、tokens/sec を引用する意味が無くなる。

## 生成長は 64 と 200

GPT-2 の表は 64 と 256 だが、**stories110M は 243 トークン目で BOS を出して停止する** (llama2.c では BOS が系列の区切り、`run.c:763`)。256 を要求すると条件ごとの仕事量が揃わないので、その手前の 200 を使う。

## GPU: Cumo 対 CuPy 対 PyTorch

tokens/sec、**プロセスごとに best-of-3 の中央値、10 ラウンド**。**Cumo / CuPy / PyTorch / 対照 (Cumo をもう一度) の 4 系列 × 4 条件** を 1 ラウンド内でインターリーブし、系列の順序をラウンドごとに回転させて、計 160 プロセスを直列に走らせた。**クロックは `-lgc 3090` / `-lmc 14001` で固定してある** (段の実態は下記)。**Cumo の列は QKV と FFN の行列積を結合し、scores の積を 1 本の縮約に畳んだあとの値である** (下記の節)。cumo は master `49153d31` (#475)。**バッチの頭に捨てるラウンドを 1 本置いてある** (計測の作法 22)。

### KV キャッシュの効き目は 1 プロセス 1 条件でしか測れない

上の表から、キャッシュは Cumo で **64 トークン 1.39 倍、200 トークン 2.26 倍** (538.99 / 389.08、511.10 / 226.34)。長いほど差が開くのは GPT-2 と同じ形である。**融合を取り込んだ時点では 1.55 / 2.72 まで開いたが、埋め込みを gather にして無しの側が上がったぶん縮んだ** (最初は 1.37 / 2.19)。**キャッシュの効き目そのものではなく、無しの経路がどれだけ無駄をしていたかで動く数字である。**

**この数字を 1 プロセスの中で取ろうとすると逆の符号が出る。** 受け入れテストが当初そうしていて、stories260K を 128 トークン生成したときの比は次のようになった。

| stories260K、128 トークン、Cumo | キャッシュ無し | キャッシュ有り | 比 |
|---|---|---|---|
| **1 プロセス 1 条件** | 284.66 | **780.28** | **2.7 倍** |
| 1 プロセスに両方を詰める | 255.9 | **168.3** | **0.66 倍** |

**同じ操作が 4.6 倍違って出る。** キャッシュ有りの経路が `[t, t]` のマスクを作らず小さな配列ばかり確保するのに対し、無しの経路は大きな一時配列を確保するので、**2 つを交互に走らせるとメモリプールの状態が条件と相関する**。AGENTS.md の計測の作法 11 番がそのまま出た形である。

**受け入れテストは時間ではなく回数を検査する形に直した。** キャッシュ無しなら 8 トークンで 36 行 (1+2+...+8)、有りなら 8 行をブロックに通す、という決定的な量を数える。tokens/sec の主張はベンチ側 (`script/llama2_generate.rb` と上の表) が持つ。

## GPT-2 124M との差はどこから来るか

**層あたりの行列重みが完全に一致する。** これは偶然だが、比較にとっては都合がよい。

| | GPT-2 124M | Llama 2 110M |
|---|---|---|
| 層あたりの行列重み | `12C²` = 7,077,888 | `4D² + 3DH` = **7,077,888** |
| lm_head | 50257 x 768 = 154.4 MB | 32000 x 768 = **98.3 MB** |
| decode 1 トークンで読む重み | 494.6 MB | **438.1 MB** (0.886 倍) |
| decode 1 トークンの gemv | 48 + 1 = **49** | 84 + 1 = **85** (1.73 倍) |

`C` = 768、`D` = 768、`H` = 2048。**読む量が減るのは語彙の差だけで、層の中は 1 要素も違わない。**

**gemv が 1.73 倍に増えるのは、2 箇所で行列が割れるからである。** GPT-2 は QKV を `[C, 3C]` の 1 本に束ねているが Llama は `wq` / `wk` / `wv` に分かれていて (+2)、FFN が 2 本から SwiGLU の 3 本になる (+1)。**層あたり 4 本から 7 本** で、PLAN-llama2.md が「SwiGLU の gemv が 1 本増える」と見積もっていたのは過小だった。

**この 2 つは逆向きに効く。** 帯域律速なら Llama が 1.13 倍有利、投入律速なら GPT-2 が 1.73 倍有利になる。どちらが出るかは実装による。

### Cumo では投入側が勝つ

同一セッションで 2 モデルをインターリーブし、2 条件それぞれ 10 プロセスずつ測った (Cumo、クロック固定、生成長を揃えてある)。**この 4 つの値は融合カーネルを取り込む前のものである。** 上の表の現行値と突き合わせないこと。

| 条件 | GPT-2 中央 | Llama 2 中央 | ペア比 (GPT-2 / Llama 2) | 1 をまたぐ | GPT-2 が速い回 |
|---|---|---|---|---|---|
| 有り、64 | 456.88 | 394.26 | **1.166** (1.106〜1.191) | いいえ | **10/10** |
| 有り、200 | 440.88 | 377.70 | **1.165** (1.145〜1.191) | いいえ | **10/10** |

**GPT-2 のほうが 1.17 倍速い。** 読む重みが 11% 少ないことは、gemv が 1.73 倍に増えたことを埋め合わせない。**Cumo の decode は投入律速のままで、そこに Llama の形が不利に働く** ということである。GPT-2 側で「CPU が busy な時間が GPU を下回った」ところまで来ていた ([gpt2-124m.md](gpt2-124m.md)) が、**この差で釣り合いは再び投入側に戻る。**

## 1 トークンあたりのカーネル数 (nsys 実測)

`--length 72` と `--length 40` の差を 32 で割った。KV キャッシュ有り、cumo 0.8.0、同一セッション。**GPT-2 の 640 本は記録と 1 本も違わずに再現した。**

| | GPT-2 124M | Llama 2 110M | 差 |
|---|---|---|---|
| `store_sfloat_kernel_dim2` | 38 | **231** | **+193** |
| `mul_kernel_dim2` | 146 | 98 | −48 |
| `mul_kernel_dim3` | 0 | **96** | +96 |
| gemv | 49 | 85 | +36 |
| `add_kernel_dim2` | 121 | 60 | −61 |
| その他 | 286 | 321 | +35 |
| **合計** | **640** | **891** | **+251** |

**増分の主役は gemv ではなくコピーである。** gemv が 36 本増えるのに対し、`store_sfloat_kernel_dim2` が 193 本増えている。`mul_kernel_dim3` の 96 本は `12 層 × 2 回 (q と k) × 4 つの積` で、**RoPE の回転そのもの** の数と一致する。

### RoPE が 1 トークンあたり 360 本を占める

疑いを裏付けるために `Ops.rope` を恒等写像に差し替えて数え直した (**出力は当然壊れる。起動数と wall だけを見るためのアブレーションである**)。

| | カーネル/トークン | gemv |
|---|---|---|
| Llama 2 110M | 891 | 85 |
| 同、RoPE を消したもの | **531** | 85 |
| GPT-2 124M (参考) | 640 | 49 |

**RoPE 1 つで 360 本、Llama 2 の起動の 40% を占める。** 24 回の呼び出し (12 層 × q と k) で 360 本なので、**1 回あたり 15 本** になる。

### その 15 本のうち 6 本は `reshape` である

**`reshape` は連続配列でもコピーする。** ビューではない。`Cumo::CUDA::MemoryPool.used_bytes` で数えると、`[40, 768]` の配列に対して次のようになる (GC 無効、ウォームアップ後、1 回ずつ)。

| | 確保 |
|---|---|
| `reshape` 1 回 | **122,880 B** (配列と同じ大きさ) |
| 要素演算 1 回 (対照) | 122,880 B |
| `dup` 1 回 (対照) | 122,880 B |
| **`reshape!` 1 回** | **0 B** |

**これは Cumo の欠陥ではなく NArray の仕様である。** Numo も同じで、`reshape` の結果を書き換えても元の配列は変わらない (スライスのほうはビューである)。cumo 側の `cumo_na_reshape` (`data.c:509`) も `dup` してから形を差し替えるだけで、docstring に `Copy and change the shape of NArray. Returns a copied NArray.` と書いてある。**numpy の `reshape` が可能ならビューを返すのと違う** ので、そちらから来ると「形を変えるだけ」のつもりで配列 1 本ぶんのコピーとカーネル 1 本を払うことになる。

`Ops.rope` の内訳はこれで合う。

```
reshape x 6  +  積 x 4  +  和差 x 2  +  concatenate の store x 2  ≒ 15
```

**1 トークンあたり 144 本 (6 x 24) が「形を変えるだけ」に使われている。** 891 本の 16% にあたる。`reshape!` が 0 バイトなので置き換えの余地があるが、**受け手の形を破壊する** ので、`trace` が掴んでいる配列には使えない。所有権の整理が先になる。

**`store_sfloat_kernel_dim2` が 231 本ある理由もここにある** (GPT-2 は 38 本)。大半は非連続ビューのコピーではなく、連続配列に対する `reshape` である。

### `zeros` の fill も捨て札だった

`Ops.contiguous` は `zeros(*shape)` してから `store` で **全要素を上書き** していた。fill は捨て札なので `new(*shape)` に変えた。`fill_kernel_dim1` が 1 トークンあたり 87 → 24 本、キャッシュ無しの経路が 853 → 789 本になる。

**wall でも出る。**`contiguous` だけを差し替えて同一セッションで 10 ペアインターリーブした。

| 条件 | `zeros` | `new` | ペア比 | 最小〜最大 | 1 をまたぐ | 勝率 |
|---|---|---|---|---|---|---|
| Llama 2、無し、64 | 287.36 | **301.50** | **1.041** | 1.006〜1.073 | いいえ | **10/10** |
| Llama 2、無し、200 | 177.89 | **179.68** | **1.013** | 1.000〜1.024 | いいえ | **10/10** |
| Llama 2、**有り**、64 | 411.26 | 412.06 | 1.001 | 0.975〜1.029 | **はい** | 5/10 |
| GPT-2、無し、64 | 298.26 | 303.37 | 1.024 | 0.984〜1.071 | **はい** | 8/10 |

**キャッシュ有りが陰性対照になっている。** decode は `contiguous` をほとんど通らないので、そこで差が出ないことが、無しの条件で出た差の出どころを示している。

**cumo 側の単体計測では逆が出る。**`new` は確保すらせず (`Cumo::SFloat.new(2,2)` は `(empty)`)、確保は `store` の中の `allocate` に遅れて起きる。1 ケースを毎回新しく確保して測ると `zeros` より遅い (`4096x768` で 47.6 対 35.8 us)。**生成ループでは同じ形を繰り返すのでプールが温まっている、という説明はできるが、確かめていない。**

**順序が効いた例でもある。**`Ops.attention` を「非連続スライスを先に `contiguous` してから `reshape!`」に書き換えたとき、`contiguous` が 2 本 (fill + store) のうちは **差し引きゼロで「効かない」と出た**。`contiguous` を 1 本にして初めて GPT-2 のキャッシュ無しが 757.5 → 685.5 本になる。**片方だけ測って「効かない」と結論すると取りこぼす。**

### RoPE を書き直した: 891 -> 747 本、wall で 1.15〜1.18 倍

`Ops.rope` の `reshape` を `reshape!` に置き換えた。引数の 3 本 (`x` / `cos_t` / `sin_t`) は形をその場で変えてから `ensure` で戻す。**この関数はどれにも書き込まないので、呼び出し側からは見えない。** 残りは一時配列なので、そのまま `reshape!` にできる。

| | カーネル/トークン | うち `store_sfloat_kernel_dim2` |
|---|---|---|
| 書き直し前 | 891 | 231 |
| **書き直し後** | **747** | **87** |

**減ったのは 144 本ちょうどで、全部がコピーである。**「reshape 6 回 × 24 呼び出し」の予測と 1 本も違わない。gemv は 85 本のままで、GPT-2 側は `Ops.rope` を通らないので **640 本は動いていない**。

wall も動く (同一セッションで 10 ペアインターリーブ)。

| 条件 | 書き直し前 | 書き直し後 | ペア比 | 最小〜最大 | 1 をまたぐ | 勝率 |
|---|---|---|---|---|---|---|
| 有り、64 | 332.72 | **382.06** | **1.152** | 1.119〜1.188 | いいえ | **10/10** |
| 有り、200 | 323.32 | **375.44** | **1.181** | 1.129〜1.212 | いいえ | **10/10** |

**起動を 16% 削って wall が 15〜18% 動いた。** decode がまだ投入律速だということの、もう一つの証拠になっている。

**トークン列は変わらない。**`run.c` とのバイト一致も、参照活性との一致も、テスト 174 件がそのまま通る。

### decode_attention も同じ手で 36 本

`Ops.decode_attention` にも `reshape` が 4 箇所あり、うち 3 箇所は受け手が一時配列かキャッシュのビューなので `reshape!` にできる (残り 1 つは `weights.transpose` という非連続ビューで、**`reshape!` は非連続を明示的に拒否する** ので黙って壊れる心配は無い)。

**両モデルとも 36 本ちょうど (3 箇所 × 12 層)。** RoPE の 144 本が `store_sfloat_kernel_dim2` に出ていたのに対し、こちらは `dim1` である。連続配列どうしのコピーは 1 次元ループに畳まれるためと思われるが、**確かめていない。**

| 条件 | 前 | 後 | ペア比 | 最小〜最大 | 勝率 |
|---|---|---|---|---|---|
| GPT-2、64 | 450.89 | 477.08 | 1.048 | **0.989〜1.103** | 9/10 |
| GPT-2、200 | 438.55 | 461.56 | **1.052** | 1.035〜1.086 | **10/10** |

**上の 4 条件の表はこの書き換えの前に測ってある。** Cumo の列はこのぶん低い。

### `mulsum` は Llama 2 でだけ速くなったので、入れなかった

`Ops.decode_attention` の `(a * b).sum(axis:)` を `a.mulsum(b, axis:)` にすると、**Llama 2 は `有り、200` で 1.044〜1.068 倍 (10/10、1 をまたがない)** 速くなる。**しかし同じ変更で GPT-2 は 2 通りとも遅い側に出る** ので、採用しなかった。経緯と数字は [gpt2-124m.md](gpt2-124m.md) の該当節にある。

**この節は「入れなかったもの」の記録である。** Llama 2 側だけ見れば本物の利得なので、GPT-2 の負の理由が分かれば拾い直せる。

### 埋め込みを gather に変えた: キャッシュ無しで 1.11〜1.17 倍

`one_hot(ids) . token_embedding` を `token_embedding[ids, true]` に置き換えた。理由と切り分けは [gpt2-124m.md](gpt2-124m.md) の該当節にある (Ruby の Array を添字にすると同期しない)。

### 融合カーネルを取り込んだ: 1.314 倍

`Ops.rmsnorm` / `silu` / `softmax_rows` を cumo の融合カーネルに切り替えた (`rms_norm` は #458、`silu` は #460 で、どちらも **released 0.8.0 より後** である)。分岐と測り方は [gpt2-124m.md](gpt2-124m.md) の該当節にまとめてある。

| 条件 | 融合なし | 融合あり | ペア比 | 1 をまたぐ | 勝率 |
|---|---|---|---|---|---|
| 有り、64 | 410.30 | **540.06** | **1.314** (1.250〜1.347) | いいえ | **10/10** |
| **対照** (融合どうし) | 540.06 | 533.96 | 0.995 (0.944〜1.028) | **はい** | 3/10 |

**GPT-2 の 1.476 より小さい。** Llama 2 は融合できる 3 本のほかに **RoPE の 216 本** を抱えていて、そこは融合カーネルが無いので動かない。上の節のとおり RoPE を消すと 1.6 倍動くので、**残っている最大の塊はいまも RoPE である。** **この 216 本はその後 120 本になった** (下の「RoPE をヘッド全体の 1 式にする」)。この節の比はそれより前の測定である。

**これは実装側の余地であって、cumo の欠陥とは限らない。** 今の `Ops.rope` は 2 つの非連続ビュー、4 つの積、2 つの和差、`concatenate` での再合成という素直な書き方をしている。**融合するか、ストライド代入を使うか、cos/sin を [t, head_size] に広げて 1 回の積で済ませるか** といった余地がまだ残っている。どれが効くかは測っていない。

## 残差を GEMM に畳む

GPT-2 側で測った残差の畳み込み ([gpt2-124m.md](gpt2-124m.md)) を Llama 2 でも測った。**こちらはバイアスが無いので `x + attn.dot(wo_t)` の 2 本がまるごと 1 本になる。**

| | カーネル/token | `add_dim2` |
|---|---|---|
| 現行 | 486 | 48 |
| 残差を畳む | **463** | **24** |

**減りは 23 本で、24 本ではない。** 埋め込みのコピーが 1 本増えるためで、理由は次のとおりである。

### `decode_embed` が返すのは埋め込み表のビューである

`@token_embedding[token_id, true]` はコピーではなく **ビュー** なので、`x.inplace` を通すと **最初のブロックが重みそのものを書き潰す**。

**落ちない。** 生成は自然な文のまま進み、**9 トークン目で初めて分岐した**。表が少しずつ壊れていくので、壊れ方が出力に現れるまで間がある。**GPT-2 は安全である** (`decode_embed` が `@wte[id, true] + @wpe[pos, true]` の結果で、新しい配列になる)。

1 トークンに 1 回 `Ops.contiguous` を通せば直る。**層ごとではなく token ごとなので 1 本** で済む。

### 速度は判定できなかった

長さ 1000、プロセス内 best-of-5、クロック固定。**10 ラウンドで 1 をまたいだので 10 ラウンド足し、20 ラウンドを 1 つの集合として見た。**

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| Llama 2 | 0.993〜1.141 19/20 | **はい** | 1.031 |
| GPT-2 (参考) | 1.005〜1.022 10/10 | いいえ | 1.011 |

**1 ラウンドだけ 0.993 が出ており、それが判定を決めている。** 中央値は GPT-2 より大きいのに、判定は GPT-2 のほうが確かという形になった。**削る割合はむしろ小さい** (GPT-2 は 269 本中 24 本で 8.9%、Llama 2 は 486 本中 23 本で 4.7%) ので、中央値の大きさを効果の大きさとして読まないこと。

**トークン列は 201 個完全一致する** (埋め込みのコピーを入れた後)。

## RoPE をヘッド全体の 1 式にする

**RoPE は 1 トークン 486 本のうち 216 本を占めていた。** 内訳を数えると、24 回の呼び出し (1 層 2 回 x 12 層) が 1 回あたり 9 本を出していた。

| | 本数/token | 1 回あたり |
|---|---|---|
| 積 (`mul_dim3`) | 96 | 4 |
| 差 (`sub_dim2`) | 24 | 1 |
| 和 (`add_dim2` の一部) | 24 | 1 |
| `concatenate` の出力確保 (`fill_dim2`) | 24 | 1 |
| `concatenate` の書き込み (`store_dim2`) | 48 | 2 |
| **合計** | **216** | **9** |

### `concatenate` だけを外しても 24 本しか減らない

出力を先に確保してストライド代入に置き換えると **486 → 462** になる。**消えるのは `fill` の 24 本だけで、書き込みの 48 本は残る。** 2 つの半分をどこかに書く以上、その 2 本は避けられない。**当初「`concatenate` で 72 本が消える」と見積もっていたが、それは誤りだった。**

### ヘッド全体を 1 式で回すと 96 本減る

**cos を対ごとに 2 回並べ、sin に符号を持たせる** と、偶奇に分けずに書ける。

```ruby
(x * cos_t + x[true, true, true, [1, 0]] * sin_t).reshape!(t, num_heads * head_size)
```

`[1, 0]` は対の中の 2 要素を入れ替える。**Ruby の Array を添字にしているので同期しない** (AGENTS.md の gather の節。`CUMO_SHOW_WARNING=ON` で生成ループ中に出るのは貪欲法の `extract_cpu` だけだった)。テーブルは `rope_tables` が起動時に 1 回作るので、呼び出しごとの費用は増えない。

| | カーネル/token | RoPE 1 回あたり |
|---|---|---|
| 分けて `concatenate` | 486 | 9 |
| 出力を確保してストライド代入 | 462 | 8 |
| **ヘッド全体を 1 式** | **390** | **5** (入替 1、非連続のコピー 1、積 2、和 1) |

**生成トークン列は 201 個ビット完全一致** し、llama2.c とのバイト一致テストも Numo / Cumo の両方で通る。

### 速度は判定が付かなかった

長さ 1000 (1 回 1.8〜1.9 秒)、プロセス内 best-of-5、クロック固定。**10 ラウンドで 1 をまたいだので 10 足し、20 ラウンドを 1 つの集合として見た。**

```
r1-r10 : 1.062 1.057 0.991 1.007 1.053 1.048 1.084 1.066 1.095 1.039
r11-r20: 1.084 1.058 1.098 1.009 1.025 1.036 1.049 1.101 1.035 1.086
```

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| 20 ラウンド | 0.991〜1.101 19/20 | **はい** | 1.055 |
| 後半 10 ラウンドのみ | 1.009〜1.101 10/10 | いいえ | 1.058 |

**反対に出たのは r3 の 1 本だけで、1 を 0.9% 下回る値である。** プロセスごとの分布は `base` が 521.7〜556.1、`new` が 547.5〜585.9 でほとんど重ならない。**それでも判定規則ではまたぐので、この測定からは「5.5% 速くなった」とは書けない。**

**その後、段を記録するハーネスで測り直して判定が付いた** (`036bc8b` 以降。両アームとも `script/llama2_generate.rb --no-eot` を通し、差は `lib` だけにしてある)。

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| スクラッチのモンキーパッチ、20 ラウンド | 0.991〜1.101 19/20 | はい | 1.055 |
| **段の資格付き、10 ラウンド** | **1.016〜1.093 10/10** | **いいえ** | **1.039** |

**20 プロセスすべてが最上段だった** (窓あたり 8〜10 サンプル)。**落とすべきラウンドは出なかったので、資格付けが効いたのか外れが起きなかっただけなのかは、この 1 回では分からない。**

### 同じ形が 3 件続いている

**カーネル数が決定的に減り、トークン列も変わらないのに、wall の判定が付かない** という結果が、2026-09-18 の 1 セッションで 3 件出た。

| 変更 | カーネル/token | ペア比 (窓なし) | 判定 | ペア比 (段の資格付き) | 判定 |
|---|---|---|---|---|---|
| GPT-2 バイアスを C に | 269 → 222 | 0.848〜1.199 17/20 | またぐ | **1.013〜1.037 10/10** | **いいえ** |
| Llama 2 RoPE を 1 式に | 486 → 390 | 0.991〜1.101 19/20 | またぐ | **1.016〜1.093 10/10** | **いいえ** |
| Llama 2 残差を C に | 390 → 367 | 0.993〜1.141 19/20 | またぐ | 0.937〜1.017 4/10 | またぐ (下記) |

**窓なしの 3 件は、20 ラウンドのうち 1〜3 本の外れが判定を決めていた。** 外れる回は毎回違い (1 本目のこともあれば 3 本目のこともある)、方向も両側に出る。**測り直した 2 件では中央値がほとんど動いていない** (1.019 → 1.020、1.055 → 1.039) ので、**効果そのものは最初からあって、外れ値だけが判定を殺していた** と読める。

**ハーネスにはクロックの段を記録する口を入れた** (`036bc8b`、`CLOCKS=1`)。**ただし捕まえられるのは段だけである。** ブラウザや kwin のような描画クライアントが SM を奪っても段は最上段のままなので、**その競合は素通しする。**`nvidia-smi pmon` なら見えるが最小間隔が 1 秒で、1.8 秒の窓には 1〜2 サンプルしか入らない。**そこは限界として残っている。**


### 残差を C に置く案は入れなかった

GPT-2 では **バイアス** を C に置いたが ([gpt2-124m.md](gpt2-124m.md))、**Llama 2 にはバイアスが無いので C が空いている。** 残差 (`x = x + attn.dot(wo_t)`) をそこに置けば、GPT-2 のように排他にならない。**カーネルは確かに減る。**

| | カーネル/token |
|---|---|
| 現行 | 390 |
| 残差を C に | **367** |

内訳は残差の加算 24 本が消えて、埋め込みのコピーが 1 本増える。コピーが要るのは `decode_embed` が `@token_embedding[token_id, true]` という **埋め込み表のビュー** を返すためで、そのまま C に渡すと **重みを書き潰す** (上記)。**生成トークン列は 200 個一致した。**

**それでも wall は動かず、入れなかった。** 段を記録したハーネスで 10 ラウンド、20 プロセスすべて最上段。

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| 残差を C に | 0.937〜1.017 4/10 | **はい** | **0.993** |

**当初ここには「そして新しい側だけが二峰性になる」と書いていたが、取り下げた。**

```
new : 536 541 543 547 551 | 578 586 586 589 594
prev: 556 559 565 576 579 580 581 582 582 583
```

**この 2 行は昇順に並べ替えたもので、測った順ではない。生の時系列は残っていない。** そのうえで、**二峰性という読み自体を取り下げる。** 理由が 2 つある。

### 隙間を幅で割っていなかった

**絶対値の隙間 (27 対 11) を比べていたが、幅が 2.1 倍違うので比例しているだけだった。**

| | 幅 | 最大隙間 | **隙間 / 幅** |
|---|---|---|---|
| `new` | 58 (10.8%) | 27 | **47%** |
| `prev` | 27 (4.9%) | 11 | **41%** |

**47% と 41% はほぼ同じである。** 別セッションが単峰分布から 10 点取る試行を 20 万回まわしたところ、**最大隙間 / 幅の中央値が 30%、90% 点が 44%** だった (正規でも一様でもほぼ同じ)。**`new` は「弱い異常」止まり、`prev` は完全に並である。**

**10 点では足りない。** n=15 なら 90% 点が 35% まで落ちる。**点を 5 つ足すだけで判定力が変わる。**

### 予算が足りない (これが決定的)

**変えたのは `wo` の行列積だけで、その重みは `768 x 768 x 4 x 12 層` = 28.3 MB/token である。** このカードの帯域で読み切る時間はこうなる。

| 帯域の段 | 時間 | 1 トークン (1866 us) に対して |
|---|---|---|
| 413 GB/s (最低段) | 68.6 us | **3.67%** |
| 600 GB/s (最上段) | 47.2 us | **2.53%** |

**2 つの塊の差は 7.33% である** (低 543.6 / 高 586.6 tok/s、時間に直して)。**この gemm を丸ごと 0 にしても 2.5〜3.7% しか動かないので、7.33% の分離はここからは出ない。** どの段で読んでも足りない。

**単体でも出なかった。** 別セッションが同じ形 (`[1,768] x [768,768]` SFloat、12 層/token) を 15 プロセスずつ測ったところ、**どちらも単峰** で、幅の非対称も **こちらと逆向き** だった (new 5.2% / prev 10.7%)。**そのベンチは gemm 以外を外していて、gemm を 1 トークンの 2.5% から 100% に拡大している。** gemm 固有の二峰性があれば 40 倍に増幅されて出るはずだった。

### 何が残るか

**「入れなかった」という判断の理由が消えた。** 当初の理由は「分布の形が変わるのは別の話」だったが、**分布の形は変わっていなかった。**

残るのは次のとおりで、**入れるかどうかは決め直しになる。**

- **カーネルは確かに 390 → 367 に減る** (残差の加算 24 本が消えて、埋め込みのコピーが 1 本増える)
- **wall は判定が付かない** (ペア比 0.937〜1.017、4/10、またぐ)
- **トークン列は 200 個一致した**
- **埋め込み表を書き潰す危険がある** ので、`decode_embed` のビューをコピーする必要がある (上記)

**二峰性がなぜ見えたのかは未分離である。** 別セッションは自分の側で同じ形を出して **ウォームアップが固定回数だったため** と突き止めているが、**こちらの測定は段の資格付きで 20 プロセスすべて最上段** なので、同じ話がそのまま当たるとは言えない。**代わりの帰属は置かない** (計測の作法 24)。

**GPT-2 側の同じ手 (バイアスを C に) では二峰性は出ていない** (1.013〜1.037、幅 2.4%)。**こちらも「出ていない」ではなく「そもそも見えていたものが無かった」側に寄る。**

## QKV と FFN の行列積を結合する

**`wq` / `wk` / `wv` は同じ入力を取り、`w1` / `w3` も同じ入力を取る。** それぞれ 1 本の行列にまとめると、**層あたり 7 本の行列積が 4 本** になる。

| | カーネル/token | gemv |
|---|---|---|
| 現行 | 390 | 84 |
| 結合後 (キャッシュ有り) | **354** | **48** |
| 現行 (キャッシュ無し) | 466 | |
| 結合後 (キャッシュ無し) | **454** | |

**decode では追加のコピーが出ない。** 行が 1 本なので結果の列スライスが連続で、そのままビューとして使える。**キャッシュ無しは prefill が活性を 5 本コピーする** ぶん効きが小さくなるが (−12 本)、gemv を 36 本減らしたほうが上回る。

### 結合した重みだけを持つ

分割した重みをビューで残す案は取れない。**非連続の重みを `dot` に渡すと、重み行列まるごとのコピーが 1 本増える** (単体で 100 回呼んで、連続なら 106 本、ビューなら 206 本)。両方を実体で持つと stories110M で **236 MB 増える** ので、それも避けた。**結合した側だけを持ち、prefill が活性をコピーする。**

### 1 行の列スライスの扱いが Numo と Cumo で違う

**Cumo は `[1, N]` の列スライスを `reshape!` させるが、Numo は非連続として拒否する。**`Ops.rope` が入力を `reshape!` するので、ここで割れる。**決め打ちせず起動時に試して定数にしてある** (`Ops::RESHAPABLE_ROW_SLICE`)。通る側はビュー、通らない側はコピーになる。**Cumo で通ることを確かめて Numo も通ると決めつけ、受け入れテストを 5 件落とした** ので、その形で残してある。

### 速度

長さ 1000、`--no-eot`、プロセス内 best-of-5、段を記録して 20 ラウンド。

| | ペア比 | 1 をまたぐ | 中央値 |
|---|---|---|---|
| 全 20 ラウンド | 0.994〜1.291 19/20 | はい | 1.056 |
| **資格付き (18 ラウンド)** | **0.994〜1.090 17/18** | **はい** | **1.050** |

**中央値は今日いちばん大きいが、判定はまたぐ。** 反対に出たのは r6 の 0.994 の 1 本だけで、そのラウンドは両アームとも最上段だったので **段では説明できない。**

### 資格判定が外れ値を捕まえた

落とした 2 ラウンドは **r1 と r11、どちらも 10 ラウンドのバッチの 1 本目** で、**`prev` 側が窓の全域で低い段にあった** (最上段 0%、サンプル 11 個)。そのぶん `prev` が 465.1 と 470.4 まで落ち、ペア比が 1.289 と 1.291 に跳ねていた。

**「1 ラウンド目が冷える」という現象はこのセッションで何度も見ていたが、原因が数字で確認できたのはこれが初めてである。** バッチの頭にウォームアップのラウンドを 1 本置けば消せる性質のもので、**計測の作法 4 (ウォームアップ) をプロセス単位だけでなくバッチ単位にも適用する** という話になる。

## fp16 と bf16 で測るとどうなるか

**両方とも fp32 より速い。** 4 条件すべてで、fp16 も bf16 も 10/10 で fp32 を上回る。**そして 2 つは互いに区別できない。**

これは cumo master (`e4c6f4b3`、#474) での測定である。**released 0.8.0 では Llama 2 をこの 2 つで回せない。**`rms_norm` と `silu` が 0.8.0 の後 (#458、#460) に入ったもので、リリース版の `HFloat` / `BFloat` には無いためである (`layer_norm` / `softmax` / `gelu_tanh` は 0.8.0 にもある)。**0.9.0 で 3 つとも released に入った** ので、いまは 3 つの dtype すべてに 5 本とも生えている。**#474 が入っているかはバージョン文字列では分からない** ので、シンボルで見る ([gpt2-124m.md](gpt2-124m.md) の同じ節)。

1 ケース 1 プロセス、ラウンド内でインターリーブ、10 ラウンド、プロセス内 best-of-5。クロックは固定した (アイドル SM 2797 MHz、走行中のメモリは 329 サンプル中 242 が 14001 MHz、電力は中央値 97.3 W)。

| 条件 | fp32 | fp16 | bf16 | fp16 / fp32 | bf16 / fp32 | bf16 / fp16 |
|---|---|---|---|---|---|---|
| 有り、64 | 583.4〜613.1 | 617.3〜651.4 | 620.4〜647.2 | **1.014〜1.101** 10/10 | 1.020〜1.108 10/10 | 0.990〜1.016 **またぐ** |
| 有り、200 | 563.2〜588.7 | 600.9〜634.1 | 611.6〜633.1 | **1.023〜1.118** 10/10 | 1.061〜1.124 10/10 | 0.979〜1.054 **またぐ** |
| 無し、64 | 381.6〜410.9 | 543.9〜560.4 | 538.5〜568.3 | **1.351〜1.432** 10/10 | 1.327〜1.438 10/10 | 0.974〜1.031 **またぐ** |
| 無し、200 | 229.5〜237.4 | 444.7〜468.9 | 428.3〜477.6 | **1.916〜1.997** 10/10 | 1.825〜2.044 10/10 | 0.914〜1.038 **またぐ** |

**bf16 の列は fp16 の対照として読める。** 4 条件とも比が 1 をまたぐので、**速さの面で 2 つを分ける根拠はこの測定には無い**。GPT-2 でも同じ結果になっている。

**効き幅は仕事量の順である。** キャッシュ有りの 1.01〜1.12 倍から、キャッシュ無し 200 の 1.92〜2.00 倍まで単調に増える。GPT-2 と同じ向きで、確保の回数が多い条件ほど得が大きい。

#474 前に測ったペア比は 1.031 / 1.064 / 1.269 / 1.658 だった (2026-09-17、別セッション)。**Llama 2 はもともと fp16 で速くなる側で、GPT-2 だけが遅くなっていた。**#474 はその Llama 2 側も、キャッシュ無しの 2 条件で押し上げている。

### トークン列は fp16 なら 256 まで完全一致する

貪欲法で 256 トークン生成して fp32 と突き合わせた (キャッシュ有り、EOS で止めない)。

| | fp32 と分かれる位置 |
|---|---|
| fp16 | **分かれない (256 まで一致)** |
| bf16 | 132 |

**GPT-2 とは対照的である。** GPT-2 は fp16 で 3 トークン目に分かれる。stories110M には GPT-2 のような外れ値特徴が無く、`rms_norm` が統計を fp32 で畳むので、fp16 の丸めが argmax をひっくり返すところまで届いていない。**bf16 は仮数部が 8 ビットしか無いので届く。**

**one-hot の罠はこちらには無い。** トークン埋め込みが gather なので、id を浮動小数点数に載せる箇所そのものが無い (GPT-2 の `Ops.one_hot` は損失計算にしか残っていない)。

### 計測の落とし穴: 早く止まる dtype がある

**stories110M は EOS で止まるので、生成数が dtype ごとに違う。** 256 を要求したときの実際の生成数は次のとおりで、**要求長で割ると bf16 だけ 1.20 倍水増しになる**。

| | 実際の生成数 (256 要求) |
|---|---|
| fp32 | 243 |
| fp16 | 243 |
| bf16 | **202** |

最初この水増しを「Llama 2 では bf16 が fp16 より速い」と読んだ。**誤りだった。**`stop_at_eot: false` で長さを固定して測り直すと、上の表のとおり 4 条件とも 1 をまたぐ。**tok/s に正規化しても足りない** ことに注意する。キャッシュ無しはトークンあたりの費用が位置とともに増えるので、短い系列は 1 トークンあたりが安い。**長さを揃えるのが唯一の対処である。**
