# Mamba 130M の計測結果

[kroggen/mamba.c](https://github.com/kroggen/mamba.c) の `learning` ブランチ (Mamba 1) を参照にしたもの。進め方は [PLAN-mamba.md](../plans/PLAN-mamba.md)。

**一度は PyTorch に負けた。1.29 倍離されていたのを、1 トークンあたりのカーネルを 1115 → 557 本に減らして追い越した。当初のちょうど半分である。**

| | 本/token | 要る cumo | PyTorch / Cumo |
|---|---|---|---|
| 当初 | 1115 | | **1.29** |
| `XF.zeros` → `allocate` | 1091 | | |
| `softplus` 7 → 3 本 | 995 | | |
| `rmsnorm` を融合カーネルに | 845 | | 1.04〜1.06 (**負けていた**) |
| `reshape` → `reshape!` | 773 | | 0.96 |
| 分割をビューに | 677 | | |
| `mulsum` | 629 | released 0.9.0 | **0.845** |
| 残差を GEMM の C に | 605 | released 0.9.0 | |
| 融合 `softplus` | **557** | **未リリース #481** | |

**下の比較表は 629 本の側で測っている。** 残差を GEMM に畳む変更はそのあとに入れたので、**released 0.9.0 で走る現行のコードは 605 本** である (融合 `softplus` は probe で見て前の綴りに落ちる)。**605 本での 3 実装の表は取り直していない。**

**理由はこれまでと違う。** GPT-2 と Llama 2 では「1 投入あたりの費用は Cumo も PyTorch も 2.0〜2.2 us で同じなので、差は本数から来る」で説明が付いた。**Mamba では本数が逆転している** — Cumo 629 本に対し PyTorch 1302 本で、**半分以下** である。845 本のときは 35% 少なくても負けていたので、**本数だけでは説明が付かない** ままである。

## 要約

README の「数字」に書いていた要約をここに移した (2026-09-23)。**表は [README](../../README.md#数字) にある。**

attention が無く、1 トークンの仕事が小さい配列への要素演算に寄るモデル。**キャッシュの有り無しは無い** (mamba.c に再計算の経路が無い)。

**一度は PyTorch に負けた。** 最初は 1.29 倍離され、**1 トークンあたりのカーネルを 1115 → 845 本に減らしても 4〜6% 及ばなかった**。**629 本にして 18% 上回った** (10 ラウンドとも PyTorch が下、1 をまたがない)。**この表を取ったあとにさらに 2 つ入れて 557 本、当初のちょうど半分になった** (released 0.9.0 なら 605 本。**その本数での表は取り直していない**)。

**理由はこれまでと違う。** GPT-2 と Llama 2 では「1 投入の費用は同じで差は本数から来る」で説明が付いたが、**Mamba では本数が逆転している** — **Cumo 629 本に対し PyTorch 1302 本** で、2.07 倍多く投入している側が 845 本のときは勝っていた。**`wall ÷ 本数` で比べてはいけない** (torch は 1 ホスト呼び出しで平均 1.46 本出す)。**機構はこの測定では決まらない。**

**本数を減らす 10 の変更で、境目が見えた。** 0 本 (重みは 23% 減) と 2.2% は wall が 1 をまたいで見えず、**4.1% 以上は見えた**。**そして同じ 24 本を、違う場所で 2 度消したら同じだけ動いた** (1.026 と 1.028、同じセッション・同じビルド)。**ただし消えた 2 種はどちらもこの大きさでは起動律速なので、「単価によらない」までは言えない。** **「本数を減らせば速くなる」が仮説でなくなったのは、動かなかった 2 点があるおかげである。**

**分類器は転置せずに格納順のまま持つ。**`mamba.c` と同じ `[out, in]` で持って左から掛けるので、**共有分類器を 2 枚持たずに済む** (mamba-130m で 639.9 → 492.6 MiB、−23%)。答えもカーネル数も変わらず、wall も動かない。

**fp16 では走らない。**`A` が -2.8e+08 まで届いて fp16 では -Inf になり、`softplus` の引数も fp16 の `exp` の上限を超える。**黙って全部 0 を返していたので例外にした。** **bf16 は走って 5〜7% 速い** (重みは半分、参照と一致するのは 17 トークンまで)。

**5 実装すべてが `mamba.c` と同じ 255 トークンを出す。** 期待値の出どころは C の参照そのもので、このリポジトリではない。

## 数字

tokens/sec、プロセスごとに best-of-3 の中央値、10 ラウンド。**Cumo / CuPy / PyTorch / 対照 (Cumo をもう一度) の 4 系列 x 2 条件** を 1 ラウンド内でインターリーブし、系列の順序をラウンドごとに回転。**先頭 1 ラウンドは位置で捨ててある** (計測の作法 22)。クロックは `nvidia-smi -lgc 3090` / `-lmc 14001` で固定 (アイドル SM 2790 MHz)。GPU は RTX 5070 Ti Laptop。

**このページの tok/s は全部クロック固定で取ってある。** 固定は測り終えたあとに外した。外した状態の負荷中は **SM 1852 MHz / MEM 11001 MHz**、固定中は **SM 2790 MHz / MEM 9001 MHz** で (cumo 側の実測)、**絶対値は条件が違えば動く**。ペア比は同条件どうしなので残るが、**固定なしで測り直したときに同じ比が出るかは確かめていない**。

**キャッシュ有り無しの区別は無い。** Mamba に再計算の経路が無く、`mamba.c` にも無い。

**cumo は released 0.9.0。**`gem install cumo` から再現できる値である。**融合 `softplus` は 0.9.0 に入っていない** ので `FUSED_SOFTPLUS` が false に落ち、**1 トークン 629 本** で走ったときの数字である (581 本にするには未リリースの #481 が要る)。

**18% 上回った。** 10 ラウンドとも PyTorch が下で、1 をまたがない。

## 本数が逆転している

decode 1 トークンあたりに GPU へ投入するカーネルの本数 (nsys、`--length 72` と `--length 40` の差 ÷ 32)。

| | カーネル/token | PyTorch / Cumo |
|---|---|---|
| Cumo (29a5f5d) | 1091 | 1.29 |
| Cumo (aec5f83) | 845 | 1.04〜1.06 |
| Cumo (743e9e8、released 0.9.0) | 629 | **0.845** |
| Cumo (現行、released 0.9.0 なら) | 605 | (取り直していない) |
| **Cumo (現行、cumo master)** | **557** | |
| **PyTorch** | **1302** | |

**1091 本のときは、PyTorch が 19% 多く投入して 29% 速かった。845 本にしても 4〜6% 負け、773 本で初めて上回り、629 本で 18% 上回った。** PyTorch は 2.07 倍多く投入している。

**`wall ÷ カーネル数` で比べてはいけない。** 当初ここには「Cumo 3.18 us 対 PyTorch 2.07 us」と書いていたが取り下げる。cumo 側が、**torch の最も安い 1 呼び出しが 2.22 us で、2.07 us はその床を割っている** ことを指摘した。数えたら **torch は 892 回のホスト呼び出しで 1302 本**、つまり **1 呼び出し 1.46 本** だった (`TorchFunctionMode`)。

## ホスト呼び出しの回数

**cumo 1360 回/token 対 torch 892 回/token。こちらのコードは cumo を 1.5 倍多く呼んでいる。**

cumo 側は深さ 0 だけを拾う `TracePoint` で数える (cumo が内部で呼ぶ `allocate` は既に別の呼び出しの内側なので落ちる)。

```ruby
tp = TracePoint.new(:c_call, :c_return) do |t|
  next unless t.defined_class.to_s.include?('Cumo')
  if t.event == :c_call
    tally[t.method_id] += 1 if depth.zero?
    depth += 1
  else
    depth -= 1 if depth.positive?
  end
end
```

**2 つのカウンタが同じ母集団を測ることは、同一ワークロードで確かめた。** 問い合わせ 3 + op 6 を 20 周させると **両方とも 180 回** で、メソッドごとに 1 対 1 で対応する。

| cumo | | torch | |
|---|---|---|---|
| `ndim` | 20 | `__get__` | 40 |
| `shape` | 20 | (ndim + shape) | |
| `size` | 20 | `size` | 20 |
| `*` | 20 | `mul` | 20 |
| `+` | 20 | `add` | 20 |
| `sum` | 20 | `sum` | 20 |
| `zeros` | 20 | `zeros` | 20 |
| `[]` | 20 | `__getitem__` | 20 |
| `[]=` | 20 | `__setitem__` | 20 |

**`TorchFunctionMode` は属性アクセスも `__get__` として数える。** 一度「`TracePoint` だけが問い合わせを拾うので比べられない」と書いて取り下げたが、**それは誤りだった** (cumo 側が指摘し、こちらで再現した)。

### カーネルを出さない呼び出しが半分以上ある

**本数を 1091 → 773 に減らしても、呼び出しは 2181 → 1936 回にしか減らない。** 同じ `TracePoint` を 29a5f5d のワークツリーに当てて 2181.0 を再現してあるので、3 つの数は同じ数え方である (どれも 20 歩と 40 歩で小数点以下まで同じ値になる)。

| | 呼び出し/token | カーネル/token | カーネルを出さない | 割合 |
|---|---|---|---|---|
| 29a5f5d | 2181 | 1091 | 1090 | 50.0% |
| aec5f83 | 1910 | 845 | 1065 | 55.8% |
| d69d353 | 1936 | 773 | 1163 | 60.1% |
| d798730 | 1504 | 581 | 923 | 61.4% |
| **現行** | **1360** | **557** | **803** | **59.0%** |

**分割をビューにしたところで呼び出しも減った。** 1936 → 1624 で、`Ops.contiguous` が消したのは `store` だけでなく `shape` と `initialize` でもある。その後 `mulsum` で 1576、融合 `softplus` で 1504、残差を GEMM に畳んで 1360 になった。

**最後の 1 歩で割合が下がった。**`dot` をやめて `gemm` を直に呼ぶ形になったので、**`dot` が 1 回につき 4 回問い合わせていた `ndim` が 388 → 292 に落ちた** (24 回ぶん)。カーネルを出さない呼び出しが 120 回減り、出す側は 24 本しか減らないので、割合が 61.4% → 59.0% に戻る。**呼び出しとカーネルは別の量である。**

**最後の 1 歩で呼び出しが増えている。**`reshape` 72 回が `reshape!` 96 回になったためで (`xc` を戻す 1 回が層ごとに増える)、**カーネルは 72 本減って呼び出しは 24 回増えた**。呼び出しとカーネルは別の量である。

cumo は 1 呼び出しあたり 0 本か 1 本で、2 本以上は出さない (cumo 側が確認)。だから差は引き算で出る。

**減った 271 回のうち 246 回はカーネルを出していた呼び出しで、出さない側は 25 回しか減っていない。** 削ったのは仕事のほうで、**床はほとんど動いていない**。

|---|---|---|---|---|
| `ndim` | 388 | 388 | 0 | **cumo の `extra.rb`**。`dot` が 1 回につき 4 回問い合わせる (97 dot x 4) |
| `cast` | 194 | 194 | 0 | 同じ `dot` の中。同型なので self が返る |

差を足すと -271 で、2181 - 1910 に閉じる。

**`NMath` の 145 回は `method_missing` を通っていた。** 内訳は `silu` 48、`softplus` の `exp`/`log` 48、SSM の `exp` 24、`rmsnorm` の `sqrt` 25 である (前にここには「`silu` 48、`exp`/`log` 48、`sqrt` 25」と書いていたが、SSM の `exp` 24 を落としていた)。**`Cumo::SFloat::Math` を直に呼ぶと `method_missing` を通らない** ので、いま残っているのは融合 `silu` の 48 回だけである。cumo 側は `NMath` の振り分けを速くするパッチを書いたが、**効果が 2.25 us の呼び出しに対して 1.5〜2.7% だったので master には入らなかった**。回避策のほうは既に入っている。

**`reshape` はこの床に入らない。** 当初ここには「993 回が形と型の問い合わせ」と書いて `reshape` 72 回を数え入れていたが、**`reshape` はコピーを返す** (cumo 側の指摘を受けて確かめた。結果を書き換えても元が変わらず、numo でも同じ)。**確保 1 本 + カーネル 1 本** である。`reshape!` のほうはビューなのでカーネルを出さない。

床に入るのは、aec5f83 では **921 回** で 1065 の 86% だった (`ndim` 388 + `cast` 194 + `initialize` 121 + `shape` 97 + `reshape!` 73 + `coerce` 24 + `allocate` 24)。**現行では 805 回** で、803 とほぼ一致する (`ndim` 292 + `reshape!` 147 + `[]` 146 + `cast` 146 + `initialize` 25 + `inplace` 24 + `allocate` 24 + `shape` 1)。`coerce` は融合 `softplus` が `1.0 +` を消したので 0 になった。

**そして引き算が閉じる。** 現行 (557 本) でカーネルを出す側を足すと **555 本** になる。

    * 144 + `+` 96 + gemm 97 + []= 48 + mulsum 48
    + silu 48 + rms_norm 25 + softplus 24 + exp 24 + store 1 = 555

**計測値 557 との差は 2 本。** aec5f83 (845 本) でも 843 対 845 で **同じ 2 本** だった。`reshape` を床に入れていたときだけ 74 本ずれていて、それは `reshape` がコピーだと知らなかったためである。**残る 2 本の出どころは分けていない。** nsys の差分法 (`--length 72` と `--length 40` の差 ÷ 32) の値なので、整数でちょうど閉じることを求める筋合いでもない。

**`dot` 1 回につき `ndim` が 4 回と `cast` が 2 回、というのはこちらのコードの書き方では減らせない。**

**ただしこれが PyTorch との差を説明するとは書かない。** GPU が遊んでいる (cumo 側の実測で、縮約以外は投入し終えた時点で GPU が終えている) ので **ホスト側の CPU 時間が効く形ではある** が、**呼び出し 1 回あたりの CPU 費用を両者で測ってはいない**。

**機構は決まらない** (AGENTS.md 18)。

### cumo は 1 op ごとでは速い

cumo 側が同じ形・同じ op で並べた (2026-09-19、`[1536, 16]` fp32、1 ケース 1 プロセス、ウォームアップ 2x500 のあと 500 回 x best-of-5、**こちらでは追試していない**)。

| op | cumo | torch |
|---|---|---|
| `mul` | **2.34 us** | 2.78 us |
| スカラー倍 | **2.33** | 3.22 |
| `exp` | **2.42** | 2.60 |
| ブロードキャスト (列) | **2.30** | 3.08 |
| ビューの copy | **2.27** | 3.26 |
| `gemv` | 5.52 | 5.70 |
| `sum(axis: -1)` 連続 | **2.72** | 3.47 |
| **`sum(axis: -1)` ビュー** | **4.21** | **3.46** |

**gemv 以外のすべてで cumo が 10〜45% 速く、負けるのはストライドのあるビューの縮約だけ。** そちらはカードになっている (同じ形の連続配列より 1.6 倍遅く、`copy` してから縮約しても改善しない)。**こちらの経路は縮約の前に必ず連続な中間配列を作るので、踏んでいない見込みだが確かめていない。**

**そして両ライブラリとも完全に CPU 投入律速である。** 縮約を除く全 op で「投入 + 同期」と「投入だけ」の差が 0.007 us、つまり 500 本を投入し終えた時点で GPU は既に終えている。床は CUDA ドライバの起動そのもの (1.1〜1.4 us) とのこと。

## `softplus` の 7 本のうち 4 本は、参照に無いガードだった

`mamba.c:222` は **素の `logf(1.0f + expf(x))` で、桁あふれを何も見ていない**。x が大きければ `expf` が Inf になり、答えも Inf になる。こちらはそこに clip のガードを足していた。

```ruby
# 7 本: clip / exp / add / log / clip / sub / add
XM::NMath.log(1.0 + XM::NMath.exp(x.clip(nil, 88.0))) + (x - x.clip(nil, 88.0))

# 3 本: exp / add / log
MATH.log(1.0 + MATH.exp(x))
```

**`x.clip` が 2 回書いてあった** ので、ガードは 3 本ではなく 4 本ぶんだった。**そして実データでは一度も要らない** — mamba-130m の 64 トークンで `softplus` の入力の最大は **26.47** である。

**`log1p` は使えない。**`log1p(exp(x))` なら 2 本になるが、**参照は `1.0f + expf(x)` を先に足して丸めてから `logf` に渡す** ので別の値になる。

**あわせて `XM::NMath` を `XF::Math` に替えた。** cumo の `NMath` は `method_missing` で捌いており、cumo 側の実測で **0.17 us/回** の上乗せがある。答えは同じで、`NMath` は引数の dtype で同じモジュールに振り分けているだけである。

### 今度は wall が動いた

| 長さ | 前 | 後 | ペア比 | またぐ |
|---|---|---|---|---|
| 64 | 275.6 | **301.0** | 1.083 (1.002〜1.112) | **いいえ** 10/10 |
| 200 | 275.9 | **307.9** | 1.121 (1.053〜1.247) | **いいえ** 10/10 |

**本数は 1091 → 995 (−96)。** 10 ラウンド、順序を毎ラウンド入れ替え、クロック固定。**2 条件とも 1 をまたがず 10/10。**

**`.allocate` のときと何が違ったか。** あちらは 24 本 (2.2%) で 1 をまたぎ、こちらは 96 本 (8.8%) でまたがない。**削った本数が 4 倍である。**

1 トークンあたりの短縮は **306 us (長さ 64) と 377 us (長さ 200)**。96 本で割ると **3.19 us と 3.92 us** になるが、**2 条件で 22% 食い違うので、1 本あたりの値として扱わない。** cumo 側が単独で測った基本 op の 2.2 us より高い側に出ている、というところまでである。

## `XF.zeros` の fill は全部無駄だった

`shift_in` は `[d_inner, d_conv]` を作って **全列を上書きする** ので、ゼロ埋めは 1 つも残らない。`XF.new(...).allocate` に替えると **答えはビット一致** のまま `fill_kernel` が 24 本消え、**1115 → 1091 本** になった。

**ところが wall は動かない。**

| 長さ | zeros | allocate | ペア比 | またぐ |
|---|---|---|---|---|
| 64 | 284.3 | 291.4 | 1.020 (0.997〜1.045) | **はい** 9/10 |
| 200 | 287.2 | 291.2 | 1.010 (0.992〜1.035) | **はい** 7/10 |

**2 条件とも 1 をまたぐので「速くなった」とは言えない。** 1115 本の 2.2% では足りない。**それでも入れた** — 答えが変わらず本数が確実に減るので、入れない理由が無い。

**この形は cumo 側が測って教えてくれた。** あわせて「非連続スライス同士の代入は 1 本で、行ごと起動ではない」ことも確認されている (`[1536, 4]` で 2.50 us、連続の全体代入 2.07 us との差は 0.43 us)。

## `rmsnorm` は融合カーネルに替えられた

`mamba.c:234` は `o[j] = x[j] * weight[j] * ss` と左から掛ける。`llama2.c` は `weight[j] * (ss * x[j])` なので、**`Ops.rmsnorm` は別の結合** である。そのため Mamba 側に自前の 7 本の実装を置いていた。

**測ったら替えられた。**

|---|---|---|---|
| Cumo | 4.272e-04 | **4.272e-04** (1 ビットも動かない) | 128 トークン一致 |
| Numo | 4.120e-04 | **3.738e-04** | 一致 |

**Cumo の融合カーネルは、この形では `x * weight * ss` と同じ答えを出している。** 中でどう畳んでいるかは読んでいない。Numo 側は `llama2.c` の結合に落ちるので少し動くが、**`mamba.c` との差は小さくなる側** だった (どちらが「正しい」わけでもなく、**基準が `mamba.c` だというだけ** である)。

**採用の基準はトークン列が変わらないこと。** 両バックエンドとも満たした。

| 長さ | 前 | 後 | ペア比 | またぐ |

## fp16 では走らない。bf16 では走って 5〜7% 速い

**fp16 は黙って壊れる。**`DTYPE=fp16` にすると 200 トークンすべてが token 0 になり、それでいて 382 tok/s という数字が出る。**理由は 2 つあって、どちらもこの実装ではなくモデルの値域の側にある。**

1. **`A` が fp16 に入らない。** mamba-130m の `A` は最小 **-2.836e+08** で、fp16 の上限 65504 の 4300 倍である。重みを fp16 で持つと **589824 要素のうち 1535 (0.26%) が -Inf** になる。`dt` が 0 の要素と掛かると `0 x -Inf = NaN` で、そこから先は全部 NaN になる。
2. **`softplus` の引数が fp16 の `exp` の上限を超える。** 引数は最初のトークンで **22.26** に達するが、fp16 の `exp` は **11.09** で Inf である (`exp(11.09) = 65513 > 65504`)。

**2 は直せるが、1 は直せない。**`softplus` を `min(x, 11.0)` で頭打ちにして超過分を足し戻す形にすれば 2 は消える (確かめた) が、それでも `A` の -Inf が残るので答えは NaN のままである。**`A` を fp32 で持てば通るが、それは「fp16 で動かした」ことにならない。**

**なので黙って答えずに例外にした。**`Ops.layernorm` / `rmsnorm` が fp16 の非融合経路で同じことをしているのと揃えてある。**全部 0 のトークン列に tok/s を付けて表に載せるのが、いちばん悪い壊れ方である。**

**bf16 は走る。** 指数部が fp32 と同じなので上の 1 も 2 も起きない。

| | 重み | tok/s (長さ 700) | 参照と一致するトークン数 |
|---|---|---|---|
| fp32 | 492.6 MiB | 391.13 | **257 (全部)** |
| bf16 | **246.3 MiB** | **420.88** | 17 |

仮数部が 8 ビットしかないので **index 17 で分岐する** (15548 対 330)。AGENTS.md が言う「トークン id は 256 で飛ぶ」はここでは効かない — 埋め込みを gather で引いているので、id が fp16 / bf16 の配列に入ることが無い。

**そして速い。**

| 生成長 | bf16 / fp32 | 対照 (fp32 を 2 度) |
|---|---|---|
| 200 | **1.055 (1.028〜1.108) またがない 10/10** | 1.003 (0.957〜1.031) **またぐ** |
| 700 | **1.078 (1.045〜1.098) またがない 10/10** | 1.005 (0.985〜1.015) **またぐ** |

**`reshape` → `reshape!` の前後で 2 度測って、どちらも同じところに出た** (前は 1.074 / 1.055、後が 1.055 / 1.078)。**別ビルドではないので比べてよい** が、条件ごとの大小が入れ替わっているので、**5〜8% のどこ、までしか言えない**。

**2 条件 x 10 ラウンド、どちらも 1 をまたがず 10/10。** 対照は両方またぐ。クロック固定、順序はラウンドごとに回転、先頭 1 ラウンドは位置で捨ててある。

**GPT-2 の fp16 ほどは効かない。** あちらは重みを半分にすると素直に帯域が効いたが、Mamba は投入律速なので、**重みが半分になっても 5〜7% しか動かない**。

**Numo には bf16 が無い** ので、この節は Cumo だけである。**CuPy と PyTorch を並べた 3 実装の表も作れない** (numpy にも cupy にも bfloat16 が無く、fp16 はこのモデルでは走らない)。

## `reshape` はコピーだった

`reshape` は **新しい配列にコピーを返す**。numo も cumo もそうで、仕様である。**`reshape!` は形だけ書き換えてビューを返す。**

ブロックの中に `reshape` が 3 か所あり、**24 層で 72 回、カーネル 72 本** を出していた。845 本の **8.5%** である。

```ruby
# 前: 3 か所とも新しい [1536] のコピーを 1 つずつ作っていた
xc.reshape(1, inner).dot(w[:x_proj_t])
... xc.reshape(inner, 1) * (dt * b)
y.reshape(1, inner).dot(w[:out_proj_t])
```

**`reshape!` は破壊的なので、`xc` は形を戻す必要がある。**`w[:d] * xc` が `[1536]` を要求するためで、`xc` は行 → 列 → 行と回って元の形で終わる。`y` は以降使わないのでそのままでよい。

```ruby
xc.reshape!(1, inner).dot(w[:x_proj_t])
xc.reshape!(inner, 1)
... state.ssm(layer) * da + xc * (dt * b)
(ssm * c).sum(axis: 1) + w[:d] * xc.reshape!(inner)
y.reshape!(1, inner).dot(w[:out_proj_t])
```

**本数は 845 → 773 (−72)。** 差分法を順序を入れ替えて 2 回取り、**4 profile すべてが 773.0** だった。ホスト呼び出しは `reshape!` が 1 回増えるので 1912 → 1936 になる。

**wall が動いた。**

| 生成長 | `reshape!` / `reshape` | 対照 (同じものを 2 度) |
|---|---|---|
| 200 | **1.075 (1.041〜1.104) またがない 10/10** | 1.002 (0.991〜1.017) **またぐ** |
| 700 | **1.093 (1.071〜1.116) またがない 10/10** | 0.996 (0.976〜1.015) **またぐ** |

10 ラウンド、順序はラウンドごとに回転、先頭 1 ラウンドは位置で捨てる、クロック固定。

**2 条件 x 10 ラウンド、どちらも 1 をまたがない。** 答えは変わらず、Numo と Cumo のどちらも 257 トークンが `mamba.c` と一致する。

**この 1 つで PyTorch を追い越した。** 本数が 8.5% 減って wall が 7.5〜9.3% 動いた。

**見つけたのは cumo 側である。** こちらは 1065 回の「カーネルを出さない呼び出し」の内訳に `reshape` 72 回を数え入れていた。**問い合わせだと思い込んでいた。** 指摘を受けて確かめたら、結果を書き換えても元が変わらないのでコピーだった。**引き算が 74 本ずれていたのが 2 本になった** のは、その訂正の副産物である。

## 分割の 4 つのコピーはビューで済んだ

ブロックは `xz` を `xc` と `z` に、`x_db` を `dt` / `B` / `C` に割る。どちらも **行が 1 本しかない** のに、`Ops.contiguous` でコピーを作っていた。

**行を整数で選べば、両バックエンドで連続ビューになる。**

```ruby
xz[true, 0...inner]   # Numo はこれを非連続と言い、reshape! を拒む
xz[0, 0...inner]      # [1536] の連続ビュー。Numo も Cumo も通る
```

`true` で取った形しか見ていなかったので、リポジトリには `RESHAPABLE_ROW_SLICE` という probe があって **Cumo だけビューを使い、Numo はコピーしていた**。整数添字ならその分岐が要らない。

**本数は 773 → 677 (−96)。**`store` が **97 → 1 本** になった。毎層 4 回の `Ops.contiguous` が、埋め込みの 1 回だけになったためである。`shape` も 97 → 1、`initialize` は 121 → 25 に落ちた。

**答えは変わらない。** コピーがビューになるだけで、読む値は同じである。

## 積と和は `mulsum` 1 本になった

`(conv * w).sum(axis: 1)` は積のカーネルと和のカーネルで 2 本を使い、間に `[1536, 4]` の中間配列を作る。`mulsum` は 1 本で済ませる。畳み込みと SSM 出力の 2 か所にある。

```ruby
conv.mulsum(w[:conv1d_weight], axis: 1)
ssm.mulsum(c, axis: 1)
```

**本数は 677 → 629 (−48)。**

**丸めは変わる。** Numo の参照との `max|d|` が 3.738e-04 → **3.967e-04** に動いた (閾値 5e-3)。**Cumo は 3.510e-04 で動かなかった。** **トークン列はどちらも 257 件すべて一致する。**

**軸を明示するのが要点である。** cumo #480 は「縮約軸をマークしたビュー」に対する `mulsum` の誤答を直したものだが、**`axis:` を渡すとマークは読まれない** ので、この形はその経路を通らない (cumo 側が実機で確認)。0.8.0 でも 0.9.0 でも同じ答えになる。

## 融合 `softplus` は 3 本を 1 本にした

`MATH.log(1.0 + MATH.exp(x))` は `exp` / `add` / `log` の 3 本。cumo #481 の `Cumo::NMath.softplus` は 1 本で、**和を先に取る形なので `mamba.c` と同じ数を返す** (`log1p` ではない)。

**本数は 629 → 581 (−48)。**`FUSED_SOFTPLUS` の probe で見て、無ければ前の綴りに落ちる。**released 0.9.0 には入っていない** ので、上の 3 実装の表は 629 本で走ったときの値である。

**fp16 は救われない。** この融合は 16 ビットでも float で畳んで最後に 1 回丸めるので `exp` の 11.09 では溢れないが、**`A` の −2.836e+08 が残る** ので答えは NaN のままである。例外はそのままにしてある。

## `sigmoid` は使わなかった

cumo #482 で `Cumo::NMath.sigmoid` が入ったので試した。**`Ops.silu` を `x * sigmoid(x)` と書いても、257 トークンすべてが一致する。**

**落ちると予想していたが、外れた。** cumo 側が「`silu(x)` と `x * sigmoid(x)` で値が変わる要素の個数」を測っていたので、トークン列も割れると見ていた。**別の量を読んでいた。**

    ① 何個の値が動くか          cumo 側が測ったのはこれ
    ② どれだけ動くか            こちらの max|d| は 9 点で 7.3e-12
    ③ 離散的な受け入れが変わるか  こちらの 257 トークン一致

**① が大きくても ② が小さければ ③ は動かない。** そして ① は定数ですらなかった — cumo 側が取り直したところ、標本の範囲を ±5 から ±100 に広げると 37.9% から 22.6% まで動く (飽和域では両方の書き方が厳密に一致するので、動かない点で薄まる)。**性質の値ではないので、ここには書かない。**

**それでも採らない。本数が 581 → 629 に増える** (+48)。融合 `silu` が 1 本でやることを、`sigmoid` と積の 2 本でやる形になる。**このリポジトリに素の `sigmoid` を呼ぶ場所は無い**、という最初の見立てのほうが正しかった。

## 残差は GEMM の C に畳めた

ブロックの終わりは `y . out_proj_t` のあと `+ x` で残差を足す 2 段だった。cuBLAS は C を受けて `beta` で足し込めるので、**1 本で済む**。GPT-2 がバイアスで既に使っている形 (`Ops.linear_into`) である。

```ruby
# 前: gemm 1 本 + add 1 本
out = y.reshape!(1, inner).dot(w[:out_proj_t])
out + x

# 後: gemm 1 本だけ
Ops.linear_add(y.reshape!(1, inner), w[:out_proj_t], x)
```

**本数は 581 → 557 (−24)。**`Numo` に `gemm` は無いので `GEMM_WITH_C` で分岐し、そちらは 2 段のまま。

**`x` は上書きされる。** cuBLAS は C に結果を書くので、残差として渡した配列は失われる。ここでは安全で、理由は 2 つある。呼び出し側が `x = block(...)` で結果に束ね直すこと、そして `Ops.rmsnorm(x, ...)` がビューではなく新しい配列を返すことである。**読んで確かめたうえで、トークン列でも確かめた** — 両バックエンドとも 257 件一致する。

**cumo の検査は別名を見つけてくれない。**`gemm` は非連続な C を `c must be contiguous` で撥ねるが (`ext/cumo/narray/gen/tmpl/gemm.c:443`)、**`cumo_na_check_contiguous` はオフセット付きの連続ビューを Qtrue にする** (`narray.c:1153-1163`)。大きい配列の連続な一部を C として渡すと **検査を通り、元の配列ごと書き換わる**。検査が保証するのは「非連続なら事故になる前に止まる」までで、**C に渡すものが他から読まれないかは呼ぶ側が確かめるしかない。**

**wall は動いた。ただし小さい。**

| 条件 | ペア比 | またぐ | 対照の幅 |
|---|---|---|---|
| 200 (1 回目) | 1.028 (0.898〜1.062) 9/10 | **はい** | 11.2% |
| 200 (2 回目) | **1.016 (1.001〜1.045) 10/10** | いいえ | 13.7% |
| 700 | **1.028 (1.002〜1.093) 10/10** | いいえ | 5.5% |

**200 を 2 回測った理由は、腕の値ではなく対照である。** 1 回目は対照が 11.2% 振れて 1 ラウンドが 1.133 に飛び、そのラウンドは両アームとも壊れていた。**測り直す判断を腕と無関係な量で決めたので、両方の結果を残す。**

**3 測定中 2 つで 1 をまたがない。効きは 1.6〜2.8%。**

## 同じ 24 本を、違う場所で 2 度消した

**`zeros` → `allocate` を、いまの本数でもう一度測った。** この変更は当初 1115 本のときに入れたもので、そのときは 24 本 (2.2%) で **ペア比が 1 をまたいだ**。本数が 581 本まで減ったいまなら同じ 24 本が 4.1% になる。

**測る形は残差のときと寸分同じになる。** どちらも **581 → 557 本** で、消える本数も分母も一致する。**違うのは消えるカーネルの種類だけ** である。

| 変更 | 消えるもの | 200 | 700 |
|---|---|---|---|
| 残差を GEMM の C に | 要素ごとの加算 24 本 | 1.016 (10/10) / 1.028 (9/10 またぐ) | **1.028 (1.002〜1.093) 10/10** |
| `zeros` → `allocate` | fill 24 本 | 1.014 (0.990〜1.036) 9/10 **またぐ** | **1.026 (1.001〜1.066) 10/10** |

**揃った。** 同じセッション・同じビルド・同じクロック固定で測っている。**この帯では、どこを触るかではなく何本消えるかで決まる。**

**ただしこれは「消えたカーネルの単価が効く」という説の反証にはならない。** 当初ここには「別種のカーネルなのに一致したので種類では説明が付かない」と書いたが、**仮説は種類ではなく単価の話だった** (cumo 側の指摘)。cumo の 1 演算の固定費は 2.0 us で、**この大きさでは fill も要素ごとの加算も起動律速** である。帯域で見れば加算が 3 倍読み書きするが、帯域に届く前に起動で決まる。**この 2 点は「別種・同単価」の対で、単価仮説から見れば一致して当然である。** **反証ではなく、この対では判定できない。** 判定するには **高いカーネルを 24 本消す変更** という別の腕が要る。

**そして同じ変更が、分母によって見えたり見えなかったりする。**

| `zeros` → `allocate` を測った分母 | 割合 | ペア比 (200) | またぐ |
|---|---|---|---|
| 1115 本 (当時) | 2.2% | 1.010 (0.992〜1.035) | **はい** |
| **581 本 (いま)** | **4.1%** | 1.014 (0.990〜1.036) | **はい** |
| **581 本 (いま、長さ 700)** | **4.1%** | **1.026 (1.001〜1.066)** | いいえ |

**消えるカーネルは 24 本のまま、コードも同じである。** 変わったのは残りの本数だけで、**同じ絶対量が小さくなった分母で大きく見える**。分母の比は 1115 / 581 = **1.92 倍**、効きの比は 1.4〜2.6 倍で、**向きは合う**。

**精度の話としては弱い。** 1115 本の 1.010 は **別セッション・別ビルド** の値で (計測の作法 10)、しかもその点自体が 1 をまたぐ。**またぐ点を土台にした比なので、一致したことを強く読んではいけない。** 言えるのは **「表の横軸は本数ではなく割合である」** までで、それはこの 2 行が示している。

**この読みは cumo 側から来た。** こちらは「2.2% では見えず 4.1% では見える」を閾値の発見として書いていたが、**同じ変更の割り直しでしかない** と指摘された。**閾値はワークロードの性質ではなく、こちらの測り方の分解能である。**

## 本数と wall の対応

**同じワークロード・同じ測り方で 9 点そろった。** 割合は「減った本数 ÷ 変更前の本数」。

| 変更 | 減った本数 | 割合 | ペア比 (長さ 200) | またぐ |
|---|---|---|---|---|
| 共有分類器の転置をやめる | **0** | 0% | 1.007 (0.986〜1.049) | **はい** |
| `XF.zeros` → `allocate` (1115 本のとき) | 24 | 2.2% | 1.010 (0.992〜1.035) | **はい** |
| `XF.zeros` → `allocate` (581 本のとき) | 24 | 4.1% | 1.014 (0.990〜1.036) | **はい** (700 では 1.026 でまたがない) |
| 残差を GEMM の C に | 24 | 4.1% | 1.016 (1.001〜1.045) | いいえ (1 回目はまたいだ) |
| `mulsum` | 48 | 7.1% | 1.053 (1.023〜1.074) | いいえ |
| 融合 `softplus` | 48 | 7.6% | 1.062 (1.040〜1.103) | いいえ |
| `reshape` → `reshape!` | 72 | 8.5% | 1.075 (1.041〜1.104) | いいえ |
| `softplus` 7 → 3 | 96 | 8.8% | 1.121 (1.053〜1.247) | いいえ |
| 分割をビューに | 96 | 12.4% | 1.090 (1.074〜1.105) | いいえ |
| `rmsnorm` 7 → 1 | 150 | 15.1% | 1.125 (1.086〜1.141) | いいえ |

**この表を削るなら、`allocate` の 2 行は最後に残すこと。** 他の 8 行はすべて別々の変更なので交絡するが、**その 2 行だけは同じコードを 2 つの分母で測った内部対照である**。横軸が割合であることを示しているのはその 2 行だけで、残りは 1 行ずつでは何も決めない。

**境目は 2.2% と 4.1% の間にある。ただしそれは割合の話であって、本数の話ではない。** 同じ 24 本が 1115 本の分母では見えず、581 本の分母では (長さ 700 で) 見える。**線を引くなら「予想される効き」の軸であり、そこでは 1.0% が見えず 1.6〜2.6% が見える。** **これはワークロードの性質ではなく、この測り方の分解能である。**

**効きは本数比より小さい。** ペア比から 1 を引いて並べると、`allocate` 1.4〜2.6% (本数 4.1%)、残差 1.6〜2.8% (4.1%)、`mulsum` 5.3% (7.1%)、融合 `softplus` 6.2% (7.6%)、`reshape!` 7.5% (8.5%)、ビュー化 9.0% (12.4%)、`rmsnorm` 12.5% (15.1%) で、**どれも本数比の 0.4〜0.9 倍** に収まる。**比例するとは書かない** — 7 点しかなく、`softplus` 7 → 3 (8.8% で 12.1%) は別セッション・別ビルドで、並びに入れると崩れる。

**換算率は生成長でも動く。** 同じ 2 点を長さ別に出すと、こうなる。

| | 長さ 200 | 長さ 700 |
|---|---|---|
| 残差を GEMM に | 1.6 / 4.1 = **0.39** | 2.8 / 4.1 = **0.68** |
| `zeros` → `allocate` | 1.4 / 4.1 = **0.34** | 2.6 / 4.1 = **0.63** |

**変更どうしの差 (0.39 対 0.34) より、長さの差 (0.35 → 0.65) のほうがずっと大きい。** 散らばりの大半は、消すカーネルの違いではなく生成長から来ている。

**それでも長さを揃えると、まだ説明の付かない差が残る。** 長さ 200 で並べると、24 本の 2 点が 0.34 と 0.39、48〜150 本の 5 点が 0.73 / 0.75 / 0.82 / 0.83 / 0.88 で、**24 本の 2 点だけが低い**。候補は 2 つあり、**どちらも【疑い】で、こちらも cumo 側も検証していない**。

1. **単価。** 消えた 24 本が平均より安い。平均は 2.137 ms / 581 本 = 3.7 us、起動律速の小さいカーネルは 2.0 us なので、予想される換算率は 0.55 前後。**長さ 700 の 0.65 は近いが、長さ 200 の 0.35 は低すぎる**
2. **隠れている。** 消えた 24 本が長い GEMM の隣にあり、既に裏に隠れていた。**残差の加算は GEMM の直後** なので形は合う

**2 のほうが、長さ 200 で低くなることをうまく説明する。** どちらも測っていない。**nsys の行ごとの時間では区別できない** — 同じ profile で対照行が 2.57 倍動き、順序を入れ替えたら 0.68 倍に反転した実績がある。区別するには **高いカーネルを 24 本消す変更** という別の腕が要る。**それが無いので【疑い】のまま置く。**

**幅はセッションの後半で広がった。** 上の 8 点は対照の幅が 2〜5% のときに取った値で、**残差の行だけ 3.5〜13.7% のときに取っている**。同じ機械・同じ手順で、違うのは時刻だけである。**同じ精度で読んではいけない** (計測の作法 7)。「本数を減らせば速くなる」が仮説でなくなったのは、**動かなかった 2 点があるおかげ** である。

**0 本の行が効く。** 共有分類器の転置は重みを 23% 減らすが **本数を 1 本も減らさない**。そして wall も動かない。**減るのが本数でなければ動かない、という向きの証拠** になっている。

**48 本の 2 点が割れたかどうかは、この表では決まらない。**`mulsum` 1.053 と融合 `softplus` 1.062 は近いが、**同じ条件で並べていない**。(a) 割合が 7.1% と 7.6% でそもそも同じでない、(b) 融合 `softplus` は長さ 700 では 1 ラウンドだけ 0.993 に落ちて **またいだ** (そのラウンドの幅が 5.7〜6.8% と広く、7.6% と区別が付かなかった)、(c) **`mulsum` は released 0.9.0、融合 `softplus` は master ビルドで測っている** ので、2 つを突き合わせるのはビルドをまたぐ (計測の作法 10)。**言えるのは「7% 前後の 2 点は、どちらも見える側に落ちた」までである。**

**同じ 96 本が 1.121 と 1.090 に分かれているのも、根拠にしない。**`softplus` 7 → 3 は別セッション・別ビルドの値である。

**すべてクロック固定** (`-lgc 3090` / `-lmc 14001`、アイドル SM 2790〜2805 MHz)、**10 ラウンド、順序はラウンドごとに回転、先頭 1 ラウンドは位置で捨てる**。対照は 8 点すべてで 1 をまたいだ。

## 正しさ

**mamba-130m の 255 トークンが `mamba.c` と完全一致する。** Numo と Cumo の両方で、2 つは互いにも完全一致。fp16 や int8 でやった「一致する長さを記録する」扱いにはならなかった。

**Python の 3 実装も同じ列を出す** (numpy、CuPy、torch/cpu、torch/cuda)。**5 実装すべてが一致する。**

**期待値の出どころは C の参照である。**`script/mamba_fixtures.rb` が `script/mamba_dump.c` 経由で `mamba.c` の `forward()` を回し、自分の argmax を食べ直させて作る。`mamba.c` の CLI ではこれができない — プロンプトを必ず要求し、50277 語彙のトークナイザで符号化するので、`<|endoftext|>` 単独から始められない。

フォワード 1 回の一致は [PLAN-mamba.md](../plans/PLAN-mamba.md) の第一段階にある (logits `max|d|` が 4.1e-04、閾値 5e-3)。

## 測っていないこと

- **`mamba_ssm` との比較。** 融合 CUDA カーネルを持つので、使うと「同じ算法の比較」ではなく「レシピの比較」になる。この表は算法を固定している
- **リングバッファ。** 残る 2 本を消せるが `sum_along_last_dim` の和の順序が変わる
- **605 本での 3 実装の表。** 上の表は 629 本のときの値で、そのあと残差を GEMM に畳んで 24 本減っている。**released 0.9.0 に戻して取り直していない**
- **カーネルを出す呼び出しの合計と、計測値の差 2 本**
- **残る 73 回の `dot` を `gemm` の直呼びにするとホスト側がどれだけ減るか。** cumo 側の実測で `dot` 5.98 us に対し `gemm` 5.45 us。**カーネルは 1 本も減らない** ので、上の表の「またぐ」帯に落ちる見込み。残差の 24 回は既に `gemm` になっていて、そのぶん `ndim` が 96 回減った
- **prefill が途中のトークンでも logits を計算している。** プロンプトが長ければ最終 RMSNorm と語彙射影を P−1 回省ける。**こちらのプロンプトは 1 トークンなので表の数字は動かない**
