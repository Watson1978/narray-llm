# Llama 2 の int8 (Q8_0) の計測結果

llama2.c の `runq.c` が読む version 2 チェックポイントを Numo / Cumo で動かしたもの。参照は `runq.c` そのもの。

**結論から書くと、いまの NArray では int8 のほうが遅い。** stories110M (dim 768) で **1.55 倍** である。重みは 3 分の 1 になるが、**1 トークンあたりのカーネルが 2.3 倍に増える** ためで、実装の粗さではなく **バックエンドに int8 の GEMM が無いこと** の直接の帰結である。

**ここまで 3 段階で縮んだ。**

| | 本/token | int8 / fp32 | 何が変わったか |
|---|---|---|---|
| 当初 | 1569 | 0.246 (**4.1 倍遅い**) | |
| cumo #477 | 1484 | 0.378 (**2.6 倍遅い**) | 重みを行列積のたびに fp32 へ戻すのをやめた。**こちらのコードは変えていない** |
| cumo #476 を使う | 889 | 0.588 (**1.7 倍遅い**) | 量子化の 9 本を `quantize_symmetric` 1 本 + `XF.cast` 1 本に畳んだ |
| 量子化の共有 | **781** | **0.647 (1.55 倍遅い)** | runq.c と同じく q/k/v と w1/w3 で量子化を使い回した |

**残りは 2 つ。**`XF.cast` の 49 本 (`Int8 x Int8` が Int8 で累算するので避けられない) と、行列積そのものの縮約である。

**大きさを変えても逆転しない。**「小さいモデルで測ったから遅く出ただけ」ではない (理由は下記)。

## 要約

README の「数字」に書いていた要約をここに移した (2026-09-23)。**表は [README](../../README.md#数字) にある。**

llama2.c の `runq.c` が読む重みを、同じ手順で 3 実装並べたもの。**キャッシュ有りのみ** (runq.c に全系列を再計算する経路が無い)。

**ここだけ関門が短い。** 全実装が一致するのは 131 トークンまでで、その先は畳む順序の違いで 3 つの組に分かれる (Numo と Cumo は同じ組にいる)。**分かれ方は下の「数値の一致」に書いてある。**

**fp32 では PyTorch を 10〜19% 上回るだけだが、int8 では 2.7 倍になる。** 3 つのうち **重みを int8 のまま読めるのが Cumo だけ** だからで、PyTorch は行列積のたびに fp32 のコピーを作る (`torch.einsum` が混合 dtype を拒む)。`torch._int_mm` は列数が 8 の倍数でないと動かないので、**1 トークンの decode では使えない**。

**それでも int8 は fp32 より 1.55 倍遅い。** 重みは 3 分の 1 になるが、1 トークンあたりのカーネルが 342 → 781 本に増える。当初は 4.1 倍遅く、cumo #477、#476、そして量子化の共有でここまで来た。**経過と、なぜ遅いのかは下の各節にある。**

**この int8 の表だけは 0.10.0 で測り直していない。** README のほかの表とは別のバッチなので、**またいで比を取らないこと** (計測の作法 10)。

**README の表の Cumo の列は cumo 0.9.0 以降が要る。**#476 (`quantize_symmetric`) と #477 (`Int8 x SFloat` のカーネル内昇格) が 0.9.0 で released に入った。**0.8.0 では動くが遅い**。コードは `respond_to?` で見て古い書き方に落ちるので、動かなくなることはない。

## 作り方

`export.py --version 2` を PyTorch のチェックポイントに対して回す。量子化済みの配布は無い (`karpathy/tinyllamas` にあるのは fp32 の `.bin` と `.pt` だけ)。

```
ruby script/download_llama2.rb runq.c export.py model.py stories15M.pt stories110M.pt
cd vendor/llama2.c && ../../python/.venv/bin/python export.py \
  ../../data/stories15M_q80.bin --version 2 --checkpoint ../../data/stories15M.pt
../../python/.venv/bin/python export.py \
  ../../data/stories110M_q80.bin --version 2 --checkpoint ../../data/stories110M.pt
```

**`group_size` はチェックポイントごとに違う。**`export.py` は `dim % group_size` が 0 になるまで半分にするので、`dim` が 288 の stories15M では既定の 64 ではなく **32** になる。dim 768 の stories110M は **64** のままである。ヘッダから読むこと。

| | dim | hidden | 層 | group_size | fp32 | int8 |
|---|---|---|---|---|---|---|
| stories15M | 288 | 768 | 6 | 32 | 58 MB | 17.1 MB |
| stories110M | 768 | 2048 | 12 | 64 | 438 MB | 116 MB |

生成側は同じスクリプトで、**ファイルの magic を見てモデルを選ぶ**。

```
ruby script/llama2_generate.rb stories15M_q80 --length 200
```

## 形式

| | |
|---|---|
| マジック | `0x616b3432` (`"ak42"`)、バージョン 2、ヘッダ 256 バイト |
| fp32 のまま | RMSNorm の 1 次元の重み 3 本 |
| int8 | 行列すべて。`int8[size]` の直後に `float[size / group_size]` |
| 埋め込み | **読み込み時に fp32 へ戻す** (`runq.c:204`)。行を引くだけなので量子化する意味が無い |

`data/stories15M_q80.bin` は 17.1 MB で、fp32 の 58 MB に対して 3.4 分の 1。

**並びは fp32 版と突き合わせて検証した。** 脱量子化して `stories15M.bin` と比べると `wq[0]` の最大差が 0.002333 で、**これは `export.py` が「全重み中の最大量子化誤差」として報告した値そのもの** である。

## int32 は要らない

`runq.c` はグループごとに `int32_t` へ畳んでから float に戻す。**同じ整数が fp32 でもそのまま出る。**

```
1 グループの部分和の上限 = group_size x 127 x 127 = 64 x 16129 = 1,032,256
fp32 が整数を厳密に表せる上限 = 2 ** 24 = 16,777,216
```

**丸めが一度も起きないので、加算の順序も結果を変えない。**`Int32` に上げる必要が無く、`Int8#mulsum(SFloat)` がそのまま使える。

**ただし「累算器が fp32 なら要らない」という意味である。**`Int8#mulsum(Int8)` は Int8 に畳むので、そちらは同じ上限を必ず超える (後述)。

## 1 トークンあたりのカーネル数

2 つの生成長の差 ÷ その差、キャッシュ有り。15M は `--length 128` と `--length 64`、110M は `--length 72` と `--length 40` で取った。

| | fp32 | int8 | 比 |
|---|---|---|---|
| stories15M (6 層) | **180** | **795** | 4.42 |
| stories110M (12 層) | **342** | **1569** | 4.59 |

**4.4〜4.6 倍に増える。** 内訳は 2 つに集約され、**どちらも層数と行列積の本数にそのまま比例する** ので、大きいモデルでも比が下がらない。

stories110M の 1 トークンあたりで、**int8 側にだけ立つのは 1275 本あり、これがちょうど「行列積 85 回 x 15 本」である** (85 = 7 行列積 x 12 層 + 分類器)。内訳は量子化が 9 本 (`abs` `max` `div` `clip` `ceil` `sub` `add` `div` `round`)、重みを fp32 に実体化する `store_int8` が 1 本、積と縮約とスケールの畳み込みが 5 本。**代わりに fp32 の `gemv` 49 本が消える** ので、差し引き 1227 本の増加になる。

### 活性の量子化が 1 回 9 本

`runq.c` の `quantize` は 1 パスのループだが、NArray では 9 つの演算になる。

```
abs -> max(axis: 1) -> / 127 -> clip -> ceil -> 1.0 - x -> + scale -> / scale -> round
```

(`clip` / `ceil` / `sub` / `add` は、全要素が 0 のグループで 0 除算にならないようにするためのもの。)

**これが 1 トークンに、行列積の回数だけ呼ばれる。** 15M は 43 回 (7 行列積 x 6 層 + 分類器)、110M は 85 回。`abs` も `round` も `clip` も `ceil` も、その回数がそのまま 1 トークンあたりの本数に出る。

### 混合型の `mulsum` は int8 を fp32 に実体化する

`Int8#mulsum(SFloat)` は **カーネル内で昇格しない**。単体で数えると 1 回あたり 2 本で、内訳は **キャストと縮約** である。

| 呼び方 | カーネル/回 |
|---|---|
| `Int8#mulsum(SFloat)` | **2** (`sfloat_store_int8` + `reduction_zip`) |
| `SFloat#mulsum(SFloat)` | 1 |

**つまり重み行列が毎回 fp32 で書き出される。** int8 で保持する意味がここで消える。読むバイト数は int8 の 1 に対し「int8 を読む 1 + fp32 を書く 4 + fp32 を読む 4」で、**fp32 のまま持つより増える。**

**#477 の前は大きいほうが悪かった。** dim 288 で 3.2 倍、dim 768 で 4.1 倍。**#477 で 2.6 倍、融合量子化で 1.7 倍まで戻った** (下記)。

stories15M の 2 行の差は cumo #475 で、**動いたのは fp32 の側だけ** だった (下記)。stories110M は #475 の入った cumo で測っている。

**段の資格判定は 15M では薄く、110M では効く。** 15M は 1 回が 0.14 秒 (fp32) と 0.44 秒 (int8) しかなく、200 ms 間隔のサンプラでは窓に 1〜3 個しか入らない。10 ラウンド中 6 つが「サンプル不足」または「段が混ざる」で資格外になったが、**残った 4 ラウンドでも 0.313〜0.320** だった。110M は int8 側の窓が 1.2〜1.9 秒あって 6〜10 個入り、**資格を満たす 8 ラウンドで 0.210〜0.249、全 10 ラウンドで 0.210〜0.252 と、判定しても変わらない。**

**110M では後半 3 ラウンドで両アームが揃って落ちる** (fp32 が 656 → 468、int8 が 155 → 103)。熱のドリフトだが **比は 0.236 → 0.210 → 0.232 と幅の中に収まる** ので、インターリーブが効いている。

### cumo #475 は int8 には効かなかった

#475 は `mulsum` の **最内軸をブロードキャストする形** を直したもので、`decode_attention` の values 側がそれに当たる。**int8 の matmul は逆向きである。**

| | ブロードキャスト | 縮約 | #475 |
|---|---|---|---|
| attention の values 側 | `[t, 12, 1]` = 最内軸 | axis 0 | **13.49 → 4.81 us** |
| 量子化 matmul | `[groups, GS]` を `[out, groups, GS]` に = 最外軸 | axis 2 | もともと速い側 |

**1 トークンあたりの最大の行 (`reduction_zip`、GPU 時間の 31%) は 0.3295 → 0.3273 ms とほぼ動かなかった。** カーネル数も 795 → 789 で、減った 6 本は attention の values 側 (6 層 x 1) である。

**その一方で fp32 は速くなったので、比は 0.315 から 0.297 に開いた。** int8 が遅くなったのではなく、**fp32 が先に行った**。

## 3 実装を並べる

fp32 の表と同じ手順で、`stories110M_q80` を Cumo / CuPy / PyTorch で測ったもの。**キャッシュ無しは測らない** (runq.c に全系列を再計算する経路が無く、量子化が行ごとに定義されているため)。

tokens/sec、プロセスごとに best-of-3 の中央値、10 ラウンド。**Cumo / CuPy / PyTorch / 対照 (Cumo をもう一度) の 4 系列 x 2 条件** を 1 ラウンド内でインターリーブし、系列の順序をラウンドごとに回転。クロックは固定 (アイドル SM 2805 MHz)。

| 生成長 | Cumo | CuPy | PyTorch | Cumo / CuPy | Cumo / PyTorch |
|---|---|---|---|---|---|
| 64 | **410.71** | 62.17 | 152.57 | **6.61** | **2.69** |
| 128 | **411.98** | 62.37 | 152.75 | **6.61** | **2.70** |

| 条件 | Cumo / CuPy | Cumo / PyTorch | 対照 |
|---|---|---|---|
| 64 | 6.582 (6.224〜6.720) またがない 10/10 | 2.687 (2.628〜2.746) またがない 10/10 | 1.011 (0.909〜1.043) **またぐ** |
| 128 | 6.602 (6.393〜6.820) またがない 10/10 | 2.731 (2.581〜2.922) またがない 10/10 | 0.987 (0.955〜1.024) **またぐ** |

**量子化を共有する前は 6.99 / 3.02 と 7.05 / 3.04 だった。** 修正は 3 実装すべてに入れたので、**3 つとも速くなって比が縮んだ**。伸び幅は Cumo +11%、CuPy +18%、**PyTorch +24%** である。

**fp32 の表では Cumo が PyTorch を 10〜19% 上回るだけだったが、int8 では 3 倍になる。** 理由は 1 つで、**この 3 つのうち重みを int8 のまま読めるのが Cumo だけ** だからである。

| | 重みの読み方 |
|---|---|
| **Cumo** | `Int8#mulsum(SFloat)` が **カーネル内で昇格する** (#477) |
| PyTorch | `torch.einsum` が混合 dtype を拒むので `w.float()`。**呼ぶたびに fp32 のコピーを作る** |
| CuPy | `cupy.einsum` は混合を受けるが、**1 回あたりのカーネル数は Cumo より多い** |

**PyTorch の int8 GEMM は使えない。**`torch._int_mm` は 2 つ目のオペランドの列数が 8 の倍数であることを要求し、**1 トークンの decode では 1 になる**。

```
_int_mm N=1  : mat2.size(1) needs to be greater than 0 and a multiple of 8, but got 1
_int_mm N=16 : OK
```

つまり **バッチ 1 の decode には、フレームワーク側にも逃げ道が無い**。これは #477 が入る前の Cumo が 2.6 倍遅かったのと同じ位置である。

### Python 版で踏んだもの

**`round` の半端の扱いが違う。** runq.c の `round()` は 0 から遠いほうへ丸めるが、**numpy と torch は偶数へ丸める**。Numo / Cumo は C と同じ。

```
入力         -2.5  -1.5  -0.5   0.5   1.5   2.5
Numo/Cumo      -3    -2    -1     1     2     3
numpy/torch    -2    -2    -0     0     2     2
```

合わせる定番の `trunc(x + copysign(0.5, x))` は **使えない**。0.5 直下の float (`0.49999997`) で **加算そのものが 1.0 に丸まる** ため、1 だけ大きく出る。分数を 2 倍するほうは厳密である。

```python
t = xp.trunc(x)
r = t + xp.trunc((x - t) * 2.0)
```

**2,200,010 要素 (ちょうど .5 が 99,861 件、上の病的な値を含む) で Numo の `round` と 0 件の不一致** を確認した。

**`(w * xq).sum(axis=2)` ではなく `einsum` を使う。** 前者は `[32000, 12, 64]` の中間配列を fp32 で作る。`einsum("ogk,gk->og", ...)` は作らない。

## 数値の一致

## 数値の一致

**トークン 0 の logits は 32000 要素すべて `runq.c` とビット一致する。**

そこに至る途中で **共有の `Ops` に 1 ulp の差が 2 つ見つかった。** どちらも「除算」と「逆数を取ってから乗算」の違いである。

```c
runq.c  rmsnorm:  ss = 1.0f / sqrtf(ss);      o[j] = weight[j] * (ss * x[j]);
runq.c  silu   :  val *= (1.0f / (1.0f + expf(-val)));
```

**fp32 の経路でもずっと同じずれを抱えていた** が、トークン列が一致していたので表に出ていなかった。**量子化してはじめて表面化した。** 直した (`ab9fccc`) あとも、既存の受け入れテストは両バックエンドとも通る。

### それでも生成は途中で分かれる

200 トークンでは `runq.c` と一致しない。**そして ulp を 1 つ潰すたびに分岐位置が動く** (615 → 192 文字目)。**収束しないので、ここを追うのは筋が悪い。**

| | 40 トークン | 200 トークン |
|---|---|---|
| stories15M | 一致 | 192 文字目で分岐 |
| stories110M | **一致** | 448 文字目で分岐 (全 665 文字) |

#### 7 実装はちょうど 3 つの組に分かれる

stories110M を 200 トークン生成して突き合わせたもの。**組の中はバイト一致、組をまたぐと 131 トークン目か 171 トークン目で分かれる。**

| 組 | 実装 | 文字数 |
|---|---|---|
| A | **runq.c**、numpy | 665 |
| B | CuPy、torch/cpu | 670 |
| C | Ruby (Numo)、Ruby (Cumo)、torch/cuda | 692 |

**CPU と GPU の別ではない。** Ruby は Numo と Cumo が一致し (バックエンド間一致の関門は満たしている)、**torch は cpu と cuda が別の組に落ちる**。numpy だけが runq.c と 200 トークンすべて一致した。

**どれが「正しい」かは決まらない。** 部分和は fp32 で厳密なので、分かれるのはグループごとのスケールを畳む順序のほうである。**なぜ 3 つに分かれるかはこの測定では決まらない** (AGENTS.md 18)。

**関門は全実装が一致する内側に置く。** Python 側のベンチは **64 と 128** で測る (131 トークン目まで全実装一致)。長さ 200 を要求すればトークン検査が落ちるが、それは正しい振る舞いである。

**ビット一致は原理的に達成できない。** 理由が 2 つある。

- **Cumo は `rms_norm` と `softmax` に融合カーネルを使う。** 中の演算順序はこちらで決められない
- **参照が 2 つあって算術が違う。**`Ops` は GPT-2 で llm.c と、Llama 2 で llama2.c と一致させる必要があるが、**両方にビット一致する共有実装は存在しない**

したがって関門は **トークン列の一致** であり、一致する長さを記録する扱いになる (fp16 と同じ)。

## 大きさを変えても逆転しない

cumo 側から「この 3.2 倍は dim 288 で測った値で、大きいモデルには外挿できない」という指摘を受けた (2026-09-19)。根拠として出された単体の `mulsum` は次のとおり (**こちらでは追試していない**)。

| `mulsum` | int8 x int8 | fp32 x fp32 | int8 x fp32 (いまの形) |
|---|---|---|---|
| `[288, 288]` | 5.09 us | **3.64 us** | 4.98 us |
| `[288, 768]` | **2.40 us** | 2.54 us | 5.19 us |
| `[4096, 4096]` | **59.60 us** | 213.27 us | 385.67 us |

**指摘は正しかったが、向きが逆だった。** dim 768 で測り直したら 3.2 倍が **4.1 倍** になった。理由は表の **右端の列** にある。

**いまの実装が使っているのは `int8 x fp32` の列で、そこは 3 つの形すべてで最も遅い。** しかも fp32 に対する比は `[288, 288]` の 1.37 倍から `[4096, 4096]` の 1.81 倍へ **開く**。大きくすると良くなるのは左端の `int8 x int8` の列だけで、**そこはこちらからは使えない** (次節)。

### `int8 x int8` は Q8_0 には使えない

**`Int8#mulsum(Int8)` は Int8 に畳む。** 両バックエンドで確認した。

```ruby
a = XM::Int8.new(1, 4).seq(100, 0)
a.mulsum(a, axis: 1)   # => Int8 [64]  正しくは 40000
```

Q8_0 の 1 グループの部分和は `group_size x 127 x 127` = 最大 1,032,256 に達するので、**Int8 の累算では必ず壊れる。** 上の表で `[4096, 4096]` が 59.60 us と速いのは、**答えが合わない演算を測った値** である。`Int32` にキャストすれば正しくなるが、そのときは 1 要素 4 バイトを読むので int8 で持つ意味が消える。

**これは numo / cumo だけの癖ではない。** numpy も `dot` と `einsum` は int8 のまま畳んで 64 を返す。**分かれるのは純粋な縮約のほうで、`sum` は int64 に広げて 400 を返す。** そして `einsum` は **累算器を明示できる**。

```python
np.einsum('ij,ij->i', a, a)                   # array([64], dtype=int8)
np.einsum('ij,ij->i', a, a, dtype=np.int32)   # array([40000], dtype=int32)
a.sum(axis=1)                                 # array([400])  int64 に広がる
```

**つまり `mulsum(b, accum: Int32)` のような形には numpy の前例がある** (向こうの綴りは `dtype=`)。既定を変えると numpy とも numo とも分岐するが、**明示の口を足すだけなら分岐しない。**

**つまり「小さいから遅く出た」ではなく、「使える形がどの大きさでも遅い」である。**

## cumo に要るもの

この 2 つが埋まれば、int8 は「重みが 3 分の 1 になって遅くならない」ところまでは行くはずである。

1. **`mulsum` が、被演算子より広い型に累算する** こと。いま要るのは 2 つで、どちらも同じ穴から来ている。**(a)** `Int8 x SFloat` が狭い側を fp32 に実体化せずカーネル内で昇格すること。**(b)** `Int8 x Int8` が Int8 ではなく Int32 か SFloat に畳むこと。**(b) が無いので (a) しか選べず、その (a) が一番遅い**、というのがいまの位置である
2. **グループごとの量子化を 1 本にする** こと。9 本が 1 本になる

**int8 GEMM (cuBLAS の `cublasGemmEx`) まで行けばさらに変わる** が、上の 2 つは既存の演算の延長で、要求としては小さい。

### cumo 側の状態 (2026-09-19)

**両方マージ済み。(a) は適用して測った。② はまだ入れていない。**

| | 状態 | こちらの扱い |
|---|---|---|
| (a) `Int8 x SFloat` の in-kernel 昇格 | **master #477 (8ca65301)** | **入れて測った** (コード変更不要) |
| ② グループごとの量子化の融合 | **master #476 (9d43b005)** に `quantize_symmetric` | まだ (コード変更が要る) |

`quantize_symmetric` は最後の軸を 1 グループとする対称量子化で、`scale = max(|row|)/127`、`xq = round(row/scale)`、0 の行は scale 0 / 値 0。**こちらの `quantize_groups` は `[1, dim]` を `[groups, group_size]` に reshape してから最後の軸で縮約しているので、そのまま当てはまる。** 戻り値の `xq` が `Int8` なので、`XF.cast(xq)` を 1 本挟む必要がある (`Int8 x Int8` は上記のとおり壊れるため)。

**(a) の単体の数字は cumo 側のもの。** 3 形とも `(a*b).sum` と誤差 0 とのこと。

| `mulsum` | 修正前 | (a) 適用 | fp32 x fp32 |
|---|---|---|---|
| `[288, 288]` | 4.98 us | **3.72** | 3.59 us |
| `[288, 768]` | 5.19 us | **2.34** | 2.53 us |
| `[4096, 4096]` | 385.67 us | **135.37** | 216.58 us |

**`[4096, 4096]` で fp32 比が 1.81 倍から 0.63 倍に変わる。** 上の「右端の列が 3 形すべてで最も遅い」は、この修正が入れば解消する。

**ただしこちらの 4.1 倍はそれでは消えない。**`store_int8` が 1 回 1 本なので、消えるのは 85 本 (1569 本のうち 5%) である。残りは量子化の 9 本 x 85 で、**そこは層数と行列積の本数に比例し続ける**。

**引数の順序では逃げられない。** cumo 側が `Int8#mulsum(SFloat)` と `SFloat#mulsum(Int8)` の両方を数えて、**どちらにも `store_int8` が同じ本数出る** ことを確認している (`[4096, 4096]` 10 回で 10 本ずつ、対照の `SFloat#mulsum(SFloat)` には 1 本も出ない)。壁時計では 367.0 / 366.0 us で、対照が 161.0 us、キャスト単体が 228.5 us。**228.5 + 161.0 が観測とほぼ一致する** ので、足し算でも裏が取れている。dispatch がどちら向きでも狭い側を広げるためで、**これはこちらでは追試していない**。

#### この行の推定量は、差分法に決まった

`store_int8` は **AGENTS.md 9 の 2 つの例外が逆を向く** 行だった。モデル読み込みのページフォルトを踏むので `Max / Med` が 1838 に跳ね (9(a) は中央値を指す)、同時に `[768,768]` `[2048,768]` `[768,2048]` `[32000,768]` の 4 形が混ざる (9(b) は平均を指す)。3 つの取り方が 2.9 倍に散った。

| 取り方 | 値 |
|---|---|
| `Med x 本数` | 0.574 ms |
| **総時間の差分** | **1.306 ms** |
| `Avg x 本数` | 1.666 ms |

**差は分解できる。** 2 本の profile の生の値はこうなっている。

| | 本数 | 総時間 | Avg | Max |
|---|---|---|---|---|
| `--length 72` | 6121 | 119.941 ms | 19.6 us | 12411.6 us |
| `--length 40` | 3401 | 78.138 ms | 23.0 us | 15336.0 us |

生成に比例する分は `(119.941 - 78.138) / 32` = **1.306 ms/token**。残る `119.941 - 72 x 1.306` = **25.9 ms** が生成長に比例しない分で、`Max` が 12〜15 ms もあることから **モデル読み込みのページフォルト** である。

`Avg x 本数` はこれを 1 トークンあたりに撒く: `25.9 / 6121 x 85` = **0.360 ms**。そして **1.306 + 0.360 = 1.666** で `Avg x 本数` にちょうど一致する。

**つまり `Avg x 本数` が総時間と一致するのは 1 本の profile の中だけで、差分法はそれとは別の量を出している。** 1 トークンあたりの費用が欲しいなら、**形が混ざっていても差分法のほうが正しい。** 9(b) が平均を勧めるのは「中央値が 1 つの形の値でしかない」からで、**差分法はその問題を持たない。**

**帯域では決められなかった。** 1.306 ms は 547.5 MB (int8 を 109.5 MB 読み、fp32 を 438.0 MB 書く) に対して 419 GB/s に当たる。cumo 側が **冷えた読み側で** 測ったキャストのレートは全形 317〜344 GB/s なので、419 は超えている。**ただし 547.5 MB が全部 DRAM に出るとは限らない** — 書いた fp32 は直後の `reduction_zip` が食べるので、1 本ぶん 2.36 MB なら L2 に載ったまま済む可能性がある。**そこは両方とも測っていないので、算術で推定量を選ぶことはしない。** cumo 側のベンチは 300 MB を巡回させて書き側も必ず DRAM に出すので、**そこから出る 1.62 ms はこちらの条件に対しては上限側** である (cumo 側も同意)。

**この分解は cumo 側とも合意した。** 当初は向こうが「形が混ざる行では `Avg x 本数` が正しい」としていたが、1.306 + 0.360 = 1.666 がちょうど合うことで取り下げている。

### 量子化は行列積ごとではなく、入力ごとだった (2026-09-19)

**`runq.c` は量子化した活性を使い回す。** こちらは行列積のたびに量子化していて、`Ops` のコメントにも「runq.c quantizes the activation before every matmul」と書いていたが、**それが誤りだった**。

runq.c:367  quantize(&s->xq, s->xb, dim);
runq.c:368    matmul(s->q, &s->xq, w->wq + l, ...);
runq.c:369    matmul(s->k, &s->xq, w->wk + l, ...);
runq.c:370    matmul(s->v, &s->xq, w->wv + l, ...);
runq.c:450  quantize(&s->xq, s->xb, dim);
runq.c:451    matmul(s->hb,  &s->xq, w->w1 + l, ...);
runq.c:452    matmul(s->hb2, &s->xq, w->w3 + l, ...);

**q/k/v は同じ `h`、w1/w3 は同じ `h2` を読む。** 層あたりの量子化は 7 回ではなく 4 回 (q/k/v、wo、w1/w3、w2) で、1 トークンでは **85 回 → 49 回** になる。

### DTYPE=fp16 / bf16 では動かさない

**int8 の経路は fp32 でしか正しくない。** 読み込み時に例外にしてある。

```
int8 needs fp32: a group sum reaches 516128, which fp16 cannot hold exactly. Drop DTYPE.
```

**fp16 は上限を超える。**`Int8#mulsum(HFloat)` は HFloat を返すので、`group_size x 127 x 127` が 65,504 を超えると **スケールを掛ける前に Inf になる**。stories15M の最初の decode で **行列積 43 本のうち 12 本 (28%) が上限を超えていた** (最大 81,697)。

**bf16 は指数部が足りるが仮数部が足りない。** 厳密に表せる整数の上限が fp32 の 2^24 に対し **2^8 = 256** しかなく、「部分和に丸めが起きないから加算の順序が結果を変えない」という前提が崩れる。

**弾く前は分かりにくい形で落ちていた。**`quantize_symmetric` は **scale を累算器のクラスで返す** ので、HFloat / BFloat を渡しても **SFloat** が返る (cumo の README に書いてある仕様で、`cT` の 2 バイトで確保して `float` で書くと境界外書き込みになるため)。そのため `ival * scales * xs` の時点で全体が SFloat に転び、**次の `rmsnorm` が `Cumo::SFloat#rms_norm: invalid NArray type (class)` になる**。Inf は表に出ないまま型エラーになる。

**このメッセージからは原因にたどり着けない。** どの引数が問題なのかも、何が期待されていたのかも出ない。しかも `x + w` は昇格するのに融合カーネルは厳密なので、**演算子で通る組み合わせがここで落ちる**。cumo 側が直すことになった。

### ② のうち 3 本は、こちらでも消せる### ② のうち 3 本は、こちらでも消せる

**cumo を待つ必要があるのは 9 本のうち 6 本で、残り 3 本はいまの `Ops` の書き方の問題である。** 0 除算ガードが `clip` → `ceil` → `sub` → `add` の 4 本になっているが、**下限つきの `clip` 1 本で足りる**。

```ruby
scale = rows.abs.max(axis: 1, keepdims: true) / Q_MAX
(rows / scale.clip(TINY, nil)).round          # いまは (scale + (1.0 - ceil(clip(scale, 0, 1))))
```

`scale` は `abs.max` なので負にならず、**ガードが要るのは厳密に 0 のときだけ** である。`clip` の下限を dtype の最小正値にすれば、0 のグループだけが置き換わる。**0 を含む入力で両バックエンドとも `xq` がビット一致することは確認した。**

**まだ適用していない** (カーネルは 1 トークンあたり 255 本減る計算だが、**速度への効き幅は測っていない**)。`quantize_symmetric` を使えば Cumo 側ではこの 3 本ごと消えるので、**この書き換えが要るのは Numo 側のフォールバックだけ** である。

## いまの扱い

**(a) と ② の両方を入れて測った。** 依存する cumo (#476 / #477) は **測ったときは master 直** で、**0.9.0 で released に入った**。0.8.0 には入っていない。**`FUSED_QUANTIZE` の probe があるので、古い cumo でも Numo でも動く。**

**次に効くのは (b) である。** 889 本のうち 85 本が `XF.cast(q)` で、`Int8 x Int8` が Int8 ではなく Int32 か SFloat に畳めれば消える。**ただし numo と numpy が同じ既定なので、既定を変えずに明示の口 (`mulsum(b, accum: Int32)`) を足す形になる。** cumo 側のトラッカーに載っているが未実装。

**それが入っても int8 が fp32 に追いつくかは分からない。** 残る本数は 804 で、fp32 の 342 の 2.4 倍ある。
