# 計測の作法の実例

[AGENTS.md](../AGENTS.md) の「計測の作法」が、どの測定から来たかの記録。**則そのものは AGENTS.md にあり、ここにはその根拠と、外した経緯だけを置く。** 番号は AGENTS.md の作法の番号に対応する。

**ここを読むのは、則の理由を知りたいときと、同じ形を踏みかけたときである。** 日々の計測に要るのは AGENTS.md のほうで足りる。

## 1. best-of-N

単発測定で **存在しない 2.5 倍差を「発見」した** ことがある。

**best-of-N が偏りを増幅した (2026-09-21)。**`script/gpt2_generate.rb` が **表示用の生成で数えたトークン数を、計測用の生成の時間で割っていた**。サンプラは計測ごとに乱数が進むので毎回違う列を出し、**EOT に当たった回は途中で止まる**。

```
3 回目  0.184 s  実際  89 トークン  正しい 482.8 tok/s  スクリプトの式 4882.0 tok/s
4 回目  1.357 s  実際 655 トークン  正しい 482.6 tok/s  スクリプトの式  663.2 tok/s
```

`times.min` を採るので、**いちばん短く止まった回を系統的に選ぶ**。**ノイズなら N を増やせば消えるが、偏りは N を増やすほど悪化する。** **`min` を採る設計は、分子が固定で分母だけが揺れるときに、揺れの下端を拾う装置になる** (別セッションの整理)。**`best-of-N` を使うたびに、分子と分母が同じ 1 回の実行から来ているかを確かめること。**

**気づけたのは「サンプリングが貪欲法より 3 倍速い」というありえない値が出たからである。** EOT 停止だと当たりを付けたら外れ (`stop_at_eot: true` でも 900 生成された)、`stop_at_eot` 自体も無関係 (1.616 対 1.624)。**スクリプトがサンプラを使い回している** ことに気づいて再現した。**正しさを確かめる仕掛けではなく、壊れたときに黙っていない仕掛けが見つけた。**

## 4. ウォームアップ

**固定回数のウォームアップが、速いアームだけを冷やした。** 別セッションが自分の単体ベンチで踏んだ (こちらでは追試していない)。`new` が `prev` の 2.4 倍速いので、**同じ反復回数では 2.4 分の 1 しか温まらない**。低群の系列が `13.9 → 15.1 → 15.1 → 14.0 → 18.6` と上昇中で定常に達しておらず、**バーストを 4 倍にしたら二峰性が消えた**。

## 7. プロセス間の幅

同じ機械・同じ手順で 8〜10 プロセスずつ 4 度測ったら、**幅そのものが** 9.1 / 3.2 / 6.0 / 0.4%、3.6 / 3.5 / 10.5 / 1.2%、11.2 / 6.0 / 7.1 / 1.6%、7.1 / 3.5 / 9.6 / 0.9% **と動き、条件ごとの大小の順位まで入れ替わった**。

**当初「幅は 1 回の計測時間に反比例する」と書いていたが、言い過ぎだった。** 安定して言えるのは「1 回が約 2 秒の条件だけが 0.4〜1.7% に収まり、1 秒未満は 3.0〜11.2% ぶれる」まで。

幅を測らずに 2 ビルドを比べて、**実際には無い改善を docs に書いた** 実績がある (#296 の +1.6% と #287〜#292 の +9.2%)。

**符号が揃っただけで結論にした例。** 幅が 7〜10% ある条件で 5 ラウンドすべて同じ向きに出たあと、**6 ラウンド目で反転して最終的に 9/10** になった。

### 「またぐから疑い」で本物の退行を落としかけた (2026-09-21)

cumo の HEAD と 0.9.0 を 7 ワークロードで並べたとき、**GPT-2 の top-p だけ HEAD が遅い側に符号が揃った**。24 ラウンド取り直しても **ペア比は 1 をまたいだ** (0.9870、0.9663〜1.0025) ので「疑い」として上流に投げた。**本物だった** — cumo #498 が **逆順ビューの `cumsum` を 2.9 倍遅くしていた** (別セッションが単体で 27.7 us 対 9.5 us まで分離。予算 22.5 us/token に対し実測 +19.7 us)。

**またぐかどうかは「大きさが決まるか」の判定で、「向きが決まるか」の判定ではない。** 幅が効果より大きければ範囲は必ずまたぐが、向きはそれとは独立に決まりうる。**符号検定を併せて出すこと。**

| | 片側に揃った本数 | 両側 p |
|---|---|---|
| **HEAD / 対照** | **22/24** | **3.59e-05** |
| 対照 / 0.9.0 (同じビルドどうし) | 15/24 | 3.07e-01 |

**帰無分布は対照ペアが与えてくれる。** 対照が 15/24 でランダムなのに本命が 22/24 なら、偶然ではない。**対照を「またぐことの確認」だけに使うと、この較正を捨てている** (作法 20 と同じ形)。

**そして「疑い」でも投げること。** 確定していないから黙る、をやっていたら退行がリリースに乗っていた。**確度を明記して渡すのと、渡さないのは別である。**

### 分布の形を読もうとして外した (2026-09-20)

Llama 2 の残差を GEMM の C に置いた件で、10 プロセスの tokens/sec が 2 つの塊に見えた。

```
new : 536 541 543 547 551 | 578 586 586 589 594
prev: 556 559 565 576 579 580 581 582 582 583
```

**この 2 行は昇順に並べ替えたもので、測った順ではない。生の時系列は残っていない。**

**隙間を幅で割っていなかった。**

| | 幅 | 最大隙間 | **隙間 / 幅** |
|---|---|---|---|
| `new` | 58 (10.8%) | 27 | **47%** |
| `prev` | 27 (4.9%) | 11 | **41%** |

**47% と 41% はほぼ同じである。** 別セッションが単峰分布から 10 点取る試行を 20 万回まわしたところ、最大隙間 / 幅の **中央値 30%、90% 点 44%** (正規でも一様でもほぼ同じ)。**`new` は「弱い異常」止まり、`prev` は完全に並。** n=15 なら 90% 点が 35% に落ちる。

**そして予算が足りなかった** (作法 24)。詳細は [results/llama2-110m.md](results/llama2-110m.md)。

**ラウンド内の位置が 3.2% 効いた (2026-09-21)。** 6 条件をインターリーブしたとき、そのラウンドの中央値を 1 とした相対速度がこうなった。

```
位置 0: 0.989   位置 1: 0.990   位置 2: 0.999
位置 3: 1.021   位置 4: 1.015   位置 5: 1.000
```

**両端と真ん中は同じではない。** **6 条件を 10 ラウンドで回すと、各アームが各位置を 1〜2 回しか取れず揃わない。** **ラウンド数は条件数の倍数にすること。** この回は対照のほうが位置の取り方で不利 (1.00399 対 1.00494) だったので観測された偏りを説明しなかったが、**説明しなかったことと、効いていないことは別である。**

**同じアームを両端に置いて挟む形 (`新 → 旧 → 新`) は、この偏りを挟めない。** 挟まれた側が毎回 1 つの位置に固定されるので、その位置の効きがそのまま結論になる。**挟む側を交互にする** (`旧 → 新 → 旧` を混ぜる) と打ち消せる。**そして両端の一致は「単調なドリフトが無い」までしか言えない** — V 字の外乱は素通りする。下記 14 のビルドの外乱がまさにその形で、**ラウンド 5 と 6 だけ落ちて前後は揃っていた。**

## 8. 差分法は温まった長さで

`--length 8` は 1 カーネルあたりが系統的に遅く (gemv の中央値が **27.36 対 21.87 us**)、その遅い側を引くので差が縮む。

## 9. nsys の時間の読み方

**(a) 平均が壊れる例。**`store_sfloat` などモデル読み込み時のページフォルトを踏む行は、最大値が中央値の 1 万倍以上に跳ねる。

**(b) 中央値が壊れる例。** 層内 gemv の 48 本は 4 種類の形の混在で、中央値 x 本数にすると **2 割水増し** (1.05 対 0.88 ms)。

**1 本の profile では決まらない。** 同じ回数のカーネルを起動する 2 ビルドを 2 本ずつ profile したら、層内 gemv 48 本が **0.758 / 0.883 / 0.880 / 0.882 ms** となり、1 本だけ 14% 速く出た (ベンチ直後で GPU がブーストしたまま入った回)。

**行の時間を wall と取り違えた例。** 1 トークンに 1 本 275 us と出た行を追いかけたが、fp32 にも同じものが中央値ルールに隠れていたうえ、**その演算を丸ごと消しても tokens/sec は動かなかった** (3 往復で符号が反転)。

**差分法でも `Max / Med` の判定は要る。**`--length 128` と `--length 64` の差を取れば一度きりの費用は相殺されると思い込んで平均で通したことがある。int8 の経路は matmul のたびに fp32 のバッファを確保するので、**長く回すほどプールが伸びて初回タッチが増える**。`store_int8` は `Max / Med` が 3960 で、**平均 0.2504、中央値 0.0743 ms/token と 3.4 倍違った**。そのまま「① が ② とほぼ互角」と別セッションに報告し、**実際は ② が 2.9 倍だった**。

**推定量より総時間の差分。**`store_int8` の 1 行で、`Med x 本数` が 0.574、**総時間の差分が 1.306**、`Avg x 本数` が 1.666 ms/token と 2.9 倍に散った。内訳はこう閉じる。

```
生成に比例する分   (119.941 - 78.138) / 32        = 1.306
比例しない分       119.941 - 72 x 1.306           = 25.9 ms  (Max が 12〜15 ms、読み込みのページフォルト)
Avg はそれを全本数に撒く   25.9 / 6121 x 85       = 0.360
                                     1.306 + 0.360 = 1.666
```

この行は後に **cumo #477 で演算ごと消え、GPU 時間がちょうど 1.306 ms 減って** 差分法の値が当たっていたことが確かめられた。

**分母が小さいと使えない。**`--length 72` と `--length 40` (差 32、全体の 44%) では安定するが、`--length 288` と `--length 256` (差 32、全体の 11%) では合計が **1.132 / 1.645 / 2.212 ms/token** と倍近く散り、**変更が触らない `gemvx` 48 本が 0.141〜0.769 ms と 5.5 倍に散って**、1 トークンあたりが負になる行まで出た。

**相手と比べる前に自分を 3 組 (2026-09-20)。** Whisper の encode で Cumo と PyTorch の GEMM を差分法で出したら、1 組目が **5.048 対 4.183 ms/encode** で「GEMM が 21% 遅い」と書けた。**3 組取ったら Cumo 自身が 5.048 / 4.381 / 4.172 と 21% 動き、3 組目は PyTorch と同じ値だった** (4.172 対 4.137、PyTorch 側の幅は 1.1%)。ペア比 0.997〜1.220 で 1 をまたぐ。**同じ profile の中で、本数は 3 組とも 1 本も動かず (78 / 139 / 99)、時間だけが 21% 動いた。** なお同じ 3 組で GEMM 以外は重ならなかったが (1.348〜2.027)、それでも wall の差はそこに帰属させていない (作法 24)。

**時間が読めないときは本数に降りる (2026-09-21)。** GPT-2 の backward の内訳を差分法で取ったとき、**時間は負の値を出した** (`store_sfloat_kernel_dim1` が −0.44 ms)。forward アームは profile 全体に対する差が 15% しかなく、作法 9 の言う不安定域だった。**ありえない値が門番になった。** 一方 **本数は 331 → 319 と 1 本の狂いもなく閉じ**、書いたコードから数えた予測とも一致した (`mean` 100 対 100、`sum` 111 対 111)。**本数は分解能を持たないので、同期にもクロックにも外乱にも汚されない。** **時間で詰まったら本数に降りること。**

**ただし本数が減ることと速くなることは別である。** 同じ日に 2 回踏んだ。

| 変更 | 本数 | wall |
|---|---|---|
| `Backward.matmul` の連続化を外す | 1755 → 1657 (**−98**) | 27.59 → 28.69 ms (**遅くなる**) |
| `Ops.attention` の連続化を外す | 331 → 319 (**−12**) | ペア比 0.9975、**1 をまたぐ** |
| ソートを共有する | 290 → 281 (**−9**) | ペア比 0.9851、**1 をまたぐ** |

**カーネルが消えて、答えがビット一致で、それでも wall は動かない。** 消える本数に 1 本あたりの費用を掛ける見積もりは、**その本数が何かの陰に隠れていないときにだけ成り立つ**。GPT-2 の AdamW の平坦化を「1.17 倍」と見積もって外したのも同じ形で、**44P の通信が 36.5 ms あるあいだに投入は追いつくので、起動費の大半は隠れている** (実測 37.71 ms との差は 1.2 ms しかない)。

## 11. 1 プロセス 1 ケース

7 ケースを 1 プロセスに詰めて 3 プロセスずつ測ったとき、`[256,768].sum(axis: 1)` が 0.88 倍、`[12,64].transpose * 0.125` が 0.94 倍と出て docs に書いたが、**1 ケース 1 プロセスに分けたら両方消えた** (ペア比 0.982 と 0.989、範囲が 1 をまたぐ)。見分けたのは **対照** で、同じときに測った `a + b` が 0.983 と同じだけ動いた。

**2.3〜2.6 us の土俵は cumo の 1 演算あたりの固定費** (起動 + プール + ndloop + Ruby) そのもので、カーネル側の差は原理的に出ない。

## 12. 出力を毎回確保しない

`[768,50257]` の転置コピーは、出力を毎回 `zeros` で作るとペア比 0.648、使い回すと 0.599。**後者だけが同じ大きさの連続コピーと同じ帯域** (373〜460 対 387〜475 GB/s) に届く。**改善を過小評価する向きに出る。**

## 13. 連続運転でも測り直す

融合カーネルで 1 トークンあたりを 640 → 308 本にしたとき、バーストが **585 対 444 tok/s**、20 秒の連続運転が **580 対 433 tok/s** で一致したので、この件は結果的に問題なかった。

**ただし順序を入れ替えずに 1 往復だけ測ったときは、融合版が 378.7 対 429.7 と逆転して見えた** (そのとき融合版は負荷中のメモリクロックが 9001 MHz・39 W、融合なしは 14001 MHz・98.6 W)。**3 往復インターリーブしたら再現しなかった。** **この 39 W は 1 往復の観測で、後日の持続負荷では中央値 99.4 W しか出ていない** (AGENTS.md の「環境」)。

## 14. クロックの読み

**固定なしのアイドル SM は 400〜700 MHz 台。** 2026-09-20 に 405 / 630 / 697 MHz を観測した。**当初「400〜500 MHz 台」と書いていたが、上は 700 MHz 近くまで出る。**

**`-lgc 3090` は 3090 MHz を出さない。** 固定ラウンド 1720 サンプルで SM の最大は 2805 MHz、負荷中は 2752〜2805 に散る。

**撤回した解釈。** 当初「`-lmc 14001` はコマンドが成功してもカードが従わないことがある (負荷中 41 サンプル中 38 が 9001 で、そのとき SM は 2745〜2805 と高く、電力が SM 側に回っていた)」と書いていたが、**後半は撤回する**。2745〜2805 は「高い」のではなく固定時の通常値そのもので、「電力が SM 側に回っていた」という読みには根拠が無い。**観測 (38/41 が 9001) だけが残る。**

**メモリの段は電力に付いて動き、40 W 未満では 14001 に一度も達しない** (1720 サンプル中 0/41。詳細は [machine.md](machine.md))。

**隣のビルドが計測を潰した (2026-09-21)。** ラウンド 5 と 6 だけ全アームが一斉に落ちた (対照も 660 → 600 tok/s)。GPU 側の指標は **全区間で一様** だった。

```
nvidia-smi --query-compute-apps   ビルドは出ない
clocks.sm / clocks.mem            SM 2520〜2660、メモリ 9001 が 8〜15%、全区間一様
power.draw                        99.5 W に張り付いたまま
load average                      1.37 / 4.76 / 6.09  ← ここにだけ出る
```

**別セッションの `rake compile` だった。** GPU を占有しなくても CPU を埋めればカーネル投入が遅れ、そのまま wall に出る。**「GPU が空いているか」の確認に `--query-compute-apps` しか使っていなかったのが穴で、load average も見ること。** **確実なのは、相手が計測中かをプロセス一覧ではなく本人に聞くことである。**

**そして原因は GPU 側の指標からは永久に分からない。** クロックも電力も「異常なし」に見えていた。**指標が対象を見ていないとき、値が正常に見えることは安心材料にならない。**

## 15. 外から覗くサンプラ

`nvidia-smi` を 200 ms 間隔で回して 40 ms のバーストを 12 プロセスぶん採ったとき、メモリクロックは **54 サンプルすべてが 9001** だった。**しかし GPU が動いていたのは全体の 1.6%** (12 x 40 ms ÷ 30 秒) で、サンプラがバーストの中に落ちる期待値は 1 回しかない。**同じ演算を 1 回 350 ms にして 10 プロセスで回したら、192 サンプル中 146 が 14001 だった。**「段が上がらない」と結論していたら誤りだった。

## 16. 指標を 2 つ以上

クロック固定の件では、メモリクロックだけを見て「固定が効いていない」と読んだが、SM クロックと電力とイベント理由を並べたら別の像になった (**SM の 2797 は固定の上限そのもの、9001 は低電力帯の既定**)。

## 17. 交絡を外す

**1 つ目の例。**`Ops.contiguous` の `zeros` → `new` は、カーネル数だけ見て入れたときは wall が **789 対 789** で「変わらない」と出た。`Ops.attention` の改造を先に入れてから測り直したら 1 トークンあたり **−72** になった。**変更の順序が結論を変えた。**

**交絡が 2 つで、同じ大きさだった例 (2026-09-20)。** GPT-2 のバッチ比較で「batch 8 で PyTorch が 1.5% 上回る」と書いたが、欠陥が 2 つ乗っていた。

| | 欠陥 | 大きさ |
|---|---|---|
| (a) | 差を 5 ラウンドで確定扱いにしていた (作法 7 は 10 ラウンドを要求する) | — |
| (b) | Python 側の移植が 1 ステップに B 回読み戻していた | **約 1.6%** |

(b) は `[int(v) for v in x.argmax(axis=1)]` がデバイス配列を 1 要素ずつ `int()` する形で、**B=8 で 1 ステップ 36〜44 us、長さ 256 なら総時間の約 1.6%**。**主張していた 1.5% と同じ大きさだった。**

**だから片方だけ直しても数字が動かない。**(b) を直さずに 10 ラウンド取れば「再現した」になり、ラウンドだけ増やして 5 ラウンドのままなら差は残って見える。両方直して測り直したら 10 ラウンドで 1 をまたいだので、主張は取り下げた。

**疑う理由を消していたのは自分のコメントだった** — 該当行には「バッチ全体で 1 回」と書いてあった。

## 18. 機構を提案しない / 探索をやめない

**正しい説明で手が止まった (2026-09-20)。** cumo の `cumsum` は `CUMO_CUM_MIN_KERNEL_SIZE` (8192) 未満でホストループと同期に落ちる。**閾値を 0 にしたら Switch の実ワークロードで 4.6% 速かった** (10 ラウンド、10/10、対照はまたぐ)。単体では逆にホストループが 3〜8 倍速い、という別セッションの測定もあった。

**「単体では負けるのに実使用で勝つ」に説明が付いた** — 単体は `cumsum` 1 回を孤立させるが、実際には後ろにキューが積まれていて同期がそれを全部待たせる。**この説明は正しい。**

**そこで形を振るのをやめた。** 別セッションが軸方向を実装して測ったところ、こうなった (向こうの測定、こちらでは追試していない)。

| 形 | 旧 (ホスト) | 新 (カーネル) | 比 |
|---|---|---|---|
| `(1024, 8).cumsum(axis: 1)` | 311.8 | 7296.9 | **23 倍遅い** |
| `(1024, 1024).cumsum(axis: 1)` | 3122.6 | 7896.1 | 2.5 倍 |
| `(16, 20000).cumsum(axis: 1)` | 161.3 | 155.6 | 変化なし |

**ndloop が行ごとにイテレータを呼ぶので、カーネル経路は 1 行 1 起動。** ホスト経路の同期は 2 行目以降デバイスが空で安い。**同期は行数で償却され、起動費は償却されない。**

**この一文は測る前に言えた。** 言わなかったのは、勝ちの説明で手が止まっていたからである。**測ったのは償却がまったく効かない 1 次元だけだった。**

**根拠の弱い当たりは、外れよりも探索を止める (2026-09-21)。** ResNet-18 で cumo の cuDNN が PyTorch より 1.81 倍遅く、その行き先を「起動費 0.2 ms と要素演算 1.6 ms を引いて、残る 69% は cuDNN 呼び出しそのもの」と書いた。**コードレビューで取り下げた** — 帯域から出した 1.6 ms は所要時間の **下限** で、それを実測差から引いて残りに名前を付けることはできない (作法 24)。

**ところが取り下げた推測は、方向としては当たっていた。** 実際に効いていたのは cuDNN 呼び出しの側で、**cumo がワークスペース上限を既定 8 MiB に固定していたこと** だった (環境変数 1 本で 1.62 倍、12/12)。

**それでも取り下げは正しかった。** **当たっていたのは結論であって、根拠ではない。** そして順序が効いた — **根拠ごと通していたら「cuDNN 呼び出しの中身」という漠然とした場所を 2 セッションで見に行っていた** はずで、**環境変数 1 本だけを振る清潔な A/B には戻れなかった。** 取り下げが土俵を作り直した。

**外れた推測は誰かが潰す。当たった推測は誰も潰しに行かない。** だから根拠の弱いまま残り、次の探索の出発点になる。**「合っていたからよい」で通さないこと。**

## 20. 動かないはずの行

**対照が切り分けの唯一の根拠になった例。** クロック固定の表で「融合なし」の行が **+0.2〜2.1%** しか動かなかったことが、融合版の **+8.6〜9.6%** をセッション間ドリフトから切り分けた。

**対照を派生量に当てて閉じた例。** cumo #477 の計測で、行ごとの減りを足すと 1.493 ms、全体の減りが 1.320 ms と **13% 超過** した。**対照の fp32 が、コードを 1 行も変えていないのに GPU 時間だけ 6.3% 動いていた** (カーネル数 342 本のまま、wall も 654.8 → 648.4 でほぼ不変)。比 0.937 を内訳に当てると +1.9% で閉じる。

**当てなかったので外した例。**`GPU / wall` を占有率として読んで「40% は投入で遊んでいる」と書いたが、**同じ計算を対照の fp32 に当てると 126〜136% になる** (GPU 時間が wall を超える)。表には fp32 の行が最初から入っていたので、**割り算を 1 つ増やすだけで分かったはずだった**。

**群にまとめて機構が消えた例 (2026-09-20)。** GPT-2 のバッチごとのカーネル数を「gemv 系 / gemm 系 / その他」の 3 群で数え、**「その他」が 188 / 214 / 214 / 202 / 226 と動いていたのに、なぜ動くのかを問わなかった**。生のカーネル名で数え直すとこうなる。

| batch | `gemvx` | `gemmSN` | cutlass sgemm | `splitKreduce` | その他 | 合計 |
|---|---|---|---|---|---|---|
| 1 | 49 | 0 | 0 | 0 | 188 | 237 |
| 2 | 0 | 37 | 12 | 12 | **202** | 263 |
| 4 | 0 | 37 | 12 | 12 | **202** | 263 |
| 8 | 0 | 48 | 1 | 0 | **202** | 251 |
| 16 | 0 | 25 | 24 | 24 | **202** | 275 |

**「その他」は batch 2 以上でどれも 202 本で一定** で、動いていたぶんは全部 `splitKreduce` だった。**cutlass の sgemm に行った GEMM が splitKreduce を 1 本連れてくる** という 1 対 1 の対応 (12 と 12、24 と 24) が、群をまたいだせいで消えていた。合計の差もこれで閉じる (251 + 12 = 263、251 + 24 = 275)。**数字はどちらでも同じで、隠れたのは機構のほうである。**

`gemmSN_NN_kernel` を `gemvx` と同じ群に入れた判断自体は名前からは妥当だった (SN = small N)。**まとめすぎたかどうかは、群の中を 1 つずつ見るまで分からない。**

**対照が外乱を検出した (2026-09-21)。** 上記 15 のビルドの件で、**対照が同じラウンドで一緒に落ちた** ことが「アームの違いではない」という結論を与えた。**原因が分からなくても、その結論だけは確実に取れる。**

**対照が真の対照でなかった (2026-09-21)。** 同じ回で、対照の worktree を `/tmp` (tmpfs) に置いていて、**本体はディスク上だった**。計測区間はどちらも GPU の仕事だけなので効くとは考えにくいが、**「効くとは考えにくい」は交絡を外したことにならない**。対照は貪欲法より 1.4% 速い側に 8/10 で偏り、**位置の効きでは説明が付かなかった** (位置の取り方は貪欲法のほうが有利だった)。ペア比が 1 をまたぐので「差がある」とは言わないが、**原因は未分離である。** **対照は「何も違わない」でなければならず、複製は同じファイルシステムに置く。**

## 21. 主張の根拠の範囲を書く

4 条件表のうち **1 条件だけを測った段階で「4 条件が反転した」と別セッションに報告** し、相手はそれを 4 条件の結果としてトラッカーに記録した。**後から残り 3 条件を埋めて結論は変わらなかったが、変わらなかったのは結果論である。**

**埋めてから初めて言えることもある** — 4 条件が揃って初めて「効き幅が仕事量の順に単調」と言えた。

**「計測ではない」と明示しても、順位は独り歩きした (2026-09-21)。** PyTorch との区間比較を 3 ステップ 1 本で取り、**「計測ではない」と書いて別セッションに渡した**。相手もそう扱うと返した。**それでも順位は伝わった。**

```
                3 ステップ 1 本   10 ラウンド
forward              1.28            1.21
backward             2.07            1.64
update               1.40            1.87
```

**区間ごとに違う向きにずれていて、いちばん開いている区間が backward から AdamW に入れ替わった。** 受け取る側が先に覚えるのは数字ではなく **「backward がいちばん開いている」という順位** で、**明示は正しさの代わりにならない。** **暫定値を渡すなら、順位が入れ替わりうることまで書くこと。**

## 24. 1 つの要因に帰するなら対照が要る
**倍率を見つけたら、その倍率が掛かる量を全部書き出してから大きさを比べること (2026-09-21)。** ResNet-18 の 2 次元畳み込みで、`shift` (タップごとに行列積) と `unfold` (窓行列を作って行列積 1 本) のどちらが速いかを測った。**測る前に負ける形を名指ししてあった** (作法 18) — 1 次元では `unfold` が 1.65% 勝ったが、**2 次元では窓行列が入力の 3 倍から 9 倍になる** ので `unfold` が負けるかもしれない、と。

**予想は外れた。**`unfold` が **47% 勝った** (1.4741、12/12、対照はまたぐ)。

**「9 倍」は正しかったが、小さいほうだった。**

| 1 パス (16 枚) | |
|---|---|
| **`shift` の累積の往復** (`gemm(beta: 1)` がタップごとに出力を読み書き) | **6.79 GB** |
| `unfold` の窓行列 (往復) | 1.88 GB |
| 差 4.75 GB → 600 GB/s で 7.9 ms、**実測の差 8.3 ms** | |

**どちらも 9 倍になるのに、数えたのは 3.6 倍小さいほうだけだった。**`3 x 3` なら `shift` は出力を 9 往復し、`7 x 7` なら 49 往復する。**予算を立てていれば測る前に分かった。**

**別セッションも同じ見落としをしていた** — 「1 次元で 1.65% しか勝っていないなら、9 倍の書き出しが乗った時点で足りなくなるのが素直な読み」。**2 人とも同じ係数に気づき、2 人とも小さいほうに掛けた。** 向こうの整理はこうだった。**「9 倍」という係数に気づいた時点で満足して、その係数が何に掛かるのかを列挙しなかった。**

**そして目立ったのは離散量のほうだった。** カーネルは 526 本から 330 本に減る (GEMM が 196 → 20) ので、本数の差は一目で見える。**だが増える 196 本を起動費 2.1 us で掛けても 0.4 ms で、実測差 8.3 ms の 5% にしかならない。** **効いていたのは数えなかった連続量 (往復するバイト数) のほうである。**

**「負ける形を先に名指しする」をやっていても、名指しした形が小さいほうなら当たらない。名指しの次に大きさの比較が要る。**


**対照より先に、予算で落ちることがある (2026-09-20)。** Llama 2 の残差を C に置いた件で、2 つの塊の差は **時間にして 7.33%** (低 543.6 / 高 586.6 tok/s) だった。変えた `wo` の重みは `768 x 768 x 4 x 12 層` = **28.3 MB/token**。

| 帯域の段 | 読み切る時間 | 1 トークン (1866 us) に対して |
|---|---|---|
| 413 GB/s (最低段) | 68.6 us | **3.67%** |
| 600 GB/s (最上段) | 47.2 us | **2.53%** |

**この gemm を丸ごと 0 にしても 2.5〜3.7% しか動かない。** 段の不確かさを最大に振っても 7.33% には届かないので、**測る前に帰属が落ちる。**

**単体でも出なかった。** 別セッションが同じ形 (`[1,768] x [768,768]` SFloat、12 層/token) を 15 プロセスずつ測って **どちらも単峰**、幅の非対称も **逆向き** だった。そのベンチは gemm を 1 トークンの 2.5% から 100% に拡大しているので、**gemm 固有の二峰性があれば 40 倍に増幅されて出るはずだった。**



**2026-09-20 に踏んだ。** Switch の MoE で `cumsum` を厳密下三角との行列積に置き換えたら **6.4% 速くなった** (ペア比 1.064、10 ラウンド、10/10、対照はまたぐ)。**2 つのアームはカーネル数も 2121 本で同じ、答えも同じ** で、違うのは同期の回数が 7 回か 1 回かだけに見えた。そこで **6.4% を 6 で割って「同期 1 回が約 74 us」と書いた**。

**同じ場所で `cudaDeviceSynchronize` を 6 回呼ぶだけの対照アーム** を作ったら、**1.007 (0.995〜1.033) で 1 をまたいだ**。**同期そのものは測れる大きさではなかった。** **置き換え全体の 6.4% は残り、分解だけが消えた。**

**そして取り下げの文の中で「効いていたのはホストループのほうだ」と書き、同じ間違いをもう一度やった** — 対照が示したのは「同期だけでは差が出ない」までで、残りをどこかに帰属させる根拠はそこには無い。

**取り下げた直後の数字を疑わなかった (2026-09-20)。** 上の予算の誤りに気づいて「7.1 倍」を取り下げたあと、**PyTorch の `torch.optim.AdamW` の実装差から「融合の価値は 26%」と書き直した**。

**その 26% は PyTorch の 1 ステップに対する割合だった。** しかも比較元の `foreach` は **既に複数テンソルをまとめて回す実装** で、こちらの素の式はそこに来ていない。

```
PyTorch  foreach - fused = 11.8 ms   融合版を下限 5.8 ms と置くと foreach の AdamW ≒ 17.6 ms
cumo     素の式の AdamW   38.4 ms    PyTorch の foreach の 2.2 倍
         融合したら        5.8 ms    差し引き 32.6 ms = step の 42%、全体で 1.73 倍
```

**最初の見積もり (1.72 倍) に戻った。** **6.6 倍は大きすぎて怪しかったので検算したが、26% は落ち着いて見えたので検算しなかった。**

**理想化した実装の予算と比べた (2026-09-20)。** GPT-2 の AdamW が 1 ステップで触る量を、`g` / `m` / `v` / `p` を 1 度ずつ読んで 3 つ書く **7P = 3.25 GB** として出し、実測 38.4 ms と比べて「帯域の底から 7.1 倍」と書いた。

**書いた式は融合していない。** 演算ごとに中間配列を読み書きするので、実際の走査はこうなる。

| 行 | 走査 |
|---|---|
| `m = b1*m + (1-b1)*g` | 9P |
| `v = b2*v + (1-b2)*g*g` | 12P |
| `c = (m/c1)/(sqrt(v/c2)+eps)` | 11P |
| `p -= lr*(c + wd*p)` | 12P |
| 合計 | **44P = 21.9 GB** |

**600 GB/s で 36.5 ms。実測 38.4 ms との比は 1.05。** **このコードは自分のトラフィックの 5% 以内で走っていた。**

**結論まで反転した。**「テンソルを 148 本から 1 本に平坦化するのが先」と書いたが、**平坦化で消えるのは起動費だけ** ((2861 − 19) x 2us = 5.7 ms、1.17 倍) で **44P は残る**。**融合は 6.6 倍で桁が違う。**

**7.1 倍は「それらしい値」だったので門番が働かなかった。** 表示桁の量子化 (`0.0%`) は不自然なので気づけたが、こちらは気づけなかった。

**測っている対象が出荷されていなかった (2026-09-20)。** 上の 4.6% は、**1 つのビルドで両アームを回し**、同期警告で経路が分かれていることを確かめ、**トークン列の一致** まで見て取った。**A/B の公平さは丁寧に作った。**

**そのうえで測った綴りは、計測のためだけに差し戻した古い版だった。** 現行の `first_maximum` は厳密下三角との行列積で `cumsum` を使わない。**閾値を落としてもこのリポジトリのどこも速くならない。**

**docs には「計測のあいだだけ差し戻した」と書いてあった。** 書いていなかったのは **そこから出る結論** のほうで、受け取った側もそれを組み立てなかった。

**別セッションがこの分解を自分のカードに記録していたので、取り下げが 2 か所に波及した** (作法 21 のとおり、主張は数字より速く伝わる)。**この形は 1 日に 3 度出た** — いずれも観測は正しく、そこに乗せた主張が広すぎた。
