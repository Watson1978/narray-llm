# cumo で踏んだ問題の記録 (解決済みと経緯)

このリポジトリで cumo について調べたことを、踏んだ順に残したもの。解決した問題、版ごとの測定、取り下げた帰属を含む。**まだ直っていない問題は [cumo-issues.md](cumo-issues.md) にまとめてある。**

## Numo と Cumo の挙動差

このプロジェクトの第 0〜2 段階で実際に踏んだ差。すべて手元で再現を確認したもので、推測は含まない。

**結論から書くと、ここに挙げた差は「cumo のバグ」ではない。** 実体は `[]` と縮約の戻り値が 0 次元 NArray か Ruby のスカラーかという 1 点の違いで、そこから先の挙動は Numo に真の 0 次元 NArray を渡した場合とまったく同じである。そして `CUMO_COMPATIBLE_MODE=ON` でその 1 点は消える。当初このファイルには「上流に投げる価値がある」と書いていたが、別セッションでの cumo 本体側の切り分けと、こちらでの追試の結果、その判断は誤りだったので訂正した。

## 唯一の差: `[]` と縮約の戻り値

| 式 | Numo | Cumo (既定) |
|---|---|---|
| `x[0].class` | `Float` | `Cumo::SFloat` (0 次元) |
| `x.sum.class` | `Float` | `Cumo::SFloat` (0 次元) |
| `x.max_index.class` | `Integer` | `Cumo::Int32` (0 次元) |
| `bit.count_true.class` | `Integer` | `Cumo::UInt64` (0 次元) |

デバイスからの読み戻し (同期) を避けるための意図的な設計。AGENTS.md にも書いてあるとおり、ループの中で読み戻すとパイプラインが切れる。

## 0 次元 NArray の挙動そのものは Numo も同じ

`Numo::SFloat.cast(5.0)` で真の 0 次元を作って渡すと、Numo も Cumo と同じ挙動をする。つまり以下は Cumo 固有ではない。

```ruby
z = Numo::SFloat.cast(5.0)   # ndim=0
z <=> 1.0                    # => nil          (Cumo も nil)
1.0 <=> z                    # => nil          (Cumo も nil)
z.nan?                       # => NoMethodError (Cumo も NoMethodError)
Math.sqrt(z)                 # => TypeError     (Cumo も TypeError)
(z < 1.0) ? :yes : :no       # => :yes          (Cumo も :yes)
[1.0, z].max                 # => ArgumentError (Cumo も ArgumentError)
```

Numo でこれらに当たらないのは、`[]` や縮約が Ruby の `Float` を返してしまって 0 次元を作る機会がほとんど無いからにすぎない。したがって「`<=>` が nil を返す」「`nan?` / `zero?` / `finite?` / `Math.sqrt` が使えない」は cumo に報告する話ではなく、numo-narray(-alt) 側の 0 次元 NArray の仕様である。

## 実害: 0 次元 Bit が truthy なのでテストが空振りする

Ruby では `nil` と `false` 以外はすべて真なので、値が 0 の 0 次元 `Bit` も真になる。

```ruby
Cumo::SFloat[5.0][0] < 1.0                 # => Cumo::Bit#shape=[] (値 0) だが truthy
(Cumo::SFloat[5.0][0] < 1.0) ? :yes : :no  # => :yes   (Numo は :no)
```

**このプロジェクトでの実害**: `test/test_ops.rb` の `assert_operator(p[0, 1], :>, p[0, 0])` などが `GPU=1` のとき全て空振りしていた。GELU を erf 版に差し替える変異を入れても Cumo 側だけテストが緑のままだった。

`if` / `&&` / 三項演算子は再定義できないので、これを Ruby のコード側で塞ぐ手段は無い。配列同士の比較が `Bit` を返すのは Numo も同じで、そちらは想定内。

## 対処 1: CUMO_COMPATIBLE_MODE

`CUMO_COMPATIBLE_MODE=ON` (環境変数) または `Cumo.enable_compatible_mode` (コード) で、`[]` と縮約が Numo と同じ Ruby のクラスを返すようになる。追試した範囲では比較も `true` / `false` に戻る。

```
--- compatible_mode: OFF ---        --- compatible_mode: ON ---
x[0].class        = Cumo::SFloat    x[0].class        = Float
(x[0] < 1.0)      = Cumo::Bit       (x[0] < 1.0)      = false
x.sum.class       = Cumo::SFloat    x.sum.class       = Float
x.max_index.class = Cumo::Int32     x.max_index.class = Integer
count_true.class  = Cumo::UInt64    count_true.class  = Integer
[1.0, x[0]].max   = ArgumentError   [1.0, x[0]].max   = 5.0
```

**このリポジトリでは採用していない。** 読み戻しが増えて同期が入るため本番コードでは使えず、テストだけ ON にすると本番と違う挙動を検査することになるから。代わりに、値を Ruby の数値として使うところを全て `NArrayLLM.scalar` / テストの `host` ヘルパ経由に統一してある。ただし「numo 向けに書かれた既存のテストを cumo で回す」用途には有効なので、選択肢として記録しておく。

## 対処 2: 個別のエスケープハッチ

compatible_mode を全体に効かせずに 1 か所だけ Ruby の値が欲しいとき。境界は「`*_cpu` を呼ぶ時点でレシーバがまだ NArray かどうか」で、これを外すと compatible_mode を有効にした瞬間に壊れる。

**両モードで安全 (レシーバが NArray のまま)**

```ruby
a.aref_cpu(0) < 1.0                  # => false  (OFF/ON とも)
(a > 1).count_true_cpu               # => 2      (OFF/ON とも)
Cumo::DFloat.cast(5.0).extract_cpu   # => 5.0    (OFF/ON とも)
```

**ON で壊れる (compatible_mode が Ruby オブジェクトに変えた結果への後付け)**

```ruby
(a[0] < 1.0).extract_cpu   # OFF => 0    / ON => NoMethodError (レシーバが既に false)
a.sum.extract_cpu          # OFF => 7.0  / ON => NoMethodError (レシーバが既に Float)
```

**最も素直なのは Kernel の変換。** `to_f` / `to_i` 経由なので 0 次元でも Ruby の数値でも通り、Numo でも同じように使える。

```ruby
Float(a.sum)           # => 7.0  (Cumo OFF/ON、Numo とも)
Integer(a.max_index)   # => 0    (Cumo OFF/ON、Numo とも)
```

このリポジトリの `NArrayLLM.scalar` は `is_a?(Numeric)` を先に判定してから `extract_cpu` に落ちるので、compatible_mode の ON/OFF どちらでも同じ値を返す (実測確認済み)。分岐を 1 か所に閉じ込めてあれば、後からモードを切り替えても壊れない。

## 本物の cumo 固有の性能崖: 併合できない置換の非連続ビュー

ここまでの項目と違い、これは cumo でだけ起きる。第三段階のバッチ化で attention の転置を書くときに踏みかけたので記録する。

**この崖は `CUMO_NA_INDEXER_OPTIMIZED_NDIM` を 8 に上げた cumo master + PR #284 (master に取り込み済み) で解消済み。** 下表は定数が 4 だったビルドでの測定で、解消後の値は最後に併記する。`Cumo::VERSION` はどちらも `"0.5.9"` を返すので、`ext/cumo/include/cumo/indexer.h:224` の定数か `cumo.so` のサイズ (4 なら約 42.6 MB、8 なら約 53 MB) で判別する。

16 MiB (4,194,304 要素 SFloat) を次元数と置換だけ変えて `dup` した帯域 (GB/s)。ウォームアップ 20 回、同じ表を 2 回出して一致を確認したもの。

| ndim | 置換 | 種類 | cumo | numo |
|---|---|---|---|---|
| 4 | `[0,1,2,3]` | 連続 | 446 / 499 | 26 / 27 |
| 4 | `[1,0,2,3]` | 外側 2 つ入替 | 637 / 646 | 24 / 24 |
| 4 | `[2,0,3,1]` | インタリーブ | 477 / 477 | 11 / 11 |
| 4 | `[3,2,1,0]` | 全反転 | 327 / 325 | 3 / 3 |
| 5 | `[0,1,2,3,4]` | 連続 | 492 / 428 | 27 / 24 |
| 5 | `[1,0,2,3,4]` | 外側 2 つ入替 | 641 / 646 | 26 / 27 |
| 5 | `[2,3,4,0,1]` | 回転 2 | 359 / 355 | 3 / 4 |
| 5 | **`[2,0,3,1,4]`** | **インタリーブ** | **8 / 8** | 15 / 15 |
| 5 | **`[4,3,2,1,0]`** | **全反転** | **6 / 6** | 3 / 3 |
| 6 | `[0,1,2,3,4,5]` | 連続 | 515 / 442 | 22 / 26 |
| 6 | **`[2,0,3,1,5,4]`** | **インタリーブ** | **8 / 8** | 11 / 11 |
| 6 | **`[5,4,3,2,1,0]`** | **全反転** | **6 / 6** | 3 / 3 |

絶対値ではなく **連続との比** で読む。CPU はもともと帯域が 1 桁小さいので、絶対値を並べても意味がない。非連続で最も遅いケースを連続と比べると、

| | ndim 4 | ndim 5 |
|---|---|---|
| numo | 8.7 倍遅い | 8.7 倍遅い |
| cumo | 1.4 倍遅い | **77 倍遅い** |

**numo は ndim を上げても比が変わらず、cumo だけ 4 から 5 で跳ねる。** 原因は `ext/cumo/include/cumo/indexer.h` の `CUMO_NA_INDEXER_OPTIMIZED_NDIM 4`。4 次元までは次元数がコンパイル時定数の特殊化があってループが展開され添字がレジスタに乗るが、汎用版は `indexer->ndim` が実行時なので展開できず添字配列がローカルメモリに落ちる。

### 判断基準は ndim ではなく「併合後の実効次元」

ndim 5 でも落ちるものと落ちないものがある。`ndloop` が **順序どおり隣接した軸を 1 軸に併合してからカーネルに次元数を渡す** ため、置換によって実効次元が変わる。

- `[1,0,2,3,4]` は末尾 3 軸が順序どおり隣接したまま残る → 実効 3 次元 → 速い (646)
- `[2,3,4,0,1]` は `2,3,4` と `0,1` の 2 塊 → 実効 2 次元 → 速い (355)
- `[2,0,3,1,4]` は隣接ペアが 1 つも残らない → 実効 5 次元 → **崖 (8)**
- `[4,3,2,1,0]` も同様 → **崖 (6)**

したがって一般則は「非連続ビューを 5 次元以上にするな」ではなく **「併合後の実効次元が 5 以上になる置換を避けろ」**。ndim だけで判断すると、実際には最速だった `[1,0,2,3,4]` まで避けることになる。落ちるのは全反転特有の現象でもない (`[2,0,3,1,4]` は全反転ではないが落ちる)。

このリポジトリの attention は `transpose(0, 2, 1, 3)` の 4 次元コピーを Q/K/V で 3 本取る。これを「`[B,T,3,H,HS]` にして 1 本にまとめる」最適化は、併合できない 5 次元の置換になるので **やってはいけない**。上表のとおり 4 次元なら置換によらず崖には落ちない。

`sum(axis: -1)` などの縮約は `reduce_kernel.h` の別機構 (`axes_are_flat` / `axes_offset`) を通るので、この定数を上げても直らない。

### 定数を 8 にしたビルドでの再測定

同じ表を `CUMO_NA_INDEXER_OPTIMIZED_NDIM 8` のビルドで取り直すと、崖は消える (dup の GB/s、2 パス)。

| ndim | 置換 | 定数 4 | 定数 8 |
|---|---|---|---|
| 5 | インタリーブ `[2,0,3,1,4]` | 8 / 8 | **413 / 378** |
| 5 | 全反転 `[4,3,2,1,0]` | 6 / 6 | **316 / 298** |
| 6 | インタリーブ `[2,0,3,1,5,4]` | 8 / 8 | **337 / 324** |
| 6 | 全反転 `[5,4,3,2,1,0]` | 6 / 6 | **307 / 301** |

連続や併合できる置換の値は変わらない (ndim4 連続が 462/487、ndim5 外側 2 つ入替が 648/586)。定数を超える次元でだけ効いていることの確認になる。

### 測るときの注意

**疑わしい測定をまとめて捨てないこと。** 最初にウォームアップ 1 回で測ったとき、同一ケースが 2 回の測定で 20 倍食い違った (636 GB/s と 31 GB/s)。それを見て表全体を JIT 汚染と判断して破棄したが、その表の中の `[2,0,3,1,4]` = 9 GB/s は **本物** で、ウォームアップ 20 回でも 8 GB/s と再現した。汚染を疑うのは正しくても、値を個別に検証せずまとめて捨てると本物を落とす。

ウォームアップは 20 回以上取り、同じ表を 2 回出して一致を確認する。プロセス起動後の最初の 1 ケースだけ 18 倍動くことも観測している。

**ウォームアップは本番と同じ配列で行う。** 小さい別配列で温めても、本番サイズの最初の 1 回が初回コストを被る。上表でもパス 1 の先頭ケースだけ他パスと 10% 以上ずれている (ndim3 連続が 446 と 499、ndim5 連続が 492 と 428)。

## 差ではなかったもの (誤って直さないよう記録)

- `min_index(axis: 1)` が平坦化した通し番号を返すのは **Numo でも同じ**。`Numo::SFloat.new(2,3).seq.min_index(axis: 1)` は `[0, 3]` を返す。Cumo 固有の挙動ではない。
- 非連続ビューを `dot` に渡しても cumo 0.5.9 では速度が落ちない。`a.dot(w.transpose)` は 10.2 TFLOP/s、連続化済みは 13.5 TFLOP/s で、cuBLAS の転置フラグが効いている。
- `M=1` と `M=256` の GEMM で結果がビット一致しないのは cuBLAS がカーネルを切り替えるためで、不具合ではない。実測で最大絶対差 1.9e-04 (相対 3.0e-06)。

## このリポジトリで入れている対処

1. デバイス上の値を Ruby の数値として使うときは必ず `NArrayLLM.scalar` を通す (`lib/narray_llm/backend.rb`)。
2. 真偽が欲しい比較は 0 次元 NArray のまま `if` や `assert_operator` に渡さない。テストヘルパの `host` を経由させる (`test/test_helper.rb`)。
3. フラグは比較ではなく `clip` + `ceil` の算術で作る (AGENTS.md の方針どおり)。

## スカラーを含む演算のカーネル起動 (cumo #287〜#292 で改善)

cumo は `a + 1.0` のようなスカラー混じりの演算で、スカラーを 0 次元 NArray に変換してから二項カーネルを起動していた。#287〜#292 でこれを数値のままカーネルへ渡す形に変えている。

同じマシン・同じスクリプトで前後を測った (`d58cf0fe` = #286 と `1b85c99b` = #292 + 未マージ 1 本、256 要素、GPU を実負荷で温めてから best-of-5)。

| 演算 | #286 | #292 以降 | 効果 |
|---|---|---|---|
| `a + 1.0` (右がスカラー) | 5.06 us | **2.43 us** | 2.1 倍 |
| `a.clip(0.0, 1.0)` (#288) | 11.21 us | **2.25 us** | **5.0 倍** |
| `a ** 2.0` (#289) | 4.28 us | **2.74 us** | 1.6 倍 |
| `0.5 * a` (**左** がスカラー) | 4.71 us | 4.97 us | 変化なし |
| `a + b` (配列同士、対照) | 2.67 us | 2.56 us | 変化なし |

`clip` が最も効くのは、境界を 2 つとも 0 次元配列にしていたぶんがそのまま消えるため。

**左オペランドがスカラーの場合 (`0.5 * a`) は効いていない。** 右の `a + 1.0` が 2.1 倍になるのと対照的で、Ruby の `Float#*` から `coerce` 経由で入る別の入口が残っているように見える。

この違いは実ワークロードにそのまま出る。生成 1 トークンあたりの内訳で layernorm は 0.864 → 0.804 ms (6.9% 改善) だが、gelu は 0.441 → 0.467 ms とほぼ横ばい。gelu のスカラー演算が `0.044715 * x`、`GELU_SCALING_FACTOR * (...)`、`0.5 * x` と **左スカラーの形に偏っている** ためで、上の表と整合する。**ただしこの内訳は `DETAIL=1` の別計測で、プロセス間の幅を測っていない。** 6.9% がその幅の外かどうかは未確定として読むこと (区間ごとに同期するぶん 1 回が長いので、上の逆比例則からすると tok/s の行より幅は狭いはずだが、確かめていない)。向きの根拠として確かなのは、左スカラーだけが取り残されるというマイクロベンチの形のほうである。

end-to-end では 64 トークン生成が 382.99 → 418.25 tok/s (9.2% 改善)、256 トークンが 372.35 → 391.52 tok/s (5.1% 改善) だった。**ただしこの 2 行も後の計測で足元が細くなった。** 同じ条件のプロセス間の幅を 7〜8 プロセスで測ると 64 トークンが 9.1%、256 トークンが 3.2% あり (後述)、9.2% と 5.1% はそれぞれ「幅とほぼ同じ」「幅の少し外」でしかない。**この節で確かなのは上のマイクロベンチ (2.1〜5.0 倍) のほうで、end-to-end の 2 行は向きの裏付けとしてだけ読むこと。**

### 左スカラーは交換すれば避けられる (可換な演算のみ)

原因は演算子ではなく `coerce` にある。`0.5 * a` は `Float#*` から `a.coerce(0.5)` を呼び、cumo の `coerce` (`ext/cumo/narray/narray.c:1337`) が `SFloat.cast(0.5)` で 0 次元配列を作る。この cast が 1 カーネル (約 2.1 us) で、`a * 0.5` にはこれが無い。0 次元配列を直接渡す `zerodim * a` は `a * b` と同速なので、演算子側は既に最適化済み。

**可換な演算 (`*` と `+`) はオペランドを入れ替えるだけで速い経路に乗る。** ただし **各二項演算を個別に交換すること。まとめて末尾へ動かすと再結合になり数値が変わる。**

```ruby
cube = 0.044715 * x * x * x   # 元: ((0.044715 * x) * x) * x
cube = x * 0.044715 * x * x   # 交換のみ: ((x * 0.044715) * x) * x   max|d| = 0.0
cube = x * x * x * 0.044715   # 再結合: ((x * x) * x) * 0.044715     max|d| = 2.4e-07
```

このリポジトリの `Ops.gelu` は 4 箇所すべてを交換した。**33.84 → 25.44 us (1.33 倍)、ビット完全一致。** 生成の内訳では gelu が 0.467 → 0.373 ms/token、end-to-end で 64 トークンが 404.21 → 423.87 tok/s (+4.9%)、256 トークンが 391.64 → 403.94 tok/s (+3.1%)。

`-` `/` `**` のような非可換な演算には使えない。このリポジトリでは `1.0 / XM::NMath.sqrt(...)` (layernorm、25 回/token) と `1.0 - ...` (one_hot、prefill で 1 回) が残った。

## 左スカラーは cumo #296 で解消した

原因は演算子ではなく `coerce` の中の `cast` だった。#296 (master `8527d4d6`) で `cast` が数値を Ruby 側に持ったまま 0 次元 NArray を返し、要素が読まれたときに初めてデバイスに載せる形になった。`binary.c` / `cond_binary.c` / `pow.c` がその値を直接使うため、coerce 経由のオペランドはデバイスに届かない。

手元で確認した (256 要素、実負荷で GPU を温めてから best-of-5、2767 MHz):

| 演算 | `8527d4d6` |
|---|---|
| `0.5 * a` (**左**) | 2.36 us |
| `a * 0.5` (右) | 2.38 us |
| `2.0 - a` (**左**) | 2.55 us |
| `1.0 / a` (**左**) | 2.63 us |
| `2.0 ** a` (**左**) | 2.41 us |
| `3 * i32` (**左**) | 2.38 us |
| `a * b` (配列同士、対照) | 2.22 us |

左右の差は消えている。`XM::SFloat.cast(1.0) / x` も 5.26 us で `1.0 / x` の 4.96 us とほぼ同じなので、明示的な `cast` も同じ経路に乗る。**このため古い挙動を同一プロセス内で再現できず、時間による A/B はビルドを入れ替えるしかない。**

これで非可換の 2 箇所も速い経路に乗った。layernorm 単体 (`[1,768]`) は 26.51 us で、含まれる中間配列は 10 本 (次節の方法で実測)。1 本あたり約 2.3 us なので、`1.0 /` の 1 本が消えたぶんは 25 回/token で約 58 us、1 トークン 2.3 ms に対して **2.5% 程度** という見積もりになる。

### 時間ではなくメモリプールの確保量で数える

余分な 0 次元配列が作られればメモリプールのビンを必ず 1 つ食うので、`XM::CUDA::MemoryPool.total_bytes` の差分を見れば **時間を測らずに中間配列の本数が数えられる**。クロックにもサーマルにも左右されないので、上の時間の表よりはるかに安定する。

```ruby
pool = XM::CUDA::MemoryPool
100.times { f.call }                                  # 先にビンを作らせる
XM::CUDA::Runtime.cudaDeviceSynchronize
pool.free_all_blocks; GC.start; pool.free_all_blocks
before = pool.total_bytes
keep = []; 100.times { keep << f.call }               # 結果を保持して回収させない
XM::CUDA::Runtime.cudaDeviceSynchronize
pool.total_bytes - before
```

**1 ケースにつき 1 プロセス** で測ること。同一プロセスで続けて測ると、先行のケースが残した空きビンが再利用されて `total_bytes` が動かない。結果を `keep` に積むのは、ループ中に GC が走って解放済みブロックが再利用されるのを防ぐため (100 回程度なら GC が走らないので積まなくても同じ値になるが、積むほうが決定的)。

**確保量は「どの中間配列が実体化されるか」だけの関数である。** ここから見える範囲が測らずに導ける。実体化される配列の並びが同じなら、**1 つ 1 つのカーネルの中身がどう変わっても確保量は動かない** — 起動本数、ループ構造、ストライド対 indexer、暗黙の同期。逆に、中間配列そのものが増減する変更 (0 次元配列の生成、式の融合による一時配列の消滅) は確実に出る。

見えない側の実例が cumo #292 (`NMath.atan2` / `hypot` / `ldexp` の INDEXER_LOOP 化) で、非連続ビューでカーネル 256 本が 1 本になり 1024² の転置で 2.06 → 0.19 ms (11 倍) 変わるのに、**確保量は前後で完全に同一** になる。追試するなら #292 より前の cumo で contiguous 対 transpose の `atan2` を 1 プロセスで回す (今のビルドでは差そのものが消えているので再現しない)。cumo 側での実測で、この 3 つはこのリポジトリでは未使用なのでこちらでは追試していない。

使い分けは次のとおり。

| 変わるもの | 見る道具 |
|---|---|
| 確保 (0 次元配列、中間配列、コピーの有無) | `MemoryPool.total_bytes` |
| 起動本数・同期 (ループ構造、ストライド vs indexer) | nsys の `cuda_gpu_kern_sum` |

前者で足りるなら常に前者がよい。クロックにもサーマルにも左右されないため。

cumo が検討しているカーネル削減の 2 案が、この境界の両側にきれいに分かれる。**「カーネル数を減らす」という同じ目的でも、効いたかどうかを見る道具は別になる。**

| 案 | 中間配列 | 見る道具 |
|---|---|---|
| 式の融合 (`a * b + c` の一時配列を消す) | 減る | `MemoryPool.total_bytes` |
| CUDA Graph (同じカーネルを同じバッファで再生) | 変わらない | 投入側の CPU 時間。起動本数すら変わらない |

`8527d4d6` での実測 (100 回、`a` は 256 要素で結果 100 個ぶんが 102,400 バイト):

| 式 | 確保量 | 結果ぶん | 余分 |
|---|---|---|---|
| `a * 0.5` (右) | 102,400 | 102,400 | **0** |
| `0.5 * a` (**左**) | 102,400 | 102,400 | **0** |
| `1.0 / a` (**左**) | 102,400 | 102,400 | **0** |
| `a.clip(0.0, 1.0)` | 102,400 | 102,400 | **0** |

左スカラーが 0 次元配列を作らなくなったことが、時間を経由せずに確認できる。#296 前は同じ計測で 153,600 バイト (0 次元配列 100 個が最小ビン 512 バイトずつ) になる — これは cumo 側の回帰テストの値で、こちらでは #296 後しか測っていない。

同じ方法で `[1,768]` の中間配列を数えると **`Ops.gelu` が 9 本、`Ops.layernorm` が 10 本** (layernorm の 17,920 バイト/回は 3,072 × 5 + 512 × 5 で、`[1,1]` の mean / variance が最小ビンに丸められたぶん)。上の 2.5% の見積もりはこの本数に基づく。

そして **`Ops.gelu` は交換済み (`x * 0.044715 * x * x`) と元の順序 (`0.044715 * x * x * x`) で確保量が完全に一致する** (どちらも 2,764,800 バイト)。「#296 以降は順序を戻しても損しない」ことの、時間に依らない裏付けになっている。

### 実ワークロードへの効果

`1b85c99b` (#292) と `8527d4d6` (#296) で生成速度を比べた。**別セッション・別ビルドをまたいだ比較で、同一セッション内の A/B ではない。** そのためプロセス間のばらつきも併記する (best-of-3 をプロセスごとに取り、3〜5 プロセス)。

| 経路 | `1b85c99b` | `8527d4d6` | 差 | プロセス間のばらつき |
|---|---|---|---|---|
| バッチ + キャッシュ、64 | 423.87 | **430.85** | +1.6% | 423.3 / 426.6 / 428.7 / 430.9 |
| バッチ + キャッシュ、256 | 403.94 | **422.85** | +4.7% | 417.7 / 422.6 / 422.9 |
| バッチ、キャッシュ無し、64 | 274.31 | **285.71** | +4.2% | 275.9 / 281.9 / 283.2 / 284.4 / 285.7 |
| バッチ、キャッシュ無し、256 | 132.88 | **133.48** | +0.5% | 132.8 / 133.5 |

**カーネル 1 本あたりの重みが大きい行ほど効き、演算量が支配する行では効かない** という向きは揃っている。キャッシュ無し 256 は毎ステップ全系列を再計算するので演算量が支配的で、カーネル 25 本ぶんは埋もれる。(なお decode 全体は起動律速ではなく帯域律速であることが後で分かった。`results/gpt2-124m.md` の nsys 実測を参照。消えた 25 本は投入時間だけでなく GPU カーネルそのものも減らしている。)

**ただし、この表の「差」の列は後の計測で足元が崩れた。** 上のばらつきは 3〜5 プロセスから見積もったものだが、後日 `07f0af91` で条件ごとに 7〜8 プロセス測り直したところ、幅は条件により **0.4〜9.1%** あった (さらに 0.5.10 で 8 プロセス測り直すと 1.2〜10.5% で、条件ごとの順位も入れ替わった)。同じ機械・同じ条件なので、この幅は上の表にもそのまま当てはまると見るべきである。2 度の計測で条件ごとに大きいほうの幅を取ると、**4 行のうち 3 行 (+1.6% 対 9.1%、+4.2% 対 10.5%、+0.5% 対 1.2%) は幅の内側に埋もれる**。残る 1 行 (+4.7% 対 3.2〜3.5%) もかろうじて外に出ている程度でしかない。**#296 の効果を tokens/sec で主張するのは無理があった。** この節で確かなのは回数で数えた事実 (`new_dim0` のカーネルと確保が消えたこと) のほうで、上の表は「少なくとも遅くなってはいない」以上を読まないこと。

なお `CACHE=0 --length 64` で一度だけ 161.85 tok/s (通常の 0.59 倍) を観測した。同じ条件で 5 回続けても再現せず (0.224〜0.234 s)、原因は特定できていない。単発測定を信じてはいけない例として記録しておく。

## 添字が確保していないインデックス配列を解放していた (cumo #297)

`results/gpt2-124m.md` の nsys 計測で `cudaFree` が **172 回/token** 出ていた。確保側の `cudaMallocManaged` は差が 0 で、**解放だけ 172 回・確保 0 回** という辻褄の合わない形だった。中央値も 124 ns (min 105) と、本物のチャンク返却 (cumo 側の実測で 1,689 ns) より 1 桁速い。`cudaFree(NULL)` の早期 return ではないか、という疑いとして cumo 側に投げた。

原因は `ext/cumo/narray/index.c:922` の `cumo_na_aref_md_ensure` が、**添字の全次元を NULL チェック無しで解放関数に渡していた** こと。範囲・ステップ・スカラー・`true` の添字はインデックス配列を確保しないので `idx` は NULL のままで、`cudaFree(NULL)` に落ちていた。sonots/cumo#297 で修正済み。

こちら側の呼び出し回数を Ruby で数えると、**nsys の 172 と完全に一致する**。

| 場所 | 種類 | 回数/token | 次元/token |
|---|---|---|---|
| `kv_cache.rb:78` (`view`) | `[]` | 24 | 48 |
| `kv_cache.rb:62` / `:63` (`append`) | `[]=` | 24 | 48 |
| `model.rb:127` / `:128` / `:131` (qkv の分割) | `[]` | 36 | 72 |
| `model.rb:119` (`wte` / `wpe`) | `[]` | 2 | 4 |
| **合計** | | **86** | **172** |

`[]=` も同じ経路を通るので数に入る (`cumo_na_aset` も `cumo_na_aref_md` を経由する。cumo 側の A/B で `a[true, 0...32] = b` 100 回が 200 → 0 回)。**1 添字の次元数ぶんだけ `cudaFree(NULL)` が出る** という対応がそのまま出ている。

見込みは 172 × 124 ns = **21 us/token (トークンの 0.9%)**。CPU が busy な時間 1.92 ms に対して 1.1% で、**こちらの end-to-end の再現性 (プロセス間 ±0.9%) と同じ桁** なので、生成速度では判別できない見込み。効果を測るなら `qkv[true, C...2C]` 単体のマイクロベンチのほうが分解能が出る (cumo 側の実測で添字 1 回が 1.8〜2.3 倍)。

### 測り直した結果 (`07f0af91`)

master に入った `07f0af91` を clean ビルドして測り直した。**`cudaFree` は 172 回/token から 0 回/token になった。**

| | `8527d4d6` | `07f0af91` |
|---|---|---|
| `cudaFree` の回数/token | 172 | **0** |
| `cudaFree` の時間/token | 22.5 us | **0** |
| CUDA API 呼び出しの回数/token | 1625 | **1453** (ちょうど −172) |
| `cudaLaunchKernel` の回数/token | 677 | 677 |
| `cudaDeviceSynchronize` の回数/token | 1 | 1 |
| カーネルの本数/token | 677 | 677 |

残る `cudaFree` は `--length 40` と `--length 8` の両方に 1 回ずつ出る一度きりの呼び出しで、差分では相殺される。カーネルは 1 本も減っていない。#297 が削るのは CPU 側の API 呼び出しであって、GPU の仕事ではないからである。

**そして見込みどおり、生成速度では判別できなかった。** 4 条件の tokens/sec は `8527d4d6` に対して +1.9% / +0.8% / −1.8% / −0.1% と **符号が揃わず**、いずれも今回のプロセス間のばらつき (条件により 0.4〜9.1%) の内側だった。同じ 2 回の nsys 走行のあいだで `cudaLaunchKernel` の行が 1.364 → 1.431 ms と 0.067 ms 動いており、**削れた 0.022 ms はそこに埋もれる**。

したがって #297 について書けるのは次の 2 つに限る。**`cudaFree` の回数が 172 → 0 になったという離散的な事実** と、**添字単体の 1.8〜2.3 倍** (cumo 側の実測)。実ワークロードの tokens/sec は #297 の効果の証拠にならない。上の「ばらつきと同じ桁なので判別できない」という事前の予想は、測り直しても変える必要が無かった。

リリースされた 0.5.10 でもう一度確かめた。`cudaFree` は nsys の `cuda_api_sum` に **行として現れない**。tokens/sec は `07f0af91` との差が中央値で +0.07〜+1.0% で、やはり幅の内側だった。

**そのときのプロセス間の幅は 1.2〜10.5% で、上に書いた 0.4〜9.1% と条件ごとの順位すら入れ替わっていた。** 同じ機械・同じビルド・同じ手順である。幅は毎回測り直すものであって、前回の値を持ち回ってよい定数ではない。

### 交換の書き換えは元に戻した

#296 以降は `x * 0.5` と `0.5 * x` が同速なので、**性能上は元の数式どおりの順序に戻してよい**。それが 0.5.10 でリリースされたので、`Ops.gelu` と `Ops.causal_mask` を llm.c と同じ並び (`0.5 * x * (1.0 + tanh(...))`、`MASK_VALUE * (...)`) に戻した。

戻す前に 2 つ確かめてある。

- **ビット同一。** 交換したのは 1 つの演算子の左右だけで、結合は変えていない (`x * 0.044715 * x * x` → `0.044715 * x * x * x` は最初の乗算だけを入れ替えたもの)。4096 点の入力で `to_binary` を突き合わせ、Numo でも Cumo でも完全一致した。**`x * x * x * 0.044715` のような結合の変更なら丸めが変わる。**
- **カーネルが増えていない。** nsys で decode 1 トークンあたり 677 本、CUDA API 1453 回で、書き換え前と 1 つも違わない。

**0.5.10 未満の cumo で動かすと、この書き換えの分だけ遅くなる。** 左スカラーが 1 演算あたり 1 カーネル余分に走るため。

## 0.6.0 (#335〜#364) は縮約と要素演算を速くした

**0.5.11 までと違い、この版はこのワークロードの通る経路に入っている。**#347 が連続軸の縮約に連続したスレッド群を割り当て、#350 が縮約のオペランドをローカルメモリから追い出して短い strided 行のスレッドあたり要素数を増やし、#351 が要素演算を「書き込む側のオペランドのメモリに沿って」歩くようにした。decode の 628 本はまさに要素演算と縮約なので、ここは効く側である。

0.5.11 と同一セッション内でインターリーブし、4 条件それぞれ 10 プロセスずつ測った (詳しい表は results/gpt2-124m.md)。

単体でも同じものが出る。`[256,768]` の `sum(axis: 1)` が 4.27 / 4.29 → 2.95 / 2.51 us と 1.5〜1.7 倍になり、`a + b` (256 要素) は 2.23〜2.65 対 2.59〜2.61 us で変わらない。**縮約と、行の長い要素演算が速くなった** という切り分けになる。

**キャッシュ有りの 1.9% は、このトレースでは説明が付かない。** decode は 1 トークンあたり 677 カーネル・1453 API で回数が完全に一致し、`cudaLaunchKernel` は 1.357 対 1.356 ms、GPU 時間はむしろ 1.901 → 1.866 ms と縮む (628 本の要素演算・縮約が 0.633 → 0.597 ms)。それでも wall は 1 トークンあたり 0.045 ms 増える。**残差はホスト側の時間で、CUDA API を通らないのでこのトレースには現れない。** decode は CPU と GPU がほぼ釣り合う点にいるので、ホスト側が伸びればそのまま wall に出る。特定するには CPU 側のサンプリングが要る。

**数値の互換性は保たれている。** GPU テスト 123 件がすべて通り、生成トークン列は Numo の正解列に対して 64 / 256 トークン × KV キャッシュ有無の 4 通りで完全一致した。このファイルが挙げている挙動 (`x[0].class` から `Integer(a.max_index)` まで) も 0.6.0 で変わっていない。#341 で `extract` が 0 次元 Bit を返すようになったが、上の表と対処の記述はそのまま成立する。

## 0.7.0 (#365〜#422) は転置コピーを速くした

0.6.0 の 56 コミット後。**このワークロードが通るのは 2 か所だけで、どちらも decode には出ない。**

1. **2 次元の転置ビューのコピー (#415)。**`Ops.contiguous(w.transpose)` がこれで、モデル読み込みでちょうど 49 回通る (層ごとの重み 4 本 × 12 層と `wte_t`)。`[768,50257]` の実測で、書き込み先を使い回せばペア比 0.599 (0.483〜0.727、8/8) で **連続コピーと同じ帯域に届く** (373〜460 対 387〜475 GB/s。0.6.0 は 180〜283)。同じ設計で測った連続コピーが 1.002 (3/8) と動かないのが対照になる。`Ops.contiguous` のように毎回 `zeros` を確保する形だと、確保と managed の初回タッチに削られて 0.648 (8/8) になる。nsys には `store_sfloat_transpose_kernel` という新しい行が 49 本ちょうど出て、0.6.0 で同じ 49 本を含んでいた `store_sfloat_kernel_dim2` が 1729 → 1680 本になる。**それでも読み込みの wall は 0.409 対 0.408 s で動かない。** 410 ms のうち転置は数 ms で、残りはディスクとホストからの転送だからである。
2. **`Cumo::HFloat` (#365〜#371)。** これで fp16 が released の gem で測れるようになった (下記)。

**decode は 0.6.0 と区別が付かない。** 1 トークンあたり 677 カーネル・1453 API で行ごとに一致し、tokens/sec もペア比の範囲が 1 をまたぐ (4 条件 × 10 プロセス、詳しくは results/gpt2-124m.md)。要素演算の転置タイル (#416) は 32 未満の辺を除外するので、decode の `[12, t]` と `[t, 12]` には乗らない。

**破壊的変更はどれも踏まない。**`narray.h` の構造体変更 (#421) は cumo に対してコンパイルする拡張の話で、`gemm` の `RangeError` (#399) は 1 行列 2^31 要素からなので最大の `[768, 50257]` (3,860 万要素) でも遠い。`store_binary` が非連続ビューを拒否する件 (#389) と `to_binary` が型基準になった件 (#393) は、このリポジトリが `from_binary` しか使わないので関係しない。`Int8.upcast(UInt8)` (#378) も Bit の修正 (#380 #396 #401) も通らない。GPU テスト 123 件が通り、生成トークン列は 4 通りとも完全一致する。

## `cumsum` はホストへ同期する (2026-09-20、cumo 0.9.0 + master)

**cumo 自身が `FIXME` と書いている。**

```
Warning: FIXME: Method "cumsum" for dtype "sfloat" synchronizes with CPU.
```

`CUMO_SHOW_WARNING=ON` で見える。**`max(axis:)` も `clip` も `ceil` も警告を出さないので、同期するのは `cumsum` だけである。**

**境目は 8192 要素。**`ext/cumo/narray/gen/tmpl/cum.c:22` が `i >= CUMO_CUM_MIN_KERNEL_SIZE` ならカーネルを起動し、**それ未満はデバイス全体を同期してからホストのループに落ちる**。定数は `ext/cumo/include/cumo/template.h:74` で 8192 (cumo 側が機構を示し、こちらでソースと実測の両方で確かめた)。

```
n=8191  Warning: FIXME: Method "cumsum" ... synchronizes with CPU.
n=8192  警告なし
n=8193  警告なし
```

**8192 という値の根拠は、cumo 側も測っていないとのことである。**

**踏んだ場所。** Switch Transformer の MoE で、同点の expert を 1 つに絞る走査に使った。**その経路は「デバイスから出ない」ことを目的にしていた** ので、疎な層ごとに 1 回、1 トークンあたり 6 回の同期が増えて台無しになっていた。

**回避できる。** 走る向きが短い (expert 8 個) 場合は、**厳密下三角のブロックとの行列積** が同じ値を出す。`before[k, j]` を `k < j` で 1 にすると `x.dot(before)` が各列より前の合計になる。

```ruby
i = XF.new(size, 1).seq
j = XF.new(1, size).seq
before = (j - i).clip(0.0, 1.0).ceil
```

**カーネル数は変わらなかった** (どちらも 2121 本/token)。**置き換えで wall が 6.4% 動いた** (ペア比 1.064、10 ラウンド、対照はまたぐ)。

**ただしそれは同期の値段ではない。** 当初ここには「同期 1 回が約 74 us」と書いたが、**取り下げた**。三角行列版に **同じ場所で `cudaDeviceSynchronize` を 6 回呼ぶだけ** の対照を作ったところ、**1.007 (0.995〜1.033) で 1 をまたいだ**。**同期そのものはこの地点では測れる大きさではない。**

**残りの内訳は未分離である。**`cum.c` は同期のあと **ホスト側でループを回す** ので managed メモリを 1 要素ずつ触ることになり、そこが候補ではあるが、**測っていない**。**カーネル数と出力が同じでも、違いが同期だけとは限らない。** 詳細は [results/switch-base-8.md](results/switch-base-8.md)。

## NArray を添字にした gather は 0.9.0 でも同期する (2026-09-19)

`docs/idea.md` が MoE を外していた理由がこれで、**#470 が範囲検査をデバイス側に移したあとも警告は出る**。

```
Ruby Array 添字   警告なし
NArray 添字       Warning: Method "cumo_na_parse_narray_index" ... synchronizes with CPU.
```

**Switch の実装はこの経路を通らない。** expert 番号を **ホストに読み戻してから Ruby の Array で添字にする** ので、同期は疎な層ごとに 1 回で済み、そのあとの gather と scatter は同期しない。**デバイス上に添字を置いたまま引く経路は、依然として踏んでいない。**

## Cumo::HFloat (fp16) で踏むもの

`Cumo::HFloat` は **0.7.0 (#365〜#371) で入った** 16 ビット浮動小数点。このリポジトリの実装は fp32 のままだが、計測対象には含めている (結果は results/gpt2-124m.md)。挙動として引っかかるのは次の 3 つ。

### 縮約は fp32 で畳むが、答えは fp16 に丸めて返る

`sum` / `mean` / `var` / `stddev` / `rms` / `mulsum` / `dot` / `gemm` / `cumsum` は fp32 で累算してから最後に 1 度だけ丸める。40000 要素の総和が正確に出るのはこのためである。**ただし守られているのは累算であって答えではない。**

```ruby
x = Cumo::HFloat[2000.0, -2000.0, 1000.0, -1000.0]
x.var      # => Infinity   (真の値 3.33e6 が fp16 に入らない)
x.stddev   # => 1826.0     (正しい。sqrt してから丸めるので入る)
```

`prod` / `cumprod` は意図的に広げない。

### var は不偏 (n-1)

numo の定義をそのまま継いでいるので SFloat / DFloat でも同じで、fp16 固有の話ではない。layernorm が使うのは母分散なので `(n-1)/n` を掛ける。

### 整数が正確なのは 2048 まで

トークン id を fp16 の配列に入れてはいけない。

```ruby
Cumo::HFloat.cast([2048.0, 2049.0, 50257.0]).to_a   # => [2048.0, 2048.0, 50272.0]
```

このリポジトリは埋め込みを one-hot の GEMM で書いている (gather が同期するため。AGENTS.md)。その one-hot は **`SFloat` で作ってから cast する** 必要がある。`50257` 幅の `seq` を fp16 で作ると 32 刻みに飛んで、一致判定が壊れる。

同じ理由で、因果マスクの `-1.0e9` は fp16 で `-Infinity` になるので置き換える。`-1.0e4` で足りる (fp16 の `exp` はそこへ行く前に 0 に落ちる)。

## encode で PyTorch が 15.3% 速い。出どころは未分離 (2026-09-20)

Whisper tiny の encode (1500 位置、217 本/回) で、**PyTorch がこちらの Cumo 実装より 15.3% 速い** (ペア比 1.153、1.150〜1.163、10 ラウンド 10/10、対照は 1 をまたぐ)。詳細と条件は [results/whisper-tiny.md](results/whisper-tiny.md)。

**これは「Python が速い」ではない。** 同じ表で **Cumo は CuPy に 27.6% 勝っている** (1.276、10/10)。**PyTorch だけが速い。**

**3 実装とも畳み込みを行列積で書いてある。** PyTorch 側も `F.conv1d` ではないので **cuDNN は経由しない**。**同じ形の GEMM を cuBLAS に渡していることになる。**

### 前提は測った。GEMM の本数も形も 3 実装で同じである

候補を並べる前に「3 実装とも同じ形の GEMM を cuBLAS に渡している」という前提を検査した。**それまでこれはコードを読んだだけの記述だった。** nsys で encode 1 回あたりの本数を差分法で出す (`--inner 20` と `--inner 10` の差 ÷ (repeat 3 x 10) = 30 encode)。

| 実装 | GEMM | GEMM 以外 | 合計 |
|---|---|---|---|
| **Cumo** | **78** | 139 | **217** |
| **CuPy** | **78** | 330 | 408 |
| **PyTorch** | **78** | **99** | **177** |

**3 実装とも GEMM は 1 encode あたり 78 本で、完全に一致する。** **PyTorch は融合していない。**

**Cumo と PyTorch は cutlass のタイルと grid まで同一だった。**

| 本/encode | grid | block | kernel |
|---|---|---|---|
| 24 | 192x2x1 | 128x1x1 | `sgemm_128x64_8x5_tn_align1` |
| 24 | 24x1x9 | 128x1x1 | `sgemm_64x64_8x5_nn_align1` |
| 30 | 96x1x3 / 192x2x3 / 188x1x1 | 128x1x1 | `sgemm_128x64_8x5_nn_align1` |

**CuPy だけ 30 本の内訳が違う** (27 本が `nn`、3 本が `nt_align1`)。転置の向きが 1 か所違う。

**cutlass のタイル選択は形に依存するので、同じタイル・同じ grid が出たことは「同じ形を渡している」ことの傍証になる。** ただし **傍証であって、形そのものを読み出したわけではない。**

**この前提が生きているので、候補①〜④は意味を保つ。** 崩れていたら (PyTorch のほうが GEMM が少なければ) 比較の土俵が別になっていた。

### GEMM の時間は区別できない。GEMM 以外は区別できる

**同じ profile から GPU 時間も差分で出せる。** ただし **時間は 1 本の profile では決まらない** (計測の作法 9) ので、**3 組取った**。

| 実装 | 組 | GEMM 本 | GEMM ms | 他 本 | 他 ms | 合計 ms |
|---|---|---|---|---|---|---|
| **Cumo** | a | 78 | **5.048** | 139 | 1.453 | 6.501 |
| **Cumo** | b | 78 | 4.381 | 139 | 1.646 | 6.027 |
| **Cumo** | c | 78 | **4.172** | 139 | 1.706 | 5.877 |
| **PyTorch** | a | 78 | 4.183 | 99 | 1.078 | 5.261 |
| **PyTorch** | b | 78 | 4.162 | 99 | 0.842 | 5.003 |
| **PyTorch** | c | 78 | 4.137 | 99 | 0.891 | 5.028 |
| CuPy | a / b / c | 78 | 4.729 / 4.426 / 4.191 | 330 | 3.087 / 3.336 / 3.068 | 7.816 / 7.762 / 7.259 |

| | Cumo の幅 | PyTorch の幅 | Cumo / PyTorch |
|---|---|---|---|
| **GEMM** | **21.0%** | 1.1% | **0.997〜1.220 (1 をまたぐ)** |
| **GEMM 以外** | 17.4% | 28.0% | **1.348〜2.027 (またがない)** |
| 合計 | 10.6% | 5.1% | 1.117〜1.299 (またがない) |

**1 組目だけを見ると「GEMM が 21% 遅い」と読めた** (5.048 対 4.183)。**3 組取ったら Cumo の GEMM 時間そのものが 21% 動き、3 組目は PyTorch と同じ値になった** (4.172 対 4.137)。**ペア比が 1 をまたぐので、GEMM の時間は区別できない。**

**Cumo の 1 組目は、その日の最初に取った profile である。** 位置で説明が付きそうだが、**そう決めたわけではない** (組は 3 つしかない)。

**本数は 3 組とも 1 本も動かなかった** (78 / 139 / 99)。作法 9 の「回数は動かないが時間は動く」がそのまま出た。

**GEMM 以外は 3 組とも重ならない** (Cumo 1.453〜1.706、PyTorch 0.842〜1.078)。**合計も重ならず 1.117〜1.299** で、wall の 1.153 と向きも大きさも矛盾しない。

**ただしこれは nsys の duration であって、wall の仕事とは限らない** (作法 9)。**その演算を消して wall が動くまでは、15.3% をここに帰属させない。**

### 本数で見えるのは GEMM 以外のほうである

**GEMM が同数なのに、GEMM 以外は Cumo 139 対 PyTorch 99 で、1 encode あたり 40 本違う。**

**この 40 本が 15.3% の出どころだとは言えない。** 本数と時間は別で、**その演算を消して wall が動くまで行の時間は信じない** (計測の作法 9)。**時間の帰属は未分離である。** 上の表で GEMM 以外の GPU 時間が 3 組とも重ならなかったが、**それも nsys の duration であって wall ではない。**

**本数の内部検査。** Cumo の合計 217 本は、別に測ってあった値 (docs/results/whisper-tiny.md の「本数と時間」) と一致する。差分法の分母が正しいことは、**3 実装とも本数が整数で出たこと** でも確かめられる。

### 候補 (すべて未計測)

**どこから来るかは分けていない。** cumo セッションがソースを読んで候補を 4 つ挙げたが、**4 つとも未計測である**。

| | 候補 | 状態 |
|---|---|---|
| ① | cumo は 2 次元 1 本の行列積でも `gemmStridedBatched` を通す (`gen/tmpl/gemm.c`)。batch=1 でも同じ道 | **未計測**。素の `cublasSgemm` と同じ速さかを測っていない |
| ② | PyTorch は cuBLASLt のヒューリスティクスを使うが、cumo は `CUBLAS_GEMM_DEFAULT` 固定 | **未計測** |
| ③ | 呼び出しごとのホスト側の費用 (レイアウト判定・連続性検査) | **未計測** |
| ④ | ワークスペースやハンドルの設定 | **未計測** |

**①と②は単体の土俵で分けられる** ので cumo 側で測る。**このワークロードで測る話ではない。**

**Mamba の 10 点の表とは別の形である。** あちらは全部が投入律速の帯にいて「本数が減れば速くなる」で説明が付いた。**encode はそもそも本数の話ではない。** 同じ Whisper の decode (341 本/位置、投入が支配) では Cumo が PyTorch を 5.4% 上回る。**同じモデルの中で向きが割れる。**

## `MemoryPool.used_bytes` は GC の前に読むと多く出る (2026-09-20)

**参照が切れていても、Ruby の GC がまだ回収していないブロックは「使用中」に数えられる。** Whisper tiny の重みを読んだ直後に `Cumo::CUDA::MemoryPool.used_bytes` を読むと **294.9 MiB**、`GC.start` を挟むと **218.9 MiB** になった。**差の 76 MiB は転置の元になった中間である。**

**これを「余分な写しを持っている」と読みかけた。** 同じモデルの埋め込みが `[51865, 384]` = 76.0 MiB なので、**算術がぴったり合ってしまう**。原因は違った。

**cumo のプールを測るなら、読む前に GC を回すこと。** CuPy の `used_bytes()` や PyTorch の `memory_allocated()` は参照カウントで即座に返るので、**同じ名前でも意味が違う。**

**`total_bytes` は GC に依存しない。** 別セッションの指摘で、手元でも確かめた。

```
keep のみ                   used 16.0 MB   total 16.0 MB
中間 2 本、参照を切った直後  used 48.0 MB   total 48.0 MB
GC.start の後               used 16.0 MB   total 48.0 MB   <- used だけ動く
free_all_blocks の後        used 16.0 MB   total 16.0 MB
```

**ただし 2 つは別の問いに答える。**`total_bytes` は **プールがドライバから取った量** で、`free_all_blocks` まで返らない。`used_bytes` は **いま参照されている量** のつもりだが、Ruby の GC が挟まるので **そのままでは意図どおりに読めない**。

- **生きているテンソルが何バイトか** を知りたいなら `GC.start` してから `used_bytes`
- **プールがカードからいくら取っているか** を知りたいなら `total_bytes` (GC は不要)

**そして `nvidia-smi` の per-process 値とプールの値は別物である。** **cumo は `cudaMallocManaged` で確保する** (`ext/cumo/cuda/memory_pool.cpp:73`)。managed メモリはホストにも居られるので、**`nvidia-smi` はデバイス常駐ぶんしか数えない**。同じ走行でプール 418.8 MiB に対し、外からは 222 MiB に見えた。**CuPy (536 MiB) や PyTorch (510 MiB) と並べて「cumo が省メモリ」と読んではいけない。** テンソルの実量は 3 実装ともほぼ同じ (218.9 / 222.7 / 223.2 MiB)。

7 ワークロード x 3 条件 (0.10.0 / master / 対照 = master をもう一度)、10 ラウンド。**比は 7 つとも 1 をまたいだが、符号検定で 2 つが偏った** ので、2 つだけ 24 ラウンドで取り直した。

| | master / 0.10.0 | 1 未満 | 両側 p | 対照 (master / master) |
|---|---|---|---|---|
| **Mamba** (24 ラウンド) | **1.0194** (0.9926〜1.0424) | 3/24 | **2.8e-04** | 12/24、p = 1 |

**もう一方の master の腕と 0.10.0 の比も同じ向き** (Mamba 24/24、Switch 21/24) なので、**2 つのビルドの差としては本物である。**

**ところが #532 からは出ない。** Mamba の +1.9% は予算の 100 倍以上ある。**Switch は 1 トークンあたり 5535 本のカーネルを、名前ごとに同じ本数だけ走らせている** (nsys の差分法)。

**比べた 2 つは #532 以外にも違う可能性がある。** 0.10.0 は `gem install`、master は `rake compile` でビルドしたもので、**GPU 向けのコードはどちらも sm_120 の 20 本で PTX なし** である。**当初ここには「ホスト側のコンパイル設定は gem のログに残っていなかった」と書いたが、誤りだった。** 行頭に色のエスケープが付いていて `^gcc` で拾えなかっただけで、**数えると 3 つのビルドとも `-O3 -fno-fast-math` と `-ggdb3` で同じ** だった (別セッションの指摘)。

### 同じ作り方のビルドを並べると、2 本は別の原因だった

**別セッションが v0.10.0 を master と同じ `rake compile` で別の worktree にビルドした。** 4 条件 (gem の 0.10.0 / rake の 0.10.0 / master / 対照 = master をもう一度)、**25 ラウンドの先頭を捨てて 24**。3 つの `.so` は `nm -D` の `fill_stridx_kernel_launch` の数 (0 / 0 / 14) とファイルサイズで取り違えていないことを確かめた。

| | **rake 0.10.0 / gem 0.10.0** (作り方だけ違う) | **master / rake 0.10.0** (#532 だけ違う) | 対照 (master / master) |
|---|---|---|---|
| **Mamba** | 0.9971 (16/24 が 1 未満)、p = 0.15 (**差なし**) | **1.0244** (1/24 が 1 未満)、**p = 3.0e-06** | 0.9970 (14/24)、p = 0.54 |
| **Switch** | **0.9898** (20/24 が 1 未満)、**p = 0.0015** | 0.9926 (16/24 が 1 未満)、p = 0.15 (**差なし**) | 0.9994 (12/24)、p = 1 |

**Switch の −1.6% はソースではなく、作り方の違いだった。** 同じ v0.10.0 のソース、同じ最適化設定でも、gem と rake のバイナリで 1% 動く。

**Mamba の +2.4% はソースの側についてくる。ところが #532 のコードは Mamba のループを通らない。**

- nsys の差分法で、**1 トークンあたり 1114 本のカーネルが、名前ごとに同じ本数**。**`fill` もスカラーの `store` (`new_dim0`) も 1 トークンあたり 0 本** で、#532 が変えた `fill.c`、`fill_kernel.cu`、`store_numeric.c` はループの中で呼ばれていない
- 70 トークンの区間で、**GPU が動いていた時間は 202.62 ms 対 202.21 ms (0.2% 差)**、全体は 424.93 ms 対 411.23 ms。**縮んだのは GPU が待たされている時間だけ** で、差はホスト側にある (nsys 自身が投入を遅くするので使用率 48% は実際より低いが、2 本は同じ条件である)

**最も整合するのは、ソースが変わったことでバイナリの配置が変わり、ホスト側の速さが動いた、という読みである。** **Mamba (1114 本 / token) と Switch (5535 本 / token) は、この中でいちばん投入の多い 2 つ** で、ホスト側の差がいちばん出やすい。**ただしバイナリの配置を直接いじって確かめてはいないので、機構としては書かない** (計測の作法 18)。**#532 がこのリポジトリを速くしたとは言えない。**
