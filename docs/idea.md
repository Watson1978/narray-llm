# アイディア

次に何を作るかの検討メモ。**選ぶ基準は「Numo / Cumo の踏んでいない経路を増やすこと」** で、モデルとして有名かどうかではない。

**モデルとは限らない。** バッチ生成のように、既にあるモデルに足すほうが安く広く踏めることがある。下の「モデル以外の候補」がそれで、**新しい重みも新しい参照実装も要らないぶん着手が軽い**。

このファイルは決定ではなく候補の記録である。**未確認のものは未確認と書いてある。**

## いま踏んでいるもの

2 モデルで既に踏んでいるので、これらを増やしても範囲は広がらない。

| | GPT-2 124M | Llama 2 110M |
|---|---|---|
| 正規化 | LayerNorm | RMSNorm |
| 活性 | GELU (tanh 近似) | SwiGLU (SiLU) |
| 位置 | 学習済み埋め込み | RoPE |
| attention | MHA、QKV 融合 | GQA (stories260K は `num_heads` 8 / `num_kv_heads` 4) |
| 語彙 | 50257、埋め込みを共有 | 32000、`wcls` が別 |
| dtype | fp32 / fp16 (`DTYPE=fp16`) | 同左 |

共通して踏んでいるもの: 要素演算、縮約、GEMM / gemv、転置コピー、softmax、因果マスク、KV キャッシュ、添字 gather。

## 選ぶときの分かれ目: 参照値をどこから取るか

**このリポジトリの受け入れ条件は「トークン列の完全一致」** である。それを保つなら参照実装が要る。

| 方針 | 受け入れ条件 | 選べるモデル |
|---|---|---|
| **単一ファイルの C 参照があるものだけ** | いまと同じバイト一致がそのまま使える | 少ない (下記の int8 と Mamba) |
| **PyTorch を参照値にしてよい** | 条件を作り直す必要がある | 多い ([OpenArch](https://github.com/anuj0456/OpenArch) の 18 種から選べる) |

`python/gpt2_torch.py` は既に PyTorch を参照点として使っているので、後者も前例はある。ただし **いまのバイト一致の強さは失われる**。

## 候補 1: int8 量子化 (推奨) — **実装した**

**2026-09-18 に実装し、測った。結果は [results/llama2-int8.md](results/llama2-int8.md) にある。** 以下はその前に書いた検討で、**「未確認」としていたものは全部埋まった**。要点だけ先に書くと、**動くが stories110M で 1.7 倍遅い**。当初は 4.1 倍で、`mulsum` が重みを行列積のたびに fp32 へ実体化するのと、量子化が 9 本のカーネルに散るのが原因だった。**cumo #477 と #476 で両方が埋まり、1 トークンあたり 1569 → 889 本になった** (測ったときは master 直、0.9.0 で released に入った)。**int32 での畳み込みは要らなかった** (部分和が fp32 の厳密表現の内側に収まる)。


参照は [`karpathy/llama2.c` の `runq.c`](https://github.com/karpathy/llama2.c/blob/master/runq.c)。**いま vendoring している `run.c` と同じリポジトリにある。**

### 新しく踏むもの

- **整数 dtype**。`Int8` の store / cast / broadcast。**cumo で最も手薄な経路** で、`div` / `mod` がスカラー除数でも全体同期する不具合 (cumo #466) がそのまま残っていたのが証拠である
- **int32 での畳み込み**。`int32_t ival = 0;` に int8 同士の積を積む
- **グループごとのスケール**。`w->s[(in + j) / GS] * x->s[j / GS]` の形で、`[n, GS]` に reshape して `[n, 1]` を掛ける broadcast になる
- **活性も量子化する。** 重みを戻すだけではなく、matmul のたびに活性をグループごとに量子化する (絶対値の最大を採って割って丸めて `[-127, 127]` に clip)。`round` と整数 clip と縮約が要る

### 実装コスト: 小

**Llama 2 の本体・トークナイザ・KV キャッシュ・生成ループ・テストがそのまま使える。** 新しく書くのはチェックポイントのローダと matmul だけで、そこがちょうど新しいカバー範囲にあたる。

### 形式 (2026-09-18 に `runq.c` の現物で確認)

- マジック `0x616b3432` (`"ak42"`)、**バージョン 2**、ヘッダは **256 バイト**
- **RMSNorm の 1 次元の重みは fp32 のまま。** attention と FFN の行列が int8
- `QuantizedTensor` は `int8_t* q` と `float* s` の 2 本。`s` はグループごとに 1 つ

### 前提と未確認

- **version 2 の別チェックポイントが要る。** 手元の `stories110M.bin` は version 1 なので使えない
- `export.py --version 2` を PyTorch の `.pt` に対して回す。**`stories110M.pt` が `karpathy/tinyllamas` にあることは確認した** が、**量子化済みの配布があるかは未確認**
- **開いた設計問題が 1 つある。** バイト一致を保つなら int32 で畳む必要があるが、**それを NArray でどう書くか** は決めていない。先に fp32 へ戻してから GEMM すると丸めが変わるので `runq.c` と一致しない。cumo の gemm が `Int8` を受けるかも未確認

### つながり

fp16 で見つかったメモリプールの問題 (`CompactIndex` が O(空きチャンク数)) が **要素バイト数で決まるのか** を、さらに半分の int8 で試せる。

## 候補 2: Mamba — **着手した**

**プランは [PLAN-mamba.md](plans/PLAN-mamba.md) にある。** 以下はその前に書いた検討で、取り消し線は読んで覆ったもの。

参照は [`kroggen/mamba.c`](https://github.com/kroggen/mamba.c)。llama2.c から派生した単一ファイルの C 実装で、Mamba / Mamba2 / Mamba3 に対応する (**版ごとに別ブランチ** で、既定は `learning` = Mamba 1)。

### 新しく踏むもの

- **attention が無い。** 選択的スキャンによる逐次処理で、**このプロジェクトが測り続けてきた「起動の固定費」に最も厳しい形** になる
- ~~**conv1d (depthwise)**。cumo の `conv.c` / cuDNN 経路は **まだ一度も踏んでいない**~~ — **参照実装を読んだら違った。**`mamba.c` の depthwise conv は手書きのリングバッファで、`conv_state * conv1d_weight` を最後の軸で畳むだけである。**この参照を追うかぎり cuDNN には触らない**
- **要素演算のブロードキャストが最内軸** (`dA[i][j] = dt[i] * A[i][j]`)。cumo #475 が `mulsum` で直したのと同じ向きを、**要素演算で踏むのは初めて**
- 状態の更新が `[d_inner, d_state]` でトークンごとに進む

### 実装コスト: 大

**モデル・ローダ・トークナイザすべてが新規。** Llama 2 から流用できるのは生成ループと KV キャッシュの外側だけで、KV キャッシュ自体は使わない。

### 未確認

- ~~チェックポイントとトークナイザの形式~~ — **両方とも読んで [PLAN-mamba.md](plans/PLAN-mamba.md) に書いた。** チェックポイントは `"Mamb"` + 256 バイトヘッダ + 整数 8 個、トークナイザは `"MbTk"` で **スコアが無い** ぶん llama2.c より単純
- mamba-130m が llama-110m と同程度の速さという記述は **二次情報** (README の要約) で、現物では確認していない
- **公式の最小が 130m しかない。** stories260K に当たるものが無いので、テストを速く回すには乱数の小さいチェックポイントを自分で書くことになる

## 候補 3: MLA (DeepSeek) — **保留** (2026-09-20)

**KV キャッシュを低ランクに圧縮する。** このプロジェクトの KV キャッシュ周りが根本的に変わるので、そこは新しい検証になる。

[OpenArch](https://github.com/anuj0456/OpenArch) に PyTorch の実装がある。**ただし小さい重みと C の参照があるかは未確認。** 無ければ PyTorch を参照値にする方針に切り替えることになる。**動くチェックポイントが見つかるか怪しいので保留にした。**

## 候補 4: Qwen3 / Gemma

**Llama 2 からの差分が小さい** (QK-Norm、`head_dim` を `dim / n_heads` から切り離す、Gemma は tanh の soft-capping と埋め込みのスケーリング)。OpenArch に実装がある。

**実装は軽いがカバー範囲の広がりも小さい。**「もう 1 つ transformer を増やす」以上のものにはなりにくい。

## モデル以外の候補

**新しいモデルを足さずに、既にあるモデルへ足す形の候補。** どれも既存の関門 (トークン列の完全一致) がそのまま使えるので、参照実装を作る手間が無い。

### A. バッチ生成 — **実装した** (2026-09-20)

**batch > 1 の実使用が 1 つも無かった。** cumo は 2 次元 1 本の行列積でも `gemmStridedBatched` を通すのに、**本来の用途で叩いたことが一度も無い** という状態だった。進め方と結果は [PLAN-batch.md](plans/PLAN-batch.md) と [results/gpt2-124m.md](results/gpt2-124m.md)。

**踏んだもの:** decode の帯が gemv から gemm に変わる、KV キャッシュが 3 次元になる、attention の縮約軸が 1 本増える。**出たもの:** 1 ステップの GEMM 49 本の振り分けがバッチについて単調でない (batch 8 で 48 本が `gemmSN` に戻る)。

### B. top-k / top-p サンプリング — **実装した** (2026-09-20)

**全モデルが貪欲法 (argmax) だけで、`sort` / `cumsum` / RNG を 1 度も踏んでいなかった。** 進め方と結果は [PLAN-sampling.md](plans/PLAN-sampling.md) と [results/gpt2-124m.md](results/gpt2-124m.md)。`script/gpt2_generate.rb` が `--temperature` `--top-k` `--top-p` `--seed` を受ける。

**踏んだもの:**

| 経路 | 結果 |
|---|---|
| **`[50257]` の `sort`** | **1 回 8 本。** CUB の radix 6 本 + `float_key_kernel` 1 本 + **`cumo_na_copy` 1 本** (`sort` は壊せないレシーバを必ずコピーする)。**外から連続化しても減らない** |
| **`cumsum` を 50257 要素で** | **1 回 2 本** (`DeviceScanInit` + `DeviceScan`)。**ホストループには落ちない** — Switch で踏んだ 8192 未満の帯の反対側で、**同じ演算の両側が実ワークロードで埋まった** |
| デバイス上の RNG | **踏んでいない。** Numo と Cumo で系列が一致せず、トークン列の完全一致という関門が壊れる。**ホストの `Random` で 1 トークンに 1 スカラーを引く** ことにした (`lib/narray_llm/sampler.rb`) |

**関門は工夫が要らなかった。** 乱数をホストに置いたので、**両バックエンドがそのままトークン列で完全一致する。**

**出たもの:** 1 トークンのカーネルは貪欲法 234 本に対し top_k 262 / top_p 276 / 両方 281 本 (+20.1%)。wall は貪欲法 646.4 tok/s に対し **top_p 1.064 倍 / 両方 1.069 倍** (10/10)、**top_k は 1.037 倍だが 1 をまたいで分離しない** (2026-09-21 に測り直した。前の表は計測スクリプトの偏りを受けていた)。**top-k と top-p は同じ並びを要求するので、`Sampler` が 1 度だけソートして両方に渡す** (共有前は 290 本)。**`reverse` はビューでカーネルを出さないので、`Ops.contiguous` を通す必要も無かった。**

### C. 2 次元の畳み込み (小さい CNN か拡散モデル)

**いちばん新しい面積が広い。** Whisper で踏んだのは Conv1d で、しかも行列積に落としてある。

- **4 次元配列** そのもの (いまの最大は 3 次元)
- Conv2d、プーリング、アップサンプリング、GroupNorm
- **2 方向同時の非連続ビュー。** cumo の ndloop とビュー周りで最も試されていないところ

**関門は作れる。** 下の「外したもの」で BERT / ViT を「生成しないので関門が使えない」として外したが、**分類器なら完全一致の関門が作れる** — N 枚に対する argmax のクラス番号が参照と 1 つも違わないこと。トークン列の一致と同じ強さである。

**実装コスト: 中〜大。** **計画は [PLAN-conv2d.md](plans/PLAN-conv2d.md) に立てた** (ResNet-18、2026-09-21)。**4 次元配列はアテンションのヘッド分割で既に踏んでいる** ので、残る理由は 2 方向のストライドビューとプーリングの縮約の 2 つである。

### D. 学習 (backward) — **実装した** (2026-09-20)

**未踏の面積は最大だった。** ブロードキャストを伴う縮約、in-place 蓄積、optimizer 状態。進め方と結果は [PLAN-training.md](plans/PLAN-training.md) と [results/gpt2-124m.md](results/gpt2-124m.md)。`script/gpt2_train.rb` と `lib/narray_llm/{backward,adam_w}.rb` がそれで、**llm.c の関門を 2 つとも両バックエンドで通る** (124,475,904 個の参照勾配と、10 ステップの損失列)。

**「推論だけ」という前提は変えた。** 関門は llm.c の debug state から借りたので、**完全一致ではなく参照との許容差** になる (`check_tensor` 2e-2、損失 1e-2)。

**出たもの:** 1 ステップの 4947 本のうち **AdamW が 58%** (パラメータ 148 本 x 要素演算 19 本)、wall でも **49%**。**AdamW は自分の式の予算どおりに動いていて** (44P = 21.9 GB、実測との比 1.03)、**こちら側に残っている手は無い** — 平坦化は 1.03 倍で、動くのは cumo が融合したときの 6.5 倍。**3 実装を並べると Cumo 13.0 / CuPy 11.9 / PyTorch 21.8 steps/sec** で、区間で割ると **AdamW が 1.87 倍、backward が 1.64 倍** 開いている。

### E. 複素数

**Numo にも Cumo にも複素数型はあるのに、このリポジトリは 1 度も使っていない。** Whisper のメルで DFT を実数の行列積 2 本に落としたのがその回避である。

**変換が無いので、複素数を要求するモデル (S4 / Hyena の長い畳み込み) を持ってきても FFT の壁に当たる。** 踏めるのは複素数の要素演算までで、**そこに価値があるかは測っていない。**

## 外したもの

- **MoE** — 面白いのは **デバイス上の添字での gather** だが、そこは cumo の未解決課題 (`error_flag_get` の同期を遅延させる設計) で止まる。小さい単一ファイルの C 参照も見当たらない。cumo 側にカードがあるので、そちらが動いてからのほうがよい。→ **2026-09-19 に着手した** ([PLAN-switch.md](plans/PLAN-switch.md))。**塞がりは 0.9.0 でも残っている** ことを確かめたうえで、塞がりを実際の用途で踏むこと自体を目的にした。参照は C ではなく transformers になる
- **BERT / ViT** — 生成しないので **受け入れ条件 (トークン列の完全一致) が使えない**。検証の枠組みを作り直すことになる。→ **分類器なら完全一致の関門は作れる** (上の候補 C)。**外した理由のほうが誤っていた** — 「トークン列」でなくても、**argmax のクラス番号なら同じ強さの検査になる**。ViT そのものより **2 次元の畳み込みを踏むこと** に価値がある
- **もう 1 つ transformer を足すこと** — Qwen3 / Gemma (候補 4) がそれで、実装は軽いが **踏む経路が増えない**。範囲を広げる目的には合わない

## OpenArch について

[anuj0456/OpenArch](https://github.com/anuj0456/OpenArch) は **PyTorch でモデルのフォワードパスだけを 1 ファイルずつ書き起こす教育用プロジェクト** である。GPT-2、Llama 2/3/4、Qwen、DeepSeek R1、Mistral、Gemma、OLMo、Kimi K2、GLM、Grok、GPT-OSS、PaliGemma、Qwen3 Vision など 18 種以上を扱う。

**このリポジトリとは目的が 2 つ違う。**

- OpenArch は **フォワードパスだけ** で、トレーニングループもトークナイザも含まない。こちらは **トークナイザとトークン列のバイト一致** まで要求する
- OpenArch は **読みやすさ優先で性能は狙わない** と明記している。こちらは性能が主目的である

**候補を探す一覧としては使えるが、そのまま移せば済むものではない。** そして **上の候補 1 と 2 は、どちらも OpenArch の守備範囲外である** (18 種はすべて transformer 系で、量子化も扱っていない)。

## どの候補にも効く前提: HF 配布の重みを直接読む

**候補そのものではなく、候補の選択肢を広げる前提。** — **2026-09-19 に実装した。**`lib/narray_llm/safetensors.rb` がそれで、Switch base-8 と Whisper tiny がこれで重みを読んでいる。**以下はその決定の記録である** (なぜ gem を使わなかったか、何を確かめたか)。

**Llama 2 には要らない。** stories110M も TinyLlama も `export.py` で llama2.c 形式に変換する経路があるので、この節が要るのは「HF の重みをそのまま読むこと」自体を目的にしたときだけである。

### 結論: 自前で読む (2026-09-18 に現物で確認)

[ankane/safetensors-ruby](https://github.com/ankane/safetensors-ruby) は使わない。**ただし「TYPES 表に BF16 が無いから」ではない。** その表を通らない経路が gem にはある。

- `Safetensors.deserialize(bytes)` は **フレームワークに依存しない**。`{"dtype" => "BF16", "shape" => [...], "data" => 生バイトの String}` を返すので、`lib/safetensors/numo.rb` の 10 種の表は関係ない。**`Cumo::BFloat.from_binary` にそのまま渡して着地することを確認した** (`trl-internal-testing/tiny-LlamaForCausalLM-3.2`、全 20 テンソル BF16)
- **使えないのは Rust 側の構造のほう。**`ext/safetensors/src/lib.rs` の `create_tensor` は `Numo` と `Torch` の定数を直接引いていて、行き先が 2 つに固定されている。**表に BF16 を足しても Cumo は作れない。** そして mmap して 1 テンソルずつ渡す良い経路 (`safe_open`) はそちら側にしか無い
- **Cumo に渡せる `deserialize` は、全テンソルを一度に Ruby String 化する** (`str_from_slice` をテンソルごとに呼んで配列で返す)。NArray に載る前にファイル全体がホストに乗るので、gpt2 の 548 MB ならピークが 1 GB 級になる。自前なら 1 テンソルずつ読んで捨てられる
- 依存としての重さは障害ではない。**Rust 拡張だが x86_64-linux のビルド済み gem があり、cargo 無しで入った** (0.3.0、2026-06-09、upstream safetensors 0.8.0)

### 自前の読み取りは動かして確かめてある

35 行で足りる。**先頭 8 バイトがヘッダ長 (LE u64)、次が JSON ヘッダ、残りが生バイト** で、各テンソルは `dtype` / `shape` / `data_offsets [begin, end]` を持ち、本体は行優先・リトルエンディアンで隙間も重なりも無い。`from_binary` で `XF` にそのまま着地する。

- **bf16**: 上の HF ファイルで、gem の `deserialize` と **全 20 テンソルがバイト一致** した
- **fp32**: `test/test_gpt2_checkpoint.rb:48` の `HF_REFERENCE` は HF の `openai-community/gpt2` から取った値だが、ヘッダを読んで `data_offsets` を計算し、**HTTP Range で必要な 20 バイトだけ** 落として突き合わせたところ 4 種すべてビット一致した (ヘッダは 14283 バイト、本体は 14291 から、`wte.weight` は F32 の `[50257, 768]` で `[287209472, 441598976]`)。**548 MB を落とさずに検証できる**

### 踏んだ罠

**`to_binary` が返す String は US-ASCII タグ** なので、`File.binread` (ASCII-8BIT) と `==` で比べると **バイトが同じでも false** になる。**Numo でも Cumo でも US-ASCII なので cumo の問題ではない。**
