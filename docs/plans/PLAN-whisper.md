# Whisper tiny 実装プラン

Whisper tiny の推論を Numo::NArray / Cumo だけで実装する。**目的は cumo の検証** で、これまでの 5 つが踏んでいない経路を叩くことに価値がある。参照は [`openai/whisper-tiny`](https://huggingface.co/openai/whisper-tiny) と transformers の `models/whisper/modeling_whisper.py`。

進め方は [PLAN-gpt2.md](PLAN-gpt2.md) の「全体の約束事」をそのまま継ぐ。**前の段階の受け入れテストが通るまで次の段階のコードを書かない。**

## なぜ Whisper か (cumo の検証として)

| 新しく叩く経路 | これまでのモデルでは |
|---|---|
| **畳み込み。**`Conv1d(80, 384, k=3, pad=1)` と `Conv1d(384, 384, k=3, stride=2, pad=1)`。**このリポジトリは一度も畳み込みを書いていない** | 全部が行列積と要素演算 |
| **入力が音声。** 80 メル x 3000 フレームで、**長さが固定**。encoder は常に 1500 位置を処理する | トークン列は長さが変わる |
| **(第三段階まで進めば) STFT・複素数・メルフィルタ** | 複素数を一度も使っていない |
| **生成に強制トークンと抑制がある。**`forced_decoder_ids` で言語・タスク・タイムスタンプ無しが埋まり、`suppress_tokens` が 87 個ある | 素の貪欲法だけ |
| **語彙 51865 に対し d_model 384。** 埋め込みが **パラメータの 53%** を占める | GPT-2 は 30%、Switch は 4% |

**畳み込みが主題である。** 汎用の配列演算だけでどう書くかに選択肢があり (窓を展開して 1 回の行列積にするか、カーネル幅 3 ぶんずらして 3 回足すか)、**どちらが速いかは測るまで分からない**。Switch の「振り分ける / 全部走らせる」と同じ形の比較ができる見込み。

## 関門をどうするか

**Switch と同じで、単一ファイルの C 参照が無い。**`whisper.cpp` は ggml の枠組みなので llama2.c のようには読めない。**参照は transformers、関門はトークン列の完全一致** にする。

**生成の関門は素の貪欲法ではない。**`forced_decoder_ids` と `suppress_tokens` を参照と同じに実装しないと、そもそも列が合わない。**そこも関門の一部になる。**

### 現物を読んで分かったこと

- **`k_proj` にだけ bias が無い。**`q_proj` / `v_proj` / `out_proj` は持つ。**self-attention でも cross-attention でも同じ**

- **メルのフレーム数 3000 は `config.json` に書かれていない。**`max_source_positions` 1500 の 2 倍で、2 つ目の畳み込みが stride 2 だから決まる
- **埋め込みが全体の 52.7%**

### 受け入れテスト — 7 件、両バックエンドで通る

- `config.json` の値がそのまま読める
- テンソル数 167 とパラメータ数 37,760,640 が `config.json` から組み立てた期待値と一致する
- **`k_proj` にだけ bias が無いことを、encoder と decoder の両方で検査する**
- 出力射影が `embed_tokens` と同じ重みを答える
- 位置表が 2 つとも入っている
- 畳み込みの形がメル入力に合っている
- **`config.json` を偽って `encoder_layers` を 2 にすると読み込みが失敗する**

## 第一段階: encoder (メルを与えて) — **完了** (2026-09-20)

**音声の前処理は後回しにした。** 参照側で作ったメルスペクトログラムを入力にして、**モデル本体だけを先に合わせた**。誤差の原因を分けられる。

### 作ったもの

- `python/whisper_dump.py` — **forward hook で本物のモデルから採る。** **波形は式で作る** ので、音声ファイルを持ち回らずに同じメルが出る。メルは **公開されている feature extractor** が作る
- `lib/narray_llm/models/whisper/conv.rb` — **`Conv1d` を 2 つの書き方で**
- `lib/narray_llm/models/whisper/encoder.rb` — 畳み込み 2 段 + 正弦波位置 + 4 層

### `Ops.gelu_erf` を足した

**Whisper は erf 版の gelu で訓練されている** (`nn.functional.gelu`)。既存の `Ops.gelu` は GPT-2 の tanh 版で、**別の関数である**。

| | |
|---|---|
| `gelu_erf` と torch の差 | **8.8e-08** |
| `gelu_erf` と `gelu` (tanh 版) の差 | **4.1e-04** |

**4.1e-04 は第一段階の閾値 5e-04 に迫る** ので、取り違えたら見える差だった。**両バックエンドに `erf` があり、Cumo には融合 `gelu` もある** ので、probe で分けてある。

### `Conv1d` の 2 つの書き方

| | |
|---|---|
| **ずらして足す** (`:shift`) | カーネル位置ごとに `[frames, in] x [in, out]` を作って足し込む。**行列積 3 回 + 加算 2 回** |
| **窓を展開する** (`:unfold`) | `[frames, in * 3]` の窓行列を作ってから **1 回の行列積**。**コピー 3 回 + 行列積 1 回** |

**padding は窓行列をゼロで作ることで済む。**`stride` が 2 のときは入力行が飛び飛びになるので、そこは連続化のコピーが要る。

### 誤差は段ごとに滑らかに増える

| | max\|d\| | 値域 |
|---|---|---|
| conv1 (gelu 前) | 8.1e-06 | 8.68 |
| conv2 (gelu 前) | 1.9e-05 | 11.89 |
| layer 0 | 1.2e-05 | 4.49 |
| layer 1 | 2.2e-05 | 10.01 |
| **layer 2** | 2.3e-03 | **246.92** |
| **layer 3** | 2.8e-03 | **270.01** |
| final_norm | **2.5e-04** | 19.75 |

**跳ねる段が無い。** 相対誤差はどこでも 1e-05 前後である。**Whisper の残差が層 2 で 247 まで伸びる** のが目を引く (fp16 を考えるなら効く)。

### 受け入れテスト — 9 件、両バックエンドで通る

- encoder 出力が transformers と一致 (shift 2.4e-04 / unfold 3.2e-04、閾値 5e-04)
- **2 つの書き方が同じ答えを返す** (差 8.3e-05)
- **`Conv1d` 単体を torch の値と突き合わせる。** stride 1 と 2 の両方、2 つの書き方の両方。**互いに一致することではなく参照と一致することを見る**
- **padding が端だけに効くこと**
- **erf 版の gelu が torch と一致し、tanh 版とは違うこと**
- メルの形が違えば撥ねること、知らない書き方を撥ねること

## 第二段階: decoder と生成 — **完了** (2026-09-20)

### 作ったもの

- `decoder.rb` — 学習済み位置、self / cross、`Cache` (自分の K/V は伸び、encoder のは固定)
- `model.rb` — 強制プロンプトと 2 種類の抑制つきの貪欲生成
- `python/whisper_fixtures.py`、`script/whisper_generate.rb`

### 言語検出を関門に入れない

`generation_config.json` の `forced_decoder_ids` は `[[1, None], [2, 50359]]` で、**`None` は言語を検出しろという意味** である。**検出に依存した fixture は何を測っているか言えない** ので、`language="en"` と `task="transcribe"` を明示して固定した。プロンプトは `[50258, 50259, 50359, 50363]` の 4 つになる。

### 繰り返し列は関門として弱い

**合成波形なので、参照の出力は 2411 が 32 個並ぶだけだった。** これだけを関門にすると、**ほとんどどう間違えても通ってしまう**。

**そこで、固定した列に対する teacher forcing のロジットを位置ごとに突き合わせる** ようにした。参照側で `decoder_input_ids` を与えて 1 回流し、`[10, 51865]` のロジットを落としてある。

| | |
|---|---|
| 10 位置のロジットの max\|d\| | **7.0e-05 (Numo) / 7.2e-05 (Cumo)**、値域 28.4 |
| 各位置の argmax | **10 位置すべて一致** |

**こちらの encoder 出力を使って測っている** ので、モデル全体を通した検査になっている。

### 抑制は飾りではない

抑制を外すと **最初のトークンが 2411 から 542 に変わる** (542 は抑制表に入っている)。**関門の一部である** ことをテストで確かめてある。

### 受け入れテスト — 6 件、両バックエンドで通る

- **位置ごとのロジットが一致し、argmax も一致する**
- **トークン列が transformers と完全一致** (2 つの畳み込みの書き方の両方)
- プロンプトが 4 つで、答えには含まれない
- **抑制を外すと答えが変わる**
- 範囲外のトークン id を撥ねる

## 第三段階: メルスペクトログラム — **完了** (2026-09-20)

### 複素数は使わなかった

**Numo にも Cumo にも複素数型はあるが、変換が無い。** そこで DFT を **余弦と正弦の実数表との行列積 2 本** で書いた。1 フレームあたり 400 x 201 回の積で、FFT なら全体で 3500 回ほどのところだが、**`[3000, 400] x [400, 201]` が 2 本で 30 秒ぶん 0.48 GFLOP** にしかならない。

**メルフィルタは組み直していない。**`preprocessor_config.json` が `[80, 201]` の表を実体で公開しているので、データとして読む。

### 窓の作り方は 3 枚のコピーで済む

フレーム t は `padded[t * 160, 400)` を覆う。hop 160 でフレーム 400 なので、**hop ブロック 2 個半** である。`[blocks, 160]` に reshape してから 3 枚のスライスを書けば、**400 回のストライドコピーが 3 回** になる。

### 参照との差は 1.6e-03。**fp32 の DFT の精度が支配していた**

| 参照の値 | max\|d\| |
|---|---|
| -0.45〜-0.40 (ほぼ下限) | **1.59e-03** |
| -0.40〜0.00 | 1.33e-03 |
| 0.00〜0.50 | 2.0e-04 |
| **0.50〜2.00** | **1.5e-05** |

**誤差は打ち消し合う帯に集中している。** 参照は numpy の FFT なので float64 で、こちらは fp32 の行列積 400 項である。`log10` がその桁落ちを拡大する。

**帰属ではなく対照で確かめた** (計測の作法 24)。**同じ手順を fp64 で踏むと 1.593e-03 が 4.75e-05 になる。** 変えたのは DFT と log の精度だけである。

**残る 4.75e-05 は DFT と FFT の畳む順序の違いと最後の丸めで、分けていない。**

### トークン列は生き残る

**こちらのメルを入れても 32 トークンすべて一致する。** encoder 出力は参照のメルを入れた場合と 6.3e-03 違う (値域 19.75)。**ただしこの入力の参照出力は同じ id の繰り返しなので、強い証拠ではない。**

### 受け入れテスト — 7 件、両バックエンドで通る

- メルが feature extractor と一致 (1.6e-03、閾値 2.5e-03)
- **誤差が静かな帯にあること** (参照が 0.5 以上の 20944 個では 1.5e-05)
- **こちらのメルでトークン列が一致すること**
- 窓が周期 Hann であること (対称版ではない)
- **反射パディングが端の標本を繰り返さないこと** (numpy の `mode="reflect"` と同じ)
- 短い波形がゼロ詰めされ、長い波形が切られること
- フィルタバンクの形が違えば撥ねること

### 前段は `XF` によらず fp32 で回す (2026-09-20 に直した)

**半精度で位相表が壊れていた。** DFT の位相表は添字の積 `n_fft * bins` = 79800 を通るので、**fp16 では Infinity になり `cos` が 80400 要素中 1415 個 NaN**、**bf16 では 79872 に丸まって余弦の符号が反転する** (値域 ±1 で max|d| 2.0)。`log10` の下限 `1e-10` も fp16 では 0 に落ちる。

**位相表だけ直しても足りない** ので、**前段全体を `Mel::PRECISION` (fp32) で計算し、出口で一度だけ変換する**。**`XF` が fp32 のときは変換を挟まない** ので、fp32 の経路は 1 演算も変わらない (カーネル 24 本、max|d| 1.593e-03 のまま)。`Ops.contiguous` が移し先の dtype を取れるようにした。

**fp16 と bf16 で生成も通る。** ただし bf16 のメルは参照との差が 3.907e-03 で、**閾値 2.5e-03 には入らない** (出口の変換そのもので、bf16 の eps が 3.9e-03)。

## 第四段階: 計測 — **完了** (2026-09-20)

**窓を展開して 1 回の行列積にするほうが速い。** ただし差は 1.65% で、消えるカーネルは 217 本中 10 本である。

| | 本/encode | `unfold` / `shift` | またぐ |
|---|---|---|---|
| `shift` | 217 | — | — |
| `unfold` | 207 | **1.0165 (1.0138〜1.0202) 10/10** | いいえ |

**幅が 0.5〜0.8% しかない。** 1 回の encode が 6.6 ms で作法 7 の帯にいるので、**区間の中で 300 回繰り返して 1.9 秒にした**。

**encoder と decoder で像がまったく違う。** encoder は 1500 位置を 217 回の起動で、decoder は 1 位置に 341 回の起動を使う。**同じモデルの中に、行列積が支配する帯と起動が支配する帯の両方がある。**

## 第五段階: Python の 2 実装と並べる — **完了** (2026-09-20)

- `python/whisper.py` (numpy / cupy)、`python/whisper_torch.py` (torch)、`python/bench_whisper.py`
- **transformers は使わない。** 他のモデルと同じく、こちらの実装をそのまま移植してアルゴリズムを固定する
- 3 実装とも fixture のトークン列を通ってから計測に入る

**同じモデルの中で勝ち負けが入れ替わった。**

| 条件 | Cumo / CuPy | PyTorch / Cumo |
|---|---|---|
| **メル** | 1.017 **またぐ** | 1.060 10/10 (対照の幅 7%) |
| **encode** | **1.276 10/10** | **1.153 10/10** |
| **decode** | **3.187 10/10** | **0.949 0/10** |

**decode では Cumo が PyTorch を 5.4% 上回り、encode では PyTorch が 15.3% 上回る。** ただし encode でも Cumo は CuPy に 27.6% 勝っている。

**畳み込みの書き方も 3 実装で測り直した。** Cumo 1.0165 / CuPy 1.0141 がどちらも 10/10 で、**`unfold` が速いのは cumo に固有の話ではない**。PyTorch は 8/10 だがペア比が 1 をまたぐ (対照の幅 4% > 効き幅 0.8%)。

**encode の 15.3% を追って、3 実装のカーネルを数えた。**

| 実装 | GEMM | GEMM 以外 | 合計 |
|---|---|---|---|
| **Cumo** | **78** | 139 | **217** |
| **CuPy** | **78** | 330 | 408 |
| **PyTorch** | **78** | **99** | **177** |

**GEMM は 3 実装とも 78 本で一致し、Cumo と PyTorch は cutlass のタイルと grid まで同じ。** **PyTorch は融合していない。** **GPU 時間も 3 組取ったが、GEMM の時間はペア比 0.997〜1.220 で 1 をまたぐ** (Cumo 自身が 3 組で 21% 動く)。**1 組目だけなら「GEMM が 21% 遅い」と書けた。** **15.3% の帰属は未分離。**
