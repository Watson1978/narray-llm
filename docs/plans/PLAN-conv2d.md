# PLAN-conv2d.md

[docs/idea.md](../idea.md) の候補 C。**2 次元の畳み込みを、実在する分類器で踏む。** 進め方は AGENTS.md に従う。**前の段階の受け入れテストが通るまで次の段階のコードを書かないこと。**

## なぜ 2 次元の畳み込みか (cumo の検証として)

**idea.md が挙げていた 3 つの理由のうち、1 つは既に払い終わっている。**

| idea.md の理由 | いまの状態 |
|---|---|
| **4 次元配列そのもの** | **もう踏んでいる。** アテンションのヘッド分割が `reshape(B, T, NH, hs).transpose(0, 2, 1, 3)` で (`ops.rb:429`、`backward.rb:133`)、学習の内訳に `store_sfloat_kernel_dim4` が 84 本/step 出ている |
| **2 方向同時の非連続ビュー** | **未踏。** Whisper の `Conv1d` は 1 方向のスライスだけだった |
| プーリング、GroupNorm、アップサンプリング | **プーリングの縮約が未踏。**`max` を 2 方向のストライドビューで取る経路 |

**残る 2 つは本物である。** AGENTS.md の「非連続ビューと dot」の表は **すべて 1 次元のビュー** (`a[1..-1]` / `reverse` / `a[idx]`) で測ったもので、**2 方向にストライドを持つビューが縮約や要素演算をそのまま受けるかは分かっていない。**

**そして畳み込み自体は GEMM に落ちる。** このリポジトリで最も踏み固められた経路なので、**新しいのは演算ではなく添字のほうである** ことを最初に認めておく。

### 測る前に言える問いが 1 つある

Whisper の `Conv1d` は 2 つの綴りを両方持っている ([docs/results/whisper-tiny.md](../results/whisper-tiny.md))。

| 綴り | 中身 | 1 次元 (kernel 3) の結果 |
|---|---|---|
| `shift` | カーネル位置ごとに行列積、足し込む。**コピー 0 回、行列積 3 回** | — |
| `unfold` | 窓行列を作ってから **行列積 1 回**。**コピー 3 回、行列積 1 回** | **`unfold` / `shift` = 1.0165 (1.0138〜1.0202)** 10/10 |

**`unfold` が勝ったのは cumo に固有ではなかった** — CuPy と PyTorch の移植でも同じ向きだった。

**2 次元にすると比が変わる。**`3 x 3` では **`shift` の行列積が 3 → 9 回**、**`unfold` の窓行列が入力の 3 倍から 9 倍** になる。**`unfold` の費用は帯域に、`shift` の費用は起動と行列積の回数に付く** ので、**どちらが勝つかは 1 次元の結果からは決まらない。**

**負ける形を先に名指ししておく** (計測の作法 18)。**`unfold` が負けるとしたら、窓行列が L2 に載らなくなる大きい特徴マップの層である。** ResNet-18 の最初の層 (出力 112 x 112、窓行列 7.4 MB) と、`layer4` (出力 7 x 7、窓行列 0.9 MB) で **符号が反転するかどうか** が、この段の中心の問いになる。

**層ごとに符号が反転したら、それ自体が結論である** (計測の作法 19)。「どちらが速いか」ではなく「どこで切り替わるか」を答えにする。

## 関門

**N 枚の画像に対する argmax のクラス番号が、参照と 1 つも違わないこと。** トークン列の完全一致と同じ強さで、これは idea.md が「分類器なら完全一致の関門が作れる」と書いていたとおりである。

二段構えは他のモデルと同じ (AGENTS.md のテストの作法)。

1. **Numo vs 参照** (実装が正しいか)。参照は transformers。Switch と Whisper が同じ形で使っている
2. **Cumo vs Numo** (バックエンド間の一致)

**乖離したときのために、層ごとの中間活性を比べる関数を第 0 段階で用意する。** 畳み込みは段数が深いので、最終出力だけ見て切り分けるのは無理である。

**`shift` と `unfold` は互いの関門でもある。** Whisper と同じで、2 つの綴りが一致しなければどちらかが間違っている。

## モデルの選定

**ResNet-18 を第一候補にする。** 理由は、欲しい経路が全部入っていて、余計なものが入っていないこと。

| 要る経路 | ResNet-18 のどこ |
|---|---|
| **`7 x 7` stride 2 の畳み込み** | `conv1` |
| **`3 x 3` の畳み込み** | 16 層 |
| **stride 2 の畳み込みと `1 x 1` の射影** | 各 `layer` の先頭 |
| **max pooling** | `maxpool` (`3 x 3` stride 2) |
| **global average pooling** | `avgpool` |
| BatchNorm | 推論時はアフィンなので **畳み込みに畳める** |

**11.7M パラメータで GPT-2 124M より軽い。** 残差接続は GPT-2 で踏み終わっている。

**窓行列はいちばん大きいところで 7.4 MB なので、`unfold` を全層で持っても確保は問題にならない** (実測の表は下記)。

### BatchNorm を畳んでも argmax は動かない

畳み込み 20 本すべてに `W' = W * gamma / sqrt(var + eps)`、`b' = beta - mean * gamma / sqrt(var + eps)` を当てて、8 枚で比べた。

| | |
|---|---|
| logits の `max|d|` | **7.39e-06** |
| argmax の一致 | **8/8** |
| ビット一致 | **しない** |

**畳んだ版は argmax の関門を通る。** ただしビット一致はしないので、**中間活性の比較は畳まない側で行う。**

### 1 枚 3.63 GFLOP。当初 1.8 と書いたのは MAC 数だった

**計画に「約 1.8 GFLOP/枚」と書いたのは誤りで、正しくは 3.63 GFLOP (1.81 GMAC) である。** 世間で言う「ResNet-18 は 1.8 GFLOPs」は MAC 数のほうを指している。

**最初の計算では 0.453 GFLOP と出た。** バッチで 2 度割っていた。**合計が `conv1` 1 層ぶん (0.236 GFLOP) の 2 倍しかない** のに気づいて見直した。**ありえない値が門番になった形である。**

| 層 | 窓行列 (1 枚) | バイト |
|---|---|---|
| `conv1` (`7 x 7`, 3 → 64) | 12544 x 147 | **7.38 MB** |
| `stages.0` (`3 x 3`, 64 → 64) | 3136 x 576 | **7.23 MB** |
| `stages.3` (`3 x 3`, 512 → 512) | 49 x 4608 | 0.90 MB |
| `stages.3` の射影 (`1 x 1`) | 49 x 256 | 0.05 MB |

**M (窓行列の行数) は 12544 から 49 まで、256 倍の幅がある** (バッチ 1)。**「どこで符号が反転するか」を聞くのにちょうどよい範囲である。**

### PyTorch の基準値 (cuDNN、クロック固定、10 回平均)

| バッチ | 1 回 | 枚/s | TFLOP/s |
|---|---|---|---|
| 1 | 0.96 ms | 1041 | 3.78 |
| **8** | **2.54 ms** | **3149** | **11.42** |
| 32 | 10.98 ms | 2915 | 10.57 |

**バッチ 8 が最良で、32 では落ちる。** これは PyTorch の値であって、こちらの目標ではない。**cuDNN の畳み込みと、im2col + cuBLAS を比べることになる** ので、**アルゴリズムが違う** 点は GPT-2 の学習と同じ扱いにする (docs/method.md の対応表の外)。

### 計測の長さ

**バッチ 8 が 2.54 ms (PyTorch) なので、こちらが 3〜5 倍遅いとして 8〜13 ms。** 1 回では作法 7 の言う「1 秒未満」に遠く届かない。**Whisper の encode と同じく、区間の中で繰り返して 2 秒に伸ばす。** 150〜250 回ほどになる。

**バッチを増やして長さを稼ぐのは避ける。** M が `B x oh x ow` で増えるので、**`shift` 対 `unfold` の比そのものを動かしてしまう。** バッチは 8 に固定し、**振るなら独立の条件として振る。**

## 第一段階: Conv2d を 2 綴り — **完了** (2026-09-21)

### 作ったもの

`lib/narray_llm/models/resnet/conv2d.rb` と `test/test_resnet_conv2d.rb`。

**内部の並びは `[N, H, W, in]` (チャネル最後) にした。** torch はチャネル先で持つので、モデルが入口と出口で 1 度ずつ転置する。**Whisper の `Conv1d` が `[frames, channels]` なのと同じ理由** で、行列積がそのまま書ける並びである。

**窓は `(a..b).step(s)` で取る。** 純粋なストライドなので **添字配列の経路を踏まない** (AGENTS.md: NArray を添字にしたときだけ同期する)。Ruby の Array でも書けるが、そちらは添字配列のビューになり縮約 1 回につき 2 本多い。

**padding は入力を 1 度ゼロで広げて済ませる。** 2 方向ぶんの有効範囲を綴りごとに計算するより単純で、**費用が 2 綴りに同じだけ乗るので比較を汚さない。**

### 踏んだもの

**`XF.new` は遅延確保で、スライスへの書き込みを拒む。**`unfold` の窓行列は 9 回に分けて書くので、`new` だけでは `cannot read/write unallocated NArray` になる。**`zeros` にすると要らない fill を 1 本払う** (9 タップが全要素を書くので)。**`allocate` が両バックエンドにあり、fill なしで確保だけできる。**

**窓行列は `[N, out_h, out_w, kh * kw * in]` の 4 次元のまま埋める。**`[rows, span]` で持つとタップごとに `reshape` が要り、非連続ビューは `reshape!` を拒むのでコピーが 1 回増える。**4 次元のまま入れれば代入する形がそのまま合い、最後の平坦化はビューで済む。**

### Cumo の `unfold` は torch とビット一致する

3 つの形すべてで確かめた。

| | Numo `shift` | Numo `unfold` | Cumo `shift` | Cumo `unfold` |
|---|---|---|---|---|
| `conv1` (`7 x 7` s2 p3) | 1.91e-05 | 1.07e-05 | 1.91e-05 | **0** |
| `conv3x3` (`3 x 3` s1 p1) | 1.34e-05 | 1.81e-05 | 1.34e-05 | **0** |
| `conv1x1` (`1 x 1` s2 p0) | 9.54e-07 | 9.54e-07 | **0** | **0** |

**`unfold` は 1 本の GEMM なので、cuBLAS が torch と同じ畳み方をする。**`shift` は 9 本に分けて足し込むので順序が変わる。**`1 x 1` でだけ `shift` も一致するのは、タップが 1 つで `shift` が `unfold` に縮退するから** で、これが機構の対照になっている。

**Numo はどの形でも一致しない** (BLAS を通らないので畳み方が違う)。

**関門としては、Cumo の `unfold` だけ完全一致を要求できる。** ほかは許容差で見る。

### 受け入れテスト — 5 件、両バックエンドで通る

**計画に書いた 3 条件を満たしている。**

- **3 つのカーネル形すべてが参照と一致する** (`7 x 7` s2 p3 / `3 x 3` s1 p1 / `1 x 1` s2 p0)。許容差 5e-5
- **2 綴りが互いに一致する。** 窓から先を共有していないので、参照との一致とは独立な検査である
- **両バックエンドで同じテストが通る**
- 出力の大きさが padding と stride に従う
- **バイアスが 2 綴りとも 1 度だけ足される** (この模型は使わないが、BatchNorm を畳むと出る)

参照は `conv1` に加えて `conv3x3` と `conv1x1` を dump に足した。**形ごとに添字の算術が違うので、1 つ通っても残りは通らない。**

## 第二段階: pooling と BasicBlock — **完了** (2026-09-21)

### 作ったもの

`Ops.max_pool2d` と `Ops.global_average_pool`、`lib/narray_llm/models/resnet/block.rb` (`Norm` / `ConvLayer` / `BasicLayer` / `Stage` / `Embedder`)、`test/test_resnet_block.rb`。

**max pooling は窓の位置ごとのストライドビューを `XF.maximum` で畳む。** 添字配列を作らないので同期しない。**padding は `MASK_VALUE` で埋める** — ゼロだと、窓が全部はみ出したときに 0 と答えてしまう。

**BatchNorm は推論では channel 軸のアフィンなので、4 つのバッファを load 時に scale と shift 2 本に畳む。** これは第三段階でやる「畳み込みへの畳み込み」とは別で、**畳み込み自体はまだ独立に走る。**

### gemm の答えが inplace のフラグを持って返る

**これに 1 時間取られた。** Cumo の `Ops.linear_add` は `gemm(beta: 1)` に落ち、**返り値は `inplace?` が真** である。フラグは消費されずに下流へ流れるので、**その配列に触る式がすべて同じバッファを書き換える。**

**そして壊していたのは検査のほうだった。**

```ruby
y = Stage.new(ck, s).call(y)
dd = (y - 参照).abs.max      # ← この式が y を書き換える
y = Stage.new(ck, s + 1).call(y)   # 壊れた y が次の段に入る
```

stage.0 までは正しく、stage.1 以降が丸ごと壊れる、という出方をした。**「stride 2 が怪しい」「shortcut が怪しい」と 2 度外した** あと、**ブロック単体では両方一致する** ところまで絞って、ようやく検査の側だと分かった。**モデルは最初から正しかった。**

**`view` を通すとフラグが落ち、バッファは共有したままなのでカーネルを払わない。**`Conv2d#call` の出口に入れて、AGENTS.md にも書いた。**受け入れテストに「答えが inplace のフラグを持たないこと」を 1 件足してある。**

### 受け入れテスト — 5 件、両バックエンドで通る

|---|---|
| **stem と 4 段すべてが参照と一致する** (2 綴りとも) | 1e-4 (最悪 3.6e-05) |
| **答えが inplace のフラグを持たない**、比較しても書き換わらない | 完全一致 |
| 形が 224 → 56 → 56 → 28 → 14 → 7 と減る | — |

## 第三段階: モデル全体 — **完了** (2026-09-21)

### 作ったもの

`lib/narray_llm/models/resnet/model.rb`、`script/resnet_classify.rb`、`test/test_resnet_model.rb`。

**入口で 1 度だけ並びを変える。**`forward` は torch の `[N, 3, H, W]` を受け、`[N, H, W, C]` に直してから走る。**出口は `[N, num_labels]`。**

**`--fold` で BatchNorm を畳み込みに畳める。** norm が出力チャネルごとに掛かるだけなので、**そのチャネルを作った畳み込みの重みに乗る** (`weight * scale`、bias は `shift`)。第二段階でやった「バッファ 4 本を scale と shift に畳む」とは別の段階である。

### 関門 — 16 枚すべて、4 通りとも一致

| | logits の `max|d|` (Cumo) | クラス番号 |
|---|---|---|
| `shift`、畳まない | 1.43e-05 | **16/16** |
| `unfold`、畳まない | 1.14e-05 | **16/16** |
| `shift`、畳む | 1.81e-05 | **16/16** |
| `unfold`、畳む | 1.53e-05 | **16/16** |

**Numo も同じく 4 通りとも 16/16。**

**畳んでも答えは動かない。** logits は動く (畳む前と畳んだ後で差が 0 ではない) が、**クラス番号は 1 枚も動かない。** これは 2026-09-21 に torch 側で先に確かめたこと (logits が 7.4e-06 動き argmax は 8/8 一致) と整合する。

### 受け入れテスト — 4 件、両バックエンドで通る

- **16 枚のクラス番号が参照と完全一致する** (2 綴り x 畳む / 畳まないの 4 通り)
- logits が参照から 1e-4 以内
- **畳むと logits は動き、クラス番号は動かない。**「畳んでも何も変わらない」も落とす (変わらなければ畳めていない)
- **1 枚だけ通しても、16 枚のときと同じ答えになる**

### 速度の当たり

`GPU=1 ruby script/resnet_classify.rb --repeat 20` で **990 枚/sec** (best-of-3、16 枚 x 20 回)。**PyTorch の cuDNN が 3149 枚/sec** (バッチ 8、2026-09-21 実測) なので **3.2 倍遅い**。

**これは当たりであって計測ではない。** 1 プロセス 1 条件でもインターリーブでも対照でもないので、第四段階で測り直す。

## 第四段階: 計測 — **完了** (2026-09-21)

**結果は [docs/results/resnet-18.md](../results/resnet-18.md)。** 要点だけ。

**予想は外れた。** 符号は反転せず、**`unfold` が 47% 勝った** (1.4741、12/12、対照はまたぐ)。1 次元では 1.65% だったので、**幅が広がった。**

**効いているのは起動回数ではない。** 増える 196 本は起動費で 0.4 ms、実測の差 8.3 ms/pass の 5% にしかならない。**`shift` は `gemm(beta: 1)` で累積するので、タップごとに出力を読んで書く** — `3 x 3` で 9 往復、`7 x 7` で 49 往復、合計 6.79 GB。`unfold` は出力を 1 度書き (0.16 GB)、窓行列を往復する (1.88 GB)。**差 4.75 GB は 600 GB/s で 7.9 ms で、実測の 95% を説明する。**

**負ける形の名指しは外れたが、予算を立てていれば測る前に分かった** — **窓行列の 9 倍 (1.88 GB) より、累積の 9 往復 (6.79 GB) のほうが 3.6 倍大きい。**「窓行列が 9 倍になる」ほうだけ見て、「累積が 9 往復になる」ほうを数えていなかった。

**cuDNN を第三のアームにした (同日)。** cumo の `conv` を綴りとして足し、**綴りがモデル全体の並びを決める形** にした (`shift` / `unfold` はチャネル最後、`cudnn` はチャネル先)。**4 通りとも 16 枚のクラス番号が参照と完全一致する。**

**そして cumo の cuDNN はワークスペースを既定 8 MiB に制限していた** (別セッションの指摘)。**環境変数 1 本で 1.62 倍になる。**

| Cumo `shift` | 625.0 | |

**PyTorch との差 5.94 ms/pass のうち、4.96 ms (83%) がワークスペースの制限だった。** 残るのは 0.98 ms (1.14 倍) で、**未分離。**

**Cumo と CuPy の勝ち負けが綴りで入れ替わる。** これまでのモデルでは Cumo が一貫して勝っていたので、**逆転は初めて。** 綴りの効きも実装で違う (Cumo 1.48 倍、**CuPy 2.31 倍**)。

**Python 移植を足した** — `python/resnet.py` (numpy / cupy、Ruby の構造の写し) と `python/resnet_torch.py` (天井)、`python/bench_resnet.py`。**最初の測定では Python 側だけ計測区間の中で転送していた** ので、`prepare` を外に出して測り直した。

**層ごとの符号は反転しなかった (同日)。** 綴りを層ごとに選べるようにして、1 か所だけ `shift` に替えたアームを 5 つ測った。**5 か所すべてで `unfold` が勝ち、1 つも 1 をまたがない。** **計画では「M が 256 倍の幅を持つのでどこかで割れるほうが自然」と書いていたが、外れた。**

**部分ごとの増分 +8.13 ms が、全部替えた実測 +8.17 ms と 0.6% で閉じる。** **stem だけで penalty の 82%** で、`7 x 7` の 49 タップが 49 往復するぶんである (累積トラフィックの予算でも stem が 74%)。**つまり「2 次元で 47% 勝つ」は、ほぼ「`7 x 7` の stem で勝つ」だった。**

**ワークスペースの 1.62 倍には精度の変化が混ざっていた (同日)。** カーネル名を見ると **Winograd と FFT が入り、20 本のうち 7 本が TF32 のテンソルコア** に行く。cumo の fp32 経路は `CUDNN_DEFAULT_MATH` でテンソルコアを禁じていない。**logits の `max|d|` が 1.621e-05 から 3.752e-03 に動く** (クラス番号は 16/16 のまま)。**「torch fp32 との 1.14 倍」は精度が揃っていないので取り下げ**、方針を揃えた比較は torch の既定との **1.3969 倍** である。

**残っていること。**

- **`unfold` で CuPy に負ける 7.6% の行き先。** **未分離。** 本数では切れなかった (実装ごとにカーネル名が違うので群をまたいだ比較ができない)。合計は Cumo 330 本、CuPy 316 本
- **ワークスペースの 1.62 倍のうち、アルゴリズムの改善と TF32 の寄与の内訳。**`CUDNN_FMA_MATH` が外から振れないので分けられない。**cumo 側の話**
- **1 GiB のアームだけ幅が 3.5% ある** (他は 0.3〜0.5%)。13 点では形を読めない

## この段で cumo に返せそうなもの

**あらかじめ期待しすぎないこと。** 畳み込みは GEMM に落ちるので、**新しいカーネルの穴が出るとは限らない。** 出るとしたらこの 2 つで、どちらも「ビューを受ける側」の話である。

1. **2 方向のストライドビューが縮約と要素演算をそのまま受けるか。** 受けないなら、1 次元の表と同じ形で本数を出せる
2. **`shift` の 9 回のコピーが、行ごとカーネル起動に落ちないか。** AGENTS.md が「依存する cumo のバージョンによっては行ごとカーネル起動に落ちて 100 倍以上遅くなる」と書いている経路を、**2 方向で踏む**

**「呼び出し元を 1 つ挙げる」は最初から満たしている** (作法 24) — ResNet-18 の 20 層の畳み込みがそれである (`conv1` 1 + `3 x 3` 16 + 射影の `1 x 1` 3)。
