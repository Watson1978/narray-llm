# Mamba 実装プラン

Mamba の推論を Numo::NArray / Cumo だけで実装する。**目的は cumo の検証** で、GPT-2 と Llama 2 が踏んでいない経路を叩くことに価値がある。参照実装は [kroggen/mamba.c](https://github.com/kroggen/mamba.c) で、llama2.c から派生した単一ファイルの C 実装である。

進め方は [PLAN-gpt2.md](PLAN-gpt2.md) の「全体の約束事」をそのまま継ぐ。**前の段階の受け入れテストが通るまで次の段階のコードを書かない。**

**参照のブランチは `learning`** (既定ブランチ、Mamba 1)。`fused` / `mamba2-*` / `mamba3-*` / `cuda` は当面見ない。

## なぜ Mamba か (cumo の検証として)

| 新しく叩く経路 | GPT-2 / Llama 2 では |
|---|---|
| **attention が無い。** 1 トークンあたりの仕事が小さい配列への要素演算に寄る | 両方とも decode の中心は gemv |
| **要素演算のブロードキャストが最内軸** — `dA[i][j] = dt[i] * A[i][j]` は `[d_inner, 1]` を `[d_inner, d_state]` に広げる | cumo #475 が `mulsum` で直したのと同じ向き。**ただし要素演算に同種の問題は無い** (下記) |
| **状態が 2 本ある** — `conv_state [d_inner, d_conv]` と `ssm_state [d_inner, d_state]`。どちらもトークンごとに全要素が書き換わる | KV キャッシュは末尾に 1 行足すだけで、既存の行は動かない |
| **リングバッファ** — `conv_state` を 1 列ずらす。自分自身への重なったコピー | 無い |
| **8 の倍数でない語彙を丸める** (50277 → 50280)。埋め込みは丸めた側で保存され、**末尾 3 行はどのトークンにも対応しない** | GPT-2 は 50257 のまま、Llama 2 は 32000 |

**いちばん大きいのは 1 番目である。** mamba-130m の `[d_inner, d_state]` は `[1536, 16]` = 24,576 要素しかなく、1 層に 7 本前後の要素演算が乗る。**このプロジェクトが測り続けてきた「1 投入 2.0〜2.2 us」がそのまま支配する形** になる見込みで、そこを実際に確かめること自体が成果になる。

**ブロードキャストの向きは心配しなくてよい。** cumo 側が `[1536, 16]` の SFloat で先に測ってくれた (2026-09-19、**こちらでは追試していない**)。

| | 1 回あたり |
|---|---|
| `a * b` 別々の連続配列 | 3.48 us |
| `dt * a` ブロードキャストが左 (`dt[i] * A[i][j]` の形) | 3.41 us |
| `a * dt` ブロードキャストが右 | 3.35 us |
| `a + b` (対照) | 3.28 us |
| `a * 2.0` (スカラー) | 3.27 us |

**全部 3.3〜3.5 us で平ら。** 向きでも左右でも差が出ない。**`a + b` とスカラー倍が同じ値** なのが要点で、この規模では中身ではなく起動が決めている。24,576 要素なら帯域では 0.1 us 未満なので、**残りはすべて起動と ndloop である**。

**したがって入口は本数を数えることで、カーネル単体を疑う必要は無い。**

**conv1d は cuDNN 経路を踏まない。** docs/idea.md には「cumo の `conv.c` / cuDNN 経路はまだ一度も踏んでいない」と書いてあったが、**mamba.c の depthwise conv は手書きのリングバッファ** で、`conv_state * conv1d_weight` の要素積を最後の軸で畳むだけである。**この参照実装を追うかぎり cuDNN には触らない。**

## 1 トークンの計算 (`mamba.c:377` `forward_layer`)

層ごとに次を回す。`x` は `[d_inner]`、`A`/`dA`/`dB`/`ssm_state` は `[d_inner, d_state]`。

```
xz      = in_proj @ h                       [2*d_inner]
x, z    = xz の前半と後半                    [d_inner] ずつ
conv_state を 1 列左へずらし、最終列に x を置く
x       = sum(conv_state * conv1d_weight, axis: 1) + conv1d_bias
x       = silu(x)
x_db    = x_proj @ x                        [dt_rank + 2*d_state]
dt,B,C  = x_db の分割
dt      = softplus(dt_proj @ dt + dt_proj_bias)   [d_inner]
dA      = exp(dt[:, newaxis] * A)           [d_inner, d_state]   <- 最内軸ブロードキャスト
dB      = dt[:, newaxis] * B[newaxis, :]    [d_inner, d_state]   <- 外積
ssm     = ssm * dA + x[:, newaxis] * dB
y       = sum(ssm * C, axis: 1)             [d_inner]            <- 最外軸ブロードキャストの縮約
y       = y + D * x
y       = y * silu(z)
h       = out_proj @ y                      [d_model]
```

`forward` 側は層の前に `rmsnorm`、層の後に残差を足すだけで、最後に `rmsnorm` と分類器が乗る (`mamba.c:468`)。

**`Ops` から流用できるもの**: `rmsnorm`、`silu`、`contiguous`、`linear` / `linear_into`。**新しく要るもの**: `softplus` と、リングバッファの扱い。

## コードの置き場

`models/mamba.rb` と `models/mamba/` を足し、`NArrayLLM::Mamba` に入れる。Llama 2 と同じ形にする。

```
lib/narray_llm/models/mamba.rb
lib/narray_llm/models/mamba/
  checkpoint.rb model.rb tokenizer.rb state.rb
```

**`KVCache` は使わない。** 状態は `Mamba::State` を新設し、`conv_state` と `ssm_state` を層ぶん持つ。`Generator` は `prefill` / `decode` の形が同じなので **そのまま使えるはず** だが、第二段階で確かめる。

## 第一段階: フォワード 1 回 — **完了** (2026-09-19)

`forward_layer` をそのまま NArray に移した。

**参照は `script/mamba_dump.c` を新しく書いた。**`mamba.c` には debug ダンプが無く、CLI は 50277 語彙のトークナイザでプロンプトを符号化するので **小さいチェックポイントには向けられない**。このハーネスは **トークン id を直に受け**、`mamba.c` を丸ごと include して中間活性を書き出す。`llama2_dump.c` と同じ安全策を入れてある — **自分の写した `forward` を、別の状態を持つ 2 つ目のモデルで走らせた本物の `forward` と突き合わせ、logits が厳密に一致しなければダンプを書かない** (実測 `max|d| = 0`)。

**小さいチェックポイントには列を指定して食わせる。** 乱数の重みだと argmax が入力トークンの不動点になり、貪欲法では入力が変わらないので **埋め込みの引き方が検査されない**。

### リングバッファは見送った

プランでは「ずらさずに書き込む列を回す」としていたが、**やめた**。`sum_along_last_dim` は `j` の昇順に足すので、列を回すと **和の順序が変わって参照からずれる**。1 トークン 1 本を惜しんで基準を緩めることになるので、第一段階は `shift_matrix_left` をそのまま写した。**第三段階で、順序の違いを測ったうえで判断する。**

### rmsnorm は共有できなかった

`mamba.c:234` は `o[j] = x[j] * weight[j] * ss` と左から掛ける。`llama2.c` は `weight[j] * (ss * x[j])` で、**括り方が違うので fp32 では 1 ulp ずれうる**。`Ops.rmsnorm` は後者なので、Mamba 側に自前の実装を置いた。`Ops.silu` は `mamba.c:230` と同じ式なのでそのまま使える。

### 受け入れテスト — 7 件、両バックエンドで通る

**ビット一致は要求しない。**`matmul` の和の順序が BLAS と C で違うので原理的に届かない。既存の段階と同じく **実測して根拠を書いた閾値** にしてある。

| | 実測 (Numo) | 実測 (Cumo) | 閾値 |
|---|---|---|---|
| logits (mamba_tiny) | 9.5e-07 | 1.9e-06 | **5e-3** |
| logits (mamba-130m) | 4.1e-04 | 4.3e-04 | |
| `conv_state` (130m) | 1.6e-05 | 1.9e-05 | **1e-3** |
| `ssm_state` (130m) | 7.6e-05 | 8.0e-05 | |

**誤差は位置とともに増えない。** 16 位置で 1.1e-04 〜 4.1e-04 の間を動くだけである。`A` が負なので `dA = exp(dt * A) < 1` となり、**再帰が縮小写像になっている** ためと思われる (**これは観測からの推測で、独立には測っていない**)。

**閾値に依存しない検査も入れた。** mamba-130m のダンプは `mamba.c` が自分の argmax を食べ直して作ったものなので、**位置 p の logits が選ぶ id が位置 p+1 の参照トークンと一致する** ことを 15 位置で確かめている。16 位置を通して **上位 2 つの logits が最も近づいたときで 0.0954**、最大誤差の 230 倍あるので argmax は余裕の内側にある。

## 第二段階: 生成 — **完了** (2026-09-19)

**mamba-130m の 255 トークンが `mamba.c` と完全一致する。Numo と Cumo の両方で、しかも 2 つは互いにも完全一致する。** 一致する長さを記録する扱い (int8 や fp16 と同じ) にはならなかった。

### 共有の `Generator` をそのまま使えた

3 点だけ合わせた。

- **`new_cache` は `new_state` の別名にした。** Mamba が持ち越すのは 2 本の再帰でキャッシュではないが、**その名前にしておくと `Generator` を 1 行も変えずに済む**
- **`decode` の第 2 引数 (位置) は受け取って捨てる。** KV キャッシュと違って **状態が位置を持っている** ので要らないが、呼び出し側の形を揃えるために取る
- **`max_seq_len` は `Float::INFINITY`。** Mamba に位置の上限は無い。再帰は長さによらず同じ大きさで、`mamba.c` も位置ごとには何も確保しない

### `decode` は語彙幅で返す

`mamba.c` は丸めた幅 (50280) で logits を計算し、サンプリングは `vocab_size` (50277) の範囲で行う。**末尾 3 つはどのトークンにも対応しない** ので、`decode` はそこを落として返す。参照のダンプは丸めた幅のまま持っている。

### 参照は `mamba.c` の CLI では作れない

**プロンプトを必ず要求し、50277 語彙のトークナイザで符号化する。**`<|endoftext|>` 単独から始めることも、語彙 64 の小さいモデルに向けることもできない。そこで `script/mamba_fixtures.rb` が `script/mamba_dump.c` 経由で `mamba.c` の `forward()` を回し、**自分の argmax を食べ直させて** 列を作る。

**つまり期待値の出どころは C の参照であって、このリポジトリではない。** Llama 2 の fixture は Ruby の出力を保存したものだったので、こちらのほうが強い。

### 受け入れテスト — 5 件、両バックエンドで通る

- **64 トークンが fixture と完全一致** (`assert_equal` で、閾値は無い)
- プロンプトが区切りトークンであること、位置の上限が無いこと
- **状態を `reset` すると同じ走りを繰り返すこと** — 持ち越すものが状態で全部だという確認
- 範囲外のトークン id が拒否されること

## 第三段階: 計測 — **完了** (2026-09-19)

**結果は [docs/results/mamba-130m.md](../results/mamba-130m.md) にある。**

**予想は当たった。** 1 トークンあたりの本数は GPT-2 の 210 本、Llama 2 の 342 本に対して **当初 1115 本** で、内訳は `[1536, 16]` への小さな要素演算に寄っている。

**予想していなかったのは、PyTorch のほうが本数が多いことである。** Cumo は 845 本の時点で PyTorch 1302 本より **35% 少ないのに 4〜6% 負けていた**。629 本にして 18% 上回ったが、GPT-2 と Llama 2 で成り立っていた「1 投入の費用は同じで差は本数から来る」は、ここでは成り立たない。

**キャッシュ無しの条件は無い。** Mamba は再計算する経路を持たない (`mamba.c` にも無い)。

| 変更 | 減った本数 | 割合 | ペア比 (長さ 200) | またぐ |
|---|---|---|---|---|
| `XF.zeros` → `allocate` | 24 | 2.2% | 1.010 (0.992〜1.035) | **はい** |

**`mamba_ssm` は使わない。** 融合 CUDA カーネルを持つので、それを使うと「同じ算法の比較」ではなく「レシピの比較」になる。このリポジトリの表はどれも算法を固定して **走らせるものだけを変える** ので、`mamba.c` から op ごとに写した。

## `XF.zeros` の fill は全部無駄だった (2026-09-19)

`shift_in` は `[d_inner, d_conv]` を作って **全列を上書きする** ので、`XF.zeros` のゼロ埋めは 1 つも残らない。`XF.new(...).allocate` なら埋めずに確保でき、**答えはビット一致** (Numo と Cumo の両方で確認)。

**本数は確実に減る。** 1 トークンあたり `fill_kernel` が 24 本消え、**1115 → 1091 本** になった。

**ところが wall は動かない。**

| 長さ | zeros | allocate | ペア比 | またぐ |
|---|---|---|---|---|
| 64 | 284.3 | 291.4 | 1.020 (0.997〜1.045) | **はい** 9/10 |
| 200 | 287.2 | 291.2 | 1.010 (0.992〜1.035) | **はい** 7/10 |

10 ラウンド、順序を毎ラウンド入れ替え、クロック固定 (アイドル SM 2805 MHz)。**2 条件とも 1 をまたぐので「速くなった」とは言えない。** 1115 本の 2.2% では足りない、ということである。

**それでも入れた。** 答えが変わらず本数が確実に減るので、入れない理由が無い。**速さの主張はしない。**

**この形は cumo 側が測って教えてくれた。** あわせて「非連続スライス同士の代入は 1 本で、行ごと起動ではない」ことも確認されている (`[1536, 4]` で 2.50 us、連続の全体代入 2.07 us との差は 0.43 us)。

### ホスト呼び出しを数え直した

**2181 → 1910 回/token。** カーネルは 1091 → 845 本なので、**カーネルを出さない呼び出しは 1090 → 1065 回** で、割合は 50.0% から **55.8%** に上がった。

**減った 271 回のうち 246 回はカーネルを出していた呼び出しである。** 削ったのは仕事のほうで、床は 25 回しか動いていない。**同じ `TracePoint` を 29a5f5d のワークツリーに当てて 2181.0 を再現してある** ので、2 つの数は同じ数え方である。内訳は [docs/results/mamba-130m.md](../results/mamba-130m.md)。

### 共有分類器の転置をやめた

**重みが 639.9 → 492.6 MiB (-147.3、-23%)。**`mamba.c` と同じ `[out, in]` のまま持ち、decode で左から掛ける。答えは変わらず (257 トークン一致、テスト 210 件)、**カーネルも 845.0 本のまま** (差分法を順序を入れ替えて 2 回、4 profile すべて 845.0)。

**wall は 2 条件 x 10 ラウンドで動かなかった** (200 と 700、どちらもペア比が 1 をまたぎ、対照も同じだけまたぐ)。**それでも入れた** — `XF.zeros` → `allocate` と同じ扱いで、速さの主張はしない。

**nsys の行ごとの時間は読めなかった。** 触っていない層内 gemvx 48 本が 2.57 倍動き、順序を入れ替えたら 0.68 倍に反転した。詳細は [docs/results/mamba-130m.md](../results/mamba-130m.md)。

### fp16 と bf16 を測った

**fp16 では走らない。**`A` が -2.836e+08 まで届いて 1535 要素が -Inf になり、`softplus` の引数も 22.26 と fp16 の `exp` の上限 11.09 を超える。**黙って全部 0 を返していたので、例外にした。**

**bf16 は走って 5〜7% 速い** (2 条件 x 10 ラウンド、どちらも 1 をまたがず 10/10、対照は両方またぐ)。重みは半分 (492.6 → 246.3 MiB)、参照と一致するのは 17 トークンまで。詳細は [docs/results/mamba-130m.md](../results/mamba-130m.md)。

### `reshape` はコピーだった

**845 → 773 本 (-72)。**`reshape` は新しい配列にコピーを返す (numo も cumo も同じ)。ブロックの 3 か所 x 24 層で 72 本出していた。`reshape!` はビューなので出さない。**`xc` は `w[:d] * xc` が `[1536]` を要求するので、行 → 列 → 行と回して元の形で終わる。**

**wall が動いた** — 200 で 1.075 (1.041〜1.104)、700 で 1.093 (1.071〜1.116)、どちらも 1 をまたがず 10/10、対照は両方またぐ。**この 1 つで PyTorch を追い越した** (PyTorch / Cumo が 0.96、10 ラウンドとも PyTorch が下)。

**見つけたのは cumo 側である。** こちらは `reshape` を「形の問い合わせ」だと思い込んで、カーネルを出さない呼び出しの側に数えていた。

### codex の指摘 2 つと cumo #481 で 773 → 581 本

**分割の 4 つのコピーはビューで済んだ (-96)。** 行を整数で選べば (`xz[0, 0...inner]`) 両バックエンドで連続ビューになる。`true` で取ると Numo が非連続と言うので `RESHAPABLE_ROW_SLICE` の probe を置いていたが、整数添字なら要らない。`store` が 97 → 1 本になった。

**積と和は `mulsum` 1 本になった (-48)。** 軸を明示するので cumo #480 のマーク経路は通らない。丸めは変わり (Numo の `max|d|` が 3.738e-04 → 3.967e-04、Cumo は不変)、**トークン列は両バックエンドとも 257 件一致**。

**融合 `softplus` は 3 本を 1 本にした (-48)。** cumo #481、**未リリース**。`FUSED_SOFTPLUS` の probe で見て、無ければ前の綴りに落ちる。

**`sigmoid` (cumo #482) は採らなかった。**`Ops.silu` を `x * sigmoid(x)` と書いてもトークン列は 257 件一致するが、**本数が 581 → 629 に増える**。融合 `silu` が 1 本でやることを 2 本でやる形になる。

**8 点の表で境目が 2.2% と 7.1% の間まで狭まった。** 詳細は [docs/results/mamba-130m.md](../results/mamba-130m.md)。
