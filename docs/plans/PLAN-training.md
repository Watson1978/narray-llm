# 学習 (backward) の実装プラン

GPT-2 124M の backward と AdamW を Numo::NArray / Cumo だけで実装する。**目的は cumo の検証** で、[docs/idea.md](../idea.md) の候補 D。

進め方は [PLAN-gpt2.md](PLAN-gpt2.md) の「全体の約束事」をそのまま継ぐ。**前の段階の受け入れテストが通るまで次の段階のコードを書かない。**

## これはこのリポジトリの前提を変える

**6 実装すべてが推論だけだった。** 学習を足すと次が変わる。

| | 推論 | 学習 |
|---|---|---|
| メモリ | 重み 498 MB | 重み + 勾配 + AdamW の m/v = **約 2.0 GB** + 活性とその勾配 |
| 活性 | 使い捨て | **backward まで全部保持する** |
| 関門 | トークン列の完全一致 | **完全一致は使えない** (下記) |

**それでも入れる価値があるのは、踏む経路がまったく違うからである。**

| 新しく踏む経路 | これまでは |
|---|---|
| **外側の軸に沿った縮約。** バイアスの勾配は `[B*T, C]` を軸 0 で畳む | 縮約はほぼ最後の軸だった |
| **同じバッファへの累算。** 層をまたいで勾配を足し込む | 使い捨ての新しい配列ばかり |
| **両向きの転置行列積。**`dW = x^T . dy` と `dx = dy . W^T` | 片方だけ |
| **パラメータ 3 本ぶんのメモリ** (重み・勾配・m/v) | 重みだけ |
| **`[50257]` の softmax の逆伝播** | 順方向だけ |

## 参照と関門

**llm.c がそのまま使える。**`vendor/llm.c/train_gpt2.c` (backward の実装) と `vendor/llm.c/test_gpt2.c` (関門) を取得済み。

**`data/gpt2_124M_debug_state.bin` に全 124,475,904 パラメータの参照勾配が入っている。** 既存の `DebugState` は `grads_byte_offset` を記録して読まずに止めてある (推論に要らないため)。

### 関門 3 つ

| | 何を | 許容 | 出典 |
|---|---|---|---|
| **A** | 各 op の backward を **有限差分** と突き合わせる | 下記で決める | こちらで作る |
| **B** | 16 個の勾配テンソルを `expected_grads` と突き合わせる | **2e-2 (絶対値)** | `test_gpt2.c:20` の `check_tensor` |
| **C** | **AdamW 10 ステップの損失列** | **1e-2 (絶対値)** | `test_gpt2.c:89-99` |

**C が本命である。** 10 ステップ回して損失が `5.270007 → 4.059707 → ... → 0.376511` をたどることを要求する。**順方向・逆方向・オプティマイザのどれが狂っても通らない。**

AdamW の設定は `test_gpt2.c:172` から取る: `lr 1e-4`、`beta1 0.9`、`beta2 0.999`、`eps 1e-8`、`weight_decay 0.01`、`t = step + 1`。

**完全一致は要求できない。** 浮動小数点の累算順序が C と一致しないので、A/B/C とも許容誤差で判定する。**そのぶん、許容誤差は llm.c 自身が使っている値をそのまま借りる** ことで、根拠を自前で作らずに済ませる。

**Numo vs Cumo は別に完全一致を要求しない。** 両者とも B と C を通ることを関門にする。

- `vendor/llm.c/train_gpt2.c` と `test_gpt2.c` を取ってくる (取得済み)
- `DebugState` が `expected_grads` を読めるようにする。**パラメータと同じ並びなので `Checkpoint.tensor_shapes` がそのまま使える**
- 1 テンソルずつ読む (549 MB を一度にホストへ乗せない)

### 受け入れテスト — 4 件、両バックエンドで通る

- 16 個すべての形が `tensor_shapes` と一致する
- ファイル末尾までちょうど使い切る (124,475,904 要素)
- **並びが合っていることを、大きさではなく形で留める。** 大きさの検査はテンソルの入れ替えを見逃すので、**`dwpe` の非ゼロ行がちょうど T = 64 行**、**`dwte` の非ゼロ行がちょうど V = 50257 行** (表は 50304 行あり、パディングの 47 行はゼロ) であることを要求する
- **`wte` は分類器でもあるので、入力に出た異なりトークンが 135 個でも語彙の全行に勾配が来る。** これも留めてある (空振りしない検査であることの確認を兼ねる)

## 第一段階: op ごとの backward — **完了** (2026-09-20)

`Ops` に backward を足す。**llm.c の `*_backward` と 1 対 1 に対応させる** (`train_gpt2.c` の該当行を各メソッドのコメントに書く)。

- `encoder_backward` (wte / wpe)
- `layernorm_backward`
- `matmul_backward` (dW / dx / dbias)
- `attention_backward`
- `gelu_backward`
- `residual_backward`
- `crossentropy_softmax_backward`

`lib/narray_llm/backward.rb` に置いた。**llm.c は呼び手のバッファに足し込むが、こちらは勾配を返す。** 各 op を単独で数値微分と突き合わせられるようにするためで、足し合わせはモデル側の仕事にした。

**`XF` をどこにも書いていない。** 配列はすべて引数のクラスから作る。**`Ops.contiguous` の第 2 引数も含めて** — 既定が `XF` なので、fp64 のテストが黙って fp32 に落ちる。

### 受け入れテスト — 7 件、両バックエンドで通る

**小さい形で、自分の順方向の中心差分と突き合わせる。**`h` は 1e-6。

| | 観測した相対誤差 |
|---|---|
| 7 つすべて | **1.8e-9 以下** |
| 採った閾値 | **1e-7** (雑音の 55 倍上) |

**この harness で実際に出た誤りは 3.6e-2 だった** (下記)。閾値はそれより 5 桁下にある。

### 踏んだもの 3 つ

**① `Ops.contiguous` の既定が `XF` なので、fp64 で呼ぶと内部が fp32 になる。** 中心差分は `2h` = 2e-6 で割るので、**fp32 の丸め (1e-7) が 5 桁増幅されて 3.6e-2 に化けた**。attention の backward が誤っているように見えたが、**llm.c のループをそのまま移した参照と突き合わせたら 1e-8 で一致** していた。**誤っていたのはテストの土俵のほうだった。**

**② Cumo の `x[i]` はビューを返す。**`old = x[i]` を取っておいて `x[i] = old + h` と書くと、**`old` が読む値も変わる**。次の `x[i] = old - h` が元の値に戻すだけになり、**中心差分がちょうど半分** になった。Numo は Float を返すので出ない。**ホストへ読み戻してから使う。**

**③ `reshape` はコピーを返す。** 平坦な添字で元の配列を直接触る。

**①と②は、どちらも「Numo では出ず Cumo でだけ出る」か「その逆」である。** 両バックエンドで回していなければ片方を見落としていた。

## 第二段階: モデル全体の backward — **完了** (2026-09-20)

`lib/narray_llm/models/gpt2/training.rb` が `Model` を再オープンして `forward_train` と `backward` を足す。**包まずに再オープンしたのは、backward が forward と同じ重みを要るのに、それが公開されていないからである。**

**活性のメモリは 280 MiB だった** (B=4, T=64)。llm.c が持つもののうち、**layernorm の平均と逆偏差は `Backward.layernorm` が計算し直す** ので持たず、**`preatt` は誰も読まない** ので持たない。

### 受け入れテスト — 3 件、両バックエンドで通る (関門 B)

**16 個すべてが llm.c の閾値 2e-2 を通った。**

| | 損失の差 | 勾配の最大 max\|d\| |
|---|---|---|
| **Numo (CPU)** | 1.18e-04 | **1.244e-02** |
| **Cumo (GPU)** | 9.54e-07 | **6.822e-04** |

**同じコードなのに、Cumo のほうが llm.c と 18 倍よく一致する。** どちらも閾値の内側だが、**Numo 側は 2e-2 に対して 1.6 倍の余裕しかない。** 畳む順序の違いだと思われるが、**測っていない。**

**形も検査している。** ある層を丸ごと落としても、1 か所が支配する勾配なら値の検査は通ってしまう。

## 第三段階: AdamW と 10 ステップ — **完了** (2026-09-20)

`lib/narray_llm/adam_w.rb`。設定は `test_gpt2.c:172` から借りた。

**更新はすべて in place である。** モデルが渡すのは実際に計算に使っている配列で、**そのうち 2 本は 1 つのパラメータを指している** (トークン表を両方の向きで持っている)。**貼り替えると片方が取り残され、融合 decode 経路が古いバッファを見る。** 片割れ (`@wte_t`) は更新のあとに作り直す。

**重みの向きが llm.c と逆である。** こちらは転置して持つので、**層あたり 4 本の行列を更新の入口で転置し直す。** 勾配のほうは llm.c と同じ向きのまま返しているので、関門 B が使える。

### 受け入れテスト — 2 件、両バックエンドで通る (関門 C)

**10 ステップの損失が llm.c の列をたどる。**

| | 10 ステップの最大 \|d\| | 1 ステップ |
|---|---|---|
| **Numo (CPU)** | **1.48e-03** | 約 8 秒 |
| **Cumo (GPU)** | **1.37e-04** | 約 0.1 秒 |

閾値は 1e-2 (`test_gpt2.c:141`)。**ここでも Cumo のほうが 10 倍よく一致する** (関門 B と同じ向き)。

**AdamW の状態は 949.4 MiB。** モデル 2 本ぶんで、見積もりどおり。

**「損失列が動くこと」も検査に入れた。** オプティマイザが何もしなければ損失は初期値に留まるので、**5.27 → 0.377 と 14 倍下がることを要求する**。そうしないと「10 個の値すべてが初期値と一致する」実装でも通ってしまう。

**CPU で 10 ステップは約 80 秒かかる。** 3 つ (forward / backward / optimizer) を同時に覆う関門はこれだけなので、短縮していない。

## 第四段階: 計測 — **完了** (2026-09-20)

結果は [docs/results/gpt2-124m.md](../results/gpt2-124m.md) の「学習」。`script/gpt2_train.rb` で回す。

| 区間 | 本/step | wall s/step | 割合 (wall) |
|---|---|---|---|
| forward | 331 | 0.00923 | 12% |
| backward | 1755 | 0.02999 | 39% |
| **update (AdamW)** | **2861** | **0.03839** | **49%** |
| 合計 | **4947** | **0.07760** | 12.9 steps/sec |

- **AdamW が本数の 58%、wall の 49%。** パラメータのテンソルが **148 本** あり、1 本の更新が **要素演算 19 本** になるため (19 x 148 = 2812 で実測とほぼ閉じる)
- **AdamW は自分の式の予算どおりに動いている。** 融合していないので走査は **44P = 21.9 GB**、600 GB/s で 36.5 ms に対し実測 38.4 ms (**1.05 倍**、2026-09-21 の測り直しでは 37.71 ms で **1.03 倍**)。**当初「底から 7.1 倍」と書いたのは、融合版の予算と比べていたためで取り下げた**
- **平坦化 (148 → 1) は 1.03 倍、融合 AdamW は 6.5 倍。** 前者はこちら、後者は cumo 側の仕事で、**桁が違う**。**当初 1.17 倍と書いていたのは取り下げた** — 起動費を通信量に足し算で乗せていたが、**44P の 36.5 ms と実測 37.71 ms の差は 1.2 ms しかなく、5.7 ms は入らない** (docs/results/gpt2-124m.md)
- メモリは使用中 **2099.3 MiB**、プール **4173.5 MiB**。**`nvidia-smi` は managed なので 222 MiB としか読まない**

### 3 実装を並べた (2026-09-20)

**Python の 2 実装にも学習を足した。** 3 実装とも llm.c の 10 ステップを通る。

| 実装 | s/step | steps/sec |
|---|---|---|
| **Cumo** | 0.07725 | 12.9 |
| CuPy | 0.08406 | 11.9 |
| **PyTorch** | **0.04619** | **21.6** |

**同じアルゴリズムなら Cumo が CuPy を 8.8% 上回り、PyTorch は 1.67 倍速い** (どちらも 10/10、対照はまたぐ)。**PyTorch は autograd と `torch.optim.AdamW` なので、同じアルゴリズムではない** (対応表の外)。

**`torch.optim.AdamW` の実装を振ったら、既定と融合版の差は PyTorch の 1 ステップの 26% だった。** **ただしこの 26% はこちらには移らない** — `foreach` は既にまとめて回す実装で、こちらの素の式とは出発点が違う。**こちらで融合すると step の 42% が消え、全体で 1.71 倍。** そこで **PyTorch の既定と並ぶ** (44.8 対 46.0 ms)。

**2026-09-21 に区間で測り直した。** torch の backward だけを取り出せるようになったので (それまで `--stop-after backward` が optimizer まで走っていた)、3 区間を同じバッチでインターリーブした。

| 区間 | Cumo | PyTorch | Cumo / PyTorch |
|---|---|---|---|
| forward | 0.00954 | 0.00792 | 1.21 (幅が広く値は読めない) |
| backward | **0.02944** | 0.01805 | **1.64** 10/10 |
| **update (AdamW)** | **0.03771** | 0.02000 | **1.87** 10/10 |
| 合計 | 0.07669 | 0.04598 | 1.66 10/10 |

**いちばん開いているのは AdamW で、backward ではない。** そして **PyTorch の `foreach` AdamW は実測 20.0 ms** で、逆算していた 17.6 ms より 12% 大きかった。
