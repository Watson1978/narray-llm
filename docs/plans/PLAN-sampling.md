# サンプリングの実装プラン

温度・top-k・top-p を足す。**目的は cumo の検証** で、これまでの 6 実装が一度も踏んでいない経路を叩くことに価値がある ([docs/idea.md](../idea.md) の候補 B)。

進め方は [PLAN-gpt2.md](PLAN-gpt2.md) の「全体の約束事」をそのまま継ぐ。**前の段階の受け入れテストが通るまで次の段階のコードを書かない。**

## なぜサンプリングか (cumo の検証として)

| 新しく踏む経路 | これまでの 6 実装では |
|---|---|
| **`sort` を `[50257]` で踏む** | 1 度も呼んでいない |
| **`cumsum` を 50257 要素で踏む** | Switch の MoE で `[8, 8]` を踏んで **ホストに落ちた** (閾値 8192)。**その反対側** |
| **確率からの抽出** | 全モデルが貪欲法 (argmax) だけ |

**`cumsum` の帯が違う。** Switch で踏んだのは 8192 未満でホストループに落ちる側で、こちらは **カーネルが立つ側** である。同じ演算の両側を実使用で踏むことになる。

## 関門

**トークン列の完全一致を捨てない。**

**乱数はホスト側で引く。** Ruby の `Random` を seed 付きで 1 トークン 1 個。**Numo と Cumo の乱数生成器は系列が一致しない** (AGENTS.md) ので、デバイス上で引くと関門が壊れる。**1 トークンに 1 個のスカラーなのでデバイスで引く利点も無い。**

そのうえで:

1. **同じ seed なら Numo と Cumo が同じ列を出す** (完全一致)
2. **`top_k: 1` が貪欲法と同じ列を出す** (完全一致)
3. **温度と top-p が既定値のとき、経路が貪欲法と 1 演算も変わらない**

**idea.md には「上位 k の添字集合の完全一致を関門にする」と書いていたが、そこまで弱める必要が無かった。** 乱数をホストに置けば **列そのものの完全一致が使える**。

## Bit 配列も fancy index も使わない

AGENTS.md の通り、絞り込みは **算術で** 作る。`>=` はこう書く。

```ruby
keep = 1.0 - (threshold - x).clip(0.0, 1.0).ceil   # x >= threshold で 1.0
```

**添字の並べ替えを持ち回らない。** top-k も top-p も、**並べ替えた空間で閾値の「値」を決めて、元の空間では値で比べる**。散布 (scatter) が要らないので fancy index を踏まない。

**同値は全部残る。**`[50257]` で 10 番目の値を閾値にしたとき、その値と等しい要素が 2 個あれば 11 個残る (2026-09-20 に実測)。**k は上限ではなく「少なくとも k 個」である。** これは仕様として固定し、テストで留める。

## 第一段階: Ops に 3 つ足す — **完了** (2026-09-20)

- `Ops.top_k_keep(values, k)` — `[V]` の 0/1 マスク
- `Ops.top_p_keep(probs, p)` — 同上。降順の累積を作り、**残す最小の確率** を閾値にして元の空間へ戻す
- `Ops.sample_index(probs, u)` — 累積が `u` を超える最初の位置。**読み戻しは 1 回**

比較は `Ops.at_least(x, threshold)` に 1 つにまとめた (`1.0 - (threshold - x).clip(0.0, 1.0).ceil`)。**Bit も fancy index も通らない。**

### 受け入れテスト — 8 件、両バックエンドで通る

- 小さい語彙で値を直接確かめる
- **同値が境界にあるとき、k 個より多く残る** (6 個中 3 個を求めて 4 個返る)
- `top_k` が語彙より大きいとき全部残る、0 以下を撥ねる
- `top_p` が「p を跨ぐ札まで残す」ことを 3 点で確かめる、1.0 で全部残る、0 を撥ねる
- `sample_index` が累積を歩く、**確率 0 の札は u を 100 通り振っても選ばれない**
- **`[50257]` でも動く** (`cumsum` がカーネル側に行く帯)

## 第二段階: Generator — **完了** (2026-09-20)

`Sampler` を足して `generate(..., sampler:)` で受ける。**`sampler:` が nil のときは今の貪欲法の経路をそのまま通る。**

### 受け入れテスト — 6 件、両バックエンドで通る

- **`top_k: 1` が貪欲法と同じ列** (seed を変えても)
- **同じ seed で両バックエンドが同じ列。** 列を **リテラルで書いてある** ので、自分と比べるだけの空振りにならない
- **seed が違えば列が変わる** (検査が空振りしていないこと)
- 温度 0.01 で貪欲法に収束する、温度 0 を撥ねる
- **`top_p` 単独でも列が動く**

## 第三段階: 計測 — **完了** (2026-09-20)

結果は [docs/results/gpt2-124m.md](../results/gpt2-124m.md) の「サンプリング」。

- **1 トークンあたり 234 → 262 (top_k) / 276 (top_p) / 281 (両方) 本**
- **`[50257]` の `sort` 1 回が 8 本** (CUB 6 + `float_key` 1 + **`cumo_na_copy` 1**)、**`cumsum` 1 回が 2 本。** **`cumsum` はホストループに落ちていない** (Switch で踏んだ 8192 未満の帯とは別の経路)
- **両方ありでも sort は 1 回。**`Sampler` が 1 度だけソートして両方に渡す (共有前は 290 本)
- **`reverse` はカーネルを出さない。**`Ops.contiguous` は要らなかった
- **貪欲法の `max_index` 2 本は消える**
- wall は貪欲法比で **top_p 1.064 / 両方 1.069** (10/10)、**top_k 1.037 は 1 をまたぐ** (2026-09-21 に測り直し。前の 1.038 / 1.070 / 1.097 は計測スクリプトの偏りを受けていた)
- **単発測定が 1.40 倍と出て、10 ラウンドでは 1.069 倍だった** (作法 1)

**3 実装で並べるのは見送った。** 増分が 10% 程度で、Python 側に同じ形の抽出を書く手間に見合わない。**やるなら Ops の 3 つを移植するところから。**
