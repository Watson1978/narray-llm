# バッチ生成の実装プラン

GPT-2 124M の decode を batch > 1 で回せるようにする。**目的は cumo の検証** で、これまでの 6 実装が一度も踏んでいない経路を叩くことに価値がある。

進め方は [PLAN-gpt2.md](PLAN-gpt2.md) の「全体の約束事」をそのまま継ぐ。**前の段階の受け入れテストが通るまで次の段階のコードを書かない。**

## なぜバッチか (cumo の検証として)

| 新しく踏む経路 | これまでの 6 実装では |
|---|---|
| **`gemmStridedBatched` を batch > 1 で叩く。** cumo は 2 次元 1 本の行列積もこの API を通すが (`gen/tmpl/gemm.c`)、**本来の用途で叩いたことが一度も無い** | 全部 batch 1 |
| **decode の帯が変わる。** 1 トークンの decode は `[1, 768] x [768, C]` の gemv だが、batch 8 なら `[8, 768] x [768, C]` の gemm になる | 投入が支配する帯だけ |
| **KV キャッシュが 3 次元になる** | `[maxT, C]` の 2 次元 |
| **attention の縮約軸が 1 本増える** | `[t, nh, hs]` まで |

**そして今日の宿題に直接つながる。** Whisper の encode で PyTorch が 15.3% 速い件の候補①は「cumo は batch=1 でも `gemmStridedBatched` を通す」だった ([docs/cumo-issues.md](../cumo-issues.md))。**batch > 1 の実使用が 1 つも無いので、この API が本来の使い方で速いのかも分かっていない。**

**「Cumo が decode で PyTorch に勝つ」は batch 1 の話である。** 投入が支配する帯から外れたときに向きが保たれるかは、測っていない。

## 関門

**新しい参照実装は要らない。** 既存の batch 1 が参照になる。

1. **同じプロンプトを B 本並べたら、batch 1 と同じ列が B 本出る** (完全一致)
2. **違うプロンプト B 本なら、それぞれの batch 1 と一致する** (完全一致)
3. **両バックエンドで 1 と 2 が成り立つ**

**完全一致を要求できるので、許容誤差の議論が要らない。**

## 第一段階: KV キャッシュにバッチ軸を足す — **完了** (2026-09-20)

- `KVCache` を **`[maxT, B, C]`** にする。`batch_size:` の既定は 1
- `append` は `[B, C]` (1 位置) と `[n, B, C]` (prefill) を受ける
- `view` は `[t, B, C]` を返す

**時間を外側に置いた。** 当初は `[B, maxT, C]` で書いたが、**B > 1 の取り出しが非連続になって `reshape!` が撥ねた** (`cannot change shape of non-contiguous NArray`)。`[maxT, B, C]` なら伸びていく切り出しが B によらず連続で、**attention の縮約軸も既存と同じ 0 のまま** である。

内部は常に `[B, maxT, C]` で持ち、**B = 1 のときだけ取り出しでバッチ軸を落とす**。`[1, maxT, C]` の `[0, span, true]` は連続なので、**B = 1 の経路は 1 演算も変わらない** (KVCache は 5 モデルが共有していて、どれもまだバッチ化していない)。

### 受け入れテスト — 27 件、両バックエンドで通る

- **`batch_size: 1` でいまと同じ形が返る** (既存の 21 件が 1 つも落ちない)
- 取り出しがバッチ軸を持つ (`[B, t, C]`)、空のときも
- **系列ごとに独立に積める** (位置ごとに B 行を書いて、あとから位置を指定して取り出せる)
- prefill が系列ごとのブロックを取る (`[B, n, C]`)、そのあとに 1 行足せる
- `bytes_for` が B 倍になる
- **バッチが合わない入力を撥ねる。**`reshape` の `ArgumentError` が先に出てしまうので、**形の検査を `reshape` の前に置いた**
- 溢れを撥ねる、`batch_size: 0` を撥ねる

## 第二段階: decode を batch > 1 にする — **完了** (2026-09-20)

- `decode_embed` が B 個のトークン id から `[B, C]` を作る
- `decode_attention` が q `[B, C]`、keys / values `[B, t, C]` を受ける
- `GEMM_WITH_C` の bias スクラッチを `[B, at]` にする

**位置は B 本で揃える。** プロンプト長が違う場合は第四段階の話にして、ここでは同じ長さだけを扱う。

### 受け入れテスト — 5 件、両バックエンドで通る (`test/test_batch_decode.rb`)

- **B = 1 のバッチが、バッチでない経路と一致**
- **同じプロンプトを 3 本並べたら、batch 1 と同じ列が 3 本**
- **違うプロンプト 3 本が、それぞれの batch 1 と一致** (**3 本が互いに違うことも確かめる。** 同じなら検査が空振りする)
- **B = 2 と 4 でも batch 1 と一致**
- キャッシュとバッチが合わない呼び出しを撥ねる

**浮動小数点の比較は 1 つも無い。** トークン id の完全一致だけで済む。

### 踏んだもの

- **`gemm` の C は cumo では連続でなければならない** (`c must be contiguous`)。bias を 1 本のバッファに詰めて列で切り出す形は、**2 行以上だと strided になって撥ねられる**。各 bias が `[rows, size]` の連続ブロックになるよう並べ直した。**1 トークンあたりの `store` は 1 回のままである**
- **`row_slice` は 1 行のときしかビューを返せない。**`RESHAPABLE_ROW_SLICE` は `[1, 4]` で調べた定数なので、行数の条件を足した

## 第三段階: prefill を batch > 1 にする — **完了** (2026-09-20)

`a kv cache needs batch size 1` を「キャッシュと行数が合うこと」に置き換えた。`forward` は既に `batch_size` を受けているので、本体は **`kv_sink` が渡す batch 主体の `[B*T, C]` を、キャッシュが持つ時間主体の `[T, B, C]` に直すところ** だけだった (B = 1 では同じ並びなので 1 つも動かさない)。

### 受け入れテスト — 6 件、両バックエンドで通る

第二段階の 5 件はプロンプトを 1 本ずつ押し込む補助が消えて、**バッチのまま prefill するようになった**。加えて:

- **バッチで埋めたキャッシュが、1 本ずつ埋めたものと一致する** (全 12 層、K と V)
- バッチが合わない `prefill` を撥ねる

**この 1 件だけは浮動小数点の比較になる。** そして **閾値の上下を両方測ってから決めた。**

| | 値 |
|---|---|
| 同じ系列、バッチ有無の差 | **1.049e-05** (Numo) / **7.153e-06** (Cumo)、値域 18.366 |
| **別系列との差の最小** | **3.792** |
| 採った閾値 | **1.0e-3** (雑音の 100 倍上、取り違えの 3800 倍下) |

**差はバッチ GEMM の畳む順序で、相対 5.7e-07。** 最初これを完全一致で書いて落ちた。**トークン列のほうは完全一致のままである。**

## 第四段階: Generator — **完了** (2026-09-20)

`Generator#generate_batch` を足した。

**読み戻しは 1 ステップ 1 回のままである。**`max_index(axis: 1)` は **平坦な通し番号** を返すので (AGENTS.md)、行のオフセットをデバイス上で引いてから 1 度だけ読む。B 本ぶんを 1 回で取るので、**バッチが増えても読み戻しの回数は増えない**。

**EOT は「最後まで回して後で切る」を選んだ** (計画どおり単純なほう)。終わった本も動き続けるのでそのぶん無駄が出るが、**形が固定される**。全部の本が終わったときだけ早く止める。切り出しは `generate` と同じで **EOT 自身を残す**。

**プロンプトの長さは揃っている必要がある。** 位置がバッチ全体で 1 つなので、長さが違うと一部の本が誤った位置に入る。撥ねてある。

### 受け入れテスト — 10 件、両バックエンドで通る

- **`generate_batch` が「プロンプトごとの `generate`」と完全一致**
- プロンプト + 続きが返る、長さが合っている
- 長さの違うプロンプト / 空のバッチ / 空のプロンプトを撥ねる
- **本ごとに自分の EOT で切れる。** EOT はその本の最後にしか現れない。**「13 を実際に出す組であること」も確かめる** (出なければ検査が空振りする)

## 第五段階: 計測 — **Cumo 側は完了** (2026-09-20)

結果は [docs/results/gpt2-124m.md](../results/gpt2-124m.md) の「バッチ生成」。

- **長さ 128 では batch 16 で合計 6.7 倍** (742.9 → 4973.8 tok/s)。1 本あたりは 743 → 311 に落ちる
- **長さ 512 では単調でない。** batch 8 が batch 4 を下回る (1462 対 2033、5 ラウンドとも幅の外)。**原因は未分離**
- **1 ステップの GEMM 49 本の振り分けがバッチで変わる。** batch 2/4 は 12 本、**batch 8 は 1 本**、batch 16 は 24 本が cutlass の sgemm に行き、残りは gemv 系。**長さには依らない**
- **対照** (バッチ経路を通らない素の `generate`) は batch 1 と幅の内で重なる。**バッチの仕掛けは batch 1 に費用を足していない**

### 第六段階: Python の 2 実装もバッチ化して並べる — **完了** (2026-09-20)

`python/gpt2.py` と `python/gpt2_torch.py` に同じ形のバッチを入れ、`bench_gpt2.py` に `--batch` を足した。**両方ともバッチが batch 1 の列と完全一致する** (両バックエンド)。

| batch | Cumo | CuPy | PyTorch | Cumo / CuPy | PyTorch / Cumo |
|---|---|---|---|---|---|
| 1 | 724.6 | 226.4 | 701.2 | **3.196** 10/10 | 0.968 **またぐ** |
| 8 | 3504.5 | 1703.7 | 3591.6 | **2.059** 10/10 | 1.028 **またぐ** |

**Cumo の CuPy に対する差はバッチで縮む** (3.20 → 2.06 倍)。**PyTorch との差はどちらの batch でも決まらない。**

**当初「batch 8 で 1.5% 上回る」と書いて取り下げた。** 5 ラウンドで確定扱いにしていたのと、Python 側が 1 ステップに B 回読み戻していたのと、2 つ重なっていた (読み戻しの費用は 1 ステップ 36〜44 us で、主張していた差と同じ大きさ)。
